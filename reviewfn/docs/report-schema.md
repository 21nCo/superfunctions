# Report schema version 1

A report records three independent axes:

- execution: `queued`, `running`, `completed`, `failed`, `canceled`, or `superseded`;
- coverage: `complete` or `incomplete`, with reasons;
- verdict: `ready`, `changes_requested`, or `needs_verification`, absent unless execution is `completed`; a completed run without complete coverage or requirements is `needs_verification`.

Requirements contain immutable source anchors and exactly one assessment. Assessments distinguish `implemented`, `partial`, `missing`, `unverified`, and source-waived `not_applicable`. Evidence links to a context source, exact-head code anchor, diff, test receipt, or content-addressed artifact. An implemented assessment must include reviewed-head implementation evidence. Merge-base anchors can document deleted code but cannot alone establish implementation. An available source with no extracted requirements needs explicit source evidence with a nonblank `sourceExclusionReason`; ordinary citations do not establish exclusion.

Findings carry a fingerprint, severity, concrete trigger/impact/direction, reproduced-versus-inferred basis, requirement links and lifecycle. Model confidence never substitutes for evidence validity. Fingerprints use path, optional symbol and finding semantics, excluding revision and line coordinates. They are correlation hints, not proof of historical lifecycle. Version 0.1 receives no prior-finding provenance, so only `new` findings validate; every historical lifecycle remains unproven. Ambiguous duplicate fingerprints fail validation; distinguish actual symbols or defect semantics before correlation.

`contextManifestDigest` identifies the normalized snapshot bytes and `contextManifestArtifact` names the corresponding content-addressed stored artifact. Test receipts contain exact argv, commit, timing, exit status, stdout/stderr digests and limitations; they do not claim a retrievable log artifact unless one was actually persisted.

`changeDetail` is optional and additive; a report without it validates as before. When present, `hunksArtifact` names a content-addressed `change-hunks` artifact whose SHA-256 is `hunksDigest`. The artifact is a `ChangeHunks` v1 document, `{ version: 1, baseCommit, headCommit, files: [{ path, previousPath?, status, hunks: [{ oldStart, oldLines, newStart, newLines }] }] }`, parsed from `git diff --no-color --no-ext-diff --find-renames -U0 <mergeBase> <head>`. `status` is `added`, `modified`, `deleted`, `renamed` or `binary`. Binary files have no hunks, and the report lists them as limitations because they cannot carry line-level evidence. Diffs larger than the policy's `maxOutputBytes` are not parsed: the report omits `changeDetail` and records incomplete coverage with the reason. Combined diffs, word diffs and external diff drivers are rejected (`REVIEWFN_DIFF_UNSUPPORTED`).

An incremental run sets `since` to the previously reviewed head, a full 40- or 64-hex commit. `since` must be an ancestor of the head and a descendant of, or equal to, the merge base. Otherwise the run fails before review with `REVIEWFN_SINCE_NOT_ANCESTOR`, and it never falls back to a full review. The report then also records `deltaHunksArtifact` and `deltaHunksDigest` for `since..head`, plus `deltaPaths`, the delta's changed paths. Like every changed path, each delta path must be inspected or explicitly uninspected. The validator recomputes both digests from the stored artifacts and checks their commit ranges and paths against the change. Any mismatch fails with `REVIEWFN_CHANGE_DETAIL_MISMATCH`.

The validator rejects duplicate identifiers, unknown requirements/evidence/sources, stale commit anchors, invalid line ranges, unjustified exclusions, over-limit findings, incomplete-ready reports and any verdict inconsistent with deterministic policy.
