---
title: Secret Storage And Encryption
description: The production storage model, encrypted payload shape, KeyProvider contract, and AAD binding.
---

SecFn never stores plaintext secret values. Admin writes create a secret metadata row plus an encrypted version row.

The encrypted version payload contains:

```ts
{
  algorithm: "AES-256-GCM",
  keyId: "env:main",
  iv: "...",
  salt: "...",
  authTag: "...",
  ciphertext: "..."
}
```

Each encryption operation uses per-record randomness for IV and salt. The default env/master-key provider derives encryption material from the configured master key. Custom `KeyProvider` implementations can later bridge to KMS or HSM systems without changing the vault service.

```ts
import type { KeyProvider } from "@secfn/core";

const keyProvider: KeyProvider = {
  async resolveKey(input) {
    const keyId = input?.keyId ?? "kms:primary";
    return {
      keyId,
      secret: await kms.decryptKeyMaterial(keyId),
    };
  },
};
```

## AAD Binding

AES-GCM additional authenticated data binds ciphertext to:

- `tenantId`
- `namespace`
- `secretId`
- `version`

Moving an encrypted payload to another tenant, namespace, secret, or version fails authentication instead of decrypting.

## Schema Ownership

SecFn exports schemas but does not auto-create production tables:

```ts
import { getSecFnSchema } from "@secfn/core";

await migrationTool.ensure(getSecFnSchema());
```

Production deploys should run migrations explicitly through the same schema tooling used for the rest of the Superfunctions app.
