## 🔴 **Critical Issues (4 Total)**

### **datafn/extfn/src/proxyClient.ts - Runtime message dispatch**
**📁 File:** `datafn/extfn/src/proxyClient.ts`

#### **Issue 1:** Avoid double-sending runtime messages in callback fallback *(Codex)*
- **Severity:** High
- **Description:** In callback-only browser runtimes, the helper probes `runtime.sendMessage(message)` and then falls back to a callback-based `sendMessage` call, which dispatches the same envelope twice. A single proxied DataFn request can therefore execute duplicate mutations or transactions.
- **Location:** Line 253
- **Fix:** Collapse the probe and fallback paths into a single `sendMessage` invocation that supports both Promise and callback runtimes without dispatching twice.

### **datafn/extfn/src/authority.ts - Runtime message dispatch**
**📁 File:** `datafn/extfn/src/authority.ts`

#### **Issue 2:** Callback-based runtimes can dispatch the same message twice *(identified by cubic)*
- **Severity:** High
- **Description:** The authority send path probes `runtime.sendMessage(message)` before falling back to the callback form. On callback-based runtimes, the probe already sends the message, so the fallback sends it again.
- **Location:** Line 400
- **Fix:** Use one send path that detects Promise support from the same call instead of sending once to probe and once to complete the request.

### **extfn/cli/src/scan/rules/remoteHostedCode.ts - Remote-code scanning**
**📁 File:** `extfn/cli/src/scan/rules/remoteHostedCode.ts`

## 🟡 **Medium Severity Issues (7 Total)**

### **extfn/core/src/content/contentScript.ts - Config validation**
**📁 File:** `extfn/core/src/content/contentScript.ts`

#### **Issue 1:** Content-script target scopes are not validated against extension targets *(Codex)*
- **Severity:** Medium
- **Description:** `contentScript.targets` can include typos or out-of-scope browser targets and still pass validation. The result is silent filtering later in manifest generation, which can make a content script disappear from every shipped target without a configuration error.
- **Location:** Line 84
- **Fix:** Validate each content-script target against `extension.targets` and fail fast on typos or out-of-scope values.

### **extfn/cli/src/commands/build.ts - Vite binary resolution**
**📁 File:** `extfn/cli/src/commands/build.ts`

#### **Issue 2:** Vite CLI path is resolved from caller cwd instead of the installed package *(Codex)*
- **Severity:** Medium
- **Description:** The command hardcodes `node_modules/vite/bin/vite.js` under the caller’s cwd. That breaks in non-hoisted installs, nested workspace layouts, and global CLI usage even when `vite` is present as a dependency of `@superfunctions/extfn-cli`.
- **Location:** Line 436
- **Fix:** Resolve the Vite executable from the CLI package dependency graph rather than assuming it lives under the invoking repository root.

### **extfn/core/src/runtime/router.ts - Client API stability**
**📁 File:** `extfn/core/src/runtime/router.ts`

#### **Issue 3:** `call()` depends on `this` and breaks when destructured *(identified by cubic)*
- **Severity:** Medium
- **Description:** The returned client’s `call` method invokes `this.dispatch(...)`. If consumers destructure `call` or pass it as a callback, `this` is no longer bound and the request path breaks.
- **Location:** Line 144
- **Fix:** Capture `dispatch` in closure and call it directly instead of using `this.dispatch(...)`.

### **datafn/extfn/src/subscriptions.ts - Subscription delivery**
**📁 File:** `datafn/extfn/src/subscriptions.ts`

#### **Issue 4:** Rejected deliveries can surface as unhandled promise rejections *(identified by cubic)*
- **Severity:** Medium
- **Description:** The subscription fanout wraps `deliver(...)` in `Promise.resolve(...)` but does not handle rejection paths. Delivery failures can therefore bubble as unhandled rejections and bypass any failure callback.
- **Location:** Line 84
- **Fix:** Catch rejected deliveries and route them through the existing failure-handling path, or explicitly swallow/report them.

### **extfn/core/src/content/anchors.ts - Anchor identity**
**📁 File:** `extfn/core/src/content/anchors.ts`

#### **Issue 5:** Selector anchors reuse the same fixed key *(identified by cubic)*
- **Severity:** Medium
- **Description:** `selector` anchors always use `anchor-0`, so multiple selector strategies collide on the same key. That can destabilize mounting and reinjection when more than one selector anchor is configured.
- **Location:** Line 43
- **Fix:** Generate selector anchor keys with `createAnchorKey` or another stable per-selector/per-index scheme.

### **extfn/core/src/runtime/ports.ts - Session lifecycle**
**📁 File:** `extfn/core/src/runtime/ports.ts`

#### **Issue 6:** Closed port sessions remain in the broker map *(identified by cubic)*
- **Severity:** Medium
- **Description:** Closed port sessions are never removed from the broker’s `sessions` map. Long-lived background runtimes will retain stale sessions and leak memory over time.
- **Location:** Line 102
- **Fix:** Delete the session from the broker when the port closes or wire cleanup through a dedicated close callback.

### **extfn/core/src/config.ts - Module discovery**
**📁 File:** `extfn/core/src/config.ts`

#### **Issue 7:** `.d.ts` files are treated as executable handler modules *(identified by cubic)*
- **Severity:** Medium
- **Description:** `path.extname('foo.d.ts')` yields `.ts`, so declaration files are currently treated as loadable handler modules. At runtime those imports will fail despite passing discovery.
- **Location:** Line 564
- **Fix:** Exclude `.d.ts` entries before extension-based module filtering.

### **extfn/cli/src/scan/rules/contentSockets.ts - Scan correctness**

- **Location:** Line 13
