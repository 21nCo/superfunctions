# Summary
`datafn/server` has a **High-severity compile break** caused by multiple contract drifts and strict typing gaps: 124 `TS2709` errors around core type imports, 60 `TS2554` router invocation/signature mismatches, 135 `TS18046` unknown-body access errors, and 42 `TS7006` implicit-any errors. This is not a single-point regression; it is a layered type-boundary failure spanning `@datafn/core` type consumption, `@superfunctions/http` API usage, and server-side strictness debt.

# Observed Errors/Symptoms
- `TS2709: Cannot use namespace 'DatafnSchema' as a type.` (and similar for `DatafnPlugin`, `DatafnErrorCode`, etc.)
- `TS2554: Expected 1 arguments, but got 2.`
- `TS18046: 'body' is of type 'unknown'.`
- `TS7006: Parameter 'x' implicitly has an 'any' type.`

# Root Causes

## 1) Mixed type-boundary strategy for `@datafn/core` in `datafn/server` (Primary)
- Severity: High
- Issue title: Inconsistent core type import strategy causes package-wide TS2709 failures.
- Location:
  - `datafn/server/src/core-types.ts:2-5`
  - `datafn/server/src/routes/query.ts:10`
  - `datafn/server/src/execution/errors.ts:6-9`
  - `datafn/server/src/plugins/run-hooks.ts:6-7`
- Current code (problematic):
```ts
// core-types.ts (explicit workaround)
/** Defined here to avoid TS2709 ("Cannot use namespace as a type") ... */
export type DatafnSchema = { ... }

// many files still import directly from @datafn/core
import type { DatafnSchema, DatafnPlugin } from "@datafn/core";
```
- Expected behavior:
  - One consistent type boundary: either all server compile-time types come from local shim (`core-types.ts`) or upstream `@datafn/core` declarations are made fully compatible with server declaration emit.
- Actual behavior:
  - Server mixes both approaches. The workaround exists but is only partially applied, so TS2709 still appears across dozens of files.
- Impact:
  - `datafn/server` cannot pass `tsc --noEmit`; declaration/type pipeline is blocked.
- Evidence:
  - 124 `TS2709` errors in `/tmp/server-tsc.log`.
  - Type resolution confirms `@datafn/core` resolves to `datafn/core/dist/index.d.ts`, so this is a contract/emit compatibility issue, not path resolution failure.

## 2) Router API drift with `@superfunctions/http` (Handle signature mismatch)
- Severity: High
- Issue title: Call sites assume old router `handle(req, ctx)` shape while current API is `handle(req)`.
- Location:
  - `datafn/server/src/__tests__/namespace-auto-wrap.test.ts:48`
  - `datafn/server/src/validation/__tests__/validation.test.ts:83`
  - `packages/http/src/types.ts` (`Router.handle(request: Request): Promise<Response>`)
- Current code (problematic):
```ts
await server.router.handle(req, {});
```
- Expected behavior:
  - Call sites and wrappers should match router contract from `@superfunctions/http`.
- Actual behavior:
  - Test and endpoint paths still pass a second context arg.
- Impact:
  - 60 compile errors (`TS2554`) and unstable test typing.
- Evidence:
  - `TS2554` appears repeatedly at all `router.handle(req, {})` call sites.

## 3) Invalid function parameter ordering in route factories (TS1016)
- Severity: Medium
- Issue title: Optional parameters precede required parameters in route factory signatures.
- Location:
  - `datafn/server/src/routes/query.ts:53-56`
  - `datafn/server/src/routes/mutation.ts:40-44`
  - `datafn/server/src/routes/sync.ts` (multiple factory functions)

```ts

  maxLimit: number,
  db?: Adapter,
  plugins: DatafnPlugin[] = [],
  extractNamespace: (ctx: any) => Promise<string>,

```
- Expected behavior:
  - Required params must come before optional params.
- Actual behavior:
  - Required `extractNamespace` follows optional params.
- Impact:

- Evidence:
  - `TS1016` appears across route factory files.

- Severity: Medium
- Issue title: Test/runtime code relies on untyped `json()` payloads and implicit callback types.
- Location:

- Impact:

- Evidence:

# Proposed Fixes

## A) Stabilize the core type boundary first (unblocker)
1. Choose one strategy and enforce it repo-wide for server:
   - Recommended short-term: use `datafn/server/src/core-types.ts` for all server compile-time schema/plugin/error types.
   - Keep runtime function imports from `@datafn/core` (e.g., `validateSchema`, `ensureBuiltinKv`) as value imports.
2. Run codemod to replace `import type { Datafn* } from "@datafn/core"` with imports from `./core-types.js` (or centralized `../core-types.js` barrel).
3. Add lint rule/check to prevent direct `Datafn*` type imports from `@datafn/core` inside `datafn/server/src/**`.

## B) Align router usage with current HTTP contract
1. Update all `server.router.handle(req, {})` call sites to `server.router.handle(req)`.
2. Where parsed body/context was assumed via second arg, move that state into router context middleware or helper wrappers that conform to `RouteHandler` signature.
3. Add a small compile-only test for router contract usage to prevent reintroduction.

## C) Fix route factory signatures
1. Reorder parameters so all required params come first.
2. Optionally convert options bags to a single config object for factory constructors (`createQueryHandler({ ... })`) to eliminate ordering hazards.

## D) Eliminate strict unknown/any hotspots
1. Define response envelope interfaces for test assertions, e.g. `type ErrorEnvelope = { ok: false; error: {...} }`.
2. Parse/narrow `await res.json()` with type predicates.
3. Add explicit callback parameter types where `TS7006` occurs.

## E) Phase the rollout to reduce risk
1. Phase 1: `TS2709` + `TS1016` unblocking.
2. Phase 2: router signature migration (`TS2554`).
3. Phase 3: strictness cleanup (`TS18046`, `TS7006`, residual typing mismatches).
4. Gate each phase with `cd datafn/server && npx tsc --noEmit`.
