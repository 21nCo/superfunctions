## Summary

The datafn example todo-app (`datafn/examples/todo-app/`) currently demonstrates core DataFn features (offline-first sync, signals, KV storage, relations, transactions, plugins, capabilities) but has **zero search functionality** — neither server-side nor client-side. The SearchFn adapter architecture is now fully implemented with production-ready adapters for **Elasticsearch**, **OpenSearch**, **Meilisearch**, **Postgres**, **Memory**, and **IndexedDB**. A complete `SearchAdapter → SearchProvider` pipeline exists via `createSearchProvider` factory, `POST /datafn/search` route, client-side search plugin, and built-in mutation/sync index wiring. The example app should be updated to demonstrate this search integration end-to-end using the **Elasticsearch/OpenSearch adapter** on the server and appropriate client-side search, serving as both a reference implementation and integration test.

**Severity**: Medium — Feature gap in reference implementation, not a bug. Blocks developer onboarding and documentation.

## Observed Errors/Symptoms

This is a feature-addition issue, not a bug. The symptoms are:

1. **No search UI** — The `App.svelte` has no search input, no search results display, no search tab.
2. **No `searchProvider` on server config** — `server/src/index.ts:12-36` creates a `DatafnServer` without a `searchProvider` slot.
3. **No `indices.search` in schema** — `server/src/schema.datafn.ts` defines `indices: { base: ["completed"] }` for todos and `indices: { base: ["name"] }` for categories, but no `search` indices.
4. **No search-related dependencies** — Neither `server/package.json` nor `client/package.json` include `@searchfn/adapters`, `@searchfn/datafn-provider`, or `@searchfn/client`.
5. **No client-side search plugin** — `client/src/lib/datafn.ts` only has an `auditPlugin`, no `createClientSearchPlugin`.
6. **No `/datafn/search` route logged** — Server startup only logs query/mutation/transact/clone/pull/push/status routes.

## Available SearchFn Adapters (Current State)

All adapters are **fully implemented** and production-ready. The adapters package (`@searchfn/adapters`) uses a custom HTTP client layer (no third-party Elasticsearch/OpenSearch SDK dependency — uses native `fetch`).

### ElasticsearchAdapter (`searchfn/adapters/src/elasticsearch.ts`)

Fully implemented (284 lines). Uses a custom `ElasticClient` built on native `fetch` — no `@elastic/elasticsearch` SDK dependency.

**Constructor**:
```typescript
new ElasticsearchAdapter({
  node: "http://localhost:9200",
  engine: "elasticsearch",            // or "opensearch"
  auth: { username: "elastic", password: "changeme" },  // or { apiKey: "..." }
  indexPrefix: "searchfn",            // default: "searchfn"
  requestTimeoutMs: 30_000,           // default: 30s
  retry: { maxRetries: 3, baseDelayMs: 100, maxDelayMs: 5000 },
  logger: myLogger,                   // optional AdapterLogger
})
```

**Capabilities**: `{ persistent: true, searchAll: true, fuzzy: true, fieldBoosts: true }`

**Key implementation details**:
- `initialize()` — creates ES indices with text mappings for each resource's search fields, or updates mappings on existing indices
- `index()` — uses `_bulk` API with `refresh=wait_for` for consistent indexing
- `search()` — `multi_match` queries with optional `fuzziness: "AUTO"`, field boosts via `field^weight` syntax, deterministic sort `[_score desc, _id asc]`
- `searchAll()` — sequential per-resource searches with score-based merge and deterministic tie-break (`score DESC`, `resource ASC`, `id ASC`)
- `remove()` — `_bulk` delete with `refresh=wait_for`
- `clear()` — `_delete_by_query` with `match_all`
- `dispose()` — sets disposed flag

**Resilience**: Built-in retry with jitter for transient errors (408, 429, 500, 502, 503, 504), auth error handling (401/403), configurable timeout, AbortSignal support on all operations, sensitive data redaction in logs.

### OpenSearchAdapter (`searchfn/adapters/src/opensearch.ts`)

Extends `ElasticsearchAdapter` with `engine: "opensearch"` preset:
```typescript
new OpenSearchAdapter({
  node: "http://localhost:9201",
  auth: { username: "admin", password: "admin" },
  indexPrefix: "searchfn",
})
```

- Request timeout via `AbortSignal.any()` merge
- Sensitive data redaction in log output
- NDJSON support for bulk operations

### Phase 2: Server-Side Search Provider (Elasticsearch/OpenSearch + MemoryAdapter Fallback)

**File**: `datafn/examples/todo-app/server/src/index.ts`

The server should use `ElasticsearchAdapter` or `OpenSearchAdapter` when an ES/OS URL is configured via environment variable, falling back to `MemoryAdapter` for simple dev setups.

```typescript
import { ElasticsearchAdapter, OpenSearchAdapter, MemoryAdapter } from "@searchfn/adapters";
import { createSearchProvider } from "@searchfn/datafn-provider";

// Choose adapter based on environment
function createSearchAdapter() {
  const esUrl = process.env.ELASTICSEARCH_URL;
  const osUrl = process.env.OPENSEARCH_URL;

  if (osUrl) {
    return new OpenSearchAdapter({
      node: osUrl,
      indexPrefix: "todo_app",
      requestTimeoutMs: 10_000,
      retry: { maxRetries: 3, baseDelayMs: 100, maxDelayMs: 5_000 },
    });
  }

  if (esUrl) {
    return new ElasticsearchAdapter({
      node: esUrl,
      engine: "elasticsearch",
      indexPrefix: "todo_app",
      requestTimeoutMs: 10_000,
      retry: { maxRetries: 3, baseDelayMs: 100, maxDelayMs: 5_000 },
    });
  }

  // Default: in-memory search for development
  console.log("No ELASTICSEARCH_URL or OPENSEARCH_URL set — using in-memory search adapter");
  return new MemoryAdapter();
}

const searchAdapter = createSearchAdapter();
const searchProvider = createSearchProvider(searchAdapter, {
  resourceFields: {
    todos: ["text"],
    categories: ["name"],
  },
});

const datafn = await createDatafnServer({
  schema,
  db: adapter,
  searchProvider,  // ← Enable search
  authorize: async (_ctx, _action, _payload) => true,
  namespaceProvider: { ... },
  limits: { maxLimit: 200, maxTransactSteps: 50 },
});
```

**Implementation pattern (cross-resource search)**:

```typescript
let searchQuery = "";
let searchResults: Array<{ resource: string; id: string; score: number; data: any }> = [];
let searchAbortController: AbortController | null = null;
let isSearching = false;
let searchDebounceTimer: number | null = null;

async function handleSearch(query: string) {
  searchQuery = query;

  // Clear previous debounce
  if (searchDebounceTimer) clearTimeout(searchDebounceTimer);

  if (!query.trim()) {
    searchResults = [];
    isSearching = false;
    return;
  }

  searchDebounceTimer = setTimeout(async () => {
    // Cancel previous request
    if (searchAbortController) searchAbortController.abort();
    searchAbortController = new AbortController();

    isSearching = true;
    try {
      const result = await client.search({
        query: query.trim(),
        resources: ["todos", "categories"],
        limit: 20,
        select: ["id", "text", "completed", "priority", "name", "color"],
        signal: searchAbortController.signal,
      });
      searchResults = result.results;
    } catch (err: any) {
      if (err?.code === "DFQL_ABORTED") return; // Cancelled, ignore
      console.error("[search] Failed:", err);
      searchResults = [];
    } finally {
      isSearching = false;
    }
  }, 300);
}
```

**Alternative pattern (single-resource DFQL search)**:

```typescript
// Search within todos using DFQL search block
const result = await client.query({
  resource: "todos",
  version: 1,
  search: { query: "grocery" },
  select: ["id", "text", "completed"],
  limit: 20,
});
```

## Notes

1. **Elasticsearch/OpenSearch adapters are fully implemented** — The `ElasticsearchAdapter` (284 lines) and `OpenSearchAdapter` (12 lines, extends ES) are production-ready. They use a custom `ElasticClient` built on native `fetch` — **no `@elastic/elasticsearch` or `@opensearch-project/opensearch` SDK dependency**. The `@searchfn/adapters` package only depends on `@searchfn/core` and `pg` (for the Postgres adapter). The ES adapter supports both dialects via `engine: "elasticsearch" | "opensearch"`, and the OpenSearch adapter is a convenience subclass that sets `engine: "opensearch"`.

2. **All external adapters are fully implemented** — In addition to Elasticsearch/OpenSearch, `MeilisearchAdapter` and `PostgresAdapter` are also fully implemented. The adapters package has comprehensive tests including integration tests (`elasticsearch.test.ts`, `opensearch.test.ts`) and conformance tests (`elastic.conformance.test.ts`, `meilisearch.conformance.test.ts`, `postgres.conformance.test.ts`). All external adapters share common infrastructure: retry with jitter (`internal/retry.ts`), error helpers (`internal/errors.ts`), and sensitive data redaction (`internal/redaction.ts`).

3. **Adapter selection strategy for the example app**: The recommended approach is environment-variable-based adapter selection:
   - `OPENSEARCH_URL` → `OpenSearchAdapter`
   - `ELASTICSEARCH_URL` → `ElasticsearchAdapter`
   - Neither set → `MemoryAdapter` (zero-dependency, zero-infra dev experience)

   This lets the example app work out-of-the-box (`npm run dev`) while also demonstrating the full ES/OS integration path.

4. **Two search approaches coexist on the client**: DataFn now has two client search approaches:
   - **Legacy**: `createClientSearchPlugin()` from `@datafn/client` — uses MiniSearch, implemented as a `DatafnPlugin` with hooks (`afterSync`, `afterMutation`, `beforeQuery`).
   - **New**: `searchProvider` config slot using `@searchfn/datafn-provider` + `@searchfn/adapters` — uses the adapter architecture (IndexedDB/Memory), built-in wiring (no plugin scanning).

   The example app should ideally demonstrate the new `searchProvider` approach since that's the canonical architecture going forward (per spec BKWD-004, the plugin-based approach is being migrated away from).

5. **Schema regeneration**: Adding `indices.search` will change the generated Drizzle schema (`datafn-schema.drizzle.ts`) and types (`datafn-types.ts`). A new DB migration will be needed. The codegen tool reads search indices for type generation.

6. **`client.search()` method**: The `DatafnClient` exposes a `.search()` method that POST-es to `/datafn/search` when online, or uses the local `searchProvider` when offline. This is the primary API for cross-resource search in the UI.

7. **Debounce + AbortSignal pattern**: The search UI should implement debounced input (300ms) with `AbortController` cancellation of in-flight requests. This pattern is documented in the spec (XSRC-006) and is critical for search-as-you-type UX. The `signal` parameter is supported on both `client.search()` and the `/datafn/search` route. The `ElasticsearchAdapter` passes signals through to all ES HTTP requests.

8. **Built-in mutation → index wiring**: When `searchProvider` is configured, the DataFn server automatically calls `searchProvider.updateIndices()` after successful mutations (`server.ts` wires this in the mutation handler). No additional plugin hooks are needed. Errors are caught and logged (fail-soft) — never fail the mutation. The ES adapter uses `refresh=wait_for` on bulk ops, ensuring indexed documents are immediately searchable after mutation.

9. **Docker Compose setup**: A Docker Compose file should be provided to spin up Elasticsearch (port 9200) and/or OpenSearch (port 9201) for local development. Both should run in single-node mode with security disabled for simplicity.
