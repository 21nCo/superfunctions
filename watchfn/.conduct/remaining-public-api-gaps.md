# Remaining public facade gaps: business analytics and synthetic reports

Historical source snapshot: October 25, 2026, following the stored log-pattern alert implementation and before the stored funnel/synthetic reporting changes. Current funnel and synthetic implementation evidence is in stored-funnels-readiness.md and typescript-synthetic-lifecycle-reports.md; the corresponding placeholder descriptions below are the reproduced baseline, not current behavior. Goals, revenue and other noted gaps remain open. This is a bounded source audit of the named public facades, not a full WatchFn audit or readiness verdict. No runtime changes, service execution or additional acceptance tests were performed for this document. All original requirements remain in scope.

## Existing implementations do not close these paths

`typescript/src/business/metrics-tracker.ts` contains a separate `BusinessMetricsTracker` with local arrays/maps. The Watch facade does not instantiate or feed it. Simply connecting it would discard durable query/reopen semantics and retain two stores. Its funnel algorithm counts distinct users independently for each step: it does not enforce prior-step membership, event order or the declared `timeWindow`; missing user IDs collapse into one undefined identity. Its revenue calculation expects a top-level `BusinessEvent.value`, unlike the facade's stored properties. Its trend compares a value aggregate with prior event count. These are reasons to reuse concepts cautiously, not to present this helper as a ready implementation.

The Python package likewise contains `business/metrics_tracker.py` with a standalone process-local tracker; the inspected `watchfn/client.py` does not expose the corresponding business or synthetic facade. Python parity remains required and is not proven by implementing TypeScript queries alone.

`synthetics/http-check.ts` performs real fetch/assertions and records results, but clears its abort timer after response headers, before `response.text()`. Therefore the configured timeout does not bound a stalled body, and response buffering has no size cap. A failed fetch also leaves its timer until expiration. `SyntheticScheduler.stop()` clears intervals but does not cancel or await in-flight requests; repeated intervals can overlap, and its maps are not durable ownership. These lifecycle defects must be corrected before claiming dependable report-producing checks. No live network reproduction was run in this audit.

## Reuse and implementation order

1. **Stored business query foundation and durable goals.** Reuse `StorageAdapter`, `DatabaseStorage`, its streaming keyset iteration, `QueryEngine` and `query/time-range.ts`; keep one canonical event envelope and explicit bounded observations. Use the shared `@superfunctions/db` Adapter with internally wrapped function schema for definitions, following existing AlertManager storage. Implement exact event/property selection, finite numeric aggregation, period boundaries and immutable persisted goal configuration. Reuse named alert channels and the existing durable outbox for pace notifications rather than adding a transport. Acceptance must use actual `business.track` → `flush` → independent database reopen → progress query, including boundary times, invalid amounts, unknown definitions and storage failures. Specify timezone/pace and return shapes where the examples leave them unstated; do not fabricate measured progress.
2. **Ordered funnels on that same event stream.** Persist definitions, validate step filters and duration, and compute ordered identity-based conversions within the declared window. Preserve deterministic event ordering for equal timestamps and explicit handling of missing identity. Prove out-of-order/nonmatching users cannot advance, repeat events do not inflate conversions, and reopen/grouped dropoff matches a shared TS/Python fixture. The standalone helper's per-step independent counts must not be reused unchanged.
3. **Revenue followed by subscription/cohort analytics.** Define a validated event mapping covering the original purchase and BillFn payment examples, money units, currency, refunds and event identity. Reuse BillFn's actual producer contract once its source is inspected; this audit only confirms the Watch SPEC example and does not assert a current billing adapter contract. Persist sufficient subscription lifecycle/cohort events before claiming MRR, churn or projected LTV. No inferred subscription state from payment totals alone. Add exact grouped/time-bucket fixtures and cross-language vectors. Preserve unsupported/missing-input errors rather than returning plausible zeros.
4. **Synthetic lifecycle, persisted definitions/results, then report queries.** First validate/parse the specified intervals and all check variants; reject unsupported execution explicitly until implemented. Bound fetch including response body, track in-flight ownership, prevent unintended overlap, and cancel/await owned work on stop. Persist definitions and result identity through existing shared storage/schema primitives; define restart ownership before automatic scheduling across workers. Then implement uptime/performance and incident transitions from real stored `synthetics.check` envelopes (`type:'track'`, result under `properties`). Specify missing-data versus zero uptime and interval boundary behavior. Exercise an owned local HTTP server with success/failure/recovery, stalled body, stop/reopen, and durable report queries. Browser execution should reuse the established BrowseFn/ProbeFn browser capability after tracing its actual supported contract, not introduce a second browser launcher. Multi-location execution and original alert/retry behavior remain required follow-ups, not waived by a single-node fixture.

This order prioritizes a complete producer→persistence→query path over wiring placeholder methods to unrelated arrays. A synthetic lifecycle fix is independently urgent and can be developed in parallel with business definitions after source ownership is divided; its report outputs still depend on truthful captured results.
