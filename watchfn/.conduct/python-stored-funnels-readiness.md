# Python stored funnel parity

Original requirement: WatchFn SPEC section 8 ordered conversion funnels, time windows, grouping and dropoff analysis. The exact pre-change `9b740435f` Python package had no public `WatchFn.business` facade; an isolated archive/import confirmed this (`/tmp/watch-python-funnel-baseline.log`, owned archive removed). The disconnected `BusinessMetricsTracker` was not substituted for persisted event queries.

## Contract and implementation

Python now exposes `watch.business.track`, `create_funnel`, `get_funnel` and `get_dropoff_analysis`, using the same camelCase serialized definition/query keys and output fields as the TypeScript facade. `get_business_schema()` returns the additive `watchfn_business_definitions` migration. Hosts must create that table before durable definitions are used; migrations are not applied silently. IDs are SHA-256 over UTF-8 compact JSON `[application,"funnel",name]`; the payload is the same `funnel-v1` definition protocol. Production database calls use the existing shared adapter through `DatabaseStorage.run_transaction`, not another connection owner. Memory definitions use a locked dictionary, retained only for the same Watch instance/restart; no cross-process durability is claimed for memory mode.

Definitions are immutable: duplicate creation fails atomically. Validation and payload limits match the TypeScript implementation (2–32 steps, maximum 16 scalar filters per step, maximum one-year conversion window, 32 KiB definition, bounded text/field/identity lengths). UTF-16 code-unit lengths and valid Unicode are enforced for shared textual limits. Scalar equality distinguishes booleans from numbers; numeric grouping normalizes 1/1.0 and signed zero consistently. Groups sort by UTF-8 encoded JSON keys.

Evaluation uses the existing canonical Query/time semantics and retained storage, capped at 10000 candidates, 64 KiB/event, 16 MiB aggregate and 1000 groups. Ordered chains require strictly increasing timestamps; no hidden database order is invented for simultaneous events. A frozen prior-state batch ensures a simultaneous new first step cannot overwrite an earlier valid chain before its next step is evaluated. Users are counted once per reached depth; retries can form later valid chains. Cohorts attach to the user's first qualifying entry in the report range. Conflicting simultaneous first-entry cohorts fail explicitly. Dropoff steps are one-based and must precede another step. Missing/invalid user identity is counted as ignored, not as one anonymous shared user.

Business tracking snapshots JSON and the trusted configured application before batching. A narrow `CanonicalBusinessEvent` subclass preserves `app:{name}` without adding `app:null` to unrelated legacy Event serialization. The stored decoder explicitly recognizes the canonical track envelope, validates its keys/application/timestamp, and retains the pre-existing strict treatment of other event types. Canonical track timestamps may be timezone-qualified strings or epoch milliseconds. This subclass alone normalizes capture, direct construction and decoding to JavaScript millisecond precision: numeric epoch input truncates toward zero; ISO fractional milliseconds are discarded. Submillisecond Python arrival differences cannot fabricate an ordered conversion that TypeScript sees as simultaneous. Ordinary legacy Event precision remains unchanged. HTTP canonical-track admission preserves the envelope only for the configured application; foreign ownership and extra fields are rejected. Existing ordinary HTTP track admission remains available and unchanged, but those unowned events cannot silently become business funnel history.

Relevant stored events without an application owner fail with a migration requirement; no historical ownership is guessed. Foreign application events are excluded. This is the business producer/query boundary, not a claim that every generic query API is tenant-isolated. Legacy migration must establish ownership from actual provenance. Retention remains the existing storage policy: memory retains its configured rolling event count and durable queries use currently retained rows, not a complete historical ledger.

The existing lifecycle owner admits business calls, rejects operations after stop, and waits for already admitted reads/writes before database shutdown. The implementation does not hold the admission lock across shared database callbacks. Memory definitions survive same-instance restart; a new memory Watch has no persisted definitions.

### Exact millisecond conversion-window correction

A public memory reproduction on the first Python checkpoint exposed a boundary error: canonical events at4001ms and64001ms, exactly one minute apart, yielded[1,0]. Multiplying Python floating epoch seconds by1000 produced4001.0000000000005 and64001.00000000001, so the difference incorrectly exceeded60000. Numeric report upper bounds could exclude the same retained endpoint.

FunnelQuery now supplies its own timestamp conversion through the existing Query engine's overridable converter. Canonical datetime/ISO values use exact integer timedelta arithmetic; explicit numeric query bounds remain unchanged (including4001.5, which correctly excludes4001). Ordinary Query retains its original converter and microsecond semantics. Existing naive legacy datetime interpretation remains UTC so relevant unowned records still reach the explicit ownership-migration error. Tests cover both numeric and ISO inclusive boundaries, fractional numeric exclusions and the same actual installed bilateral SQLite vector.

The first focused correction rejected naive legacy datetime too early; retaining its existing UTC interpretation restored the ownership error.
