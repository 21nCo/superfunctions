# Canonical bug intake and BotFn issue delivery

The original CatchFn issue-sync path now uses WatchFn's canonical `bug_report` intake, shared HTTP router and internally schema-wrapped shared DB. This is opt-in prospective issue delivery, not the separate flat CatchFn report service.

## Contract and migration

Use one trusted application boundary per deployment. The existing Watch API key authorizes all configured app routes and all Watch queries. Routes are server-owned destination allowlists, not per-key app authorization. Outbox namespace scopes report identities and delivery methods, not tenant-isolated query reads. Mutually untrusted tenants require separate deployments/databases. Browser/Catch clients use the configured Watch API key, which also authorizes Watch queries; provider credentials stay server-only. When exposing that full Watch key is unsuitable, route submissions through an authenticated application backend. There is no ingestion-only credential in this implementation.

Before enabling `botfn`, apply an additive migration for `getBugIssueSchema()` alongside `getWatchFnSchema()`. The new `watchfn_bug_issues` table has a unique ID derived from namespace/app/report ID, immutable fingerprint, event reference, trusted route identity, status/revision/lease, timestamps, attempt count and verified linkage. Its queue index covers namespace/state/id. Existing event schema/data is unchanged. Missing schema causes intake failure (503), not successful delivery. Transaction capability is required; no adapter name is treated as proof of physical durability. The built-in memory/legacy event stores cannot enable this integration. Shared memory adapters remain useful for contract tests only; hosts are responsible for using a durable configured provider.

Only newly submitted canonical reports are queued. Existing generic-arrival event rows are not silently backfilled or rewritten, and their old IDs are not retrospectively deduplicated. Stop old writers before switching a deployment; choose a stable namespace and preserve new canonical IDs/content across retries. Do not replay historical reports into an enabled integration unless creating their issue is intended. Disabling the integration returns to legacy generic-arrival storage semantics; it does not process existing outbox rows. Keep a delivery-enabled worker configured until its queue is resolved, and do not mix enabled/disabled writers if replay deduplication is required.

The immutable fingerprint is computed from the original JSON envelope. Successful linkage changes only the stored event's integration fields; replaying the original envelope remains a deduplicated acknowledgment. An altered report with the same namespace/app/ID returns 409. All request routes are validated before any batch writes, but each report commits separately: later storage/conflict failures can follow earlier commits. Non-bug events retain their original arrival semantics and are not made idempotent by this feature.

A transaction commits event plus pending outbox before HTTP 202. Explicit server worker calls claim candidates with revision CAS and unique leases. Missing route/event fails before the provider call with an explicit failure code. Once a provider call is attempted, unavailable/malformed/negative responses are conservatively considered ambiguous because existing BotFn clients do not expose a reliable typed no-side-effect receipt. No ambiguous create is automatically retried. Expired claims are parked, including after a process crash. A late successful response cannot overwrite a newer claim state. Provider verification binds a trusted repository/team, stable report marker, issue ID and allowed provider URL before transactionally updating both outbox and canonical event. Operator-supplied arbitrary URLs are never accepted.

`getBugIssueStatus`, `processBugIssues` and `reconcileBugIssue` are server methods, not public HTTP routes. The host must authorize any operator API exposing them. `stop()` waits for worker/reconciliation work already admitted into that instance, but does not drain unclaimed outbox entries or other processes. Database/network stalls remain subject to provider/database runtime behavior; there is no universal shutdown deadline.

## Validation

- Core suite: 166 tests in 18 files; source `tsc --noEmit` and dual CJS/ESM/declaration build pass.
- Nineteen focused contract tests cover authentication/config gates, whole-batch route checks, credential-safe persistence, exact duplicate/conflict semantics, rollback, partial commits, two-worker CAS, namespace-scoped status, unknown outcomes, verified recovery, expired/late claims, bounded waits and stop ownership. Shared memory tests establish behavior only.
- Native acceptance: `npx vitest run --config tests/integrations/botfn-sqlite.config.ts` from `watchfn/typescript` passes two scenarios using actual better-sqlite3/Kysely, no caller adapter schema, explicit migration, real loopback HTTP and actual BotFn request clients. Pending intake survives close/reopen; both GitHub/Linear linkage survives a second reopen. A native SQL trigger failure after event insert rolls back both rows. Two SQLite connections claim one create; a provider that commits then drops its HTTP response remains parked across reopen, with no second create and verified recovery into the original canonical event.
- Fresh packed core consumers pass ESM and synchronous CommonJS on Node18.18.0, Node20.19.0 and Node22.23.3; strict Node16/NodeNext declaration emission includes the new issue schema under current TypeScript and5.0.4. Production dependency audit reports zero findings. npm10.8.2 initially failed inside Arborist (`edgesOut`); the established npm11 runner completed without force/legacy-peer flags.
- GitHub acceptance uses an ordinary PKCS#1 RSA PEM, actual Web Crypto JWT signature and installation-token request. The separate BotFn key-format prerequisite additionally verifies PKCS#8 PEM/raw-base64 compatibility and malformed-key rejection with seven tests; its source typecheck passes.
- The provider servers are local protocol fixtures. They verify actual request paths, authentication, GraphQL shape and receipt interpretation, not hosted provider entitlement, GitHub installation permissions, Linear workspace access or real external side effects. No real issue or message was created.

## Remaining original gates

This checkpoint does not establish full WatchFn, CatchFn or BotFn readiness. Catch SDK integration is validated separately. Hosted provider acceptance, BotFn packaged-consumer support, tenant-aware authorization/query isolation, provider status/webhook synchronization (Catch v1.1), retention and worker operations remain open. Existing events require an explicit operator-owned migration if historical delivery is desired.

The existing Linear client cannot cancel its underlying request; both actual clients parse unbounded provider JSON. Timeout bounds the worker's wait, not guaranteed transport cancellation or memory. The worker conservatively parks unknown outcomes and does not claim exactly-once provider delivery. Automatic search/reconciliation, requeue after definitive rejection and abandoned-report resolution are not implemented. Do not delete an uncertain row and replay it without checking the provider first. Report descriptions, steps and tags are sent to the provider; context, user and attachment payloads are retained in Watch storage but excluded from issue text. Application-level redaction still belongs before ingestion.
