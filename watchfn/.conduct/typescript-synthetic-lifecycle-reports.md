# TypeScript HTTP synthetic lifecycle and stored reports

Original scope: SPEC section 4 (HTTP/browser checks, retries, locations, failure alerts, uptime/incidents/performance reporting). This checkpoint implements the bounded HTTP execution and actual stored-report path. It does not complete browser execution, distributed locations, durable check definitions/restart scheduling, consecutive-failure alert delivery or Python parity. Those requirements remain open; unsupported browser/location/alert configurations now fail explicitly before any timer or network request is admitted.

## Reproduced behavior and implementation

The initial three focused regressions failed against head `9b740435f8352afef473eb8b4ac7179cf06721ce`: the body timeout was cleared after headers, browser creation resolved without running anything, and a slow check overlapped multiple scheduled attempts. Receipt: `/tmp/watch-synthetics-baseline.log`. The corrected first three cases passed; later validation includes the expanded cases below.

HTTP creation validates and snapshots configuration before admission. The original string intervals (`1m`, `5m`) work, alongside bounded numeric milliseconds; accepted strings use ms/s/m/h/d. Intervals range from 10 ms through the native timer maximum 2147483647 ms. IDs default to the declared name, matching SPEC report examples; duplicate IDs fail rather than replacing a live check. Each scheduler admits at most 100 checks. Configuration returned to callers is a separate snapshot.

Each attempt has a finite 1–300000 ms timeout (default 5000) covering fetch headers **and the entire body**. Actual response bytes are limited to 1 MiB by default, configurable from 1 byte through 16 MiB. Body-limit, assertion, network and deadline failures produce failed observations; response readers are canceled/released and timeout/signal listeners removed in finally. Diagnostic strings are truncated. `duration` is the final attempt's elapsed response time; `totalDuration` also includes earlier retry attempts. Retries range from zero through five and are sequential; the result records `attempts`. Cancellation does not trigger retries.

Scheduling is fixed-delay: the next interval starts after the prior execution and persistence finish. There is no catch-up queue or overlapping attempt for a check. Stop synchronously revokes all check controllers and clears timers, then joins their owned tasks. WatchFn's existing tracked-operation drain awaits scheduler cleanup and storage outcomes. An interrupted check is not published as a service outage. Stop/restart does not silently recreate prior definitions: registration is currently process-local and hosts must explicitly register after restart. Registration before start or while stopping fails.

## Producer, application ownership and report semantics

The scheduler awaits the existing `watch.ingest` path with `{type:'track',name:'synthetics.check',app:{name:configuredName},timestamp,properties:result}`. The envelope timestamp equals result completion time. Each run has a unique ID. Actual database storage and the existing event projection/retention paths are reused; no second event store is introduced. Persistence failures remain visible through owned-task/Watch drain failure handling.

Reports require a started Watch instance and are admitted to the same lifecycle drain. They reuse canonical QueryEngine time filtering over a streaming StorageAdapter, with a 10000-candidate, 64 KiB/event, 16 MiB total scan budget. Exceeding a budget fails rather than returning a truncated percentage. Relevant legacy results without an application owner fail with an explicit migration requirement; operators must establish ownership from evidence before migrating them. Results belonging to a different application are excluded. This scopes the synthetic producer/reports only, not all generic Watch query APIs or every tenant boundary.

The canonical envelope timestamp is authoritative for report windows/order. Captured external result timestamps can precede admission; they do not override query time semantics. Identical run IDs are deduplicated when outcome/time/duration agree; conflicts fail. Simultaneous contradictory outcomes for a check fail rather than guessing incident ordering.

- `getUptime`: returns `basis:'completed-checks'`, total/successful/failed counts, `observed`, and percentage `uptime`. No observations produce null uptime. This is a sample success fraction, **not a claim of continuously measured wall-clock availability**; missing/stopped periods are not fabricated as either success or failure.
- `getIncidents`: reconstructs observed consecutive failed runs and their next successful recovery, including runs beginning before the requested window and intersecting it. `leftCensored` means the first retained observation is already failing, so the true outage start is unknown. Status is as of the requested report endpoint. Full relevant retained history is scanned within the same bounds; if history exceeds the budget, the query fails. Retention can remove prior outcomes; the API does not pretend it knows the omitted history.
- `getPerformanceTrend`: supports the original responseTime metric and bounded time buckets (maximum 10000). Buckets include count/successful/failed/min/max/average, with null aggregates for empty buckets. Buckets are half-open except the exact report endpoint belongs to the last; a zero-width point range has one bucket. No interpolation fills missing samples.

## Security and final correction wave

SPEC Security & Privacy requires data masking and PII redaction. The legacy HTTP runner included response headers and assertion body values in stored results. The corrected runner reuses `@logfn/core`'s existing default redactor for response headers (including cookies/authorization and recognized textual PII), never echoes assertion expected/actual body values, and reports stable generic network errors rather than untrusted error strings that may contain URL secrets. This is the existing redactor policy, not a claim to recognize every arbitrary secret in every possible header. URLs are capped at 4096 UTF-8 bytes and request headers at 16 KiB aggregate before admission. No dependency was added.
