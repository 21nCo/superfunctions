# Stored conversion funnels

Original SPEC section8's createFunnel/getFunnel/getDropoffAnalysis returned empty placeholders. The actual business.track regression failed before implementation. The public facade now stores immutable named definitions and derives counts from canonical retained events, not the disconnected BusinessMetricsTracker arrays.

The additive getBusinessSchema() table stores protocol-tagged definitions through the shared DB adapter wrapped internally. Hosts migrate the table before use; no adapterSchema argument is required. SHA256 of the JSON namespace/kind/name tuple supplies unique identity. Concurrent duplicate creation cannot overwrite an existing definition. Memory definitions are same-instance only; database definitions reopen independently. This does not imply automatic migration, crash durability for memory storage, or a multi-query transactional snapshot of event history.

business.track snapshots its properties before admission, bounds the event to64KiB, and adds trusted app.name. Queries select that application. Matching historical business events without ownership fail with an explicit migration error; ownership is not inferred from event names. Generic track remains unchanged. Retained event history can already be incomplete because of host retention or default memory eviction; counts describe the retained query interval, not events that have been deleted.

Ordered conversion uses identified users (nonblank string userId, top-level presence wins over properties), exact event names, finite scalar equality filters and a total conversion window from each first-step attempt. Repeated attempts can restart within the interval; a user contributes once per step at their greatest reached depth. Descending updates prevent one event advancing multiple steps. Distinct steps require strictly increasing timestamps: storage does not preserve trustworthy order among simultaneous events. First qualifying entry fixes the user's cohort group; conflicting groups at the same first timestamp reject as ambiguous. Missing identities are counted separately and cannot merge into an artificial shared user. Results expose counts/rates, not user identifiers. Dropoff step numbers are one-based and refer to the transition to the following step.

Bounds:2–32 steps,16 filters perstep,32KiB definition, positive minute/hour/day/week window at most366days;10000 scanned candidates,64KiB each and16MiB total,1000 groups. Exceeding a bound rejects the complete query rather than silently truncating. Shared QueryEngine time/type/field semantics and streaming database iteration are reused. These are application bounds, not deadlines for a stalled database. Captured definitions and queries join Watch shutdown through existing operation ownership; post-stop admission rejects.

Validation: baseline failed because result.steps was absent. Initial five source/native tests passed, including actual business.track→flush→independent SQLite reopen and duplicate-name atomicity. Final combined suite passed391 tests across38 files, source types and build; fresh five-tarball installed consumers passed actual funnel capture/query, Node18/20/22 ESM/CommonJS, strict TypeScript5.0/5.3/5.4/current declarations, external Zod composition and production audit0. The installed consumer was removed. Equal-timestamp batches freeze prior chains so a simultaneous newer attempt cannot erase an older valid conversion; both input orders are covered. Test additions include window/order/restart/cohort/dropoff, same timestamp, ignored identities, snapshotting, legacy ownership, another app, shutdown drain and candidate-overflow iterator closure.

Python funnel parity, goals/pace notifications, revenue/subscription analytics and the rest of original WatchFn readiness remain required. This is not a full business analytics or production-readiness claim.
