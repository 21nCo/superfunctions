# Changelog

filefn follows semver. The `@filefn/server` version is the spine of these notes. Breaking changes are flagged.

## Unreleased

- Offline queue: a stopped `process`/`processAll` call stops waiting for the partition lock at once (its signal reaches the lock request), and an `OfflineSync`'s principal checks before its callbacks are raced with the sync's lifetime (`queue.principalIsCurrent(signal)` takes an optional signal), so a disposed sync settles even while `currentPrincipal` stalls. A `replayAccount` or `uploader.replayScope` that rejects with an `OfflineQueueError` `FILEFN_QUEUE_PRINCIPAL_MISMATCH` stops the pass like a failed `currentPrincipal` check (no attempt used, no waiter settled); any other refusal stays the generation's own outcome. An offline `uploadFile` abort now races the first upload request the guard admits (the generation is marked dispatched in that transaction) rather than the upload-step claim: an abort that commits first removes the generation and nothing is sent. The built-in replay transport admits a request only right before it is sent, after its credentials resolved (its checks around `getAuthHeaders` use the new non-admitting `checkPrincipal()` of the uploader input), so an abort while credentials are slow or missing still removes the generation. An aborted `process` or `processAll` call (an `OfflineSync`'s pass once the sync is disposed included) settles at once, `stopped`/`aborted` or an empty list, even while `currentPrincipal` stalls, and returns no entry data. `migrateLegacyUpload` removes only the legacy record incarnation it admitted, and only while its entry is still that admission's: a record rewritten under the same upload ID since stays, refused as `already-migrated`.
- `@filefn/client` upload transport: an `upload/init` answer is accepted unwrapped, as `{ ok: true, data }` or as a legacy `{ data }` envelope without `ok`. Session and version IDs are sent as one raw path segment, as before (the FileFn router matches the segment without decoding it), and may be any server-generated string of 1-1024 characters without `/`, `\`, `?` or `#` that URL parsing leaves unchanged inside a path (so `%`, `|`, `^`, `[` and `]` are kept, as before). An ID that URL parsing would change (a dot segment such as `.`, `..` or `%2e`, whitespace, control or non-ASCII characters) cannot reach the server as the same segment and is refused as `FILEFN_UPLOAD_RESULT_INVALID`. `uploadArtifact` sends such a version ID raw too.
- `@filefn/server` refuses a marked `upload/init` (`x-filefn-replay-scope`) that carries no idempotency key, in neither the header nor the deprecated body form, with 400 `FILEFN_INVALID_REQUEST` before any session lookup or creation: repeating it would create another session. So is a marked init whose header or body key is present but empty or blank, even when the other form carries a key.
- **Breaking (`@filefn/client` 0.5):** `new OfflineSync({ store, client })` over the unscoped pre-0.5 `OPFSStore` throws `FILEFN_QUEUE_LEGACY_UNSCOPED` and reads, sends and removes nothing; `syncOne`, `syncUpload`, `cancelUpload` and `waitForUpload`, which only served that form, are removed. Those uploads belong to no known principal: migrate each with `OfflineQueue.migrateLegacyUpload` once you can prove whose it is. Migration treats a legacy record or sibling that cannot be read (anything but a confirmed absence) as inconclusive: an unreadable record fails retryably and keeps its claim and data, and an unreadable sibling counts as sharing the record's replay key, so the migrated upload gets a fresh key.
- Offline queue: no server account (`replayAccount` returns null) or no credentials (`getAuthHeaders` returns null, `FILEFN_QUEUE_CREDENTIALS_UNAVAILABLE`) while `currentPrincipal` still matches leaves only that generation provisional (`scope-unconfirmed`, no attempt used); `processAll` goes on with the other entries, and only a failed `currentPrincipal` check stops a pass. A `process` or `processAll` signal (a sync's included) reaches the listing, every locked observation and the outer principal check, so disposing a sync whose `currentPrincipal` stalls frees the partition lock. Preview reads are ordered by a partition revision that every changing transaction raises, so a preview a later read of the same instance overtook is read again even for an entry the instance never saw (up to five reads, then `FILEFN_QUEUE_BUSY`). A legacy migration's source identity includes its legacy root.
- **Breaking (`@filefn/client` 0.5):** offline uploads go to a durable OPFS queue bound to `offline.partition` (a service and a user or guest namespace). Without a partition, an offline `uploadFile` throws `FILEFN_OFFLINE_PARTITION_REQUIRED`; `offline.currentPrincipal` is also required (it must answer from local state, without a network request), and queued uploads and hooks run only while it returns the partition's principal. Replays with the built-in transport need `offline.getAuthHeaders(principal)` (`FILEFN_OFFLINE_CREDENTIALS_REQUIRED` otherwise) and send only its headers, never with cookies (`credentials: "omit"`); the client's partition (frozen) and transport are captured when its queue is made. A hold stops an upload already running in any tab before its next request. Tabs announce runnable work to each other on a `BroadcastChannel`, and a started `OfflineSync` also polls while idle (`idlePollMs`). The queue journals each generation's replay key, holds, verification and publication; coordinates tabs with `navigator.locks` (or `offline.queue.coordinator`) and refuses durable work without either; and enforces entry and byte limits. Uploads staged by 0.4 and earlier are no longer replayed automatically: migrate them with `OfflineQueue.migrateLegacyUpload` once you can prove whose they are. Sync callbacks, queue listeners and `whenSettled` waiters are checked against `currentPrincipal` before each delivery, so a callback that switches the account receives nothing more of the old principal's. A quota error during `migrateLegacyUpload` is the typed capacity refusal and keeps the legacy upload. Call `client.dispose()` on logout or account switch. See Features › Offline.
- The offline queue confirms a publication only for `undefined` or a plain `{ result?, published?: true }` envelope (a `reconcile` check only for `{ published: true, result? }` or `{ published: false }`; a manual outcome refuses other keys), returns no entry from `process`, `reconcile` or `stage` once a callback switched the account, revokes every preview URL when a principal check fails, reclaims safe data and retries once when the browser runs out of quota during a stage, and disposes the syncs driving a queue when that queue is disposed (`queue.onDispose`). An `upload/init` replay that reports an ended session with a malformed session ID stays ambiguous under the same key. A verifier decides only with an exact `{ verified: true }` or `{ verified: false, reason? }` envelope. `get`, `list` and `migrateLegacyUpload` fence their results on the principal like `process`, `whenSettled` waiters a read settles settle only after that read returned, and no preview URL is created after a principal switch during its read. The pending-local preview is the highest generation of the file, not the entry written last. A hold or principal switch that stops a completed-session read-back uses no attempt. Reclamation frees the data of an entry being restaged that never committed a journal, and frees a published entry's data before writing its tombstone.
- `@filefn/client` sends the `upload/init` idempotency key in the `x-idempotency-key` header. It used to send it in the body, which the server ignored. A key must be 1-255 visible ASCII characters (`FILEFN_INVALID_IDEMPOTENCY_KEY` otherwise), and an application retry must pass the same `fileId` as its first call. Offline, each staged generation sends its own key (the caller's key, if any, is its prefix); a guest partition needs `offline.uploader`; `queue.reconcile` outcomes name their `attemptId`.
- `upload/init` also honors an `idempotencyKey` in the JSON body, with a deprecation warning, until the next minor release; a request giving both forms must give the same value. A body-only key (the pre-0.5 form) resumes only a session parts can still be uploaded to; a completed, aborted or expired session, one whose completion started, or another payload under the key gets a fresh session without the key, so a 0.4 client's retry finishes as before. An idempotent replay reports the session's `status`, and a completed session's `fileId` and `versionId`, so a client confirms the stored file instead of uploading again and starts an expired or aborted session again under a new key. A completed session that never recorded its own version reports no `fileId` or `versionId`. A completed replay adds `versionConfirmed: true` while the recorded version is still stored under its file (checked for the session's owner, no read permission needed), and `@filefn/client` settles on it without reading the version back, so a write-only uploader whose completion response was lost is no longer left ambiguous.
- A proxy part upload that finds its session completed by another request meanwhile returns `409 FILEFN_UPLOAD_ALREADY_COMPLETED` (it returned `410 FILEFN_UPLOAD_ABORTED`), and completing a session whose live completion claim outlasts its expiry waits for that completion instead of returning `410 FILEFN_UPLOAD_EXPIRED`. An offline replay starts again under a new key only when `upload/init` reports the session ended, which a replay now does only after moving the session to `expired` with a conditional write that excludes any later completion claim; an expired session an earlier FileFn left partly published is finished as a publication instead. A completion past the expiry whose claim is stale (it crashed) is ended the same way, by `upload/init` or by `upload/complete` (which records the end before returning 410), so the replay reports it ended and starts again under a new key. A session recorded as `expired` refuses part signing, part uploads, part completion and completion with `410 FILEFN_UPLOAD_EXPIRED` on every worker, whatever its clock says.
- Cross-origin hosts must allow the `x-idempotency-key` and `x-filefn-replay-scope` request headers (keyed uploads and every offline replay send them); the framework guides, the Hono quickstart and the production example now list them.
- Offline replays are bound to one account from their first request: the built-in transport marks each `upload/init`, the first included, with `x-filefn-replay-scope` set to the scope of the account the partition expects (`offline.replayAccount(principal)`, by default the partition principal's `principalId` and `tenantId`), and `@filefn/server` refuses a marked init whose caller is unauthenticated or the shared `anonymous` principal (401 `FILEFN_AUTH_REQUIRED`, also where `auth.required` is false) or has another owner or tenant (409 `FILEFN_REPLAY_SCOPE_MISMATCH`), creating nothing; the generation stays provisional under the same key. There is no `unpinned` first init. A response without `replayScope` (a server before 0.8) is ambiguous: the built-in replay needs `@filefn/server` 0.8. A custom uploader that implements `replayScope(principal, signal)` is bound the same way and receives the journaled `replayScope`.
- An offline `uploadFile` stages its generation under an admission hold owned by the call (`OfflineQueue.stageAdmitted`): it is decided released or cancelled in the transaction that ends it, and a call that never ends it (disposal, reload, a principal switch) leaves the generation runnable for its principal instead of held forever. A success envelope whose payload itself carries `ok` other than `true` or a non-null `error` proves nothing (the generation stays provisional under its key). Preview reads order by every entry of the file, so removing or publishing the newer of two entries no longer makes `getPendingLocalDescriptor` report `FILEFN_QUEUE_BUSY`. A pending `replayAccount` no longer keeps the entry lock after disposal.
- An `in_progress` replay or session status whose completion was decided reports `completionStarted: true`, and `@filefn/client` then signs no part and finishes it with the completion call (an adopted earlier publication no longer loops on part signing); a status read that reports `completed` is reconciled through the same key's replay.
- The offline queue fences every entry-returning call (`migrateLegacyUpload`, `stage` and `hold` included) after its lock coordinator returns; applies an observation only to what existed when it was read (an old read never settles a newer generation's waiter, and a late cancel never aborts or revokes a newer generation); treats a journal or partition file it cannot read as an error rather than an uncommitted remnant (nothing is removed and no generation number is reused); records the destination queue root and entry ID in a legacy admission claim, so another root is refused as `already-migrated`; and goes on with the pass, re-planning the entry, when another tab replaces or cancels the generation being uploaded.
- An explicit failure envelope (`ok` present and not `true`, or an `error`) never confirms anything: not an expired or aborted session at `upload/init` (the key is kept), and not a stored version at completion, at a completed `upload/init`, at the version readback or from a custom `offline.uploader`; the generation stays provisional under the same key. A coded 4xx from a signed storage URL, a same-origin one included, is read as a FileFn error only on FileFn's verified part route, so it stays provisional too. Every queue call that reads or writes the journal (`listLegacyUploads`, `usage`, `reclaim`, `release` and `cancel` included) passes the principal and disposal fence after its lock coordinator returns, for its errors (a generation conflict naming the current generation, say) as well as its results. A legacy migration refused before anything was admitted (`generation-conflict`, `publication-pending`, `capacity`) drops its claim, so a retry may choose a free `entryId`. A preview read that a newer stage, cancel or preview overtook is read again instead of revoking or replacing the newer preview. `stage` refuses a file larger than `maxBytes` before reading it, and an offline `uploadFile` refuses an `idempotencyKey` over 200 characters synchronously.
- `@filefn/client` decides what an upload-session answer proves in one decoder: only an unredirected 2xx `{ ok: true, data }` without `error` (or a bare legacy body) whose payload has the route's shape confirms a session, an end or a stored version; a coded refusal is read only from the FileFn route that was called, and a FileFn part request follows no redirect. Anything else leaves an offline generation provisional under the same key. The offline queue journals a replay's account scope with its key before the first request (a custom uploader opts in with `replayScope(principal, signal)`), orders observations, waiters and previews by journal position only, and stages an offline `uploadFile` held until the call releases or cancels it (a failed cancel or release rejects `done()`).
- An offline `uploadFile` abort after its staging committed is a cancellation requested through the partition lock at once, ordered against the first upload-step claim: it removes the generation only if no tab claimed it yet, and otherwise keeps the journal, key and bytes and rejects `done()` with `FILEFN_QUEUE_UPLOAD_STARTED` (it used to delete a generation another tab was already uploading). `stageAdmitted` takes the call's `AbortSignal` and passes the outer principal fence; `abortStaged` is the lock-ordered cancellation. A replay scope that is unresolved or differs from the journaled one uses no attempt and no longer ends at the retry limit (`scope-unconfirmed`, resumed by itself once the scope matches), and a scope is resolved for one generation only. The built-in replay races `offline.getAuthHeaders` with the step's signal, so a pending one no longer keeps the entry lock after disposal. A self-contradicting `upload/init` (an ended session with completion markers or a stored version, `versionConfirmed` without `completed`, `completionStarted` without `in_progress`) or a stored version naming another status confirms nothing, and only the client's own confirmation (or a custom uploader's `createUploadSessionEndedError`) retires a key. Preview reads are ordered against every observation of the file, not only earlier previews.
- Upload init and complete that cannot verify a stored size return `500 FILEFN_STORAGE_STAT_UNAVAILABLE` with the message `Upload size cannot be verified`. A complete whose proxy parts are missing returns `409 FILEFN_UPLOAD_INCOMPLETE` with the message `Upload incomplete`. Neither response names the storage adapter or the upload session.
- A metric sink passed directly in the `observability` configuration receives upload failures (`filefn.upload` / `failure`, with `labels.reason` of `size_unverified`, `parts_missing`, or `size_mismatch`), quota denials (`filefn.quota` / `denied`), and processing duration (`filefn.processing` / `complete`, with `durationMs`). Those labels are a closed set: no file id, session id, error text, or usage figure.
- A processing service built on its own with `createProcessingService` never serves an artifact whose parent file row is missing. `getArtifactDownloadUrl` answers `404 FILEFN_NOT_FOUND` (`Artifact not found`) for it with or without a `readChecker`; before, a service without a `readChecker` signed a URL for it. An artifact whose file row exists is served as before. `createFileFn` always configured a `readChecker`, so it already behaved this way. Standalone hosts that create artifact rows without a `files` row must create the file row first.

## 0.7.0 — security

An unauthenticated caller is the principal `anonymous` and owns nothing. A public upload stays readable and listable by anyone. A private one needs a grant made to `anonymous`. That caller cannot replace or delete the upload, and cannot create, list, or revoke share links or grants. Existing share links and grants on anonymous uploads keep working. Signed-in owners can manage grants for their own files over HTTP. Creating a share link requires a signed-in user with `canShare` on the file. To clean up legacy access on files owned by `anonymous`, set `revokedAt` on unwanted `fileShares` rows for those files and delete unwanted `filePermissions` rows for those files. Never return the principal id `anonymous` from `resolveSession`.

The same release also sanitizes storage keys, checks the stored upload size, tightens artifact keys and download headers, and scopes idempotency to the caller. Init validation, roles, rate limits, owner quota, and log hygiene land here, including the same key, init, and size checks in the Python client.
