## Executive verdict

The current implementation is no longer a shallow 25-component prototype. It has a deterministic 61-entry canonical catalog, 50 controller-backed primitives, 11 typed static contracts, 419 anatomy parts, three supported headless/styled framework surfaces, real public-tree tests, a substantial DOM platform, and a deployed catalog with 2,805 static route documents. The current public catalog at `https://uifn.dev` serves the expected 61-component React/Svelte/Solid inventory and is a credible showcase.

That breadth must not be confused with release readiness. The present candidate fails its source-delivery gate, has an invalid offline registry signature, has generated delivery-manifest drift, fails the styling contract, relies on stale/divergent cross-framework evidence, generates duplicate DOM IDs when public core controller factories use their documented default environment, and publicly leaks DOM-dependent utilities from the package whose architectural contract says it has no ambient DOM dependency. The worktree is not a frozen candidate, most of the new implementation is untracked, external compatibility is 0/35, human assistive-technology evidence is 0/244 rows, independent accessibility review is absent, Phase 20 does not exist, and the final release command deliberately fails closed.

The right summary is:

- **Catalog breadth:** peer-level for Ark/Zag component families.
- **Catalog deployment and visual shell:** strong and currently live.
- **Headless implementation:** substantial, with meaningful automated coverage.
- **Per-component API/documentation depth:** materially behind Ark/Zag.
- **Styled application-component breadth:** materially behind coss ui/shadcn.
- **Package/source distribution:** currently broken.
- **Production and 1.0 release confidence:** blocked.

No production, accessibility 10/10, or general 10/10 claim is supportable from the current state.

## Authoritative intent and requirements

The current baseline is the July 17 audit-fix bundle under `uifn/.conduct/specs/2026-07-17-audit-fix-fb19ad09-spec`, including its later Phase 14–20 amendments. It supersedes the earlier five-framework implementation target.

The accepted target is:

1. React, Svelte, and Solid are the stable framework set.
2. Vue and Angular are removed without compatibility wrappers.
3. One private runtime owns behavior behind the public controller contract.
4. `@uifn/core` has no framework or ambient DOM dependency.
5. `@uifn/dom` owns focus, layers, modality, portals, presence, positioning, modal behavior, forms, observers, and other browser services.
6. The stable catalog has exactly 61 GA primitives.
7. Package and copied-source delivery are first-class and derive from one canonical definition.
8. Styled packages are framework-isolated.
9. `patterns` and `sf` remain experimental and non-blocking.
10. React 18.3/19, Svelte 5, Solid 1.x, Node 20/22/24, current browser/device cells, WCAG 2.2 AA automation, signed VoiceOver/NVDA/TalkBack testing, independent accessibility review, performance budgets, security/provenance, and fail-closed release evidence are mandatory before 1.0.

### Interpretation

UIFn is already broad enough to be compared with Ark/Zag at the family-inventory level. Adding more low-level primitive names is not the immediate priority.

Ark and Zag remain materially deeper at the component-contract level:

- Ark Accordion documents controlled and uncontrolled use, provider/context access, item context, multiple/collapsible/horizontal modes, lazy mounting, animation CSS variables, exact root and part props, defaults, data attributes, context API, and keyboard support.
- Zag exposes a mature machine/connect split, individual component packages, visualizable logic, framework bindings, and detailed per-component feature/API documentation.
- Zag Carousel explicitly supports CSS Scroll Snap, start/center/end alignment, multiple visible slides, looping, autoplay, and custom spacing. UIFn Carousel supports index control, looping, orientation, autoplay, pointer threshold dragging, indicators, and announcements, but renders one active item and hides the rest. It does not expose the same alignment, slides-per-page, snap-point, spacing, or native scroll-snap model.

Coss and shadcn solve a different upper-layer problem. They are much stronger in styled application composition: cards, tables, skeleton/loading states, badges, breadcrumbs, command palettes, input groups, textareas, calendars, sidebars, and content/AI messaging surfaces. UIFn is stronger in several difficult headless controls, but its styled layer is not yet a complete application UI kit.

## Findings

### F-01 — P0 — The current candidate cannot pass the mandatory release program

**Evidence**

- `uifn/.conduct/specs/2026-07-17-audit-fix-fb19ad09-spec/phase-reports/PHASE_19-2026-07-26-a5d2b285-report.md:24-38` marks Phase 19 `BLOCKED`.
- The same report records a dirty candidate, 0/35 trusted compatibility cells, 0/244 human rows, an unprovisioned trust root, no qualified participants, and no independent assessment.
- `package.json:78-104` exposes Phase 01 through Phase 19 but no Phase 20 generator/verifier.
- `scripts/verify-uifn-release.mjs:17-23` always exits with `UIFN_RELEASE_PROGRAM_INCOMPLETE` after the current stable subset passes.
- All stable package versions inspected are still `0.0.1`; `@uifn/core` describes itself as `ga-candidate`.

**Impact**

There is no defensible path from the current checkout to publication. Compatibility, accessibility, performance, security, provenance, signing, and rollback requirements are incomplete.

**Required resolution**

Do not label or publish a release candidate. First fix all deterministic local failures, freeze a clean commit/tarball set, rerun provisional automation, obtain 35/35 signed compatibility evidence, execute the 244 signed human rows, obtain independent assessment, implement Phase 20 performance/security/release closure, and make the final release verifier derive a pass from the complete immutable evidence set.

### F-02 — P1 — The stable registry rejects its own catalog and source installation is broken

**Evidence**

- `uifn/registry/src/trust.ts:12-21` requires the embedded payload hash to equal the signed hash and verifies Ed25519.
- The current embedded payload hashes to `61dd8bd4616d0ea1edcd47ef5dddcfa9a558c8adabb8004568b6331303688930`.
- `uifn/registry/src/generated/signature.ts:3-8` is signed for `cc0951c31ca6251f7f921b8dbeba33cfff9a95e002838f2cea128196e0d1db1b`.
- `buildRegistry()` returns only `UIFN_REGISTRY_SIGNATURE_INVALID`.
- The focused stable registry test fails 4/6; the complete registry suite inside Phase 16 fails 12/17.
- Phase 16 fails with 9 findings. Registry `pack --dry-run` fails during prepack.
- React, Svelte, and Solid source-install tests all fail before writing because the registry is untrusted.
- `uifn/registry/generated/delivery-manifest.json` also fails generated-source drift verification.
- `scripts/verify-uifn-phase-16.mjs:141-144` nevertheless reports `GEN-001: passed`: generator failures are wrapped as `UIFN_PHASE16_COMMAND_FAILED`, the GEN classifier looks only for `GENERATED`/`TEMPLATE`/`PROVENANCE`/`PHASE14`, and the REG classifier absorbs every `COMMAND` failure. The requirement summary therefore understates the generator failure that is present in the same result.

**Impact**

The shadcn-style copied-source promise is unusable and `@uifn/registry` cannot be packed. `GEN-001` and `REG-001` are not satisfied, and the aggregate requirement status is itself misleading.

**Required resolution**

Regenerate package/source artifacts from the exact canonical definition, review the delta, regenerate the delivery manifest, sign the exact embedded canonical payload using the authorized registry key process, then rerun all registry adversarial, clean-consumer, source/package parity, and pack tests. Do not weaken signature checking.

### F-03 — P1 — Default public core controller factories generate duplicate DOM IDs

**Evidence**

- `uifn/core/src/environment.ts:170-203` creates a new default environment with the same `uifn-root` seed and a fresh counter for every call.
- `uifn/core/src/primitives/controllers.ts:49-63` creates IDs from that fresh environment.
- Two independent `createAccordionController({ items: [...] })` calls returned the same root ID: `accordion-root-uifn-root-accordion-1`.
- The same default-environment pattern is used throughout the primitive factories.

**Impact**

Consumers using the documented core controller factories directly can mount multiple instances with duplicate IDs, breaking `aria-controls`, `aria-labelledby`, labels, focus lookup, form relationships, CSS targeting, and hydration assumptions. Adapter-injected IDs do not make the public core API safe.

**Required resolution**

Require or create a genuinely instance-unique scope at the public factory boundary while retaining deterministic server/client hydration. Add a regression that creates multiple same-primitive and cross-primitive controllers under the default environment and under sibling/child environments, then asserts global uniqueness and deterministic hydration behavior.

### F-04 — P1 — `@uifn/core` violates its no-ambient-DOM architecture

**Evidence**

- The authoritative package table says `@uifn/core` allows no framework or ambient DOM dependency and assigns focus, portals, presence, positioning, modal behavior, and observers to `@uifn/dom`.
- `uifn/core/src/index.ts:1` exports all utilities.
- `uifn/core/src/utils/index.ts:1-8` exports focus trap, roving focus, outside click, Escape key, presence, portal, and positioning.
- `uifn/core/package.json:24-32` publishes `./utils` and wildcard utility subpaths.
- Published declarations reference `Document`, `HTMLElement`, `ParentNode`, `MouseEvent`, `PointerEvent`, and `KeyboardEvent`.
- `uifn/core/tsconfig.json:7` requires the DOM library.
- Equivalent production services also exist under `@uifn/dom`.

**Impact**

Node-only core consumers need ambient browser types, browser behavior has two public ownership paths, tree-shaking and support boundaries are less predictable, and fixes can drift between legacy utilities and the DOM platform. This directly violates the current architecture and `ARCH-003`.

**Required resolution**

Move or delete all browser utilities from core, remove their exports and DOM lib dependency, migrate consumers to `@uifn/dom`, and add a package consumer fixture compiled with only ECMAScript libs. Add static ownership checks so focus/layer/portal/presence/positioning implementations cannot reappear outside `@uifn/dom`.

### F-05 — P1 — Current styling and cross-framework evidence gates are internally inconsistent

**Evidence**

- `verify-uifn-phase-15.mjs --static-only` fails `STYLE-001` with `UIFN_STYLE_SEMANTIC_COLOR_HARDCODED`.
- The verifier rejects raw semantic `color` or `background` values at `scripts/verify-uifn-phase-15.mjs:90-96`.
- Current CSS contains raw semantic backgrounds such as `background: #182035` at `uifn/components/styles.css:1329-1339`, plus a hardcoded danger fallback and several literal color ramps.
- Phase 16’s cross-framework comparison against the latest evidence reports `UIFN_SEMANTIC_TRACE_DIVERGED`, including Solid Combobox ARIA field-presence differences.
- Current individual React/Svelte/Solid public-tree tests pass, showing that the checked-in aggregate evidence is stale or that the per-framework tests do not enforce the same normalized contract.
- `npm ls --depth=0` reports invalid installed tool versions for `components-solid` Vitest and `components-svelte` Vitest/svelte-check, although current package tests happen to pass with those older tools.

**Impact**

Local package tests, checked-in aggregate evidence, style policy, and the installed dependency graph disagree. A green leaf test cannot be promoted to a reliable release claim.

**Required resolution**

Decide which literal colors are semantic tokens and which are intrinsic data visualizations, encode that distinction in the style contract, remove or explicitly allowlist the latter, and regenerate traces from the exact clean package/source candidate. Make individual framework tests and aggregate parity use the same normalizer and mutation rules. Validate from a clean lockfile install with the declared tool versions.

### F-06 — P1 — Catalog API documentation is attractive but not complete enough for production consumers

**Evidence**

- `uifn/examples/shared/src/catalog-presentation.ts:842-931` renders the same installation, usage, API, anatomy, accessibility, and examples shell for each component.
- `catalogPropRows()` at lines 1109-1123 emits only `className`/`class`, `children`, and canonical input rows.
- Optional defaults are always documented as `undefined`; required inputs are documented as `required`.
- Descriptions are generated as “Optional {name} input from the canonical {component} contract.”
- Canonical events are not rendered as framework callback signatures.
- There is no generated per-part props table, part element type, callback detail, context/provider API, controller API, CSS variable table, data-attribute table, SSR caveat, form serialization detail, touch behavior, or known limitation.
- By contrast, Ark Accordion documents multiple runnable modes and exact root/part props, defaults, data attributes, context APIs, animation variables, and keyboard behavior.

**Impact**

Consumers cannot reliably discover the real public API or behavioral limits from the catalog. This fails the explicit `DOCS-001` completeness requirement even though route coverage and previews are strong.

**Required resolution**

Generate reference docs from exported framework types plus canonical behavioral metadata. Cover every root and part export, event/callback, controller method, state/data attribute, CSS variable, default, controlled/uncontrolled contract, form/SSR/touch behavior, accessibility exception, and limitation. Typecheck every shown snippet against packed and source-installed fixtures.

### F-07 — P2 — Ark/Zag inventory parity overstates component-level behavioral parity

**Evidence**

- UIFn covers all normalized Ark family names and all Zag families except CascadeSelect and cataloged Presence.
- Some UIFn contracts are rich: DatePicker, FileUpload, ColorPicker, Carousel, FloatingPanel, ImageCropper, Tour, and TreeView have substantive controllers and demos.
- UIFn Carousel at `uifn/core/src/primitives/range-gesture-controllers.ts:161-194` supports controlled index, autoplay, reduced motion, threshold dragging, loop, orientation, indicators, and live announcements.
- It still hides every non-active item and does not expose Zag’s scroll-snap, alignment, page snap points, multiple slides per page, or spacing contracts.
- UIFn docs do not disclose those depth differences.

**Impact**

Marketing based on component counts would imply an equivalence the implementation and docs do not establish. Long-tail behavior, not family names, is the maturity differentiator in Ark/Zag.

**Required resolution**

Create a per-family competitive contract matrix for the highest-risk 20 primitives. Record supported, intentionally different, and deferred behaviors. Prioritize alignment/snap/virtualization, collection scaling, overlay edge cases, form serialization, touch/pointer arbitration, and public context/controller APIs rather than adding more names.

### F-08 — P2 — The styled layer is not yet a complete coss/shadcn-class application kit

**Evidence**

- UIFn overlaps 37/53 normalized coss component families and 34/62 normalized shadcn families.
- Common missing styled surfaces include Alert, Badge, Breadcrumb, Calendar, Card, Command, Empty, InputGroup, Kbd, Label, Skeleton, Spinner, Table, and Textarea.
- Shadcn additionally has application/AI surfaces such as Chart, DataTable, Sidebar, Message, MessageScroller, Attachment, Bubble, Typography, Item, and Marker.
- UIFn patterns/SF panels are experimental and therefore cannot silently fill stable component gaps.

**Impact**

UIFn can credibly position itself as a broad cross-framework primitive system, but not yet as a complete drop-in application component system comparable to coss or shadcn.

**Required resolution**

After the production blockers are closed, define a separate stable styled-application roadmap. Start with form/content/loading/table primitives that compose existing headless behavior. Do not move experimental product workflows into stable packages merely to increase counts.

### F-09 — P1 — The working state is not a reviewable or reproducible release snapshot

**Evidence**

- The branch still points at the May 26 `Plugfn init (#28)` commit.
- At audit time the worktree had 115 modified, 296 deleted, and 281 untracked paths.
- Entire new stable packages, the registry, current specs, catalogs, and substantial implementation trees are untracked.
- The catalog deployment can be current while the repository has no committed source identity corresponding to it.

**Impact**

The implementation cannot be reproduced, bisected, externally attested, signed, or reviewed as one immutable candidate. Existing evidence is necessarily provisional or stale.

**Required resolution**

After deterministic failures are fixed, intentionally review and commit the complete candidate in coherent changes, produce a clean install, bind deployments/tarballs/evidence to the exact commit and hashes, and invalidate evidence that was generated from dirty or different source.

## Recommended order of work

1. **Restore deterministic local truth.**
   - Fix the registry signature/payload mismatch.
   - Regenerate and review the delivery manifest.
   - Make Phase 15 and Phase 16 fully green.
   - Reconcile public-tree leaf tests with aggregate semantic traces.
   - Validate from a clean lockfile install using declared tool versions.

2. **Fix the two architectural correctness defects.**
   - Guarantee default controller-instance ID uniqueness with deterministic hydration.
   - Remove all DOM-dependent exports and DOM lib requirements from `@uifn/core`; make `@uifn/dom` the sole browser-behavior owner.

3. **Make documentation describe the actual public packages.**
   - Generate root/part/event/context/controller/CSS/data-attribute/default/limitation reference from exported types and canonical metadata.
   - Typecheck all snippets in packed and copied-source consumers.

4. **Freeze a real candidate.**
   - Review and commit the complete source state.
   - Produce clean install, build, test, tarballs, SBOM inputs, and deployment identities from that commit.
   - Invalidate dirty/stale evidence.

5. **Execute external production gates.**
   - 35/35 signed compatibility cells.
   - Rerun Phase 18 on the exact candidate.
   - 244 signed human AT rows and independent accessibility review.
   - Implement and pass Phase 20 performance, leaks, security, provenance, release, and rollback.

6. **Only then expand the styled application layer.**
   - Prioritize Alert, Badge, Breadcrumb, Calendar, Card, Command, Empty, InputGroup, Label, Skeleton, Spinner, Table, and Textarea.
   - Keep application/product workflows in the experimental lanes until they have independent stable contracts.

## Final assessment

UIFn has reached an unusual middle state: its catalog breadth and public showcase are ahead of its release integrity. The 61-component, three-framework story is real, and the deployed catalog is useful. The production blockers are also real and directly reproducible.

The project should not spend its next cycle chasing a larger primitive count. It should make the existing 61 trustworthy: one core/DOM ownership model, collision-safe instances, a working signed source registry, one coherent cross-framework trace truth, exact consumer documentation, a clean frozen candidate, and completed compatibility/accessibility/performance/security/release evidence.

Until those are complete, the accurate label is **broad GA candidate with a production-quality catalog shell, not a production-ready 1.0 component system**.
