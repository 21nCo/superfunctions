## High-level findings

**Verdict: FAIL. The implementation has a strong inventory, build, route, and Playwright scaffold, but it is not compliant with the required interactive, collision, accessibility, visual, scenario, or release-proof semantics.**

- Intent coverage in the spec: **14/14 mapped; 0 SPEC MISSING**.

### Per-requirement notes

#### WB-001

All five private package manifests have dev, build, preview, and browser-test scripts; the hub exposes each framework by name and all builds passed. The Angular package, however, has no browser-platform bootstrap. It casts exports to constructors, calls new directly, reads renderedRoot, and writes DOM nodes itself. Angular templates, inputs/outputs, DI, lifecycle, change detection, and hydration are outside its browser proof.

#### WB-002

The Workbench component slugs exactly matched the 45 registry JSON files. Index, states, QA, default, theme, responsive, and profile routes are generated. The acceptance criterion for product-like usage is not met: the three scenarios render text cards with data-uifn-component-use markers rather than the actual component instances.

#### WB-003

Every app imports the same route and contract data. Route IDs and paths are generated once, and the current browser selection produced five complete shards totaling 736 routes. There are no intentionally unsupported current component routes that require a capability declaration.

#### WB-004

Scenarios are navigable and link to focused QA routes, but they are not realistic workflows. Patterns and SF panels likewise appear as links rather than composed workflow UI. The verifier can pass merely because the manifest says a slug is covered and the HTML contains a matching marker.

#### QA-001

There are 74 contracts: 45 registry components, one extra combobox overlay contract, 14 patterns, and 14 SF panels. Required arrays are usually populated. A contract with a missing frameworks field threw an uncoded TypeError instead of a deterministic validation result. Production verification also derives knownSlugs from the contracts being validated, so a newly added bogus contract slug declares itself known.

#### QA-002

Chromium, actual Vite servers, real URLs, hover, click, fill, wheel, Tab, Escape, screenshots, and axe are present. The generic interaction helper catches failed actions and still marks the attempted action true. Most routes never use interaction evidence as a pass/fail gate. Resize is only exercised under visual scope, not the default full browser gate.

#### QA-003

The route inventory includes all named collision cases. The cases are not faithful fixtures: mobile does not set a mobile viewport in overlay runs; nested-overlay has no nested construction; edge routes use padding/text alignment rather than viewport-edge stages; long-content changes container height rather than supplying long floating content. The verifier checks visibility/dismissal but does not enforce the vector's 8px trigger alignment tolerance or each contract's placement semantics.

#### QA-004

The live Vue Input OTP vector returned ok=true while typed=false, valueAfterInput=null, clickableCount=0, and ariaInvalid=null. The form check considered the existence of a named hidden component value sufficient. No actual form submit or FormData assertion occurred, and disabled/readonly/invalid negative paths are not exercised. Control-only components have no state-transition gate; generic interaction evidence is ignored.

#### QA-005

The live Solid data-table vector returned ok=true with 250 total rows and eight rendered rows but no sort/filter/select action, no filteredRows field, and no selectedRow. Calendar/date-picker only expose attributes; command only counts options; resizable only counts panels/handles; sidebar only counts items. Required empty/loading/error workflows and persistence are not executable QA cases.

#### QA-006

The browser confirms nonblank output, broad axe status, a visible box, absence of detected clipping/overlap, and presence of at least one expected CSS variable. It does not assert component-specific semantic roles, stable dimensions, feedback lifecycle behavior, or all applicable states. Workbench themes are a parallel hard-coded CSS definition and the token check accepts any nonempty value.

#### QA-007

Axe is injected on every selected component and scenario route. Keyboard proof is shallow: one Tab is pressed, then only focus-trap routes check whether focus happens to remain somewhere inside the root. The overlay helper mutates content by adding tabindex before focusing it. Initial focus, forward/reverse cycles, background inertness, body scroll lock, and full focus return paths are not proven.

#### QA-008

The visual helper takes real screenshots and inspects clipping, direct text-node overlap, and token presence. The committed baseline manifest is empty and a missing baseline returns ok=true. A single dark/desktop Svelte calendar entry therefore passed with baselineStatus=missing. The required four-theme by three-viewport matrix for that route timed out at 180 seconds. Default release runs only one light/desktop rendering per route and never invokes scope=visual.

#### QA-009

Fourteen controlled patterns and fourteen SF panels have nine state routes each, and SF render-model functions receive fake clients. The actual Workbench output is one generic model card in every framework. Its button updates its own DOM rather than invoking the declared controlled callback. SF call proof sums global calls already made during render instead of requiring an action-caused delta, and the fake clients are created once per app module.

#### QA-010

Framework/family/profile/slug/route filtering and five-way deterministic sharding work. Failures emitted by the JS runner include code, framework, slug, route, QA case, assertion type, and evidence. The TypeScript failure interface omits QA case and assertion type, no runtime schema validator can emit UIFN_QA_RESULT_SCHEMA_INVALID, and the runner always emits artifacts=[] even on failure. Coverage.matrix always advertises all themes/viewports although default runs execute light/desktop only.

#### SEC-001

The Workbench app sources contain no required env files or obvious external network constructors, and fake data is deterministic. Static scanning skips the browser-qa subtree despite the test vector's uifn/examples scan root. Browser monitoring ignores every same-origin request, including a potential local API call. Browser evidence sanitization does not redact email strings or embedded/multiple platform-local paths, and failure messages bypass evidence sanitization.

#### REL-001

The release script includes Workbench static, full-sharded, smoke, and overlay commands. It does not include the required full visual matrix, so a successful release cannot establish QA-008. Dry-run returns ok=true with 88 planned blocking checks and exit 0, contradicting the rule that planned/skipped browser checks cannot pass release. Full-mode verification result is recorded in the command appendix.

#### DOC-001

All acceptance criteria are present: root and framework links, ports, commands, route conventions, supported frameworks, and private/non-published status. The docs claim component-owned form behavior, collision geometry, fake-client action proof, and visual baselines that the current assertions do not establish. That is a documentation accuracy risk, but discoverability itself passes.

## Spec conflicts / spec gaps

### Internal conflicts

1. **TV-QA-001 conflicts with the contract schema.** The positive vector omits displayName, QA profiles/fields, a11y, geometry, visual, responsive, theme, and fixture fields while the SPEC interface and QA-001 acceptance criteria make those fields mandatory.
2. **The result check family excludes scenarios.** The SPEC UifnBrowserQaResult permits component, pattern, or sf checks, while QA-002/QA-007 require scenario browser checks and the implementation emits family=scenario.
3. **The failure interface omits required fields.** QA-010 requires QA case ID and assertion type, but the SPEC result failure interface omits both. The JS runner adds them ad hoc.

### Gaps

1. The spec requires exact negative envelopes but does not define one shared error type/schema or say whether every vector code is a stable public contract. The implementation consequently uses a mixture of missing, renamed, and generic codes.
2. Combobox is required by the overlay command but is not one of the 45 registry components. The implementation creates a primitive-only extra contract, but the spec does not explicitly define that ownership or its drift source.
3. The visual baseline update process is said to be explicit, but the release-ready minimum baseline population and missing-baseline policy are not stated. Release eligibility nevertheless requires reviewed drift detection, so an empty pass-through manifest cannot satisfy intent.

There is one provided spec bundle, so there are no cross-bundle precedence conflicts.

## Cross-cutting audits (security/determinism/limits/errors/compat)

### Security, authz, and validation boundaries

Positive evidence:

- Workbench app code is secret-free and deterministic at source level.
- Fake clients and data avoid live Superfunction credentials.
- External cross-origin requests are counted during browser routes.

Failures:

- Static offline scanning excludes browser-qa even though the vector names the whole examples root.
- Same-origin API requests are ignored as if they were static app assets.
- Fake clients are module singletons and call counters live on globalThis, contrary to fixture-scoped/no-global intent.
- Browser failure messages are not sanitized; evidence sanitization misses PII and embedded local paths.
- Contract validation can throw an uncoded TypeError before producing validation failures.

### Determinism invariants

Positive evidence:

- Routes and shard assignment are stable and generated from shared manifests.
- Browser pages use fixed locale, timezone, reduced motion, viewport defaults, and deterministic fixture data.
- The component registry drift check is exact.

Failures:

- Global fake-client call state leaks across routes and can make later SF checks pass from earlier calls.
- Empty visual baselines eliminate deterministic drift comparison.
- Coverage reports the entire theme/viewport matrix even when only one cell executed.
- A 12-cell visual route exceeded its 180-second aggregate timeout.

### Limits and caps

Positive evidence:

- Filters by framework, family, profile, slug, and route work.
- Five-way sharding produced 148, 147, 147, 147, and 147 routes.
- Workbench aggregation rejects missing, failed, or max-routes-truncated shards.
- Large-data fixtures are deterministic and capped for the rendered viewport.

Failures:

- The route timeout wraps the entire visual matrix rather than each matrix entry; the observed required route timed out.
- Data-rich caps are checked as counts only and do not prove virtualization, selection retention, or large-list interaction.
- Failure screenshots/traces are described as optional but no enabling/capture path is implemented; artifacts always remain empty.

### Error handling and canonical envelopes

Positive evidence:

- Browser failures generally carry framework, slug, route, QA case ID, assertion type, and sanitized evidence.
- Timeouts and no-route selection produce deterministic codes.

Failures:

- Interaction actions catch exceptions and still report attempted success flags.
