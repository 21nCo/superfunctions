## Public API and type snapshot

For each catalog primitive named `Name`, generation emits:

- `NameRoot` and `NameProvider`;
- `Name<Part>` for every catalog anatomy part;
- exact root and part prop types composed from the public core input/part types and Solid intrinsic element props;
- `Name`, a pure-annotated compound namespace with `Provider`, `Root`, and every anatomy component;
- the root `@uifn/solid` re-export and direct `@uifn/solid/<primitive-id>` export.

Roots and parts support native props, refs, children, `as`, and a typed Solid `render` callback. The callback exposes accessors for projected props, state, actions, status, lifecycle counters, and the bridge. Repeated anatomy parts require their controller key/value. Portal parts accept a target container; presence-aware parts accept `forceMount`.

The adapter deliberately does not publish a parallel Solid state machine. Its shared bridge owns one core controller and converts its snapshot/parts into Solid accessors. The public type surface does not export implementation-private runtime types, repository TypeScript paths, generic machine aliases, or React output.

## Reactivity and lifecycle proof

The shared `SolidPrimitiveBridge` provides the following lifecycle:

1. Split live root inputs from DOM/composition props without destructuring reactive values.
2. Create one public core controller, or one typed-static projection, for the root.
3. Proxy callbacks so callback identity changes do not reconstruct the controller.
4. Apply changed inputs through `controller.update()` and reconcile dynamic collections before controlled value reconciliation.
5. Re-project only subscribed state/part accessors and imperatively refresh the concrete element's attributes, properties, styles, and listeners.
6. Batch DOM-ownership refreshes so a component mount/unmount wave does not repeatedly recreate shared services or observe a partial anatomy tree.
7. Destroy every subscription, controller, listener, portal, service binding, and DOM platform lease from the Solid owner cleanup.

The focused controlled-update fixture records controller generation, DOM generation, DOM destroy count, child identity, and subtree mutations before and after a signal update. After changing Accordion from `[]` to `["one"]`:

- controller generation remains `2`;
- DOM generation and destroy count are unchanged;
- the stable child is the identical node;
- child-list mutation count is `0`;
- projected public state updates to `["one"]`.

This proves the update does not recreate the controller, replace the component tree, or invalidate/rebind the whole DOM ownership graph. A dynamic `For` collection then appends a third Accordion item through the `items` accessor, activates its generated public trigger, and commits `["three"]` through the controlled callback. Two independent Solid render roots also receive distinct native Solid IDs.

Abrupt owner disposal checks every captured bridge and requires `activeControllers = 0`, `registeredElements = 0`, `subscribers = 0`, and `domDestroyCount = domGeneration`. The same invariant passes in all six real-browser package/source runs.

## SSR, hydration, portals, and forms

Generated roots call a single adapter identity helper backed by Solid's `createUniqueId`. With the documented paired hydratable Vite transforms (`solid({ ssr: true })`), server and client invoke the same compiled component graph and reproduce exact IDs. Native Solid identity also avoids collisions across independent client render roots and honors framework `renderId` behavior.

Root and part renderers use literal catalog-selected intrinsic elements so the Solid compiler owns template generation, hydration keys, and node reuse. Reserved child accessors are skipped before value access, and root children remain lazy until the intrinsic renderer consumes them; this prevents discarded child-tree creation during SSR/hydration.

Portals render in place on the server and move through `createUIFnPortal` after hydration. The consumer requires exactly one portal node and fails strict locator resolution on duplicates. Forms use the core native hidden-input contract and imperative DOM property synchronization; `new FormData(form).get('terms')` returns `accepted` after the public Checkbox control is activated.

The consumer uses `generateHydrationScript`, `renderToString`, and `hydrate`, then invokes the returned hydration-root disposer directly while Dialog modal isolation is active. Chromium, Firefox, and WebKit all report matching IDs, one body-owned portal, correct form and controlled values, empty diagnostics, and zero leaks for both packed and source modes.

## Core corrections discovered by Solid coverage

Exhaustive Solid form and collection behavior exposed canonical issues that were fixed in their owning core layer:

- Checkbox's serialized form `value` is now separate from the selection controller's controlled `value`; `value="accepted"` no longer falsely makes checked state controlled.
- Enabled Checkbox label/root projection does not add a second click activation on top of its button control; the control prevents the native label double-toggle path.
- Disabled/read-only Checkbox root interaction still reaches the core diagnostic path and records `UIFN_ERR_DISABLED_INTERACTION`, preserving the original Phase 2 contract.
- Accordion exposes and applies `setItems` before controlled value updates, so Solid dynamic collections reconcile deterministically.

The complete core suite passes 30 files and 158 tests after these corrections. The Phase 9 contract and focused 12-test selection/input suite also pass, so the fixes preserve the earlier controlled-state, serialization, IME, and error guarantees.
