# AGENTS.md - AI Agent Development Guide for Superfunctions

> **Purpose**: This document provides AI agents with essential information for working effectively on the Superfunctions monorepo.

## 🏗️ Repository Structure

Superfunctions is a **Turbo monorepo** containing self-hosted developer tools and libraries. The repository is organized into:

### Core Functions (Top-Level Directories)

Individual superfunction packages, each providing specific developer capabilities:

- **`authfn/`** - Authentication & API key management
- **`cachefn/`** - Multi-tier caching with function memoization
- **`drawfn/`** - Cross-framework drawing canvas for brainstorming
- **`plugfn/`** - Integration platform (OAuth, webhooks, 75+ providers)
- **`searchfn/`** - Browser-first full-text search with IndexedDB
- **`secfn/`** - Security functions (secrets vault, rate limiting, monitoring)
- **`testfn/`** - Testing utilities and frameworks
- **`botfn/`** - Bot framework (Discord, GitHub, Linear integrations)
- **`hostfn/`** - Hosting and deployment utilities
- **`uifn/`** - UI components and utilities
- **`watchfn/`** - File watching and monitoring
- **`billfn/`** - Billing and payment processing
- **`browsefn/`** - Browser automation utilities
- **`chartfn/`** - Charting and visualization
- **`datafn/`** - Data processing utilities
- **`docsfn/`** - Documentation generation
- **`filefn/`** - File operations and management
- **`flowfn/`** - Flow control (queues, streams, workflows)
- **`iconfn/`** - Icon utilities
- **`logfn/`** - Logging utilities
- **`mailfn/`** - Programmable real inboxes for products, agents, and tests
- **`sendfn/`** - Email/messaging utilities

### Shared Packages (`packages/`)

Framework-agnostic core libraries used across superfunctions:

**TypeScript Packages:**

- `@superfunctions/http` - HTTP abstractions

- `@superfunctions/http-fastify` - Fastify adapter

- **`.github/`** - GitHub Actions and CI/CD

## 📦 Package Naming Conventions

### Rule A: Shared Packages Format

**Any package shared across superfunctions uses `@superfunctions/{name}` format**

Examples:

```
packages/db/          → @superfunctions/db
packages/http/        → @superfunctions/http
packages/auth/        → @superfunctions/auth
packages/cli/         → @superfunctions/cli
```

### Rule B: Core Function Packages Format

**Single-package functions**: Use simple name without scope

```
authfn/ts-sdk/        → authfn
drawfn/core/          → drawfn
cachefn/typescript/   → cachefn
plugfn/core/         → plugfn
searchfn/             → searchfn
```

**Multi-package functions**: Use `@{functionname}/{sub-package}` format (if needed in future)

```
@authfn/core          (example for future multi-package structure)
@authfn/providers     (example for future multi-package structure)
```

**Current Status**: All core functions currently use single-package structure. The scoped format is reserved for future expansion if a function needs multiple published packages.

### Rule C: Monorepo Structure

**The root `superfunctions` is a Turbo monorepo. Avoid nested monorepos.**

- ✅ Use subfolders to organize functions (e.g., `authfn/python/`, `authfn/ts-sdk/`)
- ❌ Do NOT create nested monorepos (e.g., `authfn/` should NOT be another monorepo)
- ✅ Use Turbo workspaces defined in root `package.json`

Current workspaces:

```json
{
  "workspaces": [
    "searchfn",
    "botfn/*",
    "hostfn/*",
    "authfn/*",
    "packages/*",
    "21n/*"
  ]
}
```

### Rule D: Artifact Location

**Create artifacts (`.md` files) in `.conduct` folders**

- **Function-specific artifacts**: `{function}/.conduct/`
  - Examples: `authfn/.conduct/implementation.md`, `drawfn/.conduct/audit_report.md`
- **Shared/root artifacts**: `_conduct/`
  - Examples: `_conduct/implementation.md`, `_conduct/spec.md`

Artifact types:

- `implementation.md` - Implementation plans
- `spec.md` - Technical specifications
- `audit_report.md` - Code audits and reviews
- `task.md` - Task tracking
- `walkthrough.md` - Feature walkthroughs

## 🚀 Best Practices

### Super functions ecosystem (Very important)

- Reuse shared packages from `packages/` folder like http abstraction, db abstraction, etc.
- Never duplicate shared code like http adapters, db abstractions, etc.
- Don't reexport http-adapters etc - end consumers of the core function package will use the adapters directly. Refer `authfn` implementation for usage of core http router, core db, http adapters and db interface usage.
- Function packages that accept a `@superfunctions/db` `Adapter` must wrap the incoming adapter internally with their own schema, for example `wrapWithSchema(config.database, getSchema(...))`, before passing it to services/storage. Do not require app consumers to pass `adapterSchema` to `drizzleAdapter`, `kyselyAdapter`, `prismaAdapter`, or `memoryAdapter`; `adapterSchema` is a deprecated compatibility escape hatch for direct app-level adapter use.

### Code Organization

- Keep shared code in `packages/`
- Keep function-specific code in `{function}/`
- Use TypeScript for type safety
- Provide Python SDKs for backend-focused functions
- Write comprehensive tests

### Documentation

- Update README.md with usage examples
- Create SPEC.md for complex functions
- Document breaking changes
- Keep artifacts in `.conduct/` folders

### Testing

- Use Vitest for TypeScript
- Use pytest for Python
- Maintain high test coverage
- Test adapters separately

### Versioning

- Follow semantic versioning
- Coordinate versions across language SDKs
- Document migration guides for breaking changes
