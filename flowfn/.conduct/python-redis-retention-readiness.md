# Python Redis payload retention

The P0 stream requirements (`flowfn/SPEC.md:352–381`) include retention policies and `maxLength` / age limits. TypeScript's unconfigured Redis adapter enforces exact payload trimming independently of unread/pending delivery state. The previous Python implementation protected those payloads indefinitely, unlike configured Python partitions and Memory streams.

## Baseline

At checkpoint `05ff9b949ffb354c2f516ded48019cac42923da3`, a private loopback Redis fixture executed the exact Python `trim_stream` and `_owned` Lua bodies extracted from source. Requested maximum length zero removed no rows and retained two payloads: one pending and one unread. After native `XTRIM` removed them, Python renewal returned owned despite `XCLAIM` returning no payload and removing the pending receipt. The service and private directory were removed. Receipt: `/tmp/flow-legacy-retention-baseline.log`.

## Behavior

Unconfigured Redis now uses exact `XTRIM MAXLEN` and Redis-server-time `MINID`, including fractional seconds and TypeScript's millisecond cutoff boundary. It does not scan all payloads/groups in Lua. Retention removes unread and pending payloads; the stream's own Redis receipt metadata is reclaimed by subsequent claim/renewal. Renewal returns actual `XCLAIM` cardinality and removes the token only after atomic consumer, token and expiry checks prove it belongs to this attempt. Missing payloads cancel cooperative callback work through the existing owned lease helper. Stale ACK/NACK cannot restore deleted data. Reopened consumers do not replay it.

This changes the old retention-protection behavior. Hosts should size retention for their processing and replay window. Arbitrary callback side effects remain the application's responsibility; cancellation is cooperative. PostgreSQL's older protected-payload behavior remains explicitly separate and unfinished.

## Validation

Two added actual Redis cases cover held and unread payload deletion, callback cancellation, stale ACK/NACK, token cleanup, independent reopened consumer/no replay, fractional age from Redis time, and an absent stream. The first focused command had an incorrect fixture `consume` argument list; that failure is retained at `/tmp/flow-legacy-retention-focused.log`. Correcting the fixture's consumer name yielded two passing cases (`/tmp/flow-legacy-retention-focused-fixed.log`). Production assertions were unchanged.

The old native protected-retention test now applies only to PostgreSQL. Its Redis parameter is explicitly skipped because the replacement Redis tests assert the required opposite behavior; PostgreSQL cases remain gated on configured provider availability.

Initial normal-CI attempts stopped at new fixture typing for Redis HGETALL: provider overloads mix sync/async returns and expose an untyped raw command. The assertion now uses the same explicit asynchronous callable boundary as the existing adapter, without a cast/ignore or changed runtime assertion. Ruff and strict mypy over 94 files pass. That test now retains one payload during its recovery phase, preserving its slow-handler heartbeat, unsubscribe/redelivery, and final zero-cap deletion assertions; PostgreSQL retains its original pre-recovery zero-cap expectation. Dedicated new Redis cases prove that a zero cap deletes pending/unread payloads. The failed receipt is `/tmp/flow-legacy-retention-ci-verified.log`.
