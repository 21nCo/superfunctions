# PostgreSQL stream partitioning checkpoint

The original P0 event-stream requirement in `SPEC.md` includes partitioning and a keyed `partitions: 3` example. Before this change, the count was ignored and native publication returned no assigned partition. The new native routing test reproduced that failure before implementation.

This checkpoint implements the TypeScript PostgreSQL provider, not complete cross-provider/language partition support. The policy persists a positive immutable count and `sha256-utf8-u32be-v1` routing version. Routing uses exact UTF-8 bytes and independent Python hashlib-derived vectors. A configured stream maintains independent per-group/per-partition positions while retaining global append positions, UUID identities, history ranges and retention semantics. The existing group transaction and receipt machinery provide one authoritative delivery per partition/group; an outstanding receipt blocks only its partition. Arbitrary uncooperative external effects remain at least once.

## Deployment and compatibility

`initialize()` adds `flowfn_stream_policies` and `flowfn_partition_progress`; equivalent Drizzle schema metadata remains in the repository source. Install these tables before using the new adapter. Drain older writers before configuring partitioned streams: they do not participate in the stream policy protocol. New cooperating writers serialize first configuration, publication and group creation through the same PostgreSQL transaction advisory lock. A conflicting count, unknown routing version or populated legacy stream cannot be silently reconfigured.

Legacy streams remain unpartitioned. The stopped-writer legacy import preserves historical partition labels (including null and explicit numeric labels) without claiming that these labels provide partition scheduling. There is no supported repartitioning migration in this checkpoint. Do not edit policy rows while writers are active. Public global numeric offsets retain the existing JavaScript integer-range limitation.

Memory and Redis do not yet implement this capability; the TypeScript stream API rejects requested counts and explicit partition publication on unsupported adapters. Python still lacks the production partition implementation. D1/SQS/Kafka, provider parity, installed deployment acceptance and original performance targets remain open. Publication now performs transactional policy coordination; stream throughput has not been qualified by this correctness suite.

## Retention barrier correction

The initial checkpoint's partition exclusion joined active deliveries to retained messages. Native reproduction held a callback with a one-second lease, trimmed all payloads, and then observed its same-partition successor within 148 ms: the payload foreign-key cascade had removed the delivery row and its ordering barrier. The original checkpoint alone therefore did not close the retention/ownership contract.

The corrected schema adds `flowfn_partition_barriers`, with one row per touched stream/group/partition containing only message identity, receipt and storage-clock expiry, independent of payload foreign keys. Claims, renewal and settlement use the existing group-row lock followed by delivery/barrier updates. Renewal extends the barrier only when the retained delivery can also renew. An expired receipt cannot clear a replacement barrier. Explicit current acknowledgment/requeue can release an orphaned barrier after payload deletion; otherwise it expires conservatively. No message payload is retained beyond the configured retention policy.

For an installation that ran the earlier partition implementation, drain its consumers before adding the barrier table and resuming. This is not a rolling-upgrade guarantee against older consumers that do not create barriers. Expired barrier rows remain bounded to one per touched partition/group and are replaced by future claims; they do not retain payload data. Arbitrary external work by an uncooperative expired callback remains outside receipt fencing.

The focused corrected native tests passed **2/2** in 1.24 seconds. They verify unchanged expiry after deleted-delivery renewal failure, storage-clock expiry before successor delivery, stale acknowledgment preserving a successor receipt, and immediate release by explicit authorized acknowledgment. Owned PostgreSQL/Redis PIDs 27889/27890 stopped; private `flow-owned-native-2rn911gn` data was removed and read back absent. The baseline reproduction's owned PIDs 20231/20232 and data were also cleaned up. Full follow-up validation is recorded with the final checkpoint.

## Installed declaration boundary

The first fresh installed acceptance failed strict Node16 declarations before native execution. Re-exporting the repository's Drizzle table metadata from the ordinary PostgreSQL adapter entry pulled Drizzle 0.45.2's optional Gel/MySQL/SQLite declaration graph into otherwise unrelated consumers, including intrinsic dependency declaration errors. The unpublished re-export was removed; source schema metadata remains available in the repository and `initialize()` remains the installed runtime migration entry. No typechecking suppression, broad driver dependency additions or known-broken schema subpath was introduced. That failed fixture removed its consumer, owned PIDs 39369/39370 and private cluster.

The installed fixture also exposed that repeated `createFlow().stream(name, options)` calls silently discarded changed partition counts because the factory cached the first handle. A new public API regression reproduced this. Reuse now accepts omitted or matching explicit counts, rejects changed explicit settings, and directs callers to a new FlowFn instance for persisted-policy validation. Existing non-partition option behavior is unchanged.

Full native Redis/PostgreSQL acceptance passed **93 tests**, 29.33 seconds, including both retention-barrier cases and all previous lease/crash/partition cases. Source acceptance passed **180 tests** with 93 native cases skipped in that separate no-service invocation. Source/test typechecks and ESM/CJS/declaration builds passed. An actual installed PostgreSQL consumer ran on Node 22.22.1 using independent pools and owned PostgreSQL 16.13. It exercised public createFlow stream configuration, Unicode-key routing, reopen, same-partition exclusion while another partition progresses, payload trimming with retained lease barrier, expiry recovery, stale acknowledgment, global range IDs and conflicting policy rejection. The installed database catalog confirmed the barrier table exists without a payload foreign key. The consumer/schema and native PIDs 53326/53327/private cluster were cleaned up.

**The complete packed acceptance command still exited nonzero at its unchanged final production audit gate.** It reported six propagated findings: three high and three moderate, from Zod below 4.6.6 and fast-uri advisories through the existing core/MCP/admin dependency closure. Exact output is retained in `packed-partition-audit-20261025.json`. Runtime/type successes do not waive this security gate; the checkpoint is not cleared for publication. No dependency override, suppression or broad package upgrade was used.

To include native partition acceptance in the executable installed fixture, provide an owned loopback `FLOWFN_POSTGRES_URL` to `node flowfn/typescript/scripts/packed-consumer-acceptance.mjs` after rebuilding local prerequisites/core/admin. The fixture normally installs its host pg driver, uses a UUID schema, drops only that schema, closes both pools and removes its temporary npm consumer. With no provider URL, the existing entry-point matrix runs without claiming native partition acceptance.
