FileFn handles file uploads, storage adapters (S3, R2, GCS, Azure, local), signed download URLs, and upload policies. DataFn manages the relational records that own those files. The connection is a `string` field in your schema that stores the FileFn file id.

## Schema

```typescript
// schema.ts
import { defineSchema } from "@datafn/core";

export const schema = defineSchema({
  capabilities: ["timestamps", "audit"],
  resources: [
    {
      name: "attachments",
      version: 1,
      idPrefix: "att",
      fields: [
        { name: "ownerType", type: "string", required: true }, // "document" | "comment"
        { name: "ownerId", type: "string", required: true },
        { name: "fileId", type: "string", required: true },    // FileFn file id
        { name: "filename", type: "string", required: true },
        { name: "mime", type: "string", required: true },
        { name: "size", type: "number", required: true, max: 25 * 1024 * 1024 },
      ],
      indices: { base: ["ownerType", "ownerId"], search: ["filename"] },
    },
  ],
});
```

You can also embed `fileId` directly on a resource (`avatarFileId` on `users`, `coverFileId` on `posts`). The dedicated `attachments` table is correct for many-to-one relationships.

## Clients

```typescript
// clients.ts
import { createDatafnClient } from "@datafn/client";
import { createFileFnClient } from "@filefn/client";
import { schema } from "./schema";

export const client = createDatafnClient({
  schema,
  clientId: "web-1", // Stable per device.
  sync: { remote: "/datafn" },
});

// Where your server mounts FileFn (its `basePath`).
export const FILEFN_BASE_URL = "/files";

export const files = createFileFnClient({ baseUrl: FILEFN_BASE_URL });

/**
 * A URL FileFn returned, ready for the browser. Signed storage URLs are absolute;
 * FileFn's proxy routes (`/proxy/files/...`) are relative to where FileFn is mounted.
 */
export function fileFnUrl(url: string): string {
  return url.startsWith("/") && !url.startsWith("//") ? `${FILEFN_BASE_URL}${url}` : url;
}
```

`createFileFnClient` sends requests with `credentials: "same-origin"` by default, so a session cookie for the same origin authenticates FileFn too. For a FileFn API on another origin, pass `credentials: "include"` or return an `Authorization` header from `getAuthHeaders`.

## Upload flow

```typescript
// attach.ts
import { client, files } from "./clients";

export async function attachFile(ownerType: string, ownerId: string, file: File): Promise<string> {
  // 1. Upload through FileFn. `policy` names an upload policy configured on the FileFn server.
  const upload = files.uploadFile({ policy: "attachments", file });
  const { fileId } = await upload.done();

  // 2. Create the DataFn attachment row. If this throws, the file stays in FileFn (see below).
  await client.table("attachments").mutate({
    operation: "insert",
    record: {
      ownerType,
      ownerId,
      fileId,
      filename: file.name,
      mime: file.type,
      size: file.size,
    },
  });
  return fileId;
}
```

`uploadFile` returns a handle at once: `upload.fileId` is known before the bytes are sent, `upload.onProgress(...)` reports progress and `upload.abort()` cancels. `done()` resolves with `{ fileId, versionId }` once FileFn has stored the file.

The two operations are not transactional, and a failed insert does not delete the uploaded file. An error from `mutate` does not prove that nothing was stored: if the connection drops after DataFn committed the row, deleting the file would leave a committed attachment pointing at a deleted file. A file without an attachment row is the safe failure. FileFn does not delete completed files by itself, so remove such files from the server: a scheduled job that deletes files older than a grace period (an hour, say) that no attachment row references.

## Download / display

`downloadUrl` asks FileFn for the current version's download URL: a short-lived signed storage URL when the storage adapter supports one, otherwise FileFn's proxy download route. Request it when you render, not once for the record's lifetime.

The proxy route comes back relative to FileFn's mount (`/proxy/files/<fileId>/download`, without `/files`), so pass every URL through `fileFnUrl` before the browser loads it:

```typescript
// display.ts
import { fileFnUrl, files } from "./clients";

export async function showAttachment(img: HTMLImageElement, attachment: { fileId: string; filename: string }): Promise<void> {
  img.alt = attachment.filename;
  img.src = fileFnUrl(await files.downloadUrl(attachment.fileId));
}
```

For thumbnails and previews, `files.resolveRenderable({ fileId, intent: "thumbnail" })` picks the best artifact FileFn has for the file (see `@filefn/viewer`). On storage without signed URLs, its `source.url` (for an `artifact` or `original` source) and the URL `files.downloadArtifact(fileId, artifactId)` returns are relative proxy routes too, such as `/proxy/files/<fileId>/artifacts/<artifactId>/download`; resolve them with `fileFnUrl` as well.

## Lifecycle: delete attachment

```typescript
// detach.ts
import { client, files } from "./clients";

export async function detachFile(attachmentId: string, fileId: string): Promise<void> {
  await client.table("attachments").delete(attachmentId);
  // Only after the DataFn delete succeeds, delete the file in FileFn.
  await files.deleteFile(fileId);
}
```

Why do them sequentially? The DataFn delete might fail (authz, conflict). If it does, you don't want to have already deleted the file.

## Cascade delete

When the parent (document, comment) is trashed or hard-deleted, you want the attachments to follow. Two options:

1. **Server-side hook** — `afterMutation` on the parent resource that fans out to attachments. Clean, but you're now doing work the database could do.
2. **FK + cascade in the database** — declare a foreign key on the underlying table that cascades on delete. This is the canonical option if you control the schema migrations.

For soft-deletes via the `trash` capability, neither cascades automatically — by design. You either bake the cascade into your UI ("trash this document and its 3 attachments") or accept that re-restoring the parent should also restore its attachments.

## Quota and limits

DataFn doesn't enforce file size limits — that's FileFn's job. FileFn enforces them per upload policy on its server, when the upload starts:

```typescript
// filefn-policies.ts (on the FileFn server)
import type { Policy } from "@filefn/server";

export const attachmentsPolicy: Policy = {
  name: "attachments",
  contentTypes: ["image/*", "application/pdf"],
  maxSizeBytes: 25 * 1024 * 1024,
  visibility: "private",
};
// createFileFn({ ..., policies: [attachmentsPolicy] })
```

The `max` validator on the schema's `size` field gives you a matching check on the DataFn side.

## Searching by file metadata

If you need to search by filename, index it as the schema above does: `filename` is in `indices.search`. Add `mime` to `indices.base` to filter by type.

For full-text search across file *contents*, you need a search provider that indexes file bodies (Tantivy via a worker, ElasticSearch). See [SearchFn integration](/docs/recipes/searchfn-integration).
