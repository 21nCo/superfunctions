Cloudflare Workers run DataFn close to your users. The tradeoffs are real — limited CPU, specific runtime constraints — but for read-heavy global apps it's hard to beat the latency.

## Tradeoffs

- **Excellent**: Sub-50ms latency worldwide. Zero cold starts. Per-request billing.
- **Good**: WebSockets work via the WebSocket API (Hibernatable WebSocket if you want them suspended between messages).
- **Watch out**: 30s CPU limit per request (10s on free tier). Some Node-only adapters don't work; pick edge-compatible drivers.

## Database options

| Option | When |
| --- | --- |
| **D1** (Cloudflare's SQLite) | Read-heavy global apps; you can shard writes by namespace. |
| **Hyperdrive + your Postgres** | You want Postgres, with edge-cached connection pooling. |
| **Turso** (libSQL) | You want SQLite semantics with multi-region replication. |
| **Neon** (over Hyperdrive) | Postgres with branch-per-preview and edge pooling. |

D1 is the lowest-friction; Hyperdrive is the right answer for most production apps. The DataFn Drizzle adapter supports all four.

## 1. Project scaffold

```bash
npx wrangler init my-app
cd my-app
npm install @datafn/server @datafn/core @datafn/client
npm install drizzle-orm hono
```

For D1:

```bash
npx wrangler d1 create my-app-db
```

Add the binding to `wrangler.jsonc`:

```jsonc
{
  "name": "my-app",
  "main": "src/index.ts",
  "compatibility_date": "2025-01-01",
  "compatibility_flags": ["nodejs_compat"],
  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "my-app-db",
      "database_id": "<your-id>",
      "migrations_dir": "migrations"
    }
  ]
}
```

## 2. Worker entry

```typescript
import { Hono } from "hono";
import { drizzle } from "drizzle-orm/d1";
import { createDatafnServer } from "@datafn/server";
import { drizzleAdapter } from "@superfunctions/db/adapters";
import { toHono } from "@superfunctions/http-hono";
import { schema } from "../shared/schema";
// Generated by `datafn generate` (step 3); the adapter resolves tables from it.
import { schema as tables } from "./datafn-schema.drizzle";

type Env = {
  DB: D1Database;
};

export default {
  async fetch(req: Request, env: Env) {
    const db = drizzle(env.DB, { schema: tables });
    const datafn = await createDatafnServer({
      schema,
      db: drizzleAdapter({ db, dialect: "sqlite" }),
      authorize: async () => true,
    });
    const app = new Hono();
    app.route("/", toHono(datafn.router));
    return app.fetch(req);
  },
};
```

The server is constructed per-request. That sounds expensive — and it is, ~1–2ms — but D1 caches the schema validation at the V8 isolate level, so subsequent requests are sub-millisecond.

For higher throughput, hoist the construction:

```typescript
let datafnPromise: ReturnType<typeof createDatafnServer> | null = null;

export default {
  async fetch(req: Request, env: Env) {
    if (!datafnPromise) {
      datafnPromise = createDatafnServer({
        schema,
        db: drizzleAdapter({ db: drizzle(env.DB, { schema: tables }), dialect: "sqlite" }),
        authorize: async () => true,
      });
    }
    const datafn = await datafnPromise;
    const app = new Hono();
    app.route("/", toHono(datafn.router));
    return app.fetch(req);
  },
};
```

The hoisted version uses module-level state, which is per-isolate, not per-request. Works fine in Workers.

## 3. Migrations

For D1:

`datafn generate` writes `src/datafn-schema.drizzle.ts`. Point Drizzle Kit at that file and have it write migrations to the `migrations_dir` from `wrangler.jsonc`:

```typescript
// drizzle.config.ts
import { defineConfig } from "drizzle-kit";

export default defineConfig({
  dialect: "sqlite",
  schema: "./src/datafn-schema.drizzle.ts",
  out: "./migrations",
});
```

Drizzle Kit writes `migrations/0000_<name>.sql` files, which Wrangler applies in order (it ignores the `migrations/meta` folder):

```bash
npx @datafn/cli generate --adapter drizzle --database sqlite --schema shared/schema.ts --output src/
npx drizzle-kit generate --config drizzle.config.ts
npx wrangler d1 migrations apply my-app-db --local   # then --remote
```

For Hyperdrive + Postgres, point Drizzle Kit at the same Postgres connection (not at Hyperdrive — migrations need a direct connection).

## D1 behavior and limits

The [Drizzle SQLite conformance suite](https://github.com/21nCo/superfunctions/blob/dev/datafn/server/__tests__/drizzle-sqlite/suite.ts) runs this setup (`createDatafnServer` + `drizzleAdapter({ dialect: "sqlite" })` + `toHono`) on D1 inside workerd with Miniflare's local D1, and runs the same cases on better-sqlite3. It covers queries with filters, sort and pagination; idempotent mutations and `if` guards; relations; clone, pull and push; and the REST wrappers. It runs in CI without a Cloudflare account.

D1 has no interactive transactions, so the Drizzle adapter reports `transactions.supported: false` on D1 and on every SQLite driver:

- **`transact` with `atomic: true` (the default) and any mutation step is rejected** with HTTP 400 and error code `DFQL_UNSUPPORTED` (`details.path: "atomic"`) before anything is written. DataFn never applies part of an atomic transact. Send `atomic: false` to apply the steps one at a time; a failed step then leaves earlier steps applied. Query-only transacts run normally.
- **Guarded mutations (`if`)** sent to `/datafn/mutation` run without a database transaction. The guard is checked and the write applied as separate statements, so a writer in another isolate can change the record in between.
- **`push` does not evaluate `if`** on any adapter: a pushed mutation is applied even when its guard does not match, so do not rely on `if` in pushed mutations for concurrency control. Each pushed mutation is applied on its own, without a database transaction.
- **Server sequence numbers** use a compare-and-swap on `__datafn_meta`, so concurrent writers in different isolates still get distinct `server_seq` values. This needs `@superfunctions/db` 0.3.2 or later, which reads D1's affected-row count (`meta.changes`).
- **Generate the schema with `@datafn/cli` 0.1.2 or later.** Earlier versions emitted plain `integer` columns for `boolean` fields and plain `text` for `object`, `array` and `json` fields. D1 then returned booleans as `0`/`1`, and better-sqlite3 refused to store them. Existing JSON columns need a data upgrade before you deploy; see [SQLite column modes](/docs/cli/drizzle-codegen#sqlite-column-modes) for how to upgrade an existing schema.

Live D1 has not been exercised by the suite yet; it runs against Miniflare's local D1 only.

## 4. WebSockets

Cloudflare Workers support WebSockets via the Durable Object API. The DataFn WS handler is compatible:

```typescript
import { DatafnServer } from "@datafn/server";

export class DatafnWsRoom {
  constructor(private state: DurableObjectState, private datafn: DatafnServer) {}

  async fetch(req: Request) {
    const pair = new WebSocketPair();
    const [client, server] = Object.values(pair);

    server.accept();
    this.datafn.websocketHandler.addClient(server as any, {/* auth */});
    server.addEventListener("message", (e) =>
      this.datafn.websocketHandler.handleMessage(server as any, (e as MessageEvent).data),
    );

    return new Response(null, { status: 101, webSocket: client });
  }
}
```

Use **Hibernatable WebSockets** for cost-effective long-lived connections — the DO suspends between messages, no CPU charged while idle.

## 5. Environment variables

Set via `wrangler secret put`:

```bash
echo $DATABASE_URL | npx wrangler secret put DATABASE_URL
```

Access via `env.DATABASE_URL` in the worker.

## 6. Deploy

```bash
npx wrangler deploy
```

That's it. Logs are at `wrangler tail`; the dashboard has analytics.

## Where it falls down

- **No filesystem** — anything that wants to read a file at startup won't work. Bundle the schema as a TypeScript import, not a JSON file read.
- **No native Node modules** — `better-sqlite3` won't work. Use D1 or Turso.
- **30s CPU limit** — large `/datafn/clone` calls may need pagination via the `next` cursor.
- **No long-running schedulers** — use Cron Triggers for retention pruning:

```jsonc
{
  "triggers": {
    "crons": ["0 3 * * *"]
  }
}
```

```typescript
export default {
  async fetch(req: Request, env: Env) { /* ... */ },
  async scheduled(event: ScheduledEvent, env: Env) {
    // run prune logic
  },
};
```
