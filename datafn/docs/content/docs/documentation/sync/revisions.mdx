# Record revisions

Every record has a **revision**: an integer the server raises by exactly one on every committed write to that record. Use it to tell which server state a client holds. (Write preconditions such as `ifRev` build on it; they are not part of this page.)

## The token

- **Every write bumps it, once.** Insert, merge, replace, delete, trash, restore, archive, unarchive, KV merges and relation writes that change a record (a forward many-to-one `relate` or `unrelate`; `modifyRelation` edits many-many join metadata only) each raise the record's revision by exactly one, on push, `/mutation` and `/transact`, however many changes the write records for it (an insert under an archived parent that also sets its inherited-inactive state is one write). A delete also bumps every record it changes through a relation policy (a `cascade` delete gets a tombstone revision, a `setNull` child a bump), and an inherited-inactive change bumps each affected record.
- **Serialized per record.** The bump is a compare-and-swap inside the write's transaction, so two writes to one record never commit the same revision, also for overlapping PostgreSQL transactions at `READ COMMITTED`. Two writes in the same millisecond still get different revisions.
- **Never reused.** A delete keeps the record's revision as a tombstone, so re-inserting the same id continues from it. Revisions live in the `__datafn_revisions` table: change-log pruning and sequence reservation never touch them, and only deleting the whole namespace removes them.
- **Zero means unknown history.** A record written before this release, or never written, has revision 0, and clone and versioned queries return `$rev: 0` for an existing record that no revision-aware write has touched.

On an adapter without transactions the bump and the write are best effort, like other writes there.

## Turning it on

Every write bumps revisions. The server **issues** them only with the `revisions` option:

```ts
const server = await createDatafnServer({
  schema,
  database,
  revisions: { enabled: true },
});
```

Turn it on only when every worker writing to the database runs a release that bumps revisions: an older worker writes without bumping. While it is off, responses carry no revisions and change rows record none. With it on, every DataFn route's JSON response (success or error) carries `capabilities: { revisions: true }`, and the client exposes it as `client.serverCapabilities().revisions`. A response without `capabilities` leaves the client's last announcement in place.

Do not restore a namespace in place, or roll back below this release, while revisions are on.

## Wire format

Revisions are row metadata, never part of a record's fields, so E2EE record encryption never touches them.

| Response | Where the revision is |
| --- | --- |
| Clone | `$rev` on each returned row, never newer than the row |
| Pull (per-table cursors) | `$rev` on complete `records` rows (and complete KV rows in `merged`); `deletedRevisions[resource][id]` for deletes |
| Pull (global cursor) | `rev` on each change that recorded one; `$rev` on its `record` only when that record is the complete row |
| Push | `revisions[mutationId] = { resource, id, rev, record?, deleted? }`; `record` carries `rev` again as its `$rev` |
| Query with `withRevisions: true` | `$rev` on each complete stored row the caller may read in full |
| `/mutation`, `/transact` | `rev` on each committed mutation result (never on a rolled-back step, nor on a replay while revisions are off) |

Rows and their revisions are read in one snapshot only where DataFn can verify one: a `REPEATABLE READ` transaction on PostgreSQL, or SQLite. On another database with transactions (MySQL, or a SQL database reached without raw SQL access such as Prisma), where a write and its revision commit together, the revisions are read before and after the returned rows, and a row gets `$rev` only when both reads agree, so no write to it committed in between. Without transactions (D1, Drizzle SQLite), a write and its revision are separate statements, so no read can establish the pair: clone and versioned queries return rows without `$rev` there, and the client learns revisions from pull and push. Revision lookups bind at most 90 ids per statement (D1 allows 100).

A push result carries the record's complete row after the write (read in the write's transaction) only when the caller's read policy covers every field of the resource, the caller can still access the record (checked again in the write's transaction for a shareable resource), and no later mutation of the same push changed the record again (directly, or through a cascade, `setNull` or inherited-inactive update); otherwise it carries `rev` alone. The client pairs the row only with the `$rev` on the row. A deduplicated replay carries the stored `rev` without a row. A versioned query returns its rows with `$rev` only for rows of its own resource that the caller may read in full: not for a relation traversal, a projection (`select`, `omit`), grouping, aggregation or a temporal clause. A query that does not qualify, including any query of a resource whose read policy withholds fields and any `sharedWithMe` query (its rows belong to other namespaces), returns its rows with no `$rev` and without the declared fields the read policy withholds (other keys, such as aggregation aliases, are kept); a row with a column the caller may not read also gets no `$rev`. A qualifying query runs inside the revision snapshot described above and returns its own rows as stored (as clone returns them, foreign keys included, on every query strategy), so filters, sorting, pagination, trash and archive state and row-level access are decided on the same state as the revision. A row that gets no revision is returned as the plain query projects it. If the query fails inside the snapshot (on PostgreSQL a push-down fallback aborts the transaction), it runs again outside it and returns no revisions.

Only a write's last change row for a record carries the revision, and when it writes a whole record (insert, replace, or any KV write) it records the stored row after the write, defaults and server fields included. A partial change (a merge, or a whole row followed by an inherited-inactive update in the same write) carries the revision on the change but never as `$rev` on a row, so the client leaves the revision unknown. On a resource whose read policy withholds fields (or a stored row with a column the policy does not list), revisioned pull rows have those fields removed and carry no `$rev`, also after revisions are turned off again. A pull returns the same changes, in the same buckets and order, as without revisions; revisions are only added to them. Sequence numbers are reserved before a write, so they do not give commit order, and a pull never reorders or drops changes on that basis. A per-table pull combines several rows (or KV writes) of one id as before; the combined entry keeps `$rev` only when every combined change carried one, the last has the highest, and the combined row is that last row. `deletedRevisions` lists a tombstone revision only when every delete of the id in the response recorded one. The client applies the page as before (rows, then patches, then deletes) and then pairs a record with a revision only when every change of that record in the page carried one, and the change with the highest revision is a complete `$rev` row (or a delete with its tombstone revision) and is the last one applied; otherwise it clears the record's revision. Change rows written before revisions were enabled carry no revision, so a pull returns none for them. DataFn checks for the `rev` column in the database catalog (`PRAGMA table_info` on SQLite and D1, `pg_attribute` on PostgreSQL, `information_schema` on MySQL) and adds it only when it is missing. On a SQL database reached without raw SQL access, DataFn cannot add the `rev` column to an existing `__datafn_changes` table; change rows then record a revision only if a probe shows the column exists (a driver that accepts a filter on any column name counts as unverified, so no revision is recorded).

A resource with its own field named `$rev` keeps that field as application data and gets no revisions.

### Host response filters

If your host filters read responses after DataFn has run, apply the same filter to every row DataFn returns, including the post-write rows in push results: remove `$rev` from a row you trim, or replace the row with an acknowledgement without a row. A row you drop takes its revision with it.

## Client

The client holds a revision only together with the complete server row (or tombstone) at that revision. It gets one from a clone row, a versioned query row, a push result's post-write row, or a pull change that carries the complete row (an insert or replace, or a delete). Any other change to the local copy — an optimistic local write, a partial merge from a pull, a change without a revision — clears the revision to unknown in the same storage write.

```ts
const { record, rev } = await client.getWithRevision("task", "task:1");
if (rev === undefined) {
  // Unknown: read the server's pair first.
  const result = await client.query({
    resource: "task",
    version: 1,
    withRevisions: true,
    filters: { id: "task:1" },
  });
  const row = result.data[0]; // row.$rev is the revision of exactly this row
}

const rev = await client.getRevision("task", "task:1"); // display and diagnostics
```

- `getWithRevision(resource, id)` returns the stored record and its revision (or `undefined`) from one storage read. Build a precondition from it, not from two separate reads.
- A query with `withRevisions: true` always goes to the server, also on a hydrated client, and returns the server's rows. A storage-backed client stores pairs only from a plain row read of the queried resource (never from a relation traversal, projection, grouping, aggregation, temporal or `sharedWithMe` query), and only when no pending local mutation (logged or still debounced) touches the record and the record was not written locally after the query started; a push result's row is stored on the same terms, and only from the push's final request (after a compaction replay, rows from the earlier request are not stored, since the replay may have changed those records). A pending write to the parent of an `inheritsInactive` relation, or a pending delete, counts as touching every record, since the server may change other records through it. `getWithRevision` reports an unknown revision while a local mutation is pending.
- An install never replaces a known revision with an older or equal one, so reading the same state again stores nothing, and an older row or tombstone in a clone or pull leaves the newer stored pair in place. A custom adapter's `putRecordsWithRevisions` reports these as `current`, separately from the records it `installed`. Stored pairs are re-indexed for search and refresh live queries (a `sync_applied` event with phase `revisions`, emitted only when something was stored). A live query never patches a row carrying `$rev` with local fields; it reads again.
- On an E2EE resource a versioned query may select records only by `id` (equality or a list of ids). Any other versioned query on an E2EE resource is rejected before a request is sent. Returned fields stay encrypted on the wire and are decrypted on the client.
- The memory and IndexedDB storage adapters keep revisions (`capabilities.revisions`), with a write stamp per record so an install never overwrites a newer local state, also from another tab. IndexedDB creates its revisions store with a new database, or during an upgrade that a schema change needs anyway; it never upgrades a database just for revisions, since that would close the database in tabs of an earlier release. Until the store exists, revisions stay unknown. Other open adapters reopen the database after an upgrade. Rows a memory adapter read returns are copies when they are paired with a revision, so editing one cannot change the stored pair. Record writes resolve once their transaction, revision bookkeeping included, commits. With a custom adapter without that capability, revisions are always unknown.
