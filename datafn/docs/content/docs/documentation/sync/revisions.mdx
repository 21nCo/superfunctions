# Record revisions

Every record has a **revision**: an integer the server raises by exactly one on every committed write to that record. Use it to tell which server state a client holds. (Write preconditions such as `ifRev` build on it; they are not part of this page.)

## The token

- **Every write bumps it, once.** Insert, merge, replace, delete, trash, restore, archive, unarchive, KV merges and relation writes that change a record (a forward many-to-one `relate` or `unrelate`; `modifyRelation` edits many-many join metadata only) each raise the record's revision by exactly one, on push, `/mutation` and `/transact`, however many changes the write records for it (an insert under an archived parent that also sets its inherited-inactive state is one write). A delete also bumps every record it changes through a relation policy (a `cascade` delete gets a tombstone revision, a `setNull` child a bump), and an inherited-inactive change bumps each affected record.
- **Serialized per record.** The bump is a compare-and-swap inside the write's transaction, so two writes to one record never commit the same revision, also for overlapping PostgreSQL transactions at `READ COMMITTED`. Two writes in the same millisecond still get different revisions.
- **Never reused.** A delete keeps the record's revision as a tombstone, so re-inserting the same id continues from it. A revision is raised only on evidence from the write's own statement: the affected-row count of its `UPDATE` or `DELETE` of that record (a current read on PostgreSQL, MySQL InnoDB and SQLite), or a create that succeeded. A read of the record or of its revision row is never evidence, since under MySQL's `REPEATABLE READ` it may show a snapshot older than the latest commit; where reads may be such a snapshot, DataFn runs a record `UPDATE` as a counted update and reads the row after it. A tombstone is raised only by a delete whose own `DELETE` removed the record row. A delete that removed nothing raises no revision, and its change row and push or mutation result carry none (two overlapping deletes, or a repeated one, give exactly one tombstone). Likewise, any other write raises a record's revision only when one of its own statements changed the record row: a write that changed no row (a relation or `setNull` update of a record another writer deleted first, or a batched relation update that matched only some of its targets) raises nothing for the missing record, so its tombstone stays as it is and that change row and result carry no revision, while a merge that finds the record gone and creates it raises its revision live over the tombstone. If raising a revision fails inside a transaction, the write fails and rolls back (the client retries it); change tracking does not retry it within the transaction. Without transactions a write and its revision are separate statements: a delete whose `DELETE` removed the row raises its tombstone even if another writer re-inserts the record first, and the re-inserted row is returned without `$rev` until its next write. This holds whether or not the server returns revisions (`revisions.enabled`), so a server with revisions off never turns a tombstone live for a write that changed nothing. Revisions live in the `__datafn_revisions` table: change-log pruning and sequence reservation never touch them, and only deleting the whole namespace removes them.
- **One record per write.** A write's `record.id`, when present, must equal its mutation `id`; a write naming another record (which would store or rename a row other than the one whose revision it raises) is rejected with `DFQL_INVALID` at `record.id` before anything is written, on push, `/mutation` and `/transact`. For the same reason, with `revisions: { enabled: true }` `createDatafnServer` rejects a schema whose relation writes a record's `id` column (a foreign key `fkField` or `foreignKey`, its resource field, or a tree path field named `id`). Each relation's own columns are checked, also when several relations share one foreign key.
- **Data resources, not join stores.** Every declared resource has revisions, including one whose name starts with `join_`. The many-to-many join stores derived from the schema's relations, and DataFn's internal `__datafn_` tables, have none. On pull, too, such a resource gets its own data bucket and the access checks of a private shareable resource, and only a join store goes to `joins`.
- **Zero means unknown history.** A record written before this release, or never written, has revision 0, and clone and versioned queries return `$rev: 0` for an existing record that no revision-aware write has touched.

On an adapter without transactions the bump and the write are best effort, like other writes there.

## Turning it on

Every write bumps revisions. The server **issues** them only with the `revisions` option:

```ts
const server = await createDatafnServer({
  schema,
  database,
  revisions: { enabled: true },
});
```

Turn it on only when every worker writing to the database runs a release that bumps revisions: an older worker writes without bumping. This is an operator contract that DataFn cannot check across servers. While it is off, responses carry no revisions and change rows record none. With it on, every DataFn route's JSON response (success or error) carries `capabilities: { revisions: true }`, so a caller can tell a revision-aware server from an older one (merged into a `capabilities` object the body already has; a body with a `Content-Encoding`, or one that is not UTF-8, is passed through unchanged, without it). The `@datafn/client` of this release does not understand `$rev` yet (see [Client](#client)) and stores it in its local rows as if it were a record field, where it can be sent back in a later write and rejected as an unknown field; keep revisions off for apps that sync through `@datafn/client` until it supports them.

Revisions are keyed by namespace, so `revisions.enabled` requires each namespace's rows to be its own: row-level namespace isolation on (the default with a `namespaceProvider` or a SQL adapter), or a server without a `namespaceProvider`, where every request uses the one default namespace. `createDatafnServer` rejects `revisions: { enabled: true }` together with `rowLevelNamespace: false`, a disabled `rowLevelNamespace` config, or a `namespaceProvider` without row-level isolation (for example a schema with namespace isolation turned off): there a write from one namespace would change a row whose revision another namespace holds without raising it. The same holds across servers: a server whose rows are shared across namespaces (revisions off, for example an admin instance that reads across tenants) bumps revisions under its own request namespace, not the namespace a revision-issuing server keys the row by, so it **must not write** to the tables a revision-issuing server serves. Keep such an instance read-only on those tables, or give it row-level namespace isolation. `createDatafnServer` logs a warning when rows are shared across namespaces, as a reminder of this contract; it cannot enforce it across servers.

Do not restore a namespace in place, or roll back below this release, while revisions are on.

## Wire format

Revisions are row metadata, never part of a record's fields, so E2EE record encryption never touches them.

| Response | Where the revision is |
| --- | --- |
| Clone | `$rev` on each returned row the caller may read in full, never newer than the row |
| Pull (per-table cursors) | `$rev` on complete `records` rows (and complete KV rows in `merged`); `deletedRevisions[resource][id]` for deletes that recorded one |
| Pull (global cursor) | `rev` on each change that recorded one; `$rev` on its `record` only when that record is the complete row |
| Push | `revisions[mutationId] = { resource, id, rev, record?, deleted? }`; `record` carries `rev` again as its `$rev` |
| Query with `withRevisions: true` | `$rev` on each complete stored row the caller may read in full |
| `/mutation`, `/transact` | `rev` on each committed mutation result (never on a rolled-back step, nor on a replay while revisions are off) |

Rows and their revisions are read in one snapshot only where DataFn can verify one: a `REPEATABLE READ` transaction on PostgreSQL, or SQLite. On another database with transactions (MySQL, or a SQL database reached without raw SQL access such as Prisma), where a write and its revision commit together, the revisions are read before and after the returned rows, and a row gets `$rev` only when both reads agree, so no write to it committed in between. Without transactions (D1, Drizzle SQLite), a write and its revision are separate statements, so no read can establish the pair: clone and versioned queries return rows without `$rev` there, a push result carries `rev` alone (no row and no `deleted` tombstone), and pull carries `rev` on non-delete changes but no `$rev` on their rows, no `rev` on delete changes and no `deletedRevisions` (the deleted ids are returned as before). Pull decides this from each change row's write-time provenance (the `rev_certified` column: set only when the writer committed the change together with its revision in one transaction), not from the adapter reading it, so changes written without a transaction certify nothing even when a server with transactions pulls them from the same database. Such change rows keep the write's own payload instead of a row read back after the write. A push in non-atomic mode on an adapter that exposes transactions but rejects asynchronous callbacks (Drizzle with better-sqlite3) is treated the same way. Revision lookups bind at most 90 ids per statement (D1 allows 100).

Revisions are optional metadata on reads. If DataFn cannot create `__datafn_revisions` (for example, a database role without `CREATE`), cannot open the snapshot, or a revision read or any read inside the snapshot fails, clone and versioned queries read the rows again outside the snapshot and return them without `$rev`, with their usual cursors. Only a failure of that plain row read is reported as it would be without revisions. A clone row of a resource that issues revisions which the caller may not read in full (its read policy withholds a field, or the row has a column the policy does not list) is returned without `$rev` and without the fields the policy withholds, as pull returns it, in every clone mode (including the plain fallback). Resources that issue no revisions keep their clone rows as before. A field the resource declares counts as one of its fields whatever its name: a declared `__ns` field that the read policy hides is withheld like any other, and the row gets no `$rev`, on clone, pull, push results and versioned queries. Only the undeclared `__ns` storage partition column a namespaced adapter adds is exempt.

On a resource that issues revisions, `$rev` is always the server's: a `$rev` value stored with a row or a change row (left from when the resource declared its own `$rev` field) is never returned as a revision. Pull drops it from changes that recorded no revision, a versioned query returns such a row as the plain query projects it, and clone replaces it with the row's server revision (or with none, for a row the caller may not read in full).

A push result carries the record's complete row after the write (read in the write's transaction) only on a database with transactions and only when the caller's read policy covers every field of the resource, the caller's own versioned query of that record returns it at the same revision (after every write of the push, the server sends a versioned `/query` for the written ids, with the push's request headers, through the DataFn router's current handler, exactly as an external request: every router middleware, including middleware added later with `router.use`, the configured `context` factory, route-ticket validation with the `query` scope where route tickets are configured, the server's `authorize` callback and every plugin `authorize` hook, and the plugin `beforeQuery` and `afterQuery` hooks; the row returned is the one read in the write's transaction, and only when the router's response to that query held exactly it, and only when the query ran for the written resource in the push's namespace, so middleware or a hook that denies, redirects, rewrites or trims the read leaves `rev` alone; the read is not rate limited again and is not held to `maxPayloadBytes`, since the server generated it, but nothing a caller sends can claim either exemption; at most `limits.maxBatchQueryConcurrency` of these reads run at once, and reads the router has not answered within 2 seconds of the first (for example behind router middleware that serializes requests and so waits for the push itself) leave `rev` alone; every read-back request is aborted (its request's signal) once the push stops waiting for it, whatever the answer (a non-2xx one included), and its body, which router middleware sees with the same envelope as an external `/query` and gets as soon as the handler answers (the body is read only when pulled), is no longer served to any reader, clones and tee branches included; a push a gateway routing assertion admitted gets `rev` only, because the assertion is bound to the push request and cannot admit the query; a denied read emits the query's authorization-denied event), the caller can still access the record (checked again in the write's transaction for a shareable resource), and no later mutation of the same push changed the record again (directly, or through a cascade, `setNull` or inherited-inactive update); otherwise it carries `rev` alone. Only the `$rev` on the returned row belongs to that row. A deduplicated replay carries the stored `rev` without a row, and only when the retry names the same resource and id as the stored write; a mutation id reused for another record gets no `rev`, on push and on `/mutation`, and a mutation id one push uses for more than one record gets none. A versioned query returns its rows with `$rev` only for rows of its own resource that the caller may read in full and that the plugin `afterQuery` hooks leave unchanged (a row a hook changes or adds has no `$rev`; this is checked on the response exactly as it is sent, after every serializer such as `toJSON` of the hook output, and a result whose rows are not a `data` array loses every `$rev`): not for a relation traversal, a projection (`select`, `omit`), grouping, aggregation or a temporal clause. A query that does not qualify, including any query of a resource whose read policy withholds fields and any `sharedWithMe` query (its rows belong to other namespaces), returns its rows with no `$rev` and without the declared fields the read policy withholds (other keys, such as aggregation aliases, are kept); a row with a column the caller may not read also gets no `$rev`. A qualifying query runs inside the revision snapshot described above and returns its own rows as stored (as clone returns them, foreign keys included, on every query strategy), so filters, sorting, pagination, trash and archive state and row-level access (owned rows, grants and principal memberships of a private shareable resource, resolved inside the snapshot) are decided on the same state as the revision. A row that gets no revision is returned as the plain query projects it. If any read of the query fails inside the snapshot, whether the query raises the error or recovers from it (a push-down or in-memory fallback, which on PostgreSQL would otherwise read an aborted transaction as empty), the query runs again outside the snapshot, with access resolved afresh as without revisions (never from principals an earlier query of the same batch resolved), and returns no revisions.

Only a write's last change row for a record carries the revision, and when it writes a whole record (insert, replace, or any KV write) it records the stored row after the write, defaults and server fields included. A partial change (a merge, or a whole row followed by an inherited-inactive update in the same write) carries the revision on the change but never as `$rev` on a row, since no complete row at that revision is returned. On a resource whose read policy withholds fields (or a stored row with a column the policy does not list), revisioned pull rows have those fields removed and carry no `$rev`, also after revisions are turned off again. A pull returns the same changes, in the same buckets and order, as without revisions; revisions are only added to them. Sequence numbers are reserved before a write, so they do not give commit order, and a pull never reorders or drops changes on that basis. A per-table pull combines several rows (or KV writes) of one id as before; the combined entry keeps `$rev` only when every combined change carried one, the last has the highest, the combined row is that last row, and the record's stored id is the id the pull returns (a pull trims surrounding whitespace from ids, so a row stored as `"a "` is returned as `"a"` without `$rev`). `deletedRevisions` lists a tombstone revision only when every delete of the id in the response recorded one; a visibility delete (a revoked grant or a lost membership) records none, so an id it is listed under in `deleted` gets no entry. Change rows written before revisions were enabled, or while the resource declared its own `$rev` field, carry no revision, so a pull returns none for them, also after the field is dropped. DataFn checks for the `rev` and `rev_certified` columns in the database catalog (`PRAGMA table_info` on SQLite and D1, `pg_attribute` on PostgreSQL, `information_schema` on MySQL) and adds each only when it is missing. On a SQL database reached without raw SQL access, DataFn cannot add them to an existing `__datafn_changes` table; change rows then record a revision only if a probe shows both columns exist (a driver that accepts a filter on any column name counts as unverified, so no revision is recorded).

A resource with its own field named `$rev` keeps that field as application data and gets no revisions; pulls, including combined per-table entries, return that field unchanged whether revisions are on or off.

### Host response filters

Middleware that your host runs outside the DataFn router (for example in an outer framework that calls `server.router.handle`) does not see the post-write read. If it denies or filters `/query` responses, gate push the same way, or apply the same filter to every row DataFn returns, including the post-write rows in push results: remove `$rev` from a row you trim, or replace the row with an acknowledgement without a row. A row you drop takes its revision with it.

## Client

This release adds revisions to the server's wire format only. `@datafn/client` does not store them yet: it does not keep `$rev` or `rev` from clone, pull or push, it treats a `withRevisions` query like any other query, and it has no paired-read API. Storing each record's server row together with its revision, and the paired-read APIs (`getWithRevision`, `getRevision`, `serverCapabilities().revisions`), are follow-up work (DATA-49). Until then, read revisions from the server responses described above, for example with a versioned query sent directly to the server:

```ts
const response = await fetch(`${serverUrl}/datafn/query`, {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({
    resource: "task",
    version: 1,
    withRevisions: true,
    filters: { id: "task:1" },
  }),
});
const body = await response.json();
const row = body.result?.data?.[0]; // row.$rev is the revision of exactly this row, when present
```

A row without `$rev` has no proven revision: read it again, or treat its revision as unknown.
