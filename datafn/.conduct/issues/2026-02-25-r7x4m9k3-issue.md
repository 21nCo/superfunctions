## Summary

**Severity: High** — Any `unrelate` mutation pushed by one client will silently fail to propagate to other clients. The second client's pull correctly receives a join delete entry, but the `from` and `to` values are wrong due to a composite ID separator mismatch. The `deleteJoinRow` call on the receiving client targets a non-existent row, so the relationship persists on that client indefinitely. This breaks multi-client sync for all many-many unrelate operations.

## Root Causes

### RC-1: `extractJoinDeltas` uses `::` separator but `executeRelate` uses `:` — and pull parses with `:`

There are three locations that construct or parse composite IDs for join rows, each using a different separator convention:

**Location 1 — `executeRelate` (database storage):**
[datafn/server/src/execution/mutation/relations.ts:154](datafn/server/src/execution/mutation/relations.ts#L154)
```ts
const compositeId = `${mutation.id}:${item.toId}`;   // Single colon
```

**Location 2 — `extractJoinDeltas` (change tracking):**
[datafn/server/src/execution/mutation/relations.ts:295](datafn/server/src/execution/mutation/relations.ts#L295)
```ts
const compositeId = `${mutation.id}::${item.toId}`;  // Double colon
```

**Location 3 — `executePullCanonical` (pull response construction):**
[datafn/server/src/execution/sync/pull.ts:307-308](datafn/server/src/execution/sync/pull.ts#L307-L308)
```ts
const from = change.record?.from || change.id.split(":")[0];
const to = change.record?.to || change.id.split(":")[1];
```

**What happens:**

1. Client 1 pushes `unrelate` for `todo:2ee25d80-...` removing `cat:b2c48cd5-...`
2. `executeUnrelate` correctly deletes the join row from the database
3. `extractJoinDeltas` records the change with composite ID: `"todo:2ee25d80-fc6e-4140-8dee-cc16c26a008d::cat:b2c48cd5-fde5-4181-854f-5c7ae9be28e5"` (double colon)
4. For `unrelate`, the delta has `record: null` (line 313) — no `from`/`to` fields available
5. When client 2 pulls, `executePullCanonical` hits the fallback path at line 307-308 since `change.record` is null
6. `change.id.split(":")[0]` = `"todo"` and `change.id.split(":")[1]` = `"2ee25d80-fc6e-4140-8dee-cc16c26a008d"`
7. The pull response sends `{ from: "todo", to: "2ee25d80-..." }` instead of `{ from: "todo:2ee25d80-...", to: "cat:b2c48cd5-..." }`

**Impact:** All many-many `unrelate` operations fail to propagate to other clients. The `relate` path is also affected in theory, but `relate` deltas include `record: { from, to, ... }` (line 302-306) so the `change.record?.from` path is used and the bug is masked.

**Evidence:** The user's pull response exactly matches this analysis — `from: "todo"` and `to: "2ee25d80-..."` are the first two colon-delimited segments of the double-colon composite ID.

---

### RC-2: `extractJoinDeltas` passes `record: null` for delete ops — no from/to recovery possible

[datafn/server/src/execution/mutation/relations.ts:308-314](datafn/server/src/execution/mutation/relations.ts#L308-L314)
```ts
} else if (mutation.operation === "unrelate") {
  deltas.push({
    resource: joinStoreKey,
    id: compositeId,
    op: "delete",
    record: null,    // <-- No from/to fields stored
  });
}
```

For `relate` and `modifyRelation`, the delta includes `record: { from: mutation.id, to: item.toId, ...metadata }`, so `pull.ts` can recover the correct `from`/`to` from `change.record`. But for `unrelate`, `record` is `null`, forcing the pull parsing to fall back to splitting the composite ID — which fails due to RC-1.

**Impact:** Even if the separator were consistent (single colon), parsing would still fail because both `mutation.id` and `item.toId` themselves contain colons (e.g., `todo:UUID` and `cat:UUID`). A simple `split(":")[0]` can never correctly extract multi-segment IDs.

---

### RC-3: Client-side `deleteJoinRow` receives wrong from/to values

[datafn/client/src/sync/apply.ts:219-221](datafn/client/src/sync/apply.ts#L219-L221)
```ts
for (const edge of delta.delete) {
  await storage.deleteJoinRow(joinStoreKey, edge.from, edge.to);
}
```

The client faithfully calls `deleteJoinRow("join_todos_tags_categories", "todo", "2ee25d80-...")`. Since no join row has `from = "todo"` and `to = "2ee25d80-..."` (actual rows have `from = "todo:2ee25d80-..."` and `to = "cat:b2c48cd5-..."`), the delete is a no-op. The relationship persists.

**Impact:** This is the terminal symptom — the client never removes the join row, so the UI continues showing the removed tag/category.

## Proposed Fixes

### Fix A (Recommended): Include `from`/`to` in unrelate delta record

In `datafn/server/src/execution/mutation/relations.ts`, change the unrelate delta to include the from/to values instead of `null`:

```ts
} else if (mutation.operation === "unrelate") {
  deltas.push({
    resource: joinStoreKey,
    id: compositeId,
    op: "delete",
    record: {
      from: mutation.id,
      to: item.toId,
    },
  });
}
```

This ensures `pull.ts` uses `change.record.from` / `change.record.to` (the reliable path) instead of falling back to ID parsing. This fix alone resolves the propagation bug.

### Fix B (Belt-and-suspenders): Align composite ID separator

In `extractJoinDeltas` at line 295, change `::` to `:` to match `executeRelate`:

```ts
const compositeId = `${mutation.id}:${item.toId}`;   // Was `::`
```

This makes the change tracking ID consistent with the database row ID. However, this alone does NOT fix the bug because `split(":")[0]` still cannot correctly extract IDs that contain colons.

### Fix C (Defense-in-depth): Robust ID parsing in pull.ts

Replace the naive `split(":")[0]` / `split(":")[1]` with logic that handles the actual ID format. However, Fix A makes this unnecessary since the record path is always available.

If desired, the fallback could use a known separator like `::`:
```ts
const parts = change.id.split("::");
const from = change.record?.from || parts[0];
const to = change.record?.to || parts[1];
```

But Fix A is the correct solution — the record should always carry the from/to.

## Notes

- The `relate` path is not affected in practice because the delta includes `record: { from, to }` — the `change.record?.from` path in pull.ts works correctly. Only `unrelate` sets `record: null`.
- The double-colon `::` in `extractJoinDeltas` appears to have been an intentional attempt to avoid ambiguity with IDs that contain colons, but the pull parsing was not updated to match this convention.
- Fix A is minimal (one line change — `record: null` → `record: { from, to }`) and fully resolves the issue without changing any other code paths.
- The composite ID separator inconsistency (`:` vs `::`) is a secondary concern — Fix B is optional cleanup. The real problem is the missing from/to on the delete delta.
