## Summary

The datafn server currently uses the main database adapter for all operations, including `serverSeq` tracking. This creates performance bottlenecks under high concurrency due to compare-and-swap retry loops and multiple database round trips per mutation. The server should support optional secondary databases (Redis for atomic increments, KV stores for simple key-value operations) that can be configured via a database mapping system. When a secondary database is configured for `serverSeq`, it should be used instead of the main database, with automatic fallback to the main database if the secondary database is unavailable. This requires extending `DatafnServerConfig` to accept `redis` and `kvStore` adapters, creating a database mapping configuration system, updating `ChangeTrackingService` to support pluggable sequence stores, and potentially creating adapter interfaces similar to `@superfunctions/db` for Redis/KV store abstraction. This is a **Medium** severity enhancement that improves performance and scalability, especially under high concurrency workloads.

## Observed Errors/Symptoms

1. **Performance Bottleneck**: `serverSeq` tracking uses compare-and-swap retry loops (up to 10 retries) in the main database, causing latency and contention under high concurrency.

2. **No Secondary Database Support**: The server cannot use specialized databases (Redis for atomic increments, KV stores for simple operations) even when they would be more appropriate.

3. **No Database Mapping Configuration**: There's no way to specify which database should be used for which feature (serverSeq, rate limiting, caching, etc.).

4. **Tight Coupling**: `ChangeTrackingService` is hardcoded to use the main `Adapter` interface, preventing use of specialized sequence stores.

5. **Missing Adapter Abstraction**: While `KVStoreAdapter` exists in `@superfunctions/db`, there's no unified adapter pattern for Redis-like stores that supports different implementations (Redis, Valkey, etc.).

6. **No Fallback Strategy**: If a secondary database fails, there's no automatic fallback to the main database.

```typescript
export class ChangeTrackingService {
  private sequenceStore: SequenceStore;

  constructor(
    private db: Adapter,
    private namespace: string = "datafn",
    sequenceStore?: SequenceStore,  // Optional sequence store
    private onChange?: (seq: number) => void,
  ) {
    // Use provided sequence store, or create database-based fallback
    this.sequenceStore = sequenceStore || new DatabaseSequenceStore(db);
  }

  async getNextServerSeq(): Promise<number> {
    try {
      return await this.sequenceStore.getNext(this.namespace);
    } catch (error) {
      // If sequence store fails and it's not the database fallback, try database fallback
      if (!(this.sequenceStore instanceof DatabaseSequenceStore)) {
        console.warn("Sequence store failed, falling back to database:", error);
        const dbStore = new DatabaseSequenceStore(this.db);
        return await dbStore.getNext(this.namespace);
      }
      // Re-throw if database fallback also fails
      throw error;
```

  - Better concurrency handling under high load
  - Reduced load on main database

- **Fallback Strategy**: The fallback mechanism ensures reliability - if Redis/KV store fails, the system automatically uses the main database. This provides resilience without requiring perfect secondary database availability.

- **Future Extensibility**: The `dbMapping` configuration allows easy extension for future features:
  - Rate limiting can use Redis or KV store
  - Caching can use Redis
  - Session storage can use Redis or KV store
  - Each feature can be independently configured

- **Backward Compatibility**: All secondary database configurations are optional. Existing code without `redis`, `kvStore`, or `dbMapping` continues to work exactly as before, using the main database for all operations.

- **Testing Strategy**: Test with:
  1. Redis configured and available
  2. Redis configured but unavailable (fallback)
  3. KV store configured with `incr` support
  4. KV store configured without `incr` support (fallback)
  5. No secondary databases (uses main database)
  6. Concurrent mutations to verify atomicity and performance

- **Multi-Tenant Considerations**: When implementing sequence stores, ensure they correctly handle namespace isolation. Redis keys should be namespaced (e.g., `serverSeq:tenant:acme:user:alice`), and KV store keys should follow the same pattern.

- **Operational Considerations**: 
  - Redis should be configured with persistence (AOF/RDB) to avoid sequence loss
  - Consider Redis replication for high availability
  - Monitor Redis health and capacity
  - Have alerting for secondary database failures

- **Migration Path**: For existing deployments:
  1. Deploy with secondary databases optional (backward compatible)
  2. Configure Redis/KV store in new deployments
  3. Existing data in main database remains accessible
  4. No migration needed - sequences can coexist in different stores per namespace
