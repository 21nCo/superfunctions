## Summary

The DataFn documentation for SPV2 (Sharing Protocol Version 2) is **structurally present** — four dedicated pages exist and are correctly wired into sidebar navigation — but **substantively incomplete**. Five of seven `shareable` capability schema fields are entirely undocumented, the DFQL mutations reference still shows the deprecated `userId` field instead of the canonical `principalId`, SPV2-specific error codes are absent from the error reference, and several production-critical concepts (global permissions table schema, principal hierarchy configuration, actor feed) have no documentation at all. Severity: **Medium** — the implementation is correct and passing audits, but developers cannot discover or correctly configure SPV2 features from documentation alone.

## Observed Symptoms

1. A developer reading `capabilities.mdx` sees only `levels` and `default` for the `shareable` capability — no way to discover `visibilityDefault`, `supportsScopeGrants`, `crossNsShareable`, `principalMode`, or `relationInheritance`.
2. A developer reading `mutations.mdx` will use `shareWith.userId` (line 28, lines 140-158) — the deprecated field — because the reference docs show only that form.
3. SPV2 error codes `DFQL_SHARE_SCOPE_INVALID` and `DFQL_PRINCIPAL_INVALID` are not in the error reference; developers cannot handle or debug these errors.
4. No documentation explains how to configure principal hierarchies/memberships or how hierarchy resolution works at runtime.

## Root Causes

### RC-1: `capabilities.mdx` omits 5 of 7 shareable fields

**Location:** `datafn/docs/content/docs/documentation/concepts/capabilities.mdx`, lines 62-70

**Current documentation shows:**
```typescript
shareable: {
  levels: ["viewer", "editor", "owner"],
  default: "private",
}
```

**Actual type definition** (`datafn/core/src/capabilities.ts`, lines 17-29):
```typescript
shareable: {
  levels: AccessLevel[];
  default?: "private" | "shared";
  visibilityDefault?: "ns" | "private" | "shared";
  supportsScopeGrants?: boolean;
  crossNsShareable?: boolean;
  principalMode?: "opaque-id";
  relationInheritance?: { enabled: boolean; relations?: string[]; requireRelateConsent?: boolean };
}
```

**Impact:** Developers cannot configure scope grants, cross-namespace sharing, principal modes, or relation inheritance because these fields are invisible in docs. Defaults are applied silently by `parseShareableCapability()` (schema.ts lines 530-607) but never explained.

---

### RC-2: `mutations.mdx` shows deprecated `userId` instead of canonical `principalId`

**Location:** `datafn/docs/content/docs/dfql/mutations.mdx`, line 28 (type definition) and lines 140-158 (examples)

**Current documentation shows:**
```typescript
shareWith?: { userId: string; level?: string };
```
```json
{ "shareWith": { "userId": "user:alice", "level": "editor" } }
```

**Actual server contract** (`datafn/server/src/execution/mutation/share.ts`, lines 208-223):
```typescript
shareWith?: { principalId?: string; userId?: string; level?: string };
```

The server accepts both but logs deprecation warnings for `userId` (share.ts lines 280-282, 471-474). The canonical field is `principalId`. The client's new API signature (`table.ts` lines 33-44) uses `principalId` exclusively.

**Impact:** New code written from docs will use the deprecated path, triggering deprecation warnings and requiring future migration.

---

### RC-3: `mutations.mdx` does not document `scope` field or scope grants

**Location:** `datafn/docs/content/docs/dfql/mutations.mdx`, lines 140-158

**Missing from docs:** The `scope` field (`"record"` | `"resource"`) that enables namespace-wide scope grants. The new mutation builders (`client/src/mutate.ts`, lines 94-139) emit `scope` and conditionally include `id`, but the DFQL reference has no mention of scope grants.

**Impact:** Developers cannot discover scope-level sharing (share an entire resource namespace with a principal) from the mutations reference.

---

### RC-4: SPV2 error codes missing from error reference

**Location:** `datafn/docs/content/docs/reference/core/errors.mdx`

**Missing error codes:**
- `DFQL_SHARE_SCOPE_INVALID` — returned when scope grants are attempted on a capability with `supportsScopeGrants: false`
- `DFQL_PRINCIPAL_INVALID` — returned when principal format validation fails

These are thrown by the share mutation handler (share.ts) but only `FORBIDDEN` appears in the error docs.

**Impact:** Developers cannot write proper error handling for SPV2-specific failure modes.

---

### RC-5: No documentation for principal hierarchy/membership configuration

**Location:** No doc page exists for this topic.

**What exists in code:**
- `__datafn_principal_memberships` table (generated by `cli/src/drizzle-codegen.ts`)
- `__datafn_principal_hierarchy` table (generated by `cli/src/drizzle-codegen.ts`)
- `resolveEffectivePrincipals()` with hierarchy walk, caching, cycle detection, max depth 16 (`server/src/execution/auth/principal-resolver.ts`)

**What's documented:** Only the principal format convention (`user:alice`, `team:eng`, `org:acme`) is implied from examples in `sharing-v2.mdx`. No documentation explains:
- How to populate membership/hierarchy tables
- How hierarchy resolution works (depth limits, cycle detection, caching)
- How transitive group memberships affect access resolution

**Impact:** Developers have no guidance on setting up multi-level principal hierarchies, which is a core SPV2 feature.

---

### RC-6: No documentation for global permissions table schema

**Location:** `capabilities.mdx` line 127 mentions `__datafn_permissions_{resource}` but not the global table.

**What exists in code:** `__datafn_permissions_global` table with columns for `principalId`, `resourceNs`, `resourceId`, `level`, `grantKind`, `grantedBy`, `grantedAt`, plus 10+ indexes (generated by `cli/src/drizzle-codegen.ts`).

**Impact:** Developers building custom queries, admin dashboards, or debugging permission issues have no schema reference.

---

### RC-7: Actor feed concept undocumented in sync lifecycle

**Location:** `datafn/docs/content/docs/documentation/sync/sharing-sync-lifecycle.mdx`

The sync lifecycle doc covers tombstones and backfill with sequence diagrams but does not document:
- `buildActorFeedEffects()` — how permission/membership/hierarchy changes appear in actor-visible pull streams
- `mergeCanonicalChangeStreamsBounded()` — the bounded k-way merge for memory-safe pull assembly
- How `affectedPrincipals` propagates through WebSocket invalidation

**Impact:** Developers building offline-first apps with sharing cannot understand how permission changes propagate to connected clients.

---

### RC-8: `getPermissions` client method uses `userId` in return type

**Location:** `datafn/docs/content/docs/documentation/client/tables.mdx`, lines 39-44

The documented return type shows `userId` field, but the SPV2 canonical field is `principalId`. This should be updated or documented as legacy.

**Impact:** Minor inconsistency with the principalId-first approach of SPV2.

## Proposed Fixes

### Fix 1: Update `capabilities.mdx` shareable section
- Add a full reference table for all 7 shareable fields with types, defaults, and descriptions
- Show a complete example with all SPV2 fields configured
- Document each field's effect on runtime behavior

### Fix 2: Update `mutations.mdx` share/unshare section
- Change type definition to show `principalId` as primary, `userId` as deprecated
- Add `scope` field to the type definition and explain `"record"` vs `"resource"`
- Update all examples to use `principalId`
- Add a deprecation note for `userId` with migration guidance

### Fix 3: Add SPV2 error codes to error reference
- Add `DFQL_SHARE_SCOPE_INVALID` with description and when it's thrown
- Add `DFQL_PRINCIPAL_INVALID` with description and when it's thrown

### Fix 4: Add principal hierarchy documentation
- New section in `sharing-v2.mdx` or dedicated page covering:
  - Membership table structure and how to populate it
  - Hierarchy resolution algorithm (depth limit, cycle detection)
  - Caching behavior and invalidation
  - Examples: user → team → org hierarchy

### Fix 5: Document global permissions table schema
- Add schema reference (columns, constraints, indexes) to `sharing-v2.mdx`
- Explain `grantKind` values (`"record"`, `"scope"`)

### Fix 6: Expand sync lifecycle documentation
- Add actor feed section explaining how permission changes enter pull streams
- Document bounded k-way merge behavior
- Document WebSocket principal-targeted invalidation

### Fix 7: Update `tables.mdx` getPermissions return type
- Update return type to show `principalId` field
- Note legacy `userId` field for backward compatibility
