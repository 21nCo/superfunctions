## Summary

The current IndexedDB adapter implementation uses a single "records" store for all resources and a single "join_rows" store for all many-to-many relations. This design causes O(n) full table scans for one-to-many inverse queries, many-to-many inverse queries, and queries filtering by schema-indexed fields. With 100K+ records, these queries become prohibitively slow. The proposed solution is to implement per-resource stores (one store per resource), add foreign key indices for many-one/one-many relations, and create separate join stores per many-to-many relation (similar to SQL join tables) with bidirectional indices. This will optimize all relation queries to O(log n) or O(1), enabling efficient handling of large datasets. This is a **High** severity performance issue that limits scalability.

## Observed Errors/Symptoms

1. **Performance Degradation with Scale**: One-to-many inverse queries (e.g., "get goal with all tasks") perform O(n) full table scans, causing significant slowdowns with 100K+ records.

2. **Many-to-Many Inverse Queries Slow**: Inverse many-to-many queries (e.g., "get property with all nodes that have it") require full relation scans and in-memory filtering, resulting in O(n) performance.

3. **Schema Indices Ignored**: Schema-defined indices (e.g., `indices.base: ["createdAt"]`) are not used to create IndexedDB indices, causing all filtered queries to perform full table scans.

4. **No Foreign Key Indices**: Foreign key fields (e.g., `goalId`, `parentId`) don't have IndexedDB indices, forcing O(n) scans for one-to-many inverse queries.

5. **Single Join Store Limitation**: All many-to-many relations share one "join_rows" store, making inverse queries inefficient (must scan all join rows and filter).

## Root Causes

### Issue 1: Single "records" Store for All Resources

**Location**: `client/src/adapters/indexedDbStorage.ts:61-68`

**Current Implementation**:
```typescript
// Records store: Key [resource, id]
// This effectively groups by resource and allows range queries
if (!db.objectStoreNames.contains("records")) {
  const store = db.createObjectStore("records", {
    keyPath: ["resource", "id"],
  });
  store.createIndex("by_resource", "resource", { unique: false });
}
```

**Expected Behavior**: Each resource should have its own object store (e.g., "node", "goal", "task") with resource-specific indices for optimal query performance.

**Actual Behavior**: All resources share a single "records" store with composite key `[resource, id]`. While this enables resource-based queries via key ranges, it prevents resource-specific indexing strategies and requires full table scans for filtered queries.

**Impact**: 
- Cannot create resource-specific indices (e.g., `by_status` on task store)
- All filtered queries must scan entire resource subset
- Schema-defined indices are ignored
- Foreign key indices cannot be created per resource

**Evidence**: 
- Code comment at line 61-62 explains design choice but acknowledges limitation
- `findRecords()` method (lines 263-278) falls back to full scan for any field other than "id"
- No code reads schema to create resource-specific indices

## Proposed Fixes

### Fix 1: Implement Per-Resource Stores

**File**: `client/src/adapters/indexedDbStorage.ts`

**Changes Required**:

1. **Modify `onupgradeneeded` handler** to create one store per resource:
   ```typescript
   request.onupgradeneeded = (event) => {
     const db = request.result;
     const schema = /* get from adapter config or constructor */;
     
     // Create one store per resource
     for (const resource of schema.resources) {
       if (!db.objectStoreNames.contains(resource.name)) {
         const store = db.createObjectStore(resource.name, {
           keyPath: "id",  // Simple key, no composite
         });
         
         // Create indices from schema
         if (resource.indices?.base) {
           for (const field of resource.indices.base) {
             store.createIndex(`by_${field}`, field, { unique: false });
           }
         }
       }
     }
   };
   ```

2. **Update `getRecord()` method**:
   ```typescript
   async getRecord(resource: string, id: string): Promise<Record<string, unknown> | null> {
     this.validateTableName(resource);
     const store = await this.getStore(resource, "readonly");  // Use resource name as store name
     return new Promise((resolve, reject) => {
       const request = store.get(id);  // Simple key lookup
       request.onsuccess = () => resolve(request.result || null);
       request.onerror = () => reject(request.error);
     });
   }
   ```

3. **Update `listRecords()` method**:
   ```typescript
   async listRecords(resource: string): Promise<Record<string, unknown>[]> {
     this.validateTableName(resource);
     const store = await this.getStore(resource, "readonly");
     return new Promise((resolve, reject) => {
       const request = store.getAll();  // Get all from resource-specific store
       request.onsuccess = () => resolve(request.result || []);
       request.onerror = () => reject(request.error);
     });
   }
   ```

4. **Update `upsertRecord()` and `deleteRecord()`** similarly to use resource name as store name.

**Migration Path**: Need to handle database version upgrade:
```typescript
const DB_VERSION = 2;  // Increment version

request.onupgradeneeded = (event) => {
  const db = request.result;
  const oldVersion = event.oldVersion;
  
  if (oldVersion < 2) {
    // Migration from single "records" store to per-resource stores
    const oldStore = event.transaction.objectStore("records");
    const allRecords = await oldStore.getAll();
    
    // Group by resource
    const byResource = {};
    for (const record of allRecords) {
      const resource = record.resource;
      if (!byResource[resource]) byResource[resource] = [];
      // Remove "resource" field from record
      const { resource: _, ...cleanRecord } = record;
      byResource[resource].push(cleanRecord);
    }
    
    // Create new stores and migrate data
    for (const [resource, records] of Object.entries(byResource)) {
      const newStore = db.createObjectStore(resource, { keyPath: "id" });
      for (const record of records) {
        await newStore.put(record);
      }
    }
    
    // Delete old store
    db.deleteObjectStore("records");
  }
};
```

### Fix 2: Add Foreign Key Indices

**File**: `client/src/adapters/indexedDbStorage.ts`

**Changes Required**:

1. **Analyze schema relations** to identify foreign key fields:
   ```typescript
   function getForeignKeyFields(schema: DatafnSchema): Map<string, string[]> {
     const fkFields = new Map<string, string[]>();
     
     for (const relation of schema.relations || []) {
       if (relation.type === "many-one" || relation.type === "one-many") {
         const fkField = relation.fkField || 
           (relation.type === "many-one" 
             ? `${relation.relation}Id` 
             : `${relation.inverse || relation.from}Id`);
         
         const targetResource = relation.type === "many-one" 
           ? (relation.to as string)
           : (relation.from as string);
         
         if (!fkFields.has(targetResource)) {
           fkFields.set(targetResource, []);
         }
         fkFields.get(targetResource)!.push(fkField);
       }
     }
     
     return fkFields;
   }
   ```

2. **Create FK indices in `onupgradeneeded`**:
   ```typescript
   request.onupgradeneeded = (event) => {
     const db = request.result;
     const schema = /* get schema */;
     const fkFields = getForeignKeyFields(schema);
     
     for (const resource of schema.resources) {
       const store = db.createObjectStore(resource.name, { keyPath: "id" });
       
       // Add FK indices
       const resourceFks = fkFields.get(resource.name) || [];
       for (const fkField of resourceFks) {
         store.createIndex(`by_${fkField}`, fkField, { unique: false });
       }
       
       // Add schema indices
       if (resource.indices?.base) {
         for (const field of resource.indices.base) {
           store.createIndex(`by_${field}`, field, { unique: false });
         }
       }
     }
   };
   ```

3. **Update `findRecords()` to use indices**:
   ```typescript
   async findRecords(
     resource: string,
     field: string,
     value: unknown,
   ): Promise<Record<string, unknown>[]> {
     this.validateTableName(resource);
     const store = await this.getStore(resource, "readonly");
     
     // Check if index exists for this field
     if (store.indexNames.contains(`by_${field}`)) {
       const index = store.index(`by_${field}`);
       return new Promise((resolve, reject) => {
         const request = index.getAll(value);  // O(log n) index lookup
         request.onsuccess = () => resolve(request.result || []);
         request.onerror = () => reject(request.error);
       });
     }
     
     // Fallback to full scan if no index (shouldn't happen for FK fields)
     const all = await this.listRecords(resource);
     return all.filter((r) => r[field] === value);
   }
   ```

**Performance Improvement**: One-to-many inverse queries become O(log n) instead of O(n).

### Fix 3: Implement Separate Join Stores per Many-to-Many Relation

**File**: `client/src/adapters/indexedDbStorage.ts`

**Changes Required**:

1. **Generate join store names** for all relation combinations:
   ```typescript
   function generateJoinStoreNames(schema: DatafnSchema): string[] {
     const storeNames: string[] = [];
     
     for (const relation of schema.relations || []) {
       if (relation.type === "many-many") {
         const fromResources = Array.isArray(relation.from) 
           ? relation.from 
           : [relation.from];
         const toResources = Array.isArray(relation.to) 
           ? relation.to 
           : [relation.to];
         
         // Create store for each combination
         for (const fromRes of fromResources) {
           for (const toRes of toResources) {
             const storeName = `join_${fromRes}_${toRes}`;
             storeNames.push(storeName);
           }
         }
       }
     }
     
     return storeNames;
   }
   ```

2. **Create join stores in `onupgradeneeded`**:
   ```typescript
   request.onupgradeneeded = (event) => {
     const db = request.result;
     const schema = /* get schema */;
     const joinStoreNames = generateJoinStoreNames(schema);
     
     for (const storeName of joinStoreNames) {
       if (!db.objectStoreNames.contains(storeName)) {
         const store = db.createObjectStore(storeName, {
           keyPath: ["from", "to"],  // Composite key
         });
         
         // Bidirectional indices for efficient forward and inverse queries
         store.createIndex("by_from", "from", { unique: false });
         store.createIndex("by_to", "to", { unique: false });
         
         // Add metadata indices if specified in relation
         const relation = /* find relation for this store */;
         if (relation.indices) {
   ```

## Notes

- **Database Version**: Must increment `DB_VERSION` from 1 to 2 (or higher) to trigger `onupgradeneeded` for existing databases.

- **Schema Dependency**: Adapter constructor needs to accept `DatafnSchema` parameter to create appropriate stores and indices. Consider passing schema from client initialization.

- **Migration Complexity**: Migration from single "records" store to per-resource stores requires:
  1. Reading all records from old store
  2. Grouping by resource
  3. Creating new stores
  4. Writing records to new stores
  5. Deleting old store
  This should be done atomically in a single transaction if possible.

- **Store Count**: With complex schemas (like `table-schema-sample.json`), total store count could be 30-50 stores. IndexedDB typically supports 100+ stores, so this is acceptable, but should be documented.

- **IndexedDB Limitations**: 
  - IndexedDB has limits on index count per store (typically 100+)
  - Index size limits exist but are usually generous
  - Composite indices are supported but more complex

- **Polymorphic Relation Performance**: Querying multiple stores for polymorphic relations (e.g., 16 stores for `links`) adds overhead, but each query is O(log n), so total is still O(log n) per store type. Consider batching or parallel queries.

- **Testing Strategy**: 
  - Use `fake-indexeddb` for unit tests
  - Create performance benchmarks with 10K, 50K, 100K records
  - Test migration path with real data structures
  - Verify DevTools shows indices are being used

- **Backward Compatibility Window**: Consider supporting both old and new formats during a transition period, or provide a clear migration path for users.

- **Implementation Phases**: Consider implementing in phases:
  1. Phase 1: Per-resource stores + migration
  2. Phase 2: FK indices
  3. Phase 3: Separate join stores
  4. Phase 4: Schema indices
  5. Phase 5: Polymorphic routing

This allows incremental testing and reduces risk.
