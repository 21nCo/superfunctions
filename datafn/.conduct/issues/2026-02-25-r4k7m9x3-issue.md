## Summary

**Severity: Critical/High** — Breaks all sync (pull and push) for any schema with many-many relations.

The `IndexedDbStorageAdapter.create()` method builds a `validResources` allowlist from `schema.resources[].name` only. It does not include join store keys (e.g., `join_todos_tags_categories`) that are derived from `schema.relations`. When the `SyncEngine` attempts to read or write cursors for join stores during `pullNow()` or `processPush()`, the storage adapter's `validateTableName()` guard throws `"Unknown table: join_todos_tags_categories"`, causing the entire sync operation to abort. This means **no pull or push HTTP calls are ever made** to the server for any app that uses many-many relations.

## Observed Errors/Symptoms

1. **No `/datafn/pull` network request** is ever observed in the browser network tab
2. **Repeated `sync_failed` events** emitted by the client event bus
3. **Console error**: `Error: Unknown table: join_todos_tags_categories` thrown from `IndexedDbStorageAdapter.validateTableName`
4. **Push also fails** with the same error — `processPush` calls `setCursorMonotonically` which calls `getCursor` on the join store key
5. The `sync_applied` event for clone does fire (clone succeeds because it doesn't call `getCursor` with join store keys in the same path), but all subsequent pull/push operations fail

## Root Causes

### Root Cause 1: `IndexedDbStorageAdapter.create()` does not register join store keys in `validResources`

**Location:** `client/src/adapters/indexedDbStorage.ts:84-93`

**Current code:**
```typescript
static create(options: {
  dbName: string;
  schema: DatafnSchema;
}): IndexedDbStorageAdapter {
  const resources = options.schema.resources.map((r) => r.name);
  // Ensure built-in KV resource is always valid (KV-001)
  if (!resources.includes(KV_RESOURCE_NAME)) {
    resources.push(KV_RESOURCE_NAME);
  }
  return new IndexedDbStorageAdapter(options.dbName, resources, options.schema);
}
```

**Expected behavior:** The `resources` array (which becomes `validResources` in the constructor) should include join store keys derived from `schema.relations` (e.g., `join_todos_tags_categories` for a `todos ↔ categories` many-many relation via `tags`). These keys are legitimate store identifiers used by the sync engine for cursor tracking.

**Actual behavior:** Only `schema.resources[].name` values (e.g., `"todos"`, `"categories"`) and `"_kv"` are registered. Join store keys like `"join_todos_tags_categories"` are absent.

**Impact:** Any call to `getCursor(joinStoreKey)`, `setCursor(joinStoreKey, ...)`, or `upsertJoinRow(joinStoreKey, ...)` that passes through `validateTableName()` will throw, aborting the entire sync operation.

**Evidence — the validation guard that throws:**
```typescript
// client/src/adapters/indexedDbStorage.ts:349-353
private validateTableName(table: string) {
  if (this.validResources && !this.validResources.has(table)) {
    throw new Error(`Unknown table: ${table}`);
  }
}
```

### Root Cause 2: `SyncEngine.pullNow()` iterates join store keys through `getCursor()` which hits the guard

**Location:** `client/src/sync/engine.ts:604-608`

**Current code:**
```typescript
// Add join store cursors for many-many relations
if (this.schema.relations) {
  for (const joinStoreKey of enumerateJoinStoreKeys(this.schema.relations)) {
    cursors[joinStoreKey] = await this.storage.getCursor(joinStoreKey) || "0";
  }
}
```

**Expected behavior:** `storage.getCursor("join_todos_tags_categories")` should return a cursor string or null.

**Actual behavior:** `getCursor` calls `validateTableName("join_todos_tags_categories")` which throws `"Unknown table: join_todos_tags_categories"`. The error is caught by `pullNow()`'s catch block (engine.ts:622-636), which emits `sync_failed` and returns — **the pull HTTP request is never made**.

### Root Cause 3: `SyncEngine.processPush()` also crashes on join cursor via `setCursorMonotonically`

**Location:** `client/src/sync/engine.ts:958` → `client/src/sync/apply.ts:259`

**Stack trace from console:**
```
at setCursorMonotonically (apply.ts:259:40)
at SyncEngine.processPush (engine.ts:958:19)
```

The push flow also attempts to update join store cursors after a successful push response. The same `validateTableName` guard blocks this, causing push to fail with `sync_failed` as well.

## Proposed Fixes

### Fix 1: Register join store keys in `IndexedDbStorageAdapter.create()`

In `client/src/adapters/indexedDbStorage.ts`, the `create()` method should derive join store keys from `schema.relations` and add them to the `resources` array:

```typescript
static create(options: {
  dbName: string;
  schema: DatafnSchema;
}): IndexedDbStorageAdapter {
  const resources = options.schema.resources.map((r) => r.name);
  if (!resources.includes(KV_RESOURCE_NAME)) {
    resources.push(KV_RESOURCE_NAME);
  }
  // Register join store keys for many-many relations
  if (options.schema.relations) {
    for (const rel of options.schema.relations) {
      if (rel.type === "many-many" && rel.relation) {
        const joinStoreKey = getJoinStoreKey(
          rel.from as string,
          rel.relation,
          rel.to as string,
        );
        if (!resources.includes(joinStoreKey)) {
          resources.push(joinStoreKey);
        }
      }
    }
  }
  return new IndexedDbStorageAdapter(options.dbName, resources, options.schema);
}
```

The same fix should also be applied to `createForUser()` and any other factory method that derives `validResources` from the schema.

### Fix 2 (alternative): Relax `validateTableName` for join store keys

Instead of (or in addition to) adding join keys to `validResources`, the validation could be relaxed to allow keys matching the `join_*` pattern. However, Fix 1 is more precise and safer.

## Notes

- This is a **regression** introduced when the `validResources` validation was added to `IndexedDbStorageAdapter`. The validation was correctly applied for resource stores and the built-in `_kv` store, but join store keys (a third category of logical store names) were overlooked.
- The initial clone operation succeeds because `applyCloneResult` accesses join stores via `upsertJoinRow()` which uses the IndexedDB object store name directly (the store IS created by the IDB schema setup), but the validation in `getCursor`/`setCursor` rejects the join store key because it's not in `validResources`.
- This only affects schemas with `many-many` relations. Schemas with only `one-many` or `many-one` relations (which don't use join tables) are unaffected.
- The `sync_failed` events are silent failures — no error is surfaced to the user unless they inspect the console, making this particularly hard to diagnose.
