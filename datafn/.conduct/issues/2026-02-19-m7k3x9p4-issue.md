## Summary

**Severity: High** — Three interrelated bugs cause sync operations to fail or silently lose data when using the Drizzle adapter with a real database (Postgres/MySQL/SQLite). The built-in `kv` resource has no Drizzle table, join table naming is inconsistent across four server subsystems, and clone/reconcile blindly iterate over all schema resources including built-ins. These issues affect every DataFn deployment that uses sync with a Drizzle-backed database.

## Observed Errors / Symptoms

### Symptom 1: Push crashes for KV mutations

```
Push operation failed [replace] for resource "kv", id "kv:pref:theme": Error: Drizzle adapter: no table mapping for model "kv" (resolved to "kv").
Available tables: __datafn_join_todos_tags, categories, todos
Did you forget to include this library's schema when calling drizzle()?
    at resolveTable (/packages/db/dist/adapters/drizzle/index.js:106:23)
    at Object.findOne (/packages/db/dist/adapters/drizzle/index.js:151:29)
```

### Symptom 2: Join data silently dropped during clone/pull

Clone and pull return empty join records because they query under the `join_` prefix naming pattern, while the actual database table uses the `__datafn_join_` prefix. The `try/catch` in `clone.ts:218-220` swallows the error.

### Symptom 3: Clone tries to query non-existent `kv` table

When no explicit `tables` filter is provided, clone iterates all `schema.resources` including the runtime-injected `kv`, attempts `db.findMany({ model: "kv" })`, fails, and silently returns empty data for KV.

## Root Causes

### Root Cause 1: Drizzle codegen does not emit the built-in `kv` table

**Location**: `datafn/cli/src/drizzle-codegen.ts:30-34`

**Current code**:
```typescript
const resources = [...schema.resources].sort((a, b) =>
  a.name.localeCompare(b.name),
);

for (const resource of resources) {
```

**Expected behavior**: The codegen should also emit a `kv` table with columns `id` (text, primary key) and `value` (jsonb/text depending on dialect), matching the `kv` resource definition from `ensureBuiltinKv()`.

**Actual behavior**: The codegen only processes resources from the input schema (user-defined). The `kv` resource is added at runtime by `ensureBuiltinKv()` in both `client.ts:356` and `server.ts:169`, but the codegen runs against the raw schema before this augmentation. No `kv` table is generated, and no migration creates it.

**Impact**: Every push/mutation/query/clone/reconcile targeting the `kv` model crashes with `"no table mapping for model kv"` when using the Drizzle adapter.

**Evidence**: The generated schema at `datafn/examples/todo-app/server/src/datafn-schema.drizzle.ts` contains only `categories`, `todos`, and `__datafn_join_todos_tags`. The server's `validatedSchema` (after `ensureBuiltinKv()`) includes `kv`, but the Drizzle instance's `fullSchema` does not.

**Origin**: Introduced in **`2026-02-15-change-m8k3x7p4-spec` Phase 01** when `generateDrizzleSchema()` was implemented. The spec and phase definition did not mention built-in resources. The `ensureBuiltinKv()` function had been introduced earlier in **`2026-02-06-audit-fix-k4m2p9x7-spec` Phase 02** but codegen was not aware of it.

### Root Cause 2: Join table naming mismatch across four subsystems

**Locations**:

| Subsystem | File | Line | Pattern | Example (todo app) |
|---|---|---|---|---|
| Server mutations | `datafn/server/src/execution/mutation/relations.ts` | 142 | `__datafn_join_${mutation.resource}_${relName}` | `__datafn_join_todos_tags` |
| Codegen | `datafn/cli/src/drizzle-codegen.ts` | 297-302 | `__datafn_join_${from}_${relation}` | `__datafn_join_todos_tags` |
| Push change tracking | `datafn/server/src/execution/sync/push.ts` | 136 | `join_${mutation.resource}_${relName}_${relation.to}` | `join_todos_tags_categories` |
| Clone / Pull / Reconcile | `datafn/server/src/execution/sync/clone.ts` | 205 | `join_${relation.from}_${relation.relation}_${relation.to}` | `join_todos_tags_categories` |
| Client sync engine | `datafn/client/src/sync/engine.ts` | 671 | `join_${relation.from}_${relation.relation}_${relation.to}` | `join_todos_tags_categories` |

**Expected behavior**: All subsystems should use a single canonical join table name that matches what exists in the database.

**Actual behavior**: Two incompatible naming conventions coexist:
- **DB-side** (mutations + codegen): `__datafn_join_todos_tags` — this is the actual table in the database
- **Sync-side** (push change tracking + clone + pull + reconcile + client): `join_todos_tags_categories` — this is what change tracking records and what clone/pull query

**Impact**:
1. Change tracking records changes under `join_todos_tags_categories` but the actual DB write happens to `__datafn_join_todos_tags`. Pull queries for changes under the wrong resource name.
2. Clone tries `db.findMany({ model: "join_todos_tags_categories" })` which doesn't exist in Drizzle — silently returns empty (caught at `clone.ts:219`).
3. Reconcile counts are wrong for join tables.
4. Client reconcile drift detection compares against the wrong join store names.

**Origin timeline**:
- **2026-02-07** (`2026-02-06-audit-fix-k4m2p9x7-spec` Phase 04): `extractJoinDeltas()` introduced in `push.ts` with `join_${resource}_${relName}_${relation.to}` pattern, matching client join store naming.
- **2026-02-13** (`2026-02-12-fix-r8k4m2x9-spec` Phase 03): `relations.ts` mutation execution introduced with `__datafn_join_${resource}_${relName}` pattern (no `_${to}` suffix, has `__datafn_` prefix).
- **2026-02-15** (`2026-02-15-change-m8k3x7p4-spec` Phase 01): Codegen `getJoinTableName()` uses `__datafn_join_${from}_${relation}` — matches mutations but not change tracking.
- **2026-02-15** (`2026-02-15-change-m8k3x7p4-spec` Phase 03): `relations.ts` refactored to use unified adapter CRUD, keeping `__datafn_join_` prefix.

The split happened because change tracking (Phase 04, Feb 7) was implemented before the join table refactor (Phase 03, Feb 13-15), and the refactor didn't update change tracking or clone/pull to use the new `__datafn_join_` convention.

### Root Cause 3: Clone and reconcile include built-in `kv` resource without filtering

**Location**: `datafn/server/src/execution/sync/clone.ts:64`

**Current code**:
```typescript
const tablesToClone = request.tables || schema.resources.map((r) => r.name);
```

**Also at**: `datafn/server/src/execution/sync/reconcile.ts:69-81` (validates requested resources against `schema.resources` which includes `kv`)

**Expected behavior**: Clone/reconcile should either (a) have the `kv` table available in the database, or (b) filter out built-in resources that may not have backing tables, or (c) handle missing tables gracefully per-resource.

**Actual behavior**: Clone iterates all resources from `validatedSchema` (which includes `kv` from `ensureBuiltinKv()`). For each resource it calls `db.findMany({ model: tableName })`. For `kv`, this throws in the Drizzle adapter. The error is caught at `clone.ts:188-192` and the resource returns `[]` — data is silently lost.

**Impact**: KV records that were successfully pushed to the server (if Issue 1 is fixed) will never appear in clone results. Reconcile counts for `kv` will always be 0, causing perpetual drift detection.

**Origin**: Clone was implemented in **`2026-02-06-audit-fix-k4m2p9x7-spec` Phase 06** and reconcile in **Phase 07**, both on 2026-02-07. `ensureBuiltinKv()` was added in **Phase 02** of the same spec. The Phase 06/07 implementations didn't account for runtime-injected resources not having backing DB tables.

### Root Cause 4 (Low): `coerceDateFields` silently ignores unknown resources

**Location**: `datafn/server/src/execution/sync/push.ts:62-64`

**Current code**:
```typescript
const resourceDef = schema.resources.find((r) => r.name === resource);
if (!resourceDef || !resourceDef.fields) {
  return data;  // Silent no-op
}
```

**Expected behavior**: If a resource isn't found in the schema, this should either handle it gracefully with a warning or it shouldn't happen at all (upstream validation should catch it).

**Actual behavior**: Returns uncoerced data silently. Not currently exploitable since `ensureBuiltinKv()` adds `kv` to the schema, but represents a latent fragility — if schema augmentation order changes, date coercion would silently stop working.

**Impact**: Low. No current breakage, but a defensive concern.

## Proposed Fixes

### Fix 1: Codegen should emit `kv` table

In `generateDrizzleSchema()`, apply `ensureBuiltinKv()` to the schema before iterating resources, or explicitly append the `kv` table definition. The `kv` table needs:
- `id`: text, primary key
- `value`: jsonb (postgres), json (mysql), text (sqlite)

### Fix 2: Unify join table naming to a single canonical pattern

Choose one convention and apply it everywhere. The database-side pattern `__datafn_join_${from}_${relation}` already exists in migrations and codegen. All of these must be updated to match:
- `push.ts:136` (`extractJoinDeltas`) 
- `clone.ts:205`
- `pull.ts:283` (if join store key logic exists)
- `reconcile.ts:126`
- `datafn/client/src/sync/engine.ts:671`

Alternatively, use the `getJoinTableName()` utility from codegen as a shared function in `@datafn/core`.

### Fix 3: Filter or handle built-in resources in clone/reconcile

Either:
- (a) Ensure `kv` table exists (Fix 1 handles this), making clone/reconcile work naturally, OR
- (b) Mark built-in resources with a flag (e.g., `isBuiltin: true`) and skip them in clone/reconcile when no backing table exists, OR
- (c) Handle `kv` as an internal table using `db.internal.*` CRUD rather than the public adapter interface.

Option (a) is simplest if Fix 1 is applied.

### Fix 4: Add defensive logging to `coerceDateFields`

Add a `console.warn` when a resource isn't found in the schema, to surface misconfiguration early.

### Why These Weren't Caught

1. **Memory adapter masks table mismatches**: All tests used the memory adapter which auto-creates stores. The Drizzle adapter is the only one that enforces table existence at the schema level.
2. **`ensureBuiltinKv()` is runtime-only**: It augments the schema after validation, but codegen runs against the pre-augmented schema. No test verifies codegen output includes built-in resources.
3. **Change tracking and mutations were implemented in different phases**: Phase 04 (Feb 7) added change tracking with `join_` prefix. Phase 03 (Feb 13) added mutation execution with `__datafn_join_` prefix. Neither phase updated the other's naming.
4. **Silent error handling in clone**: `clone.ts:188-192` catches adapter errors and returns `[]`, so join data loss and KV absence are invisible unless you compare expected vs actual clone results.
5. **No end-to-end sync test with Drizzle**: The sync test suite uses the memory adapter. An integration test with a real database would have caught all three issues.

## Notes

- The todo-app example is the first real-world test of the full sync pipeline with Drizzle/Postgres, which is why these issues surfaced now.
- The `kv` resource is defined with a single `value` field of type `"object"`. For Postgres, this should map to `jsonb`. For SQLite, `text` (with JSON serialization).
- The join table naming issue affects all many-many relations, not just the todo app's `todos↔categories` relation.
- Fix 2 (join naming unification) requires coordinating changes across both client and server packages, plus updating any existing change-tracking records in deployed databases.
