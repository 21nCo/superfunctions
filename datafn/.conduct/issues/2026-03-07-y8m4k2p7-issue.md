# Summary
`/datafn/push` rejects mutations containing capability-managed readonly fields (`createdAt`, `updatedAt`) with `DFQL_UNKNOWN_FIELD`, while `/datafn/mutation` accepts equivalent payloads by stripping these fields first. This inconsistency breaks core sync flows for clients that send those fields (including the todo example app), severity **High** because push/sync is a primary runtime path.

# Observed Errors/Symptoms
- Push request fails with HTTP 400.
- Error envelope:
  - `code`: `DFQL_UNKNOWN_FIELD`
  - `message`: `Unknown field: createdAt on todos`
  - `details.path`: `mutations[0].record.createdAt`
- Repro payload includes `createdAt`/`updatedAt` in `mutations[0].record` for `operation: "insert"`.

# Root Causes
## 1) Example client includes readonly capability fields in outbound mutations
- Location:
  - `datafn/examples/todo-app/client/src/App.svelte:193-201`
  - `datafn/examples/todo-app/client/src/App.svelte:213-219`
- Current code (problematic snippet):
```ts
await client.table("todos").mutate({
  operation: "insert",
  record: {
    text,
    completed: false,
    priority: newTodoPriority,
    createdAt: new Date(),
    updatedAt: new Date(),
  },
});
```
- Expected behavior:
  - Capability-managed readonly fields should be treated as server-managed, not client-authored input.
- Actual behavior:
  - App sends these fields; client date codec serializes them to epoch ms and passes through.
- Impact:
  - Sync payload contains readonly capability fields and hits push validation error.
- Evidence:
  - App mutation construction in `App.svelte`.
  - Date serialization path in `datafn/client/src/codecs/date.ts` and `datafn/client/src/mutate.ts`.

## 2) Push route validates raw records in write mode before stripping readonly capability fields
- Location:
  - `datafn/server/src/routes/sync.ts:318-323`
  - `datafn/server/src/validation/schema.ts:303-326`
- Current code (problematic snippet):
```ts
const schemaIndex = buildSchemaIndex(validatedSchema);
const validationResult = validatePushMutations(payload.mutations, schemaIndex, {
  maxIdLength: handlerOpts?.maxIdLength,
  debug: handlerOpts?.debug,
});
```
- Expected behavior:
  - Push should apply same capability-readonly handling as mutation endpoint for insert/merge/replace.
- Actual behavior:
  - `validatePushMutations` checks write-allowed fields only; readonly capability fields are rejected as `DFQL_UNKNOWN_FIELD`.
- Impact:
  - `/datafn/push` and `/datafn/mutation` have divergent behavior for same schema and payload shape.
  - Sync reliability regression for clients that include capability readonly fields.
- Evidence:
  - Error path points to push mutation record field.
  - `validateRecordKeys(..., mode='write')` rejects non-writable fields.

## 3) Endpoint inconsistency: `/datafn/mutation` strips readonly capability fields before validation, `/datafn/push` does not
- Location:
  - Mutation path strips: `datafn/server/src/routes/mutation.ts:120-129`
  - Push path missing equivalent strip: `datafn/server/src/routes/sync.ts:318-323`
- Current code (reference snippet from mutation route):
```ts
record: stripReadonlyCapabilityFields(
  record as Record<string, unknown>,
  resolvedCapabilities,
),
```
- Expected behavior:
  - Both entry points should normalize capability-managed fields consistently.
- Actual behavior:
  - Mutation endpoint normalizes; push endpoint rejects.
- Impact:
  - Different outcomes for equivalent mutations based only on transport path.

# Proposed Fixes
1. Server behavior policy (required): always strip readonly capability fields in `/datafn/push` before schema validation and execution, matching `/datafn/mutation` behavior.
2. Scope guard (required): strip only fields tied to capabilities actually enabled for the target resource (global + resource-resolved capabilities). Do not strip similarly-named fields when the capability is not enabled.
3. Client optimistic capability injection (required): during local-first/offline optimistic writes, inject capability-managed values in client storage (`timestamps`, `audit`) so local records are not partial while waiting for server round-trip.
4. Client outbound sanitization (required): before calling `/datafn/mutation` or `/datafn/push`, strip capability-managed readonly fields from outbound mutation records so client never attempts to author server-owned fields.
5. Documentation update (required): in capability docs, explicitly state:
   - capability-managed readonly fields are server-owned and client-provided values are ignored/stripped.
   - if users need app-controlled fields with similar semantics, use different names or do not enable that capability.
6. Example app hygiene (recommended): remove manual `createdAt`/`updatedAt` assignment in todo app mutations to align with capability model.
7. Test coverage (required): add push-route tests proving parity with mutation route for `timestamps`, `audit`, and `trash` readonly fields; include negative test showing no stripping occurs when capability is not enabled.
