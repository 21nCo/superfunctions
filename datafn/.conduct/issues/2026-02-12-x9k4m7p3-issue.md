## User-Reported Issue Description

> Server logs show `Failed to get current serverSeq: Error: Drizzle adapter: no table mapping for model "__datafn_meta"` when running the datafn example todo-app server with a Postgres/Drizzle backend. Every push (mutation) returns `{"ok":false,"code":"INTERNAL"}` even though the data write itself succeeds at the DB level.

## Summary

When the DataFn server runs with a **Drizzle adapter** (as opposed to the in-memory adapter used in tests), all `push` operations fail because the server's internal tables (`__datafn_meta`, `__datafn_changes`, `__datafn_idempotency`, `__datafn_seed`) are not present in the Drizzle schema registry (`db._.fullSchema`). The Drizzle adapter's `resolveTable` function throws a hard error for any model not found in the user-supplied schema. The memory adapter is schemaless and never hits this problem, which is why existing tests pass.

## Observed Errors / Symptoms

**Error message** (repeats on every mutation push):

```
Failed to get current serverSeq: Error: Drizzle adapter: no table mapping for model "__datafn_meta" (resolved to "__datafn_meta").
Available tables: todos, categories, todoCategories
Did you forget to include this library's schema when calling drizzle()?
```

**Server response to client**:

```json
{
  "ok": false,
  "code": "INTERNAL",
  "message": "Internal error",
  "path": "$",
  "retryable": false
}
```

**Behavioural symptoms**:

- Data is written to user tables (the `create` call succeeds), but `serverSeq` cannot be incremented so the push is marked as failed
- Idempotency records store the error result, meaning retries will also be deduped as failures
- Clone/pull operations that depend on `__datafn_changes` silently return empty results (caught errors return `[]`)

## Root Causes

### RC-1: `resolveTable` hard-fails on unknown models (no fallback for internal tables)

**Location**: [index.ts](file:///Users/ar/dev/superfunctions/packages/db/src/adapters/drizzle/index.ts#L127-L151)

**Current code**:

```typescript
const resolveTable = (model: string) => {
  const schema = db._.fullSchema;        // ← only user-provided schema
  if (!schema) { throw ... }
  const modelName = ctx.getModelName(model);
  const tbl = schema[modelName];
  if (!tbl) {
    throw new Error(                      // ← hard throw, no fallback
      `Drizzle adapter: no table mapping for model "${model}" ...`
    );
  }
  return tbl;
};
```

**Expected behaviour**: Internal `__datafn_*` tables should be resolved transparently without requiring the user to know about or register them.

**Actual behaviour**: Any model not in the user-supplied Drizzle schema causes a hard throw.

**Impact**: Every sync operation (`push`, `pull`, sequence tracking, change tracking, idempotency) that touches an internal table fails immediately.

**Evidence**: The error stack trace originates from `resolveTable` → `findOne` → `DatabaseSequenceStore.getCurrent` → `ChangeTrackingService.getCurrentServerSeq` → `executePush`.

---

### RC-2: Asymmetric adapter behaviour — memory adapter is schemaless, Drizzle is schema-bound

**Location**: [memory/index.ts](file:///Users/ar/dev/superfunctions/packages/db/src/adapters/memory/index.ts#L91-L96)

**Current code** (memory adapter `create`):

```typescript
async create<T>(params: CreateParams): Promise<T> {
  const tableName = context.getModelName(params.model);
  if (!store.has(tableName)) {
    store.set(tableName, new Map());     // ← auto-creates on first access
  }
  // ...
}
```

**Expected behaviour**: Both adapters should handle internal tables consistently. The adapter contract should either guarantee auto-creation or the server should pre-register internal tables.

**Actual behaviour**: Memory adapter creates collections on the fly (all server tests pass). Drizzle adapter requires pre-registration (production use breaks).

**Impact**: The bug is invisible in the test suite (which uses memory adapter exclusively) and only manifests when using Drizzle with a real database — exactly the production scenario.

---

### RC-3: Internal tables also lack DDL — physical tables don't exist in the database

**Location**: The DataFn server never runs `CREATE TABLE IF NOT EXISTS` for its internal tables when using the Drizzle adapter.

**Expected behaviour**: Internal tables (`__datafn_meta`, `__datafn_changes`, `__datafn_idempotency`, `__datafn_seed`) should be auto-created on first use or during server initialization.

**Actual behaviour**: Even if `resolveTable` were fixed to produce a Drizzle table object, the underlying Postgres database has no such tables, so queries would fail with SQL errors.

**Impact**: Two-layer fix is required — both the schema resolution and the DDL provisioning.

## Proposed Fixes

### Option A: Dynamic table creation in the Drizzle adapter (recommended)

Modify `resolveTable` in the Drizzle adapter to detect `__datafn_*` prefixed models and:

1. Dynamically create Drizzle table definitions using the dialect-appropriate builder (`pgTable` / `sqliteTable` / `mysqlTable`) at runtime
2. Cache the created table objects in an `internalTableCache` map
3. Run `CREATE TABLE IF NOT EXISTS` DDL on first access using `db.execute(sql\`...\`)`

Internal table schemas (all text-based for portability):

| Table                  | Columns                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `__datafn_meta`        | `id TEXT PK, namespace TEXT, nextServerSeq INTEGER`                                                                 |
| `__datafn_changes`     | `id TEXT PK, namespace TEXT, serverSeq INTEGER, resource TEXT, recordId TEXT, op TEXT, record TEXT, createdAt TEXT` |
| `__datafn_idempotency` | `id TEXT PK, namespace TEXT, clientId TEXT, mutationId TEXT, result TEXT, createdAt TEXT`                           |
| `__datafn_seed`        | `id TEXT PK, namespace TEXT, seedId TEXT, status TEXT, createdAt TEXT`                                              |
| `__datafn_join_*`      | `id TEXT PK, "from" TEXT, "to" TEXT`                                                                                |

### Option B: Server-level initialization (alternative)

Have `createDatafnServer` accept a `dialect` config and generate + inject internal table definitions into the adapter during initialization. Less clean because it leaks dialect knowledge into the server layer.
