## Summary

The `serverSeq` tracking system in datafn server is currently hardcoded to use the `"datafn"` namespace for all users/tenants. This means all users share the same `serverSeq` sequence, preventing proper isolation of change tracking and sync cursors per user or tenant. The `ChangeTrackingService` is instantiated with a hardcoded namespace in multiple locations (`push.ts`, `pull.ts`, `mutation.ts`, `transact.ts`, `clone.ts`), and there is no mechanism to extract user/tenant context from the request to determine the appropriate namespace. The solution is to add an `authContextProvider` parameter to `DatafnServerConfig` (using the interface from the dependent issue), extract user/tenant context from requests, and use that context to construct namespaces (e.g., `"user:${userId}"` or `"tenant:${tenantId}:user:${userId}"`) when creating `ChangeTrackingService` instances. This is a **High** severity issue affecting data isolation, security, and multi-tenant functionality.

## Observed Errors/Symptoms

1. **No User/Tenant Isolation for serverSeq**: All users share the same `serverSeq` counter, meaning changes from different users are interleaved in the same sequence, breaking isolation.

2. **Hardcoded Namespace**: The namespace `"datafn"` is hardcoded in all `ChangeTrackingService` instantiations, preventing per-user/tenant isolation.

3. **No Context Extraction**: The server has no way to extract user/tenant context from requests to determine the appropriate namespace for change tracking.

4. **Sync Cursor Confusion**: When multiple users share the same namespace, their sync cursors can become confused, as they're all tracking the same global `serverSeq` sequence.

5. **Security Risk**: Without proper isolation, users could potentially see changes from other users if cursors are not properly scoped, or if there are bugs in cursor filtering.

6. **Multi-Tenant Incompatibility**: The current implementation cannot support multi-tenant scenarios where different tenants must have completely isolated change tracking.

## Notes

- **Dependency**: This issue depends on `/Users/ar/dev/superfunctions/datafn/.conduct/issues/2026-01-28-7b07258d-issue.md` which creates the `AuthContextProvider` interface in `@superfunctions/auth`. That issue must be completed first.

- **Namespace Format**: The namespace format follows the pattern:
  - Single user: `user:${userId}`
  - Multi-tenant: `tenant:${tenantId}:user:${userId}`
  - Default (no auth): `"datafn"`

- **Backward Compatibility**: The `authContextProvider` is optional. When not provided, the system falls back to the default `"datafn"` namespace, ensuring existing code continues to work.

- **Error Handling**: If `getContext()` throws an error or returns invalid context (e.g., missing `userId`), the system should log the error and fall back to the default namespace rather than failing the request. This ensures robustness.

- **Performance Consideration**: `getContext()` is called for every request that triggers change tracking (push, pull, mutation, transact, clone). Consider caching if the auth library's context extraction is expensive, but be careful about cache invalidation when users switch.

- **Security Consideration**: The namespace extraction must be secure and cannot be manipulated by clients. The `authContextProvider` should extract context from server-side session/auth state, not from client-provided data.

- **Comparison with Client Issue**: The client-side issue (2026-01-28-7b07258d-issue.md) handles IndexedDB database name isolation. This server-side issue handles `serverSeq` and change tracking isolation. Both use the same `AuthContextProvider` interface for consistency.

- **WebSocket Considerations**: WebSocket connections may need namespace-aware cursor broadcasting. If a user's changes trigger a cursor update, only WebSocket clients for that user's namespace should receive the update. This may require additional changes to `WebSocketManager`.

- **Testing Strategy**: Test with multiple users making concurrent changes to verify:
  1. Each user gets independent `serverSeq` sequences
  2. Pull operations return only the requesting user's changes
  3. Cursors are correctly scoped per user
  4. No cross-user data leakage occurs

- **Migration Path**: For existing deployments using the default "datafn" namespace, there is no migration needed. New deployments can start using user/tenant namespaces immediately. Existing data in the "datafn" namespace will remain accessible to requests without `authContextProvider` or with users that don't match any namespace pattern.
