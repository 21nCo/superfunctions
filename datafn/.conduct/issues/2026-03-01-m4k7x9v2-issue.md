## Summary

The `/datafn/push` endpoint's merge/replace upsert fails with a PostgreSQL error (`there is no unique or exclusion constraint matching the ON CONFLICT specification`) because the upsert call in `push.ts` does not pass `conflictTarget: "id"`. The row-level namespace wrapper prepends `__ns` to the `where` clause, and the Drizzle adapter derives the conflict target from that expanded where, producing `ON CONFLICT (__ns, id)` — but no such unique constraint exists. The same bug was previously fixed in `execute.ts` (mutation route) and `relations.ts` (relation mutations) via issue `2026-02-27-x8k3m9v7`, but the fix was **not applied to the push sync path** in `push.ts`.

## Root Cause

### Push upsert at `push.ts:239-245` missing `conflictTarget: "id"`

**Location:** `datafn/server/src/execution/sync/push.ts` lines 239-245

**Current code (broken):**
```typescript
await db.upsert({
  model: mut.resource,
  where: [{ field: "id", operator: "eq", value: mut.id }],
  create: { id: mut.id, ...coercedData },
  update: coercedData,
  namespace,
  // NO conflictTarget
});
```

**The chain of failure:**

1. Push execution calls `db.upsert()` with `where: [{ field: "id", ... }]` and no `conflictTarget`.
2. The row-level namespace wrapper (`row-level-namespace.ts:203-216`) prepends `__ns` to the where clause → `where` becomes `[{ field: "__ns", ... }, { field: "id", ... }]`.
3. The Drizzle adapter's upsert (`drizzle/index.ts:262-267`) derives the conflict target from the where clause because no `conflictTarget` was provided → `target = ["__ns", "id"]`.
4. Drizzle generates: `INSERT INTO kv (...) ON CONFLICT ("__ns", "id") DO UPDATE SET ...`
5. PostgreSQL rejects because there is no unique constraint on `(__ns, id)` — only `id` has a PRIMARY KEY constraint.

**Previously fixed in other code paths:**

The identical bug was documented in issue `2026-02-27-x8k3m9v7-issue` and fixed by adding `conflictTarget: "id"` in two places:

```typescript
// datafn/server/src/execution/mutation/execute.ts line 74
conflictTarget: "id",

// datafn/server/src/execution/mutation/relations.ts line 137
conflictTarget: "id",
```

But `push.ts` was not updated. The push route uses a separate code path from the mutation route — push calls `executePush()` which does its own upsert directly, not through `executeMutationCore()` from `execute.ts`.

## Recommended Fix

**The fix is a one-line addition** — add `conflictTarget: "id"` to the upsert call in `push.ts`:

**File:** `datafn/server/src/execution/sync/push.ts` lines 239-245

```typescript
await db.upsert({
  model: mut.resource,
  where: [{ field: "id", operator: "eq", value: mut.id }],
  create: { id: mut.id, ...coercedData },
  update: coercedData,
  namespace,
  conflictTarget: "id",  // <-- ADD THIS
});
```

### Why this is the safest approach

1. **Minimal change** — one line, identical to what was already applied in `execute.ts` and `relations.ts`.
2. **No double-serialization risk** — this is purely about SQL conflict target, not data transformation.
3. **No regression risk** — the conflict target was always implicitly `id` before namespace isolation was added. This makes it explicit.
4. **Consistent with existing fix** — follows the same pattern already validated in production for the mutation and relation paths.

### Why NOT fix in the namespace wrapper or Drizzle adapter

- **Namespace wrapper approach** (auto-deriving `conflictTarget` from original where): Would work, but it's a larger change that affects all adapters, not just push. The wrapper cannot know which fields are the actual conflict target (the where clause could have non-unique fields). This approach adds complexity and risk.
- **Drizzle adapter approach** (ignoring `__ns` in conflict derivation): Fragile — the adapter doesn't know which column is the namespace column. Would break if the namespace column were legitimately part of a conflict target.
- **Both alternatives** risk creating new bugs in other code paths. The caller-side fix is explicit, safe, and already proven.

## Notes

- This is a **regression from an incomplete fix** — issue `2026-02-27-x8k3m9v7` identified and fixed the conflict target corruption in `execute.ts` and `relations.ts`, but missed the parallel code path in `push.ts`.
- The error is masked as `INTERNAL` because push.ts catches the PostgreSQL error at line 247-260 and returns a generic error. In debug mode, the actual PostgreSQL error should be logged — and indeed the server log shows `"Push operation failed"` but the error string is not visible in the user's provided logs.
- This affects **all resources pushed via sync**, not just KV. But KV is the most visible because it's the first resource most users test with.
