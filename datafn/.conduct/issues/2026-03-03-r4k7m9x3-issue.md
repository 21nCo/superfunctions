## Summary

The MUT-003 optimization (commit `ea87d7e`, 2026-02-25) replaced the `findOne + conditional update/create` pattern with `db.upsert()` for merge operations in both `push.ts` and `execute.ts`. The upsert's `create` payload only contains the mutation delta fields (e.g., `{ completed: true, updatedAt: ... }`), missing required NOT NULL columns (`text`, `createdAt`) that have no database defaults. PostgreSQL rejects the INSERT portion of `INSERT ... ON CONFLICT DO UPDATE` because NOT NULL constraints are validated before conflict detection. The error is silently swallowed and returned as a generic `INTERNAL` error. Additionally, the `logger` parameter is not passed to `executePush()` from the route handler, so the actual PostgreSQL error is never logged.

## Root Causes

### Root Cause 1: Upsert `create` payload missing NOT NULL fields for merge operations

**Location**: `datafn/server/src/execution/sync/push.ts` lines 228–262

**Current code**:

```typescript
case "merge":
case "replace":
  // MUT-003: Use db.upsert() instead of findOne + conditional create/update
  try {
    const coercedData = applyDateCoercion(schema, mut.resource, mut.record || {}, logger);
    await db.upsert({
      model: mut.resource,
      where: [{ field: "id", operator: "eq", value: mut.id }],
      create: { id: mut.id, ...coercedData },  // ← PROBLEM: only delta fields
      update: coercedData,
      namespace,
      conflictTarget: "id",
    });
    opResult = { ok: true };
  } catch (innerError) {
    // Error swallowed with generic message
    opResult = { ok: false, code: "INTERNAL", message: "Internal error", path: "$" };
  }
```

**Expected behavior**: Merge mutation updates only the provided fields on an existing record. If the record does not exist, return NOT_FOUND so the client can handle it (e.g., re-read locally and send the full record as an insert).

**Actual behavior**: The `db.upsert()` call generates `INSERT INTO todos (__ns, id, completed, updated_at) VALUES (...) ON CONFLICT (__ns, id) DO UPDATE SET ...`. PostgreSQL validates NOT NULL constraints on the INSERT data before checking for conflicts. Since `text` (NOT NULL, no default) and `created_at` (NOT NULL, no default) are missing from the INSERT, PostgreSQL raises a not-null violation error. The `catch` block swallows this into a generic INTERNAL error.

**Impact**: All merge mutations that update a subset of fields on resources with NOT NULL columns fail against real SQL databases (PostgreSQL, MySQL, SQLite with strict mode). This breaks the core sync flow — clients cannot update individual fields on existing records.

**Evidence**: 
- Drizzle schema defines `text: text("text").notNull()` and `createdAt: bigint("created_at", { mode: "number" }).notNull()` with no defaults (`datafn-schema.drizzle.ts` lines 28-29, 32)
- Mutation record from client: `{ completed: true, updatedAt: 1772514836919 }` — only 2 of 6 fields
- The `create` payload becomes `{ id, completed, updatedAt, __ns }` — missing `text` and `createdAt`
- KV upserts work because `kv` table only has `__ns` (NOT NULL), `id` (NOT NULL), and `value` (nullable JSONB)
- Todo creation (insert) works because it provides all fields

## Proposed Fix

### Approach: Update-first, NOT_FOUND on miss

Replace `db.upsert()` with `db.update()` for merge operations. If the record doesn't exist (0 rows affected), return a NOT_FOUND error and let the client handle it (e.g., read the record locally and send the full record as an insert).

This approach:
- Uses **1 DB call** in the common case (record exists) — same efficiency as upsert
- Has **no NOT NULL constraint issues** — `update()` only sets provided fields
- Has **no TOCTOU race condition** — `update()` is atomic
- Is **semantically correct** — merge means "update these fields on an existing record"
- Lets the client handle the edge case of a missing record

### Fix for `push.ts` (lines 228–262)

```typescript
case "merge":
  try {
    const coercedData = applyDateCoercion(schema, mut.resource, mut.record || {}, logger);
    const result = await db.update({
      model: mut.resource,
      where: [{ field: "id", operator: "eq", value: mut.id }],
      data: coercedData,
      namespace,
    });
    // If 0 rows affected, record doesn't exist
    if (result === 0 || (result && typeof result === 'object' && !result.id)) {
      opResult = { ok: false, code: "NOT_FOUND", message: `Record not found: ${mut.id}`, path: "id" };
    } else {
      opResult = { ok: true };
    }
  } catch (innerError) {
    logger?.error("Push merge failed", {
      error: String(innerError),
      operation: mut.operation,
      resource: mut.resource,
      id: mut.id,
    });
    opResult = { ok: false, code: "INTERNAL", message: "Internal error", path: "$" };
  }
  break;

case "replace":
  // Replace keeps upsert or uses findOne + update (needs full record)
  // ... handle separately
  break;
```

### Fix for `execute.ts` (lines 65–82)

Same pattern — replace `db.upsert()` with `db.update()` + NOT_FOUND check for the merge case.

### Fix for `routes/sync.ts` (line 369–377)

Pass the `logger` parameter to `executePush()`:

```typescript
const result = await executePush(
  beforeHookResult.payload as any,
  validatedSchema,
  db,
  idempotencyStore,
  namespace,
  sequenceStore,
  onChange,
  logger,  // ← Add logger
);
```

### Client-side handling

When the client receives a `NOT_FOUND` error for a merge mutation, it should:
1. Read the full record from local storage
2. Re-send as an `insert` mutation with all fields
3. This ensures the record is created with complete data if it was somehow missing on the server

## Notes

- The MUT-003 optimization tests passed because they use the **memory adapter**, which has no NOT NULL constraints. The bug only manifests against real SQL databases with schema constraints.
- The `replace` operation in push also uses `db.upsert()` — this may have the same issue if the client sends partial records for replace. However, the push.ts comment says "the client sends the full record" for replace, so it may be fine in practice. Should be verified.
- The original pre-MUT-003 code (`findOne + conditional create/update`) also had a latent bug in its create fallback path (partial delta would fail on NOT NULL), but it never triggered because records always existed by the time a merge came through.
- This is the same class of issue as `2026-03-01-n4k8v2m7-issue` (KV upsert conflictTarget mismatch) and `2026-03-01-m4k7x9v2-issue` (push upsert missing conflictTarget) — the upsert approach in push has been a recurring source of bugs.
