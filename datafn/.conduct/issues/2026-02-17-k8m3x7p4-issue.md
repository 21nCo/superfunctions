## User-Reported Issue Description

> Running `npm run db:push` in the todo-app example server initially failed with `column "created_at" cannot be cast automatically to type bigint` (existing DB had timestamp columns, generated schema expects bigint). After dropping and recreating tables, mutations from the client fail with `invalid input syntax for type bigint: "2026-02-17T07:29:34.118Z"` — the client sends ISO date strings but the DB column is bigint.

## Summary

The datafn date pipeline has a fundamental contract mismatch. The client-side date codec (`CODEC-001`) serializes `Date` objects to ISO 8601 strings via `.toISOString()`. However, the CLI's Drizzle codegen maps the datafn `"date"` field type to `bigint` columns (Unix epoch milliseconds). The server push handler passes mutation data directly to the DB adapter with zero type coercion. This means every push containing a date field will fail on any real database because PostgreSQL (and others) cannot insert an ISO string into a bigint column.

## Observed Errors / Symptoms

**Error 1 — Schema push (drizzle-kit push):**
```
error: column "created_at" cannot be cast automatically to type bigint
hint: 'You might need to specify "USING created_at::bigint".'
```
This occurred because existing tables had `timestamp` columns (from a previous hand-written schema) but the generated schema declares `bigint`.

**Error 2 — Runtime push (after table recreation):**
```
Push operation failed [insert] for resource "todos", id "todo:7f603dee-...":
error: invalid input syntax for type bigint: "2026-02-17T07:29:34.118Z"
code: '22P02'
where: "unnamed portal parameter $5 = '...'"
routine: 'pg_strtoint64_safe'
```
The client sends `createdAt: '2026-02-17T07:29:34.118Z'` (ISO string), but the DB column is `bigint("created_at", { mode: "number" })`.

## Root Causes

### Root Cause 1: Date codec serializes to ISO strings, not epoch numbers

**Location**: `datafn/client/src/codecs/date.ts`, line 55

**Current code:**
```ts
serialized[field.name] = value.toISOString();
```

**Expected behaviour**: Date fields should be serialized to Unix epoch milliseconds (`value.getTime()`) to match the bigint column type declared by the Drizzle codegen.

**Actual behaviour**: Produces ISO 8601 strings like `"2026-02-17T07:29:34.118Z"` which are incompatible with bigint columns.

**Impact**: Every client mutation containing a date field will fail on insert/update when the server uses the generated Drizzle schema.

---

### Root Cause 2: Server push handler performs no type coercion on date fields

**Location**: `datafn/server/src/execution/sync/push.ts`, lines 240–247

**Current code:**
```ts
case "insert":
  await db.create({
    model: mut.resource,
    data: {
      id: mut.id,
      ...(mut.record || {}),
    },
    namespace,
  });
```

**Expected behaviour**: Before passing data to `db.create()`, the push handler should inspect the schema for date fields and convert ISO strings to epoch numbers (or the appropriate DB-native format).

**Actual behaviour**: `mut.record` is spread directly into the data object with no transformation. Whatever the client sends is forwarded verbatim to the DB adapter.

**Impact**: Even if the client were fixed, there's no server-side safety net. Any date value arriving in the wrong format will cause a DB error.

---

### Root Cause 3: Inbound date codec (`parseDateFields`) doesn't handle epoch numbers

**Location**: `datafn/client/src/codecs/date.ts`, lines 104–131

**Current code:**
```ts
if (typeof value === "string") {
  const date = new Date(value);
  // ...
  parsed[field.name] = date;
} else if (value instanceof Date) {
  // Already a Date object
  parsed[field.name] = value;
} else {
  throw { code: "DFQL_INVALID", ... };
}
```

**Expected behaviour**: If the storage/transport format for dates is epoch numbers (bigint), the inbound codec should also handle `typeof value === "number"` and convert via `new Date(value)`.

**Actual behaviour**: A numeric epoch value (e.g., returned from the DB or sync payload) would be rejected with `DFQL_INVALID` because the codec only accepts strings and Date objects.

**Impact**: Even after fixing the outbound serialization, query results from bigint columns would fail to parse back into Date objects on the client.

## Proposed Fixes

### Fix 1: Change outbound date codec to produce epoch milliseconds

In `datafn/client/src/codecs/date.ts`, line 55:
```ts
// Before
serialized[field.name] = value.toISOString();

// After
serialized[field.name] = value.getTime();
```

Update the JSDoc comments at lines 1–8 to reflect `Date objects → epoch milliseconds (number)` instead of `Date objects → ISO 8601 strings`.

### Fix 2: Add epoch number handling to inbound date codec

In `datafn/client/src/codecs/date.ts`, add a `typeof value === "number"` branch before the string check:
```ts
if (typeof value === "number") {
  const date = new Date(value);
  if (isNaN(date.getTime())) {
    throw { code: "DFQL_INVALID", ... };
  }
  parsed[field.name] = date;
} else if (typeof value === "string") {
  // ... existing string handling
}
```

### Fix 3: Add server-side date coercion in push handler

In `datafn/server/src/execution/sync/push.ts`, before `db.create()` / `db.update()` calls, add a coercion step that inspects the schema for date fields and converts ISO strings to epoch numbers. This provides a safety net independent of client behaviour.
