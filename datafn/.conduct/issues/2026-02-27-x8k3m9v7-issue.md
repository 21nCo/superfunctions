## User-Reported Issue Description

> datafn example app server logs - kv and join table mutations are not working. Join table upsert fails with "there is no unique or exclusion constraint matching the ON CONFLICT specification". KV records are not persisting to the database despite mutations appearing to succeed.

## Summary

Two critical data persistence failures exist in the datafn server. Both trace to related architectural issues in the adapter layer:

1. **Many-many join table upserts fail** because the row-level namespace wrapper prepends `__ns` to the `where` clause, which the drizzle adapter then uses to derive the `ON CONFLICT` target. The resulting `ON CONFLICT (__ns, id)` has no matching unique constraint in PostgreSQL.
2. **KV `set()` never creates new records** because it uses the `replace` mutation operation, which requires the record to already exist. First-time KV writes silently fail with `NOT_FOUND`. The natural fix (switching to `merge`/upsert) is blocked by root cause #1.

## Root Causes

### Root Cause 1: Row-Level Namespace Wrapper Corrupts Upsert Conflict Target

**Location:** `packages/db/src/adapter/row-level-namespace.ts:203-216` and `packages/db/src/adapters/drizzle/index.ts:257-300`

**Current code (namespace wrapper):**

```typescript
// packages/db/src/adapter/row-level-namespace.ts:203-216
async upsert(params) {
  assertNamespace(params.namespace, mandatory);
  const where = prependWhere(          // ← prepends __ns to where
    params.where,
    namespaceWhereClause(col, params.namespace!),
  );
  const create = stampData(params.create, col, params.namespace!);
  const update = removeColumnFromData(params.update, col);
  const result = await adapter.upsert({
    ...params,
    where,    // ← now contains [{ field: "__ns", ... }, { field: "id", ... }]
    create,
    update,
  });
  return stripColumn(result, col);
},
```

**Current code (drizzle adapter — conflict target derivation):**

```typescript
// packages/db/src/adapters/drizzle/index.ts:262-265
let target: string | string[] | undefined = config.upsertKeys?.[model];
if (!target) {
  // derive from where fields
  target = where.length === 1 ? where[0].field : where.map((w) => w.field);
}
```

**Expected behavior:** The `ON CONFLICT` target should reference only the actual unique constraint columns (e.g., `id` which is the PRIMARY KEY), not include the namespace column.

**Actual behavior:** The namespace wrapper prepends `__ns` to `where`. The drizzle adapter derives the conflict target from `where` → generates `ON CONFLICT (__ns, id)`. No unique constraint exists on `(__ns, id)`, so PostgreSQL rejects it with error code `42P10`.

**Impact:** ALL upsert operations through the namespace-wrapped adapter are broken. This affects:
- Many-many relation mutations (`relate` operation) via `relations.ts:120`
- `merge` mutations via `execute.ts:153`
- Any future code using `adapter.upsert()`

**Evidence:**
- The SQL migration creates `"id" text PRIMARY KEY NOT NULL` (unique on `id` alone)
- No composite unique constraint on `(__ns, id)` exists
- The stack trace confirms the failure path: `row-level-namespace.ts:211` → `drizzle/index.ts:266`

**Schema reference (generated SQL):**

```sql
-- datafn/examples/todo-app/server/drizzle/0000_shallow_robbie_robertson.sql:1-6
CREATE TABLE "__datafn_join_todos_tags" (
  "__ns" text NOT NULL,
  "from" text NOT NULL,
  "id" text PRIMARY KEY NOT NULL,   -- unique on id alone
  "to" text NOT NULL
);
```

### Root Cause 2: KV `set()` Uses `replace` Operation Which Cannot Create New Records

**Location:** `datafn/client/src/kv.ts:108-112` and `datafn/server/src/execution/mutation/execute.ts:171-188`

**Current code (client-side kv.set):**

```typescript
// datafn/client/src/kv.ts:108-112
const executeMutation = async () => {
  // Use replace operation for deterministic set semantics
  const result = (await kvTable.mutate({
    resource: KV_RESOURCE_NAME,
    version: 1,
    operation: "replace",   // ← requires record to already exist
    id,
    record: { value },
    ...
  } as any)) as any;
```

**Current code (server-side replace handler):**

```typescript
// datafn/server/src/execution/mutation/execute.ts:171-188
case "replace":
  // Replace semantics: MUST exist, clear unspecified fields
  try {
    const existing = await db.findOne({
      model: mutation.resource,
      where: [{ field: "id", operator: "eq", value: mutation.id }],
      namespace,
    });

    if (!existing) {
      opResult = {
        ok: false,
        code: "NOT_FOUND",       // ← first-time KV set fails here
        message: `Record not found: ${mutation.id}`,
        path: "id",
      };
      break;
    }
```

**Expected behavior:** `kv.set("theme", "light")` should create the KV record if it doesn't exist, or update it if it does (upsert semantics).

**Actual behavior:** For first-time writes, `findOne` returns null → `NOT_FOUND` → record is never created. The error propagates back to the client as `{ ok: false }` but is not logged server-side in a visible way.

**Impact:** KV store is effectively write-once-only (records can only be updated after being created through some other mechanism). Since there is no `insert` path in `kv.set()`, the KV store is non-functional for new keys.

**Note:** The natural fix (switching `kv.set()` from `replace` to `merge`) depends on Root Cause 1 being fixed first, because `merge` uses `db.upsert()` which goes through the same namespace-polluted conflict target path.

## Proposed Fixes

### Fix for Root Cause 1: Add Explicit `conflictTarget` to UpsertParams

1. **Add `conflictTarget` field to `UpsertParams`** in `packages/db/src/adapter/types.ts`:
   ```typescript
   export interface UpsertParams {
     model: string;
     where: WhereClause[];
     create: Record<string, any>;
     update: Record<string, any>;
     select?: string[];
     namespace?: string;
     conflictTarget?: string | string[];  // NEW: explicit ON CONFLICT columns
   }
   ```

2. **Update the drizzle adapter** in `packages/db/src/adapters/drizzle/index.ts` to prefer `conflictTarget` over deriving from `where`:
   ```typescript
   let target: string | string[] | undefined =
     params.conflictTarget ?? config.upsertKeys?.[model];
   if (!target) {
     target = where.length === 1 ? where[0].field : where.map((w) => w.field);
   }
   ```

3. **Update the namespace wrapper** in `packages/db/src/adapter/row-level-namespace.ts` to pass through `conflictTarget` unchanged (do NOT prepend `__ns`):
   ```typescript
   async upsert(params) {
     assertNamespace(params.namespace, mandatory);
     const where = prependWhere(params.where, namespaceWhereClause(col, params.namespace!));
     const create = stampData(params.create, col, params.namespace!);
     const update = removeColumnFromData(params.update, col);
     const result = await adapter.upsert({
       ...params,
       where,
       create,
       update,
       // conflictTarget passes through unchanged from params
     });
     return stripColumn(result, col);
   },
   ```

4. **Update callers** to set `conflictTarget: "id"` explicitly:
   - `datafn/server/src/execution/mutation/relations.ts:120` (join table upsert)
   - `datafn/server/src/execution/mutation/execute.ts:153` (merge operation)

### Fix for Root Cause 2: Switch KV `set()` from `replace` to `merge`

Change `datafn/client/src/kv.ts:112` from `operation: "replace"` to `operation: "merge"`. The `merge` operation uses `db.upsert()` which can create-or-update. This fix depends on Root Cause 1 being resolved first.

Also update the debounced path at `kv.ts:139` from `operation: "replace"` to `operation: "merge"`.

## Notes

- The `merge` operation in `execute.ts:149-168` is ALSO affected by Root Cause 1 — it calls `db.upsert()` with `where: [{ field: "id", ... }]` which gets namespace-polluted to `ON CONFLICT (__ns, id)`. This means `merge` mutations for ALL resources are broken, not just KV.
- The `insert` and `replace` operations use `db.create()` and `db.findOne()`+`db.update()` respectively, which do NOT use `ON CONFLICT` and therefore work correctly through the namespace wrapper.
- The `config.upsertKeys` option in the drizzle adapter could serve as a workaround, but it's per-adapter-instance configuration and doesn't solve the architectural issue of `where` being dual-purposed for both filtering and conflict target derivation.
