## Summary

The `getNextServerSeqFromDb()` method in the change tracking service always returns `1` when running on PostgreSQL, because PostgreSQL folds unquoted column identifiers to lowercase. The internal CRUD layer creates a column named `nextServerSeq` (camelCase) in the DDL, but PostgreSQL stores it as `nextserverseq` (lowercase). When the meta record is read back via `SELECT *`, the JavaScript object has the key `nextserverseq`, but the code accesses `meta.nextServerSeq` (camelCase), which is always `undefined`. The `|| 1` fallback then ensures every call returns `1`. This causes duplicate primary key violations on the `__datafn_changes` table whenever the same resource+id pair appears in more than one mutation (e.g., insert a todo, then relate a tag to that todo). A secondary bug compounds the issue: the CAS (Compare-And-Swap) update's return value (affected row count) is never checked, so a 0-row update is silently treated as success.

## Root Causes

### Root Cause 1: PostgreSQL column name case-folding breaks property access

**Location:** `datafn/server/src/execution/internal-tables.ts` lines 3–7 (column definition) + `packages/db/src/adapters/drizzle/internal.ts` line 84–87 (DDL generation) + `datafn/server/src/execution/sync/change-tracking.ts` line 104 (property access)

**Current code — column definition:**

```typescript
// datafn/server/src/execution/internal-tables.ts:3-7
const META_COLUMNS: InternalColumnDef[] = [
  { name: "id", type: "text", primaryKey: true },
  { name: "namespace", type: "text" },
  { name: "nextServerSeq", type: "integer" },  // camelCase
];
```

**Current code — DDL generation (unquoted):**

```typescript
// packages/db/src/adapters/drizzle/internal.ts:81-87
const colDefs = columns.map((col) => {
  const sqlType = col.type === 'text' ? 'TEXT' : 'INTEGER';
  const pk = col.primaryKey ? ' PRIMARY KEY' : '';
  return `${col.name} ${sqlType}${pk}`;  // No quoting!
});
const ddl = `CREATE TABLE IF NOT EXISTS ${name} (${colDefs.join(', ')})`;
```

This produces:

```sql
CREATE TABLE IF NOT EXISTS __datafn_meta (id TEXT PRIMARY KEY, namespace TEXT, nextServerSeq INTEGER)
```

PostgreSQL folds `nextServerSeq` → `nextserverseq` (all lowercase).

**Current code — property access:**

```typescript
// datafn/server/src/execution/sync/change-tracking.ts:104
const currentSeq = (meta.nextServerSeq as number) || 1;
```

**Expected behavior:** `meta.nextServerSeq` should contain the integer value (e.g., `2`) so `currentSeq` is assigned the correct sequence value.

**Actual behavior:** PostgreSQL returns `{ nextserverseq: 2 }` (lowercase key). `meta.nextServerSeq` is `undefined`. The `|| 1` fallback always produces `currentSeq = 1`.

**Impact:** Every call to `getNextServerSeq()` returns `1` on PostgreSQL. The change ID format `change:${namespace}:${serverSeq}:${resource}:${id}` always includes `serverSeq=1`, so any resource+id that appears in more than one mutation hits a duplicate key violation.

**Evidence:** The error key `change:datafn:1:todos:todo:b93d5698-5ed5-412d-bb05-93c0dc3a2c81` shows `serverSeq=1` for what should be the second (or later) change for this todo.

### Root Cause 2: CAS update return value not checked

**Location:** `datafn/server/src/execution/sync/change-tracking.ts` lines 109–124

**Current code:**

```typescript
// datafn/server/src/execution/sync/change-tracking.ts:109-124
try {
  await this.db.internal.update(
    "__datafn_meta",
    [
      { field: "namespace", op: "eq", value: this.namespace },
      { field: "nextServerSeq", op: "eq", value: currentSeq },
    ],
    { nextServerSeq: currentSeq + 1 },
  );

  // Update succeeded - return the allocated sequence
  return currentSeq;
} catch (updateError) {
  // Update failed (concurrent modification) - retry
  continue;
}
```

**Expected behavior:** The CAS pattern should verify that the update actually modified a row. `internal.update()` returns `Promise<number>` (the affected row count). If 0 rows were affected, the CAS failed and should retry.

**Actual behavior:** The return value of `internal.update()` is discarded. A 0-row update (CAS miss) does not throw, so the code falls through to `return currentSeq` with a stale value.

**Impact:** Even without Root Cause 1, any concurrent request that triggers a CAS miss would silently return a stale serverSeq, leading to duplicate change IDs.

**Evidence:** The `internal.update()` method signature explicitly returns `Promise<number>`:

```typescript
// packages/db/src/adapter/types.ts:409-413
update(
  table: string,
  where: Array<{ field: string; op: string; value: unknown }>,
  data: Record<string, unknown>,
): Promise<number>;
```

And the Drizzle implementation correctly extracts the affected row count:

```typescript
// packages/db/src/adapters/drizzle/internal.ts:163-164
const result = await executeRaw(query);
return (result as any)?.changes ?? (result as any)?.rowsAffected ?? (result as any)?.rowCount ?? 0;
```

But the calling code never inspects this value.

### Root Cause 3: All camelCase columns in internal tables are affected

**Location:** `datafn/server/src/execution/internal-tables.ts` lines 1–42

The case-folding issue is not limited to `nextServerSeq`. All camelCase column names in internal tables will have the same problem on PostgreSQL:

| Table | Column (as defined) | Column (as stored in PG) |
|---|---|---|
| `__datafn_meta` | `nextServerSeq` | `nextserverseq` |
| `__datafn_changes` | `serverSeq` | `serverseq` |
| `__datafn_changes` | `recordId` | `recordid` |
| `__datafn_changes` | `createdAt` | `createdat` |
| `__datafn_idempotency` | `clientId` | `clientid` |
| `__datafn_idempotency` | `mutationId` | `mutationid` |
| `__datafn_idempotency` | `createdAt` | `createdat` |
| `__datafn_seed` | `seedId` | `seedid` |
| `__datafn_seed` | `createdAt` | `createdat` |

Any code reading these columns via camelCase property access will get `undefined` on PostgreSQL.

## Proposed Fixes

### Fix 1 (Recommended): Use snake_case column names throughout

Change all internal table column definitions to use PostgreSQL-idiomatic snake_case names, and update all code that reads/writes these columns.

**In `datafn/server/src/execution/internal-tables.ts`:**

```typescript
const META_COLUMNS: InternalColumnDef[] = [
  { name: "id", type: "text", primaryKey: true },
  { name: "namespace", type: "text" },
  { name: "next_server_seq", type: "integer" },
];

const CHANGES_COLUMNS: InternalColumnDef[] = [
  { name: "id", type: "text", primaryKey: true },
  { name: "namespace", type: "text" },
  { name: "server_seq", type: "integer" },
  { name: "resource", type: "text" },
  { name: "record_id", type: "text" },
  { name: "op", type: "text" },
  { name: "record", type: "text" },
  { name: "created_at", type: "text" },
];
// ... same for IDEMPOTENCY_COLUMNS and SEED_COLUMNS
```

Then update all property accesses in `change-tracking.ts`, `idempotency-db.ts`, `db-store.ts`, etc. to use the new snake_case names.

**Migration note:** Existing `__datafn_meta` and `__datafn_changes` tables in PostgreSQL already have lowercase column names (due to case folding), so a rename from `nextserverseq` to `next_server_seq` via `ALTER TABLE ... RENAME COLUMN` would be needed, or a drop-and-recreate if data loss is acceptable during development.

### Fix 2 (Alternative): Quote column names in DDL to preserve case

**In `packages/db/src/adapters/drizzle/internal.ts`:**

```typescript
const colDefs = columns.map((col) => {
  const sqlType = col.type === 'text' ? 'TEXT' : 'INTEGER';
  const pk = col.primaryKey ? ' PRIMARY KEY' : '';
  return `"${col.name}" ${sqlType}${pk}`;  // Quote the column name
});
```

Also quote column names in INSERT, SELECT WHERE, and UPDATE SET clauses. This preserves the camelCase names in PostgreSQL but adds quoting complexity throughout the internal CRUD layer.

### Fix 3 (Required regardless): Check CAS return value

**In `datafn/server/src/execution/sync/change-tracking.ts`:**

```typescript
const affected = await this.db.internal.update(
  "__datafn_meta",
  [
    { field: "namespace", op: "eq", value: this.namespace },
    { field: "nextServerSeq", op: "eq", value: currentSeq },
  ],
  { nextServerSeq: currentSeq + 1 },
);

if (affected === 0) {
  // CAS failed — another writer incremented the sequence
  continue;
}

return currentSeq;
```

## Notes

- **SQLite is not affected**: SQLite preserves column name case as-is and `SELECT *` returns the original casing. This explains why the bug only manifests with PostgreSQL.
- **MySQL behavior varies**: MySQL column names are case-insensitive on case-insensitive file systems (most Linux default is case-sensitive for table names but case-insensitive for column names). MySQL may or may not exhibit this bug depending on the `lower_case_table_names` setting.
- **Memory adapter is not affected**: The memory adapter stores columns as JavaScript object properties, preserving camelCase. Most tests likely use the memory adapter, which is why this bug was not caught in tests.
- The `recordChange()` method catches and logs the error but does not propagate it (line 178–181), so the push operation appears to succeed from the client's perspective even though change tracking is broken. This means **sync/pull will silently miss changes** — a potentially more dangerous symptom than the error itself.
- The same case-folding issue likely affects the idempotency store (`__datafn_idempotency` table), which reads `clientId` and `mutationId` columns. If those reads return `undefined`, idempotency checks may silently fail, allowing duplicate mutation execution.
