## User-Reported Issue Description

> The KV table is generated with `id` as the sole primary key. In multi-tenant mode (the default), KV IDs like `kv:pref:theme` are not namespace-scoped, so two different tenants setting the same key will collide on the primary key constraint. The `__ns` column provides row-level namespace isolation for reads/writes but is not part of the primary key, meaning the unique constraint on `id` is global — not per-tenant.

## Summary

The built-in KV resource uses `id text PRIMARY KEY` as its only uniqueness constraint. In multi-tenant mode (`multiTenant: true`, the default), the namespace wrapper stamps each row with `__ns` and filters reads by `__ns`, but the database-level primary key is only `(id)`. When two tenants insert a KV entry with the same logical key (e.g. `"pref:theme"`), both produce `id = "kv:pref:theme"`. The second insert fails with a unique constraint violation (`23505` / `UNIQUE_VIOLATION`), even though the rows belong to different namespaces. This is a **critical** bug: it makes the KV feature unusable in any real multi-tenant deployment.

## Observed Errors / Symptoms

1. **Unique constraint violation on KV insert**: When tenant B calls `client.kv.set("pref:theme", "light")` after tenant A already called `client.kv.set("pref:theme", "dark")`, the database rejects the insert:
   ```
   ERROR: duplicate key value violates unique constraint "kv_pkey"
   Detail: Key (id)=(kv:pref:theme) already exists.
   ```

2. **KV upsert overwrites wrong tenant's data**: If the operation reaches the `merge`/`replace` path (which uses `db.upsert` with `conflictTarget: "id"`), the `ON CONFLICT (id) DO UPDATE` will update the existing row — which belongs to a different tenant. The namespace WHERE clause in the wrapper scopes the `where` parameter, but Drizzle's `onConflictDoUpdate` only checks the conflict target columns (`id`), not the WHERE clause. This means tenant B's upsert silently overwrites tenant A's KV value.

3. **Todo-app masks the bug**: The example todo-app uses a hardcoded `authContextProvider` returning `userId: "user-001"` and `tenantId: "tenant-acme"` for all requests, so there is effectively a single namespace and no collision occurs.

## Root Causes

### Root Cause 1: KV table schema uses single-column primary key instead of composite key

**Location**: `datafn/core/src/kv.ts` lines 47–65, `datafn/cli/src/drizzle-codegen.ts` lines 227–232

**Current code** (`datafn/core/src/kv.ts`):

```typescript
const kvResource: DatafnResourceSchema = {
  name: KV_RESOURCE_NAME,
  version: 1,
  idPrefix: KV_RESOURCE_NAME,
  fields: [
    { name: "id", type: "string", required: true },
    { name: "value", type: "json", required: false },
  ],
  // ...
};
```

**Current code** (`datafn/cli/src/drizzle-codegen.ts`):

```typescript
if (field.name === "id") {
  def += ".primaryKey()";
}
```

This unconditionally makes `id` the sole primary key for every resource, including KV. The generated SQL is:

```sql
CREATE TABLE "kv" (
  "__ns" text NOT NULL,
  "id" text PRIMARY KEY NOT NULL,
  "value" jsonb
);
```

**Expected behavior**: In multi-tenant mode, KV uniqueness should be scoped per namespace. The primary key should be `(__ns, id)` so that:
- `(__ns="tenant:acme:user:001", id="kv:pref:theme")` ✓
- `(__ns="tenant:acme:user:002", id="kv:pref:theme")` ✓

**Actual behavior**: `PRIMARY KEY (id)` makes `kv:pref:theme` globally unique. The second insert fails.

**Impact**: KV is completely broken for multi-tenant deployments with more than one user.

### Root Cause 2: The same problem applies to ALL resource tables, not just KV

**Location**: `datafn/cli/src/drizzle-codegen.ts` line 231

The codegen applies `.primaryKey()` to `id` for every resource table. Consider a `todos` resource: if two tenants happen to generate the same `id` (e.g. from a client-generated UUID collision, or a deterministic ID scheme), the insert will fail.

In practice, most resources use random UUIDs with prefixes (e.g. `td:abc123`), making collisions astronomically unlikely. However, the KV resource is special because its IDs are **deterministic** — they are derived from the user-supplied key via `kvId(key) = "kv:" + key`. This makes KV the primary victim of this design flaw.

**Impact**: Critical for KV; low risk for other resources using random IDs, but architecturally unsound for any resource with deterministic IDs.

### Root Cause 3: Upsert conflict target is `id`-only — cross-tenant data corruption

**Location**: `datafn/server/src/execution/sync/push.ts` line 245, `datafn/server/src/execution/mutation/execute.ts` line 74

```typescript
await db.upsert({
  model: mut.resource,
  where: [{ field: "id", operator: "eq", value: mut.id }],
  create: { id: mut.id, ...coercedData },
  update: coercedData,
  namespace,
  conflictTarget: "id",
});
```

The namespace wrapper (`row-level-namespace.ts` line 203–218) stamps `__ns` into `create` and prepends `__ns` to `where`, but the `conflictTarget` remains `"id"`. The Drizzle adapter uses `conflictTarget` to build the `ON CONFLICT (id)` clause. Since `__ns` is not in the conflict target, PostgreSQL resolves the conflict based on `id` alone, and the `DO UPDATE SET` fires against the wrong tenant's row.

**Impact**: Silent cross-tenant data overwrite. Tenant B's KV write can overwrite tenant A's KV value without any error.

### Root Cause 4: `kvId()` produces namespace-unaware IDs

**Location**: `datafn/core/src/kv.ts` lines 15–21

```typescript
export function kvId(key: string): string {
  return `${KV_RESOURCE_NAME}:${key}`;
}
```

`kvId("pref:theme")` always returns `"kv:pref:theme"` regardless of which tenant/user is calling. The namespace is not embedded in the ID. While the namespace wrapper handles scoping at the query level, the primary key constraint operates at the database level and does not respect namespace scoping.

**Impact**: All tenants sharing the same logical key produce identical `id` values.

## Proposed Fixes

### Fix Option A: Composite primary key `(__ns, id)` for multi-tenant tables

When `multiTenant` is true, generate a composite primary key instead of a single-column PK:

1. **`datafn/cli/src/drizzle-codegen.ts`**: When `isMultiTenant`, don't emit `.primaryKey()` on the `id` field. Instead, use Drizzle's `primaryKey({ columns: [table.__ns, table.id] })` in the table callback.

2. **`conflictTarget` in push/mutation**: Change from `"id"` to `["__ns", "id"]` when operating in multi-tenant mode, or derive it from schema metadata.

3. **Migration**: Existing deployments need a migration to drop the single-column PK and add the composite PK.

### Fix Option B: Embed namespace in KV IDs

Modify `kvId()` to incorporate the namespace: `kvId(key, namespace) = "kv:" + namespace + ":" + key`. This keeps the single-column PK but makes IDs globally unique by construction.

**Trade-off**: This leaks namespace details into IDs and requires the namespace to be available at ID-generation time (client-side), which may not always be the case.

### Recommended Approach

**Option A** is the more principled fix — it solves the problem at the database level and doesn't require changing ID generation. It also correctly handles the general case for any resource with deterministic IDs.

## Notes

- The todo-app example masks this bug by using a hardcoded single-user auth context. Any real multi-user deployment will hit this immediately when two users set the same KV preference key.
- This issue was previously partially addressed in `2026-02-27-x8k3m9v7-issue` (namespace-polluted upsert conflict target) which fixed the conflict target being corrupted by namespace injection, but did not address the fundamental problem that `id`-only PK is insufficient for multi-tenant uniqueness.
- The `__datafn_join_*` tables have the same structural issue: `id text PRIMARY KEY` with `__ns` not in the PK. However, join table IDs are composite (`${fromId}:${toId}`) which makes cross-tenant collision less likely but still theoretically possible if two tenants relate the same pair of entities.
