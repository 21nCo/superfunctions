## User-Reported Issue Description

> In `@datafn/examples/todo-app/client/src/App.svelte` — `visibleTodos.loading` is resolving to `true` always and data is not showing on UI.

## Summary

The `createQuerySignal` function in `datafn/client/src/signals/querySignal.ts` calls `notifySubscribers()` inside the `try` block of `fetchQuery()` while `inFlight` is still `true`. The `loading` getter returns `inFlight && !isRefresh`, so every subscriber notification carries `loading: true` even when data has successfully arrived. Since `inFlight` is only cleared in the `finally` block (after notification), and no second notification is emitted after that, the Svelte store permanently shows `loading: true` alongside valid data. This causes the UI's `{#if visibleTodos?.loading}` guard to display "Loading…" indefinitely, hiding all todo items.

## Observed Errors / Symptoms

- **Error**: No runtime error — the bug is a logical timing issue
- **Location in stack**: `datafn/client/src/signals/querySignal.ts` → `LiveSignal` → `toSvelteStoreDirect` → `App.svelte`
- **Trigger**: Any query signal subscription (all table signals and KV signals)
- **Scope**: All signals created via `client.table(...).signal(...)` are affected. The todo app's `allTodosStore`, `activeTodosStore`, `completedTodosStore`, and `categoriesStore` all exhibit this behavior. The debug panel in `App.svelte` confirms data arrives (`$allTodosStore` contains records) but `loading` never transitions to `false`.

## Root Causes

### Root Cause 1: `notifySubscribers()` called before `inFlight` is cleared

**Location**: `datafn/client/src/signals/querySignal.ts`, lines 256–315 (`fetchQuery`) and lines 457–459 (`loading` getter)

**Current code**:
```typescript
// fetchQuery (lines 256–315)
const fetchQuery = async (refresh = false): Promise<void> => {
    // ...
    inFlight = true;        // line 265
    isRefresh = refresh;     // line 266
    // ...
    try {
      const result = await client.query(fullQuery);
      // ...
      currentValue = (queryResult.data ?? result) as T;   // line 277
      // ...
      notifySubscribers();   // line 285 — subscribers notified HERE
    } catch (error: any) {
      // ...
    } finally {
      inFlight = false;      // line 306 — cleared AFTER notification
      isRefresh = false;     // line 307
      // ...
    }
};

// loading getter (lines 457–459)
get loading(): boolean {
    return inFlight && !isRefresh;
},
```

**Expected behavior**: When data arrives and subscribers are notified, `loading` should be `false` so that consumers know the fetch is complete.

**Actual behavior**: `notifySubscribers()` fires at line 285 while `inFlight` is still `true` (set at line 265). The `loading` getter evaluates `inFlight && !isRefresh` = `true && !false` = `true`. The `finally` block at line 306 sets `inFlight = false`, but no notification is emitted after that, so consumers never see `loading: false`.

**Impact**: Every Svelte store (and any other signal consumer) permanently shows `loading: true` alongside the actual data. UI conditionals like `{#if visibleTodos?.loading}` in `App.svelte` (line 425) display "Loading…" and never reveal the data list.

**Evidence**: The execution order is deterministic:
1. `inFlight = true` (line 265)
2. `await client.query(...)` resolves (line 274)
3. `currentValue` assigned (line 277)
4. `notifySubscribers()` fires (line 285) → LiveSignal propagates to Svelte store → store reads `signal.loading` → returns `true`
5. `finally { inFlight = false }` (line 306) — no further notification

### Root Cause 2 (Propagation): `toSvelteStoreDirect` captures stale loading state

**Location**: `datafn/svelte/src/toSvelteStore.ts`, lines 86–110

**Current code**:
```typescript
function toSvelteStoreDirect<T>(signal: DatafnSignal<T>): DatafnSvelteStore<T> {
  return readable(
    {
      data: signal.get(),
      loading: signal.loading,       // initial: also true if fetch already started
      error: signal.error,
      refreshing: signal.refreshing,
      nextCursor: signal.nextCursor ?? null,
    },
    (set) => {
      const unsub = signal.subscribe((value: T) => {
        set({
          data: value,
          loading: signal.loading,    // reads loading at notification time → always true
          error: signal.error,
          refreshing: signal.refreshing,
          nextCursor: signal.nextCursor ?? null,
        });
      });
      return () => { unsub(); };
    },
  );
}
```

**Expected behavior**: When `signal.subscribe` callback fires with new data, `signal.loading` should reflect the completed state (`false`).

**Actual behavior**: `signal.loading` delegates through `LiveSignal.loading` → `this.raw?.loading` → `inFlight && !isRefresh`, which is still `true` at notification time. The Svelte store captures `{ data: <valid data>, loading: true }` and never receives a correcting update.

**Impact**: The Svelte readable store is permanently stuck with `loading: true`. Since `toSvelteStoreDirect` only emits when the signal's `subscribe` callback fires, and the signal only notifies once per fetch, there is no mechanism to correct the loading state.

**Evidence**: `LiveSignal.loading` (liveSignal.ts:101–103) is a pass-through getter:
```typescript
get loading(): boolean {
    return this.raw?.loading ?? false;
}
```
It reads the raw signal's `loading` at call time, inheriting the same timing issue.

## Proposed Fixes

### Fix 1 — Clear `inFlight` before notifying subscribers

Move `inFlight = false` and `isRefresh = false` out of the `finally` block and into the `try` block, immediately before `notifySubscribers()`:

```typescript
try {
    const result = await client.query(fullQuery);
    const queryResult = result as { data?: any[]; nextCursor?: string | null };
    currentValue = (queryResult.data ?? result) as T;
    currentCursor = queryResult.nextCursor ?? null;
    currentError = null;
    cachedIds = extractRecordIds(currentValue);

    // Clear flight flags BEFORE notifying so loading/refreshing read correctly
    inFlight = false;
    isRefresh = false;

    notifySubscribers();
} catch (error: any) {
    // ...
} finally {
    inFlight = false;
    isRefresh = false;
    // queued refresh handling...
}
```

Keep the `finally` assignments as a safety net for the error path.

### Fix 2 — Emit a second notification after `finally`

Add a `notifySubscribers()` call after the `finally` block clears `inFlight`, so consumers get a corrected `loading: false` emission:

```typescript
} finally {
    inFlight = false;
    isRefresh = false;

    if (queuedRefresh) {
        queuedRefresh = false;
        fetchQuery(true);
    }
}

// Emit corrected loading state to subscribers
if (currentValue !== undefined) {
    notifySubscribers();
}
```

**Recommendation**: Fix 1 is preferred — it avoids a redundant notification and is simpler to reason about. The `finally` block still acts as a safety net.

## Notes

- The same timing issue affects the `refreshing` getter (`inFlight && isRefresh`), but since refresh notifications are less visible in the UI, it may not have been noticed yet.
- The initial value passed to Svelte's `readable()` in `toSvelteStoreDirect` (line 88–94) also captures `signal.loading` at construction time. If the signal factory triggers a fetch synchronously (via `LiveSignal.bindRaw` → lazy subscribe), the initial value may also be `loading: true`. This is a secondary concern but worth verifying.
- The debug panel in `App.svelte` (lines 311–320) confirms the symptom: `$allTodosStore` contains data but the todo list doesn't render because the `{#if visibleTodos?.loading}` block on line 425 short-circuits rendering.
