**User-reported issue description (verbatim):**
> The `__ns` column in `__datafn_permissions_global` causes a problem when querying permissions that belong to a different namespace than the current request namespace. The row-level namespace wrapper prepends `WHERE __ns = <current namespace>` on every `findMany`, so grant rows stamped with a different `__ns` are invisible to the caller.

## Summary

The `__datafn_permissions_global` table has both a semantic `resource_ns` column (which namespace the grant logically belongs to) and a storage-level `__ns` column (row-level namespace discriminator from `@superfunctions/db`). When `wrapWithRowLevelNamespace` is enabled (the default for namespaced schemas), every `db.findMany` call gets an automatic `WHERE __ns = <request namespace>` filter. This means that permission grant rows stored under one namespace's `__ns` are invisible to queries running under a different namespace — even when the `resource_ns` on the row intentionally references a cross-namespace grant. This breaks `sharedWithMe` discovery and cross-namespace permission reads in per-user namespace layouts.

**Severity**: Medium — Does not break single-tenant or shared-tenant-namespace deployments, but prevents per-user namespace layouts from functioning correctly with `sharedWithMe` and cross-namespace permission inspection.

## Observed Errors/Symptoms

1. **`sharedWithMe` returns empty results in per-user namespace layouts.** When user Bob (namespace `user:bob`) queries for documents shared with him by Alice (namespace `user:alice`), `resolveSharedWithMeNamespaceAccess` calls `db.findMany` with `namespace: "user:bob"`. The row-level wrapper adds `WHERE __ns = 'user:bob'`, but the grant row was stamped with `__ns = 'user:alice'` (Alice's namespace at share time). Result: zero matching rows.

2. **`listPermissionsForInspection` cannot see grants created in other namespaces.** Same root cause: the query passes the current request namespace, filtering out rows with a different `__ns`.

3. **The `sharedWithMe` test suite seeds grant rows with `__ns` set to the *reader's* namespace**, not the sharer's — masking the production behavior where `executeShare` stamps `__ns` from the sharer's namespace.

## Root Causes

### Root Cause 1: `__ns` is stamped from the sharer's namespace at grant creation time

**Location:** `datafn/server/src/execution/mutation/share.ts` lines 370–375

```typescript
} else {
    await db.create({
      model: permissionsTable,
      data: permissionRecord,
      namespace,
    });
  }
```

`namespace` is the current request namespace (the sharer's context). The `wrapWithRowLevelNamespace` wrapper calls `stampData(data, "__ns", namespace)`, so the row's `__ns` = sharer's namespace.

**Expected behavior:** The grant row should be queryable by the grantee's namespace context (for `sharedWithMe`-style reads).

**Actual behavior:** The grant row is only visible to callers whose request namespace matches the sharer's namespace.

**Impact:** In a per-user namespace model (`user:alice`, `user:bob`), Bob can never discover grants Alice made for him via the standard `findMany` path.

### Root Cause 2: `resolveSharedWithMeNamespaceAccess` queries permissions through the namespace-wrapped adapter

**Location:** `datafn/server/src/routes/query.ts` lines 272–280

```typescript
const principals = await resolveActorPrincipals(namespace, actorId);
    for (const principalId of principals) {
      const rows = await db.findMany({
        model: globalPermissionsTable,
        where: [
          { field: "resourceType", operator: "eq", value: resource },
          { field: "principalId", operator: "eq", value: principalId },
        ],
        namespace,
      });
```

This passes `namespace` (the reader's context) to `db.findMany`. The wrapper injects `WHERE __ns = namespace`. If grants were created under a different `__ns`, they are invisible.

**Expected behavior:** Permission lookup for `sharedWithMe` should be able to see grants across all `__ns` partitions (or at least grants where `principalId` matches the current actor's effective principals).

**Actual behavior:** Only grants where `__ns` matches the current request namespace are returned.

### Root Cause 3: Test suite seeds grant rows with reader's `__ns`, not sharer's `__ns`

**Location:** `datafn/server/src/execution/query/__tests__/shared-with-me.test.ts` lines 85–100

```typescript
await db.create({
      model: "__datafn_permissions_global",
      data: {
        id: "p1",
        resourceType: "collections",
        resourceNs: "user:alice",
        resourceId: "col_trip",
        principalId: "user:bob",
        // ...
        __ns: "user:bob",   // <-- stamped with reader's namespace, not sharer's
      },
      namespace: "user:bob",
    });
```

This makes the test pass because Bob's `findMany` with `__ns = user:bob` finds the row. But in production, `executeShare` running under Alice's context would stamp `__ns = user:alice`, and the same `findMany` would return nothing.

**Impact:** Tests give false confidence that `sharedWithMe` works in per-user namespace layouts.

## Proposed Fixes

Several approaches, from least to most invasive:

1. **Use `db.internal` for permission reads.** The `internal` CRUD interface bypasses `wrapWithRowLevelNamespace`. Permission tables could be read through `db.internal.findMany` instead of `db.findMany`, since they have their own `resource_ns` semantics and don't need physical `__ns` scoping. This is already how change tracking (`__datafn_changes`) is accessed.

2. **Omit `__ns` from permission/membership/hierarchy tables in codegen.** When `nsEnabled` is true, codegen could skip adding `__ns` to `__datafn_permissions_global`, `__datafn_principal_memberships`, and `__datafn_principal_hierarchy`. These tables already have explicit `resource_ns` / `namespace` columns that encode their own scoping, and applying the generic row-level filter on top is redundant at best, broken at worst.

3. **Stamp `__ns` with the grantee's namespace (or both).** On share, store the grant row under the target principal's namespace partition so the reader can discover it. Downside: the sharer's `listPermissionsForInspection` would then need to read across `__ns` partitions too, or use `db.internal`.

4. **Duplicate grant rows.** Write one row per relevant `__ns` partition (sharer + grantee). Downside: storage growth, revocation complexity.

**Recommendation:** Option 1 (use `db.internal` for permission reads) is the smallest change and aligns with how other internal tables are already handled. Option 2 is cleaner long-term but requires a codegen change and migration.

## Notes

- This issue does **not** manifest in deployments where all users share a single DataFn namespace (e.g. `org:acme` for the whole tenant). In that case, sharer and reader have the same `__ns` and everything works.
- The sharing-app demo avoids this because it uses org-level namespaces (`org:acme`, `org:globex`) and all users within an org share the same namespace.
- The `__datafn_principal_memberships` and `__datafn_principal_hierarchy` tables have the same `__ns` column and the same potential issue for cross-namespace membership/hierarchy resolution.
- The `db.internal` API already exists and is used for `__datafn_changes`, `__datafn_idempotency`, `__datafn_seq`, and `__datafn_seed` — so there is precedent for internal tables bypassing the namespace wrapper.
