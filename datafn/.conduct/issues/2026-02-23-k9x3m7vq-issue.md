## Summary

Two bugs in the DataFn client sync engine (`@datafn/client`) cause degraded sync behavior: **(1)** When the browser window regains focus (e.g., user switches back from another app/tab), the sync engine does not pull fresh data from the server because it only listens to the narrow `document.visibilitychange` event instead of the broader `window.focus` event — this is the primary sync trigger Nucleus uses and it is missing from DataFn; **(2)** The `/clone` endpoint is called on every app reload even when local IndexedDB already has fully hydrated data, because the hydration-plan codepath in `initializeWithHydrationPlan` unconditionally clones without checking existing hydration state. **Severity: Medium-High** — Bug 1 causes stale data UX on multi-client setups; Bug 2 causes unnecessary network overhead and latency on every page load.

---

## Observed Errors/Symptoms

### Bug 1: No realtime sync when another client pushes data
- When Client A pushes a mutation, Client B does not receive the update until it either: (a) pushes something itself (triggering a post-push pull), or (b) the tab transitions from hidden to visible.
- Switching between browser windows (while the tab remains visible) does **not** trigger a pull.
- Nucleus solves this identically-scoped problem with `<svelte:window on:focus={onAppear} />` → `flux.syncDown()`. DataFn has no equivalent.

### Bug 2: `/clone` endpoint called on every page reload
- Network inspector shows `POST /datafn/clone` on every full page reload, even when IndexedDB already contains all data in `"ready"` hydration state.
- This re-downloads the entire dataset unnecessarily, adding latency to app startup.

## Root Causes

### Root Cause 1: SyncEngine only listens to `visibilitychange`, not `window.focus`

**Location:** `superfunctions/datafn/client/src/sync/engine.ts`, lines 49, 107-112, 259-263

**Current code:**

```typescript
// Line 49: only a visibility change handler is bound
private boundOnVisibilityChange: () => void;

// Lines 107-112: only visibilitychange is registered
if (typeof document !== "undefined" && document.addEventListener) {
  document.addEventListener(
    "visibilitychange",
    this.boundOnVisibilityChange,
  );
}

// Lines 259-263: handler only fires when visibilityState transitions to "visible"
private onVisibilityChange() {
  if (document.visibilityState === "visible") {
    this.pullNow();
  }
}
```

**Expected behavior:** When the user switches focus back to the app window (e.g., Alt-Tab, clicking the window), a pull should be triggered to fetch any changes made by other clients. This is the pattern Nucleus uses:

```svelte
<!-- nucleus/client/layout/layers/UserBaseLayer.svelte, line 641 -->
<svelte:window on:focus={onAppear} />

<!-- nucleus/client/products/nucleus/base/NucleusBaseLayer.svelte, line 83 -->
<svelte:window on:focus={onAppear} />
```

Where `onAppear` calls `flux.syncDown({ src: "onAppear" })` (UserBaseLayer.svelte, line 217).

**Actual behavior:** `document.visibilitychange` only fires when a tab transitions between hidden (e.g., tab switched away) and visible. It does **not** fire when:
- The user switches from another application window back to the browser (the tab was never hidden, just not focused)
- The user switches between browser windows (both containing tabs of the app)
- On mobile: coming back from a quick app switcher without the tab being fully hidden

**Impact:** On multi-client setups, Client B shows stale data indefinitely until the user either: (a) performs a mutation (triggering a push → post-push pull), (b) fully switches to another tab and back (triggering visibilitychange), or (c) WebSockets deliver a cursor notification (if enabled — the example app has `ws: false`).

**Evidence:** The Nucleus codebase uses `window.focus` as the primary trigger for `syncDown` across all product shells (NucleusBaseLayer, PointronBaseLayer, UserBaseLayer, ExtensionBaseLayer). Additionally, Nucleus has a periodic sync fallback every 3.5s via `SyncLayer.svelte`. DataFn has neither — no `focus` listener and no periodic pull interval.

### Root Cause 2: `initializeWithHydrationPlan` unconditionally clones without checking hydration state

**Location:** `superfunctions/datafn/client/src/sync/engine.ts`, lines 269-311

**Current code (hydration plan path — BUGGY):**

```typescript
// Lines 298-311
private async initializeWithHydrationPlan() {
  const { bootResources = [], backgroundResources = [] } = this.hydrationPlan!;

  // Clone boot resources and wait for them to be ready
  if (bootResources.length > 0) {
    await this.cloneResources(bootResources);  // <-- ALWAYS clones, never checks state
  }

  // Clone background resources asynchronously
  if (backgroundResources.length > 0) {
    this.cloneResourcesInBackground(backgroundResources);  // <-- ALWAYS clones
  }
}
```

**Contrast with the default path (CORRECT):**

```typescript
// Lines 277-293
let needsClone = false;

for (const res of this.schema.resources) {
  if (res.isRemoteOnly) continue;
  const state = await this.storage.getHydrationState(res.name);
  if (state !== "ready") {   // <-- Checks hydration state
    needsClone = true;
    break;
  }
}

if (needsClone) {
  await this.cloneNow();
} else {
  await this.pullNow();    // <-- Only pulls if already hydrated
}
```

**Expected behavior:** After the initial clone completes and hydration state is persisted as `"ready"` in IndexedDB, subsequent app loads should detect this and only perform an incremental `pullNow()` — not a full clone.

**Actual behavior:** Because the todo app (and any app using `hydration.bootResources`) takes the `initializeWithHydrationPlan` path, it unconditionally calls `cloneResources()` which:
1. Transitions state from `"ready"` → `"hydrating"` (valid transition per `validateTransition`)
2. Calls `remote.clone()` — full dataset download from `/datafn/clone`
3. Upserts all records into IndexedDB (overwriting existing data)
4. Transitions state back to `"ready"`

This creates a cascade effect: during step 2, any concurrent queries see `hydrationState === "hydrating"` and route to the remote `/query` endpoint instead of local IndexedDB, which explains the additional remote `/query` calls observed during reload.

**Impact:**
- Every page reload downloads the full dataset via `/clone`, adding unnecessary startup latency proportional to data size
- During the clone window, queries fall back to remote `/query` instead of local IndexedDB (defeating the purpose of offline-first)
- Unnecessary server load — every page load = one full clone request per client
- The `"ready"` hydration state in IndexedDB is effectively meaningless when `bootResources` is configured

**Evidence:** The todo app configures `hydration: { bootResources: ["todos", "categories"] }` in `examples/todo-app/client/src/lib/datafn.ts` (line 153-155). The `initializeSync` method checks for `this.hydrationPlan?.bootResources` first (line 271) and branches to `initializeWithHydrationPlan()` which has no hydration state check. The `ready → hydrating` transition is allowed by `validateTransition` (indexedDbStorage.ts line 31), so no error is thrown — the bug is silent.

## Proposed Fixes

### Fix 1: Add `window.focus` listener to SyncEngine

Add a focus event listener alongside the existing `visibilitychange` listener. This mirrors the Nucleus `onAppear` pattern without requiring a periodic pull interval.

**In `superfunctions/datafn/client/src/sync/engine.ts`:**

1. Add a new bound handler property:
   ```typescript
   private boundOnWindowFocus: () => void;
   ```

2. Bind it in the constructor:
   ```typescript
   this.boundOnWindowFocus = this.onWindowFocus.bind(this);
   ```

3. Register in `start()`:
   ```typescript
   if (typeof window !== "undefined" && window.addEventListener) {
     window.addEventListener("focus", this.boundOnWindowFocus);
   }
   ```

4. Unregister in `stop()`:
   ```typescript
   if (typeof window !== "undefined" && window.removeEventListener) {
     window.removeEventListener("focus", this.boundOnWindowFocus);
   }
   ```

5. Implement the handler:
   ```typescript
   private onWindowFocus() {
     this.pullNow();
   }
   ```

`pullNow()` already has an `if (this.pullInFlight) return;` guard (line 488), so rapid focus events won't cause duplicate pulls.

### Fix 2: Check hydration state in `initializeWithHydrationPlan`

**In `superfunctions/datafn/client/src/sync/engine.ts`:**

Filter boot/background resources to only those not yet in `"ready"` state, and pull for the rest:

```typescript
private async initializeWithHydrationPlan() {
  const { bootResources = [], backgroundResources = [] } = this.hydrationPlan!;

  // Partition boot resources into those needing clone vs already ready
  const bootNeedingClone: string[] = [];
  for (const table of bootResources) {
    const state = await this.storage.getHydrationState(table);
    if (state !== "ready") {
      bootNeedingClone.push(table);
    }
  }

  if (bootNeedingClone.length > 0) {
    await this.cloneResources(bootNeedingClone);
  }

  // If all boot resources were already ready, do a pull to catch up
  if (bootNeedingClone.length === 0 && bootResources.length > 0) {
    await this.pullNow();
  }

  // Same logic for background resources
  const bgNeedingClone: string[] = [];
  for (const table of backgroundResources) {
    const state = await this.storage.getHydrationState(table);
    if (state !== "ready") {
      bgNeedingClone.push(table);
    }
  }

  if (bgNeedingClone.length > 0) {
    this.cloneResourcesInBackground(bgNeedingClone);
  }
}
```

## Notes

- Bug 1 does not require adding a periodic pull interval. The `window.focus` listener alone provides sufficient coverage for the "return to app" use case. If WebSockets are also enabled (`ws: true`), inter-client sync becomes near-real-time even without focus changes.
- Bug 2 is silent — no errors are thrown because `ready → hydrating` is a valid state transition. The only symptom is unnecessary network traffic and brief periods of remote query routing during the re-clone window.
- The todo example has `ws: false`, which compounds Bug 1. Even with the focus listener fix, enabling WebSockets would be the most robust solution for true real-time sync across clients.
- Both bugs exist at the engine level (`SyncEngine` class), not at the framework adapter level, so fixes benefit all consumers (Svelte, React, etc.).
