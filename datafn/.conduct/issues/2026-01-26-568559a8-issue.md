## Summary

When mutations are executed in offline mode (when `offlinability` is enabled), the mutation objects are missing required `clientId` and `mutationId` fields before being passed to `handleOfflineMutation()`. The `handleOfflineMutation()` function expects these fields to be present (as documented in its JSDoc), but `executeMutation()` never adds them. While the client instance has a `clientId` configured (available in the client config and passed to `SyncEngine`), it is never injected into mutation objects before they reach the offline mutation handler. This causes `validateMutation()` in `indexedDbStorage.ts` to throw an error when trying to append to the changelog. This is a **Critical** severity issue that breaks offline mutation functionality entirely.

## Observed Errors/Symptoms

1. **Runtime Error**: `Uncaught (in promise) Error: Missing clientId in mutation` at `indexedDbStorage.ts:40:33`
   - Error occurs when calling `validateMutation()` during `changelogAppend()`
   - Validation checks for `mutation.clientId` and `mutation.mutationId` but both are missing

2. **Mutation Failures**: All offline mutations fail when `offlinability` is enabled
   - Mutations cannot be appended to the changelog
   - Local optimistic updates cannot be performed
   - Offline functionality is completely broken

3. **Error Location**: The error is thrown in `IndexedDbStorageAdapter.changelogAppend()` when it calls `validateMutation(entry)` at line 349, which validates the mutation object passed to it.

## Root Causes

### Issue 1: Missing clientId and mutationId Injection in executeMutation

**Location**: `client/src/mutate.ts:22-146`

**Current Code**:
```typescript

  remote: DatafnRemoteAdapter,
  eventBus: EventBus,
  getTimestamp: () => number,
  m: unknown | unknown[],
  storage?: DatafnStorageAdapter,
  plugins: DatafnPlugin[] = [],
  schema?: DatafnSchema,
  syncEngine?: SyncEngine,
  offlinability?: boolean,

  // ... plugin hooks ...
  
  // Local-first path (SYNC-MUT-001)
  if (offlinability && storage && syncEngine) {

      ? transformedMutation
      : [transformedMutation];

    if (allReady) {

        let result = await handleOfflineMutation(
          storage,

        // ...
      }

  }
  
  // ... remote mutation attempt ...

  if (storage && !Array.isArray(m) && isTransportError(err)) {

        storage,

```

**Expected Behavior**: Before calling `handleOfflineMutation()`, the mutation object should be enriched with:
- `clientId`: The client's configured clientId
- `mutationId`: A unique identifier for this mutation (generated deterministically)

**Actual Behavior**: The mutation object is passed directly to `handleOfflineMutation()` without adding `clientId` or `mutationId`. The function expects these fields (as documented in its JSDoc comment: "The full mutation object (including resource, version, clientId, mutationId)"), but they are never provided.

**Impact**: 
- All offline mutations fail with validation error
- Changelog cannot be appended
- Offline functionality is completely broken
- Users cannot perform mutations when offline or in local-first mode

**Evidence**: 
- `handleOfflineMutation()` at line 27-28 extracts `clientId` and `mutationId` from the mutation: `const clientId = mutation.clientId as string;`
- `validateMutation()` in `indexedDbStorage.ts:40` throws error when `clientId` is missing
- Client has `clientId` configured in `examples/todo-app/client/src/lib/datafn.ts:26`: `clientId: "client-" + Math.random().toString(36).slice(2)`
- `SyncEngine` receives `clientId` in constructor (`client/src/sync/engine.ts:38`), but `executeMutation()` doesn't have access to it

**Impact**:

Create a utility function to generate deterministic mutation IDs:

## Notes

- The `clientId` is available in multiple places:
  - `config.clientId` in `client.ts` (line 210)
  - `SyncEngine.clientId` (private field, line 38 in `engine.ts`)
  - But `executeMutation()` has no access to it

- The `mutationId` needs to be unique per mutation. Options:
  - Timestamp-based: `Date.now()` + random suffix
  - Counter-based: If determinism is required
  - UUID: Most robust but adds dependency

- The error occurs specifically when `offlinability: true` is set in sync config, which enables the local-first path in `executeMutation()`.

- The offline fallback path (line 114 in `mutate.ts`) has the same issue - it also calls `handleOfflineMutation()` with an unenriched mutation.

- The remote mutation path (line 85) doesn't have this issue because the remote server likely handles clientId/mutationId differently, or the HTTP transport adds them.

- Consider whether mutations should be enriched earlier in the flow (e.g., in `table.mutate()`) vs. later (in `executeMutation()`). Enriching in `executeMutation()` is better because:
  - It's the central execution point
  - It has access to client configuration
  - It handles both local-first and offline-fallback paths

- The `SyncEngine` has `clientId` but it's used for push/pull operations, not for enriching individual mutations. Mutations are enriched when they're added to the changelog, but by then it's too late - they need the fields before `handleOfflineMutation()` is called.
