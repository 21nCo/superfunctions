## Summary

Every successful push unconditionally triggers a pull because the client's local cursor is never updated by push — only by clone/pull. The server returns a `cursor` value in the push response that reflects newly allocated sequence numbers, which is always greater than the client's local cursor. This means `serverSeq > storedSeq` is always `true`, causing a redundant `pullNow()` after every push, even with a single client. The pull re-fetches the client's own changes (already in IndexedDB from optimistic writes) as no-ops. A naive fix using `oldCursor + appliedCount == cursor` is insufficient because relation mutations (`relate`/`unrelate`) consume multiple sequence numbers per mutation. The correct fix is for the server to return a `cursorBefore` value — the global sequence counter before processing the push — so the client can cheaply determine if any foreign changes exist. **Severity: Medium** — causes a redundant network round-trip on every push cycle, doubling sync traffic.

---

## Observed Errors/Symptoms

- Every successful push from the client is immediately followed by a `POST /datafn/pull` request
- This happens even with a single client, where no foreign changes can possibly exist
- The pull returns the client's own changes, which are already in IndexedDB from optimistic writes
- Network traffic is doubled: every push cycle = 1 push + 1 pull instead of just 1 push
- Server load is unnecessarily increased by the redundant pull queries

## Root Causes

### Root Cause 1: Local cursor is never updated by push — only by clone/pull

**Location:** `superfunctions/datafn/client/src/sync/engine.ts`, lines 813-823

**Current code:**

```typescript
// Lines 813-823 in processPush()
if (pushResult.cursor) {
  const stored =
    (await this.storage.getCursor(GLOBAL_CURSOR_KEY)) || "0";
  const serverSeq = parseInt(pushResult.cursor, 10);
  const storedSeq = parseInt(stored, 10);

  if (serverSeq > storedSeq) {
    // Trigger pull asynchronously
    setTimeout(() => this.pullNow(), 0);
  }
}
```

**Expected behavior:** After a push, if the only changes on the server since the client's last pull are the client's own mutations, no pull should be needed.

**Actual behavior:** The local cursor is only updated in `applyCloneResult` and `applyPullResult` (`client/src/sync/apply.ts`). Push never calls these. After a clone sets cursor to e.g. `"42"`, the client's local cursor stays at `"42"` until the next pull. When the client pushes and the server returns `cursor: "43"`, the comparison `43 > 42` is always `true`, so `pullNow()` is always triggered.

**Impact:** Every push cycle triggers a redundant pull. In the single-client case, this is 100% wasted. In multi-client cases, the pull may be useful (to catch other clients' changes), but the current logic doesn't distinguish between the two cases — it always pulls.

**Evidence:** The flow for a single client:
1. Clone → local cursor = `"42"`
2. User adds a todo → optimistic write to IndexedDB + changelog append
3. `processPush()` → `POST /push` → server allocates seq 43, returns `{ cursor: "43" }`
4. Local cursor is still `"42"` (never updated by push)
5. `43 > 42` → `pullNow()` triggered → `POST /pull` → re-fetches seq 43 (the client's own change)
6. Pull applies the change (no-op, already in IndexedDB) and advances cursor to `"43"`

### Root Cause 2: A naive `oldCursor + appliedCount == cursor` check is insufficient due to relation mutations

**Location:** `superfunctions/datafn/server/src/execution/sync/push.ts`, lines 444-484

**Current code:**

```typescript
// Lines 444-445: Primary mutation consumes one seq
const serverSeq = await changeTracking.getNextServerSeq();
latestSeq = Math.max(latestSeq, serverSeq);

// Lines 470-484: Relation mutations consume ADDITIONAL seqs
if (
  mut.operation === "relate" ||
  mut.operation === "modifyRelation" ||
  mut.operation === "unrelate"
) {
  const joinDeltas = extractJoinDeltas(mut, schema);
  for (const delta of joinDeltas) {
    // Each join delta gets its own serverSeq for deterministic ordering
    const joinSeq = await changeTracking.getNextServerSeq();
    latestSeq = Math.max(latestSeq, joinSeq);
    // ...
  }
}
```

**Why `appliedCount` doesn't work:** The `applied` array in `PushResult` counts mutationIds (line 440: `applied.push(mut.mutationId)`). But a single `relate` mutation consumes 2+ sequence numbers: 1 for the primary record + 1 per join delta. Example:

- `oldCursor = 42`, client pushes 1 `relate` mutation
- Primary record → seq 43, join delta → seq 44
- `cursor = "44"`, `appliedCount = 1`
- `42 + 1 = 43 ≠ 44` → pull triggered even though no foreign changes exist

This makes the mutation-count approach unreliable — it would always trigger false pulls for pushes containing relation operations.

### Root Cause 3: `PushResult` lacks a `cursorBefore` field

**Location:** `superfunctions/datafn/server/src/execution/sync/push.ts`, lines 23-33 and 520-525

**Current `PushResult` interface:**

```typescript
export interface PushResult {
  ok: boolean;
  applied: string[];
  errors: Array<{ mutationId: string; code: string; message: string; path: string; }>;
  cursor: string;
}
```

```typescript
return {
  ok: true,
  applied,
  errors,
  cursor: String(latestSeq),
};
```

**Missing:** There is no `cursorBefore` field that captures the global sequence counter value before this push started allocating sequences. Without it, the client has no way to determine whether any foreign changes were interleaved.

## Proposed Fix

### Server: Add `cursorBefore` to `PushResult`

Capture the global sequence counter before processing mutations and include it in the response:

**In `superfunctions/datafn/server/src/execution/sync/push.ts`:**

1. Update the `PushResult` interface:
   ```typescript
   export interface PushResult {
     ok: boolean;
     applied: string[];
     errors: Array<{ mutationId: string; code: string; message: string; path: string; }>;
     cursor: string;
     cursorBefore: string;  // NEW: global seq before this push started
   }
   ```

2. Capture `cursorBefore` at the start of `executePush`, before the mutation loop:
   ```typescript
   const changeTracking = new ChangeTrackingService(db, namespace, sequenceStore, onChange);
   const cursorBefore = await changeTracking.getCurrentServerSeq();  // NEW
   let latestSeq = 0;
   ```

3. Include it in the return value:
   ```typescript
   return {
     ok: true,
     applied,
     errors,
     cursor: String(latestSeq),
     cursorBefore: String(cursorBefore),  // NEW
   };
   ```

### Client: Use `cursorBefore` to decide whether to pull

**In `superfunctions/datafn/client/src/sync/engine.ts`, inside `processPush()`:**

Replace the current cursor comparison (lines 813-823) with:

```typescript
if (pushResult.cursor) {
  const stored =
    (await this.storage.getCursor(GLOBAL_CURSOR_KEY)) || "0";
  const storedSeq = parseInt(stored, 10);

  if (pushResult.cursorBefore !== undefined) {
    const beforeSeq = parseInt(pushResult.cursorBefore, 10);
    if (beforeSeq === storedSeq) {
      // No foreign changes — just advance cursor locally, skip pull
      await this.storage.setCursor(GLOBAL_CURSOR_KEY, pushResult.cursor);
    } else {
      // Foreign changes exist — pull to fetch them
      setTimeout(() => this.pullNow(), 0);
    }
  } else {
    // Legacy fallback: no cursorBefore in response, always pull
    const serverSeq = parseInt(pushResult.cursor, 10);
    if (serverSeq > storedSeq) {
      setTimeout(() => this.pullNow(), 0);
    }
  }
}
```

### Why this works

- `cursorBefore` captures the global sequence value before this push allocates any sequences
- If `cursorBefore == localCursor`: no other client allocated sequences since our last pull → safe to advance cursor locally without pulling
- If `cursorBefore != localCursor`: another client (or server-side process) pushed changes → pull to fetch them
- This is independent of how many seqs per mutation are consumed (relation mutations, join deltas, etc.)
- Backward compatible: the client falls back to the current behavior if `cursorBefore` is absent

### Edge case: concurrent pushes

If Client B pushes while Client A's push request is in flight:
- B's seqs are allocated AFTER A's `cursorBefore` was captured
- If B's seqs come AFTER A's seqs: A sees `cursorBefore == localCursor`, advances cursor to A's max seq. B's changes are at higher seqs and will be picked up on the next sync trigger (focus, visibility, WebSocket, next push cycle). This is standard eventual consistency.
- If B's seqs interleave with A's: A sees `cursorBefore == localCursor` (B's allocations happened after the snapshot). A advances to its max seq. B's interleaved seqs are below A's cursor but weren't applied locally. However, the pull on the next trigger will use per-table cursors and pick them up correctly.

Note: for truly real-time multi-client sync, WebSockets remain the recommended approach. The `cursorBefore` optimization eliminates the redundant pull in the common case (single client or no concurrent pushes) while gracefully degrading to the next sync trigger for concurrent scenarios.

## Notes

- The `getCurrentServerSeq()` method already exists on `ChangeTrackingService` (line 193 of change-tracking.ts), so the server-side change is minimal — just one additional call before the mutation loop.
- The fix does NOT address per-table cursor advancement on the client side. When skipping the pull, only the global cursor is advanced. Per-table cursors remain at their prior values and will be correctly advanced on the next actual pull. This is acceptable because per-table cursors are used for pull requests, and the global cursor is only used for the push-triggered-pull comparison.
- If per-table cursor advancement is desired (to further reduce future pull payloads), the push response could be extended to include per-resource cursor deltas. This is a separate enhancement.
