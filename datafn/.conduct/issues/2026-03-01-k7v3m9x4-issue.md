## Summary

The built-in KV resource defines its `value` field with schema type `"object"`, but the KV API (`kv.set<T>(key, value)`) is designed to accept any JSON-serializable value including strings, numbers, booleans, and arrays. When `kv.set("pref:theme", "light")` sends `record: { value: "light" }` to the server, the push validation pipeline rejects it because `validateFieldValue("object", "light", false)` fails — strings are not objects. This makes the KV store unusable for storing anything other than plain objects, which contradicts its public API contract.

## Root Causes

### Root Cause 1: KV schema defines `value` as `"object"` but KV API accepts any JSON type

**Location:** `datafn/core/src/kv.ts` lines 43–60

```typescript
const kvResource: DatafnResourceSchema = {
  name: KV_RESOURCE_NAME,
  version: 1,
  idPrefix: KV_RESOURCE_NAME,
  fields: [
    { name: "id", type: "string", required: true },
    { name: "value", type: "object", required: false },  // <-- PROBLEM
  ],
  indices: ["id"],
};
```

**Expected behavior:** The `value` field should accept any JSON-serializable value (string, number, boolean, object, array, null) because the KV API is designed as a generic key-value store: `kv.set<T = unknown>(key: string, value: T)`.

**Actual behavior:** The field is typed as `"object"`, which the validator strictly checks:

```typescript
// datafn/core/src/validate.ts lines 86-92
case "object":
  if (typeof value !== "object" || Array.isArray(value)) {
    const actual = Array.isArray(value) ? "array" : typeof value;
    return { ok: false, error: `expected object, got ${actual}` };
  }
  return { ok: true };
```

**Impact:** All non-object values (strings, numbers, booleans, arrays) are rejected. The KV store is only usable for storing plain objects, which defeats its purpose as a generic key-value store.

**Evidence:** The client KV API explicitly accepts any type via generics:

```typescript
// datafn/client/src/kv.ts lines 16-21
export interface DatafnKvApi {
  get<T = unknown>(key: string): Promise<T | null>;
  set<T = unknown>(key: string, value: T, ...): Promise<...>;
  // ...
}
```

And the `set` implementation passes the value directly without wrapping:

```typescript
// datafn/client/src/kv.ts lines 127-135
const result = (await kvTable.mutate({
  resource: KV_RESOURCE_NAME,
  version: 1,
  operation: "merge",
  id,
  record: { value },  // <-- passes raw value, could be any type
  // ...
}));
```

### Root Cause 2: No `"json"` or `"any"` field type exists in the type system

**Location:** `datafn/core/src/types.ts` line 56

```typescript
export type DatafnFieldSchema = {
  name: string;
  type: "string" | "number" | "boolean" | "object" | "array" | "date" | "file";
  // ...
};
```

The `DatafnFieldSchema.type` union does not include a type that represents "any valid JSON value". There is no `"json"` or `"any"` variant. This means there is no way to define a field that accepts strings, numbers, booleans, objects, and arrays — which is exactly what the KV store needs.

**Impact:** Even if a developer wanted to define their own KV-like resource in their schema, they cannot — there is no field type that permits arbitrary JSON values.

## Proposed Fixes

The fix requires adding a new `"json"` field type to the DataFn type system. This is the correct approach because:

1. The KV store is not the only use case for arbitrary JSON fields — user schemas may also need schemaless/flexible fields.
2. Changing the KV schema's `value` field from `"object"` to `"json"` is a natural semantic fit.
3. The infrastructure (storage, codegen) already handles this shape correctly since `"object"` and `"array"` both map to `jsonb`/`json`/`text` in SQL.

### Step 1: Add `"json"` to `DatafnFieldSchema.type` union

**File:** `datafn/core/src/types.ts` line 56

Add `"json"` to the type union:
```typescript
type: "string" | "number" | "boolean" | "object" | "array" | "date" | "file" | "json";
```

Also add `"json"` to the relation metadata type union at line 82:
```typescript
type: "string" | "number" | "boolean" | "date" | "object" | "json";
```

### Step 2: Add `"json"` case to `validateFieldValue`

**File:** `datafn/core/src/validate.ts`

Add a `"json"` case that accepts any JSON-serializable value (string, number, boolean, object, array):

```typescript
case "json":
  if (typeof value === "string" || typeof value === "number" || typeof value === "boolean") {
    return { ok: true };
  }
  if (typeof value === "object") {
    return { ok: true }; // object or array — both valid JSON
  }
  return { ok: false, error: `expected json, got ${typeof value}` };
```

### Step 3: Change KV resource `value` field type to `"json"`

**File:** `datafn/core/src/kv.ts` line 55

```typescript
{ name: "value", type: "json", required: false },
```

### Step 4: Add `"json"` mapping to CLI codegen

**File:** `datafn/cli/src/drizzle-codegen.ts` — `getColumnType()`

Add `"json"` to the same cases as `"object"` for each dialect:
- Postgres: `jsonb`
- MySQL: `json`
- SQLite: `text`

**File:** `datafn/cli/src/codegen.ts` — `mapFieldType()`

Add mapping:
```typescript
case "json":
  return "unknown";  // or "string | number | boolean | Record<string, unknown> | unknown[]"
```

### Step 5: Schema validation

**File:** `datafn/core/src/schema.ts`

Ensure the `VALID_FIELD_TYPES` set (if one exists) includes `"json"`. The TypeScript type union change in Step 1 handles compile-time checks.

## Notes

- The original KV spec (`2026-02-06-audit-fix-k4m2p9x7-spec Phase 02`) noted "KV field type: Used `object` type for maximum flexibility (can store any JSON value)" — this was incorrect since `"object"` is strictly validated to reject non-objects.
- The Drizzle codegen already calls `ensureBuiltinKv()` (line 19 of `drizzle-codegen.ts`), so the KV table is already generated in Drizzle output. Changing the field type from `"object"` to `"json"` will map to the same SQL column types (`jsonb`/`json`/`text`), so no migration is needed.
- The `"json"` type name was chosen over `"any"` because it precisely describes what the field accepts: any valid JSON value. The name `"any"` could imply acceptance of non-JSON types (functions, symbols, etc.).
- This is a type system extension, not just a KV fix. Adding `"json"` benefits any user who needs a flexible field in their own resources.
