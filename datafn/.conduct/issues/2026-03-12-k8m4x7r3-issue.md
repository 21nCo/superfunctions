> DataFn client search has three related gaps:
>
> 1. **Search options dropped at datafn boundaries**: Both `client.search()` (in `datafn/client/src/client.ts`) and the server query search (in `datafn/server/src/execution/query/search.ts`) drop `prefix`, `fuzzy`, and `fieldBoosts` options before they reach the searchfn adapter.

> 3. **SearchFn spec scope mismatch**: The searchfn spec `2026-03-12-change-p7x3k9m2-spec` does NOT cover the datafn callers that invoke the search provider.

## Summary

DataFn's search integration has three high-severity gaps that collectively render searchfn's prefix/fuzzy/fieldBoosts features unreachable from any datafn code path, and leave the client-side with two disconnected, incomplete search systems — neither of which provides a full lifecycle equivalent to the server side. The related searchfn spec (`2026-03-12-change-p7x3k9m2-spec`) does not address these datafn-side gaps.

---

## Observed Errors/Symptoms

1. **Prefix matching does not work**: In the todo-app example, adding a todo "testing" and searching "test" returns no results. The searchfn memory/IndexedDB adapters fully implement prefix matching, but it is never activated.
2. **Fuzzy matching and field boosts are also silently ignored** via the same mechanism.
3. **Client-side search indices become stale**: The `searchProvider` (IndexedDB adapter) never receives `updateIndices()` calls on local mutations, only during sync engine clone/pull phases. Between mutations and the next sync, search results are stale or incomplete.
4. **Two disconnected search systems on client**: The `clientSearch` plugin (MiniSearch) and the `searchProvider` (searchfn adapter) operate independently — the plugin handles per-resource queries with lifecycle hooks but hardcodes MiniSearch; the provider handles cross-resource queries but has no mutation lifecycle.

## Root Causes

### RC-1: `SearchProvider` interface lacks `prefix`, `fuzzy`, `fieldBoosts` in method signatures

**Location**: `datafn/core/src/search-provider.ts` (lines 1–28)

**Current code**:
```typescript
export interface SearchProvider {
  search(params: {
    resource: string;
    query: string;
    type?: "fullText" | "semantic";
    fields?: string[];
    limit?: number;
    signal?: AbortSignal;
  }): Promise<string[]>;
  searchAll?(params: {
    query: string;
    resources?: string[];
    fields?: string[];
    limit?: number;
    limitPerResource?: number;
    signal?: AbortSignal;
  }): Promise<Array<{ resource: string; id: string; score: number }>>;
  // ...
}
```

**Expected behavior**: `search()` and `searchAll()` should accept `prefix?: boolean`, `fuzzy?: boolean | number`, and `fieldBoosts?: Record<string, number>`.

**Actual behavior**: These options are absent from the interface. The searchfn `datafn-provider` casts to `any` to pass them through (`request.prefix`, `request.fuzzy`, `request.fieldBoosts`), but callers have no type-level indication these options exist.

**Impact**: The contract itself is incomplete. Even if callers wanted to pass these options, the type system doesn't guide them.

**Location**: `datafn/client/src/client.ts` (lines 1074–1081)

**Impact**: Client-side cross-resource search via `client.search()` always uses exact matching with uniform field weighting, regardless of what the user passes.

### RC-6: Client-side `searchProvider` has no mutation lifecycle — `updateIndices()` never called on local mutations

**Location**: `datafn/client/src/mutate.ts` and `datafn/client/src/client.ts` (line 788–806)

**Current code** (`client.ts:793`):
```typescript
return executeMutation(
  remote, eventBus, getTimestamp, mutation,
  resolvedStorage, config.plugins || [], schema,
  syncEngine, config.sync?.offlinability, config.clientId, debouncerMap,
);
```

**Expected behavior**: After a successful local mutation, `searchProvider.updateIndices()` should be called (same pattern as the server's `tryUpdateSearchIndex()` in `datafn/server/src/execution/mutation/execute.ts:22–43`).

**Actual behavior**: `executeMutation` has no reference to `searchProvider`. No `updateIndices()` call occurs on local mutations. The sync engine _does_ call `updateIndices()` during clone/pull phases (`datafn/client/src/sync/engine.ts:506, 585, 704, 869, 876`), but this only covers data arriving from the server, not data mutated locally.

**Impact**: After a client-side insert/merge/delete, the searchfn adapter's index is stale until the next clone or pull. In local-only mode (no sync), indices are **never** updated after initial build.

### RC-7: `clientSearch` plugin hardcodes MiniSearch — no adapter integration

**Location**: `datafn/client/src/plugins/clientSearch.ts` (entire file)

**Current code**:
```typescript
import MiniSearch from "minisearch";
// ...
const indices = new Map<string, SearchIndexEntry>(); // MiniSearch instances
// ...
const index = new MiniSearch({ fields: searchFields, storeFields: [] });
```

**Expected behavior**: The plugin should delegate to a pluggable `searchProvider` (with a real searchfn adapter like IndexedDB) for indexing and querying, providing a unified search system.

**Actual behavior**: The plugin creates its own MiniSearch instances, completely independent of any configured `searchProvider`. This means:
- Per-resource queries go through MiniSearch (plugin)
- Cross-resource queries go through the searchfn adapter (searchProvider)
- Neither system is aware of the other
- The MiniSearch plugin _does_ hardcode `prefix: true` and `fuzzy: 0.2` (line 126–127), so it actually has better search behavior than the searchProvider path — but it bypasses the searchfn adapter entirely

**Impact**: Two disconnected search systems on the client. Data indexed in one is not available in the other. The searchfn adapter's capabilities (prefix, fuzzy, field boosts, persistence via IndexedDB) are unused for per-resource queries.

### RC-8: SearchFn spec does not cover datafn callers

**Location**: `searchfn/.conduct/specs/2026-03-12-change-p7x3k9m2-spec/SPEC.md`

The spec correctly addresses the searchfn pipeline:
```
adapter-contracts → adapters → client → server → datafn-provider ✅
```

But does NOT address the datafn callers:
```
datafn client (client.search)          → searchProvider.searchAll()  ❌ drops options
datafn server (query/search.ts)        → searchProvider.search()     ❌ drops options
datafn server (cross-resource.ts)      → searchProvider.searchAll()  ❌ drops options
datafn server route (routes/search.ts) → doesn't extract options     ❌ drops options
datafn client (clientSearch plugin)    → MiniSearch (no adapter)     ❌ bypasses searchfn
```

**Impact**: Implementing the searchfn spec alone does not fix prefix matching in any datafn code path.

## Proposed Fixes

1. **Update `SearchProvider` interface** (`datafn/core/src/search-provider.ts`): Add `prefix?: boolean`, `fuzzy?: boolean | number`, `fieldBoosts?: Record<string, number>` to both `search()` and `searchAll()` param types.

2. **Forward options in `client.search()`** (`datafn/client/src/client.ts:1074`): Extract `prefix`, `fuzzy`, `fieldBoosts` from `raw` and include in the `searchProvider.searchAll()` call.

3. **Forward options in `executeSearchQuery()`** (`datafn/server/src/execution/query/search.ts:49`): Pass `prefix`, `fuzzy`, `fieldBoosts` from the query search block to `searchProvider.search()`.

4. **Update `CrossResourceSearchParams`** (`datafn/server/src/execution/search/cross-resource.ts:19`): Add the three options to the interface and forward them in `executeCrossResourceSearch()`.

5. **Update server search route** (`datafn/server/src/routes/search.ts:222`): Extract `prefix`, `fuzzy`, `fieldBoosts` from `raw` request body.

6. **Call `searchProvider.updateIndices()` on client-side mutations** (`datafn/client/src/mutate.ts` or `datafn/client/src/client.ts`): Mirror the server's `tryUpdateSearchIndex()` pattern after successful local mutations.

7. **Unify client search systems**: Either refactor `clientSearch` plugin to delegate to the configured `searchProvider`, or remove the plugin in favor of a unified search provider lifecycle that handles both per-resource and cross-resource queries through the same adapter.

## Notes

- The searchfn `datafn-provider` (`createSearchProvider`) correctly passes `prefix`, `fuzzy`, `fieldBoosts` through to adapters via `as any` casts. The problem is entirely on the datafn side — callers never send these options.
- The `clientSearch` plugin ironically provides _better_ search UX than the searchProvider path because it hardcodes `prefix: true` and `fuzzy: 0.2` (L126–127). But it uses MiniSearch directly, bypassing searchfn adapters entirely.
- The sync engine (`datafn/client/src/sync/engine.ts`) does call `searchProvider.updateIndices()` during clone (L504–509) and pull (L585, L869, L876) phases, but NOT after local mutations. This is a partial lifecycle — sufficient for sync-heavy workloads but inadequate for local-only or mutation-heavy scenarios.
- The client _does_ call `searchProvider.initialize()` at startup (L514–525) and `searchProvider.dispose()` on destroy (L874–879), so two lifecycle hooks are wired. Only the mutation lifecycle is missing.
- Severity: **High** — core search functionality (prefix matching) is silently broken across all datafn code paths.
