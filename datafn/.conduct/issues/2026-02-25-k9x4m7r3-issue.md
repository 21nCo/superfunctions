### User-reported issue description (verbatim)

> Drizzle codegen generates join tables for many-many relations with only a PRIMARY KEY on `id` and no unique constraint on `(from, to)`. This means any `ON CONFLICT` targeting `(from, to)` fails on PostgreSQL with `error: there is no unique or exclusion constraint matching the ON CONFLICT specification`. The current workaround targets the `id` PK instead, but the schema should enforce uniqueness on the actual foreign key pair for data integrity and to allow flexible conflict resolution.

## Summary

**Severity: Medium** — The upsert crash was mitigated by changing `executeRelate` to target the `id` PK (commit pending). However, the join table schema lacks a `UNIQUE(from, to)` constraint, which means: (1) data integrity is not enforced at the database level, (2) direct SQL or future code paths that target `(from, to)` will hit the same `ON CONFLICT` failure, and (3) queries filtering by `(from, to)` miss a performance-critical composite index.


**Current workaround:**
`executeRelate` now targets `{ field: "id" }` instead of `[{ field: "from" }, { field: "to" }]` for the upsert conflict target. This works because `id` is always `${from}:${to}` and has the PK constraint. However, this is a semantic mismatch — the logical uniqueness is on the `(from, to)` pair, not the composite string id.

## Root Causes

### RC-1: Drizzle codegen does not emit a unique constraint on `(from, to)` for join tables

**Location:** [datafn/cli/src/drizzle-codegen.ts:82-137](datafn/cli/src/drizzle-codegen.ts#L82-L137)

**Current codegen output (Postgres):**
```ts
export const __datafn_join_todos_tags = pgTable("__datafn_join_todos_tags", {
  from: text("from").notNull(),
  id: text("id").primaryKey(),
  to: text("to").notNull(),
});
```

**Expected codegen output (Postgres):**
```ts
export const __datafn_join_todos_tags = pgTable("__datafn_join_todos_tags", {
  from: text("from").notNull(),
  id: text("id").primaryKey(),
  to: text("to").notNull(),
}, (table) => [
  uniqueIndex("__datafn_join_todos_tags_from_to_idx").on(table.from, table.to),
]);
```

**Why this matters:**
1. **Data integrity**: Without a DB-enforced unique constraint, nothing prevents duplicate `(from, to)` rows if a bug generates a different `id` format, or if raw SQL is used
2. **ON CONFLICT compatibility**: PostgreSQL requires a unique index/constraint on the conflict target columns for `INSERT ... ON CONFLICT` to work. The Drizzle adapter and Kysely adapter both derive conflict targets from where clause fields — callers using `(from, to)` as the natural key will fail
3. **Query performance**: Join table lookups by `(from, to)` (used in `executeUnrelate`, `executeModifyRelation`, `findOne` for join existence) would benefit from a composite index

**Impact:** Medium — workaround exists (target `id` PK), but the schema is structurally incomplete. Any code path that naturally targets the `(from, to)` pair for upsert/ON CONFLICT will fail on PostgreSQL and SQLite.

### RC-2: Codegen uses a flat column list without a table callback for join tables

**Location:** [datafn/cli/src/drizzle-codegen.ts:91](datafn/cli/src/drizzle-codegen.ts#L91)

The codegen already supports the table callback pattern for regular resource indices (lines 57–66):
```ts
if (hasIndices) {
  lines.push(`}, (table) => [`);
  for (const idxField of baseIndices) {
    lines.push(`  index("${tableName}_${camelToSnake(idxField)}_idx").on(table.${idxField}),`);
  }
  lines.push(`]);`);
}
```

But join tables always emit the simple `});` closing without a callback. The fix is to always emit a `(table) => [...]` callback for join tables with a `uniqueIndex` on the `(from, to)` columns.

## Proposed Fixes

### Fix A (Recommended): Add `uniqueIndex(from, to)` to join table codegen

In `datafn/cli/src/drizzle-codegen.ts`, after the join field loop (line 136), emit a table callback with a `uniqueIndex`:

```ts
// After join fields are written...
const fromSnake = camelToSnake(fromCol);
const toSnake = camelToSnake(toCol);
lines.push(`}, (table) => [`);
lines.push(`  uniqueIndex("${jtName}_${fromSnake}_${toSnake}_idx").on(table.${fromCol}, table.${toCol}),`);
lines.push(`]);`);
```

And add `"uniqueIndex"` to the `usedImports` set.

This generates:
```ts
export const __datafn_join_todos_tags = pgTable("__datafn_join_todos_tags", {
  from: text("from").notNull(),
  id: text("id").primaryKey(),
  to: text("to").notNull(),
}, (table) => [
  uniqueIndex("__datafn_join_todos_tags_from_to_idx").on(table.from, table.to),
]);
```

The Drizzle `uniqueIndex` import path is the same as `index`:
- Postgres: `drizzle-orm/pg-core`
- MySQL: `drizzle-orm/mysql-core`
- SQLite: `drizzle-orm/sqlite-core`

### Fix B (Follow-up): Revert executeRelate to target `(from, to)` once schema is updated

After Fix A is applied and the migration is run, `executeRelate` in `relations.ts` can be updated to use the natural `(from, to)` conflict target:
```ts
where: [
  { field: fromCol, operator: "eq", value: mutation.id },
  { field: toCol, operator: "eq", value: item.toId },
],
```
This is optional — the `id` PK targeting works correctly — but it's semantically cleaner.

### Fix C (Migration): Add UNIQUE constraint to existing databases

For existing deployments, a migration must be generated to add the constraint:
```sql
CREATE UNIQUE INDEX "__datafn_join_todos_tags_from_to_idx" ON "__datafn_join_todos_tags" ("from", "to");
```

Existing databases with the todo-app must run this migration. New deployments will get it automatically via the updated codegen.

## Notes

- The `uniqueIndex` import in Drizzle is exported from the same module as `index` (`drizzle-orm/pg-core`, etc.). The codegen already imports `index` when regular resource indices are present, so the pattern is proven.
- MySQL's `UNIQUE INDEX` syntax is also supported by Drizzle's `uniqueIndex()` — the codegen works identically across dialects.
- SQLite supports `CREATE UNIQUE INDEX` — Drizzle emits it correctly via `uniqueIndex()` on `sqliteTable`.
- This issue was discovered while fixing issue `2026-02-25-m7k4x9r3` (empty update upsert). The original error masked this schema gap because the `"No values to set"` error was thrown before the `ON CONFLICT` clause was even evaluated.
