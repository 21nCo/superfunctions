## Summary

**Severity: Critical/High** — Two interrelated bugs cause data loss for merge mutations. When a client pushes a merge mutation (e.g. `{completed: true, updatedAt: ...}`), the server correctly applies the merge to its database but records only the **partial mutation record** in the changelog with a generic `"upsert"` op type instead of `"merge"`. The client's per-table cursors are not advanced after push, so the next pull re-fetches the client's own change. The pull apply logic calls `upsertRecord()` (full replacement) for all `"upsert"` ops, overwriting the complete record in IndexedDB with just the partial fields — destroying fields like `name` that weren't in the merge.

## Observed Errors/Symptoms

- User marks a todo as complete via merge mutation: `{operation: "merge", record: {completed: true, updatedAt: 1771915774749}}`
- Server correctly updates only `completed` and `updatedAt` fields (full record preserved in server DB)
- After sync, IndexedDB contains only `{id, completed, updatedAt}` — the `name` and all other fields are gone
- The todo appears blank/broken in the UI

## Root Causes

### Root Cause A: Server changelog records partial mutation record with generic "upsert" op — no merge semantics preserved

**Location**: `datafn/server/src/execution/sync/push.ts` (lines 452–458) and `datafn/server/src/execution/mutation/execute.ts` (lines 370–378)

**Current code** (`push.ts:452-458`):

```typescript
const changeRecord =
  mut.operation === "delete"
    ? null
    : {
        id: mut.id,
        ...coerceDateFields(schema, mut.resource, mut.record || {}),
      };

await changeTracking.recordChange({
  serverSeq,
  resource: mut.resource,
  id: mut.id,
  op: mut.operation === "delete" ? "delete" : "upsert",
  record: changeRecord,
});
```

**Current code** (`execute.ts:370-378`):

```typescript
await changeTracking.recordChange({
  serverSeq,
  resource: mutation.resource,
  id: mutation.id,
  op: mutation.operation === "delete" ? "delete" : "upsert",
  record:
    mutation.operation === "delete"
      ? null
      : { id: mutation.id, ...(mutation.record || {}) },
});
```

**Expected behavior**: The changelog should preserve the original operation type (`"merge"`, `"insert"`, `"replace"`, `"delete"`) so that clients can apply each correctly. For merge operations, only the changed fields should be stored (which is already the case), but the op must be `"merge"` not `"upsert"`.

**Actual behavior**: All non-delete operations are collapsed to `op: "upsert"`. For a merge of `{completed: true, updatedAt: ...}`, the changelog stores:

```json
{
  "serverSeq": 5,
  "resource": "todos",
  "id": "todo:81a3bd83...",
  "op": "upsert",
  "record": {"id": "todo:81a3bd83...", "completed": true, "updatedAt": 1771915774749}
}
```

When pulled, the client treats this as a full upsert and replaces the entire record.

**Impact**: Any merge mutation causes data loss on the next pull. All fields not included in the merge are wiped from IndexedDB.

**Evidence**: The `ChangeEntry` type in `change-tracking.ts:27` only allows `"upsert" | "delete"`, and both `push.ts` and `execute.ts` use the ternary `mut.operation === "delete" ? "delete" : "upsert"` to collapse all non-delete ops.

### Root Cause B: Per-table cursors not advanced after push — client re-fetches its own changes

**Location**: `datafn/client/src/sync/engine.ts` (lines 908–933)

**Current code** (`engine.ts:908-933`):

```typescript
if (pushResult.cursor) {
  const stored =
    (await this.storage.getCursor(GLOBAL_CURSOR_KEY)) || "0";
  const storedSeq = parseInt(stored, 10);

  if (pushResult.cursorBefore !== undefined) {
    const beforeSeq = parseInt(pushResult.cursorBefore, 10);
    if (beforeSeq === storedSeq) {
      // No foreign changes — advance cursor locally, skip pull
      await setCursorMonotonically(this.storage, GLOBAL_CURSOR_KEY, pushResult.cursor);
    } else {
      // Foreign changes exist — pull to fetch them
      setTimeout(() => this.pullNow(), 0);
    }
  }
}
```

**Expected behavior**: After a successful push, per-table cursors should be advanced for the resources that were mutated, so the client never re-fetches its own changes on the next pull.

**Actual behavior**: Only `GLOBAL_CURSOR_KEY` is advanced. The `pullNow()` method reads per-table cursors (`storage.getCursor(res.name)`), which remain at their pre-push values. On the next pull, the client re-fetches its own changes.

**Server-side contributing factor**: The push response (`push.ts:524-530`) only returns a global `cursor` and `cursorBefore` — it does not return per-table cursors:

```typescript
return {
  ok: true,
  applied,
  errors,
  cursor: String(latestSeq),
  cursorBefore: String(cursorBeforeSeq),
};
```

**Impact**: Every push is followed by a pull that includes the client's own mutations. Combined with Root Cause A, this is the direct trigger for the data loss — the partial merge record comes back via pull and overwrites the correct local state.

**Client-side pull apply** (`apply.ts:177-180`):

```typescript
for (const [resource, resourceRecords] of Object.entries(records)) {
  for (const record of resourceRecords) {
    await storage.upsertRecord(resource, record);
  }
}
```

All records from pull are applied via `upsertRecord()` (full replacement) regardless of the original operation type. With Root Cause A fixed (preserving op type), this code needs to dispatch based on op.

## Proposed Fixes

### Fix A: Preserve operation type in changelog and pull protocol

1. **Expand `ChangeEntry.op`** in `change-tracking.ts` from `"upsert" | "delete"` to `"insert" | "merge" | "replace" | "delete"`.

2. **Pass original operation** in both `push.ts` and `execute.ts` when calling `changeTracking.recordChange()`:
   - `op: mut.operation` (instead of collapsing to `"upsert"`)

3. **Update pull response** — the `op` field in change entries already flows through to the pull response. The `PullResultCanonical` type needs to support the new op types. Instead of grouping by `records` (upserts) and `deleted`, group changes with their op type.

4. **Update `applyPullResultCanonical`** in `apply.ts` to dispatch based on op:
   - `"insert"` / `"replace"` → `storage.upsertRecord()`
   - `"merge"` → `storage.mergeRecord()`
   - `"delete"` → `storage.deleteRecord()`

### Fix B: Return per-table cursors from push and advance them on client

1. **Server (`push.ts`)**: During the push loop, collect per-resource max `serverSeq` values. Add a `cursors: Record<string, string>` field to `PushResult`.

2. **Client (`engine.ts`)**: After a successful push, advance per-table cursors using the returned `cursors` map via `setCursorMonotonically()`.

3. **Update `PushResult` type** to include `cursors?: Record<string, string>`.

## Notes

- The offline mutation path (`handleOfflineMutation`) correctly uses `storage.mergeRecord()` for merge operations — the local optimistic apply is correct. The data loss only occurs after the push+pull sync cycle.
- The `__datafn_changes` table already stores only the changed fields for merge mutations, which is the desired behavior for an audit trail. The fix is to preserve the operation type so consumers know how to apply the change.
- Since the library is not yet used externally, protocol changes to `PullResultCanonical`, `PushResult`, and `ChangeEntry` are safe to make without backward-compatibility concerns.
- The same partial-record issue exists in the search index update path (`execute.ts:390-393`) — this is a separate issue but shares the same root cause pattern.
