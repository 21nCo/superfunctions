### User-reported issue description

> Query signals should emit the record array directly (`T[]`) instead of the paginated result envelope (`{ data: T[], nextCursor }`). The current design causes an awkward `.data.data` double nesting when framework adapters (like `toSvelteStore`) wrap the signal value in their own `{ data, loading, error, refreshing }` envelope. Pagination metadata (`nextCursor`) should be exposed as a separate getter on the signal object, alongside `loading`/`error`/`refreshing`.

## Summary

Query signals (`client.table("todos").signal(...)`) emit the raw paginated result object `{ data: Record[], nextCursor: string | null }` as their value type `T`. Framework adapters like `toSvelteStore` wrap every signal value in a UI-state envelope `{ data: T, loading, error, refreshing }`. The composition of these two layers produces a `.data.data` path to reach the actual record array — an unintuitive DX that caused an `{#each} only works with iterable values` runtime crash in the example todo app.

**Severity**: Medium — breaks core DX ergonomics and caused a runtime error in the reference example app. Every framework adapter consumer will hit this.

## Observed Errors / Symptoms

### Runtime error in todo app

```
Uncaught (in promise) Error: {#each} only works with iterable values.
    at create_else_block (App.svelte:519:43)
```

The `{#each todoData as todo}` block received an object `{ data: [...], nextCursor: null }` instead of an array, because `todoData` was derived as:

```svelte
$: todoData = visibleTodos?.data ?? [];
```

Where `visibleTodos` is `$allTodosStore` — a Svelte store with shape `{ data: { data: Todo[], nextCursor: null }, loading, error, refreshing }`. So `visibleTodos.data` is the paginated envelope object, not the array.

### Double nesting evidence (from console logs)

```
$allTodosStore: {
  "data": {                          ← toSvelteStore wrapper
    "data": [ ... 5 todo records ],  ← paginated result envelope
    "nextCursor": null
  },
  "loading": false,
  "error": null,
  "refreshing": true
}
```

To get the array: `$allTodosStore.data.data` — two `.data` accesses.

## Root Causes

### Root Cause 1: `executeLocalQuery` returns paginated envelope

**Location**: `datafn/client/src/offline/query.ts:114-117`

**Current code**:
```typescript
return {
  data: records,
  nextCursor: null,
};
```

The local query executor wraps the record array in `{ data, nextCursor }` — a pagination envelope. This shape is consistent with the remote server's response format, which also returns `{ data, nextCursor }`.

**Expected behavior**: For signal consumers (UI-reactive data sources), the value should be the record array directly.

**Actual behavior**: The signal's `T` is `{ data: Record[], nextCursor: string | null }`, pushing pagination concerns into every consumer.

---

### Root Cause 2: `createQuerySignal` passes through the query result as-is

**Location**: `datafn/client/src/signals/querySignal.ts:273-274`

**Current code**:
```typescript
const result = await client.query(fullQuery);
currentValue = result as T;
```

The signal stores the full `client.query()` result — including the pagination envelope — as its current value. There is no unwrapping step between the query result and the signal's emitted value.

**Expected behavior**: The signal should unwrap `result.data` as its value and expose `result.nextCursor` as a separate getter property on the signal object.

**Actual behavior**: The entire `{ data: [...], nextCursor }` object becomes the signal's `T`, which then gets wrapped again by framework adapters.

---

### Root Cause 3: `toSvelteStore` adds a second wrapping layer

**Location**: `datafn/svelte/src/toSvelteStore.ts:85-107`

**Current code**:
```typescript
function toSvelteStoreDirect<T>(signal: DatafnSignal<T>): DatafnSvelteStore<T> {
  return readable(
    {
      data: signal.get(),       // ← wraps signal value under .data
      loading: signal.loading,
      error: signal.error,
      refreshing: signal.refreshing,
    },
    ...
  );
}
```

`toSvelteStore` wraps the signal value under a `.data` key to colocate UI state (`loading`, `error`, `refreshing`). This is the correct design for a framework adapter — the problem is that the signal value is already wrapped in an envelope.

**Expected behavior**: `$store.data` should be the record array `Todo[]`.

**Actual behavior**: `$store.data` is `{ data: Todo[], nextCursor: null }`, and the actual array is at `$store.data.data`.

### Background: How this happened

The double nesting emerged from two design decisions made independently:

1. **Query layer**: `client.query()` was designed to return a DFQL-standard paginated result `{ data, nextCursor }`. Both the remote server (`unwrapRemoteSuccess` in `remote/unwrap.ts`) and the local executor (`executeLocalQuery` in `offline/query.ts`) return this shape. This is correct for the query API — callers of `client.query()` directly need pagination metadata.

2. **Signal layer**: `createQuerySignal` was built to pass through query results unchanged. This was the simplest implementation and kept signals as thin reactive wrappers over queries.

3. **Framework adapter layer**: `toSvelteStore` was designed generically to work with any `DatafnSignal<T>`, wrapping the value under `.data` alongside `loading`/`error`/`refreshing`. This is the standard pattern for framework adapters.

The problem is that nobody unwraps the pagination envelope between layers 1 and 2. The KV signal (`kv.ts:415-457`) does exactly this unwrapping — it manually extracts `queryResult.data[0].value` from the paginated result before emitting to subscribers. But the table query signal has no equivalent transform. This asymmetry confirms the missing unwrap is an oversight, not a deliberate design choice.

## Proposed Fix

Unwrap the paginated envelope at the signal layer. The query signal should emit the record array directly and expose pagination metadata as separate getters.

### Changes to `datafn/client/src/signals/querySignal.ts`

1. **Add state for pagination metadata**:
```typescript
let currentCursor: string | null = null;
```

2. **Unwrap in `fetchQuery`** — replace `currentValue = result as T` with:
```typescript
const queryResult = result as { data?: any[]; nextCursor?: string | null };
currentValue = (queryResult.data ?? result) as T;
currentCursor = queryResult.nextCursor ?? null;
```

3. **Expose `nextCursor` getter** on the returned signal object:
```typescript
get nextCursor(): string | null {
  return currentCursor;
}
```

4. **Update `extractRecordIds`** — currently handles both `result.data` (array inside envelope) and direct arrays. After the unwrap, the signal's `currentValue` will always be an array, so the `result.data` branch becomes dead code for signals (but should remain for the function's general use).

5. **Update `applyOptimisticPatch`** — currently patches `currentValue.data` (the array inside the envelope). After unwrap, `currentValue` IS the array, so patching logic simplifies to direct array manipulation.

### Changes to `datafn/core/src/types.ts`

Add optional `nextCursor` to the `DatafnSignal` interface:
```typescript
export interface DatafnSignal<T> {
  get(): T;
  subscribe(handler: (value: T) => void): () => void;
  readonly loading: boolean;
  readonly error: DatafnError | null;
  readonly refreshing: boolean;
  readonly nextCursor?: string | null;   // ← new
  dispose(): void;
}
```

### Changes to `datafn/svelte/src/toSvelteStore.ts`

Update `DatafnSvelteStore` type and implementation to surface `nextCursor`:
```typescript
export type DatafnSvelteStore<T> = Readable<{
  data: T;
  loading: boolean;
  error: DatafnError | null;
  refreshing: boolean;
  nextCursor?: string | null;   // ← new
}>;
```

### Changes to `datafn/client/src/signals/liveSignal.ts`

Add a `nextCursor` passthrough getter on `LiveSignal`:
```typescript
get nextCursor(): string | null {
  return (this.raw as any)?.nextCursor ?? null;
}
```

### Changes to `datafn/client/src/kv.ts`

The KV signal's manual unwrap logic (`kv.ts:417-432`) becomes simpler — after the query signal itself unwraps the envelope, the KV signal only needs to extract `.value` from the first record in the array (rather than navigating `queryResult.data[0].value`).

### Changes to example apps

`App.svelte` and any other consumers can use the clean path:
```svelte
$: todoData = visibleTodos?.data ?? [];
<!-- {#each todoData as todo} works directly -->
```

## Notes

- The KV signal in `kv.ts` already performs the exact unwrap pattern proposed here (extracts values from `queryResult.data`), confirming this is the expected direction — it was just never applied to table query signals.
- `client.query()` should continue returning `{ data, nextCursor }` — the unwrap happens only at the signal boundary, not in the query API itself. Direct `client.query()` callers who need pagination metadata are unaffected.
- The `applyOptimisticPatch` function in `querySignal.ts` currently handles three shapes: `result.data` array, direct array, and single record. After the unwrap, only the direct array and single record branches are needed — the `result.data` branch becomes dead code within the signal context and can be removed.
