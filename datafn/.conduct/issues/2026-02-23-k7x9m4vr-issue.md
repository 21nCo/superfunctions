## Summary

Three related issues affect the DataFn client library and example app, all stemming from incremental development by separate agents that each solved problems locally without consolidating the overall API surface. (1) The sync engine has no awareness of browser connectivity state — there is no `navigator.onLine` check, no `online`/`offline` event listener, and no observable signal the UI can use to show connection status. The engine silently retries with backoff, leaving users unaware of why their app isn't syncing. (2) The todo example app manually reimplements mode-switching with `export let client`, `clientStore = writable(client)`, and `switchMode()` instead of using the existing `SwitchableClient` that was purpose-built for this. (3) The client library and Svelte adapter each export two parallel APIs (`createDatafnClient` + `createSwitchableClient`, `toSvelteStore` + `toReactiveSvelteStore`) where the "advanced" version is strictly better and should be the default.

## Historical Context: How This Happened

The current API surface is the result of three separate development phases by different agents, each adding alongside rather than refactoring:

### Phase 1 — Initial Client (pre-Feb 2026)

`createDatafnClient` was the only client factory. It creates a one-shot client bound to a fixed auth context and storage adapter. The Svelte adapter provided `toSvelteStore` which takes a concrete `DatafnSignal` and returns a Svelte `readable` store. No mode switching, no tenant switching.

### Phase 2 — SwitchableClient Added (Feb 12, 2026)

**Issue**: `2026-02-12-p8x2k4m7-issue` — User asked about multi-tenant switching.
**Completion**: `2026-02-12-p8x2k4m7-completion` — Agent built `createSwitchableClient()` as a separate wrapper around `createDatafnClient`.

The agent chose not to modify `createDatafnClient` itself ("Option C: stable Proxy wrapper"). This was locally reasonable — avoid breaking the existing API — but created the first duplication. The `SwitchableClient` has a Proxy that always delegates to the current `realClient`, `switchContext()` for tenant switching, and `subscribeClient()` for lifecycle observation.

Meanwhile, the todo example app needed a simpler sync/local-only toggle. Instead of using `SwitchableClient` (which was tenant-focused and required `AuthContext`), a different agent added manual `makeClient()` + `switchMode()` to `datafn.ts` with a module-level `export let client`. This introduced a parallel pattern for mode-switching that ignored the existing `SwitchableClient`.

### Phase 3 — Signal Rebinding Fix (Feb 23, 2026)

**Issue**: `2026-02-23-m6bx9tkf-issue` — After `switchMode()`, all Svelte signal stores went dead because `client.destroy()` disposes signals.
**Completion**: `2026-02-23-m6bx9tkf-completion` — Agent added:

1. `toReactiveSvelteStore(clientRef, signalFactory)` to `@datafn/svelte` — auto-recreates signals on client switch.
2. `clientStore = writable(client)` to the todo app's `datafn.ts` — a Svelte store the reactive adapter can subscribe to.
3. `wrapSubscribeClient()` helper to adapt `SwitchableClient.subscribeClient` into a `ClientRef`.

The agent was instructed to be additive (keep `toSvelteStore` for backward compatibility). This created the second duplication — `toSvelteStore` (static, breaks on switch) alongside `toReactiveSvelteStore` (reactive, handles switching). The todo app ended up with three exports (`client`, `clientStore`, `switchMode`) instead of using `SwitchableClient`.

### Result: Accumulated Debt

| Layer | What was added | Why | What it duplicates |
|---|---|---|---|
| `createDatafnClient` | Original client factory | First implementation | — |
| `createSwitchableClient` | Proxy wrapper + `subscribeClient` + `switchContext` | Multi-tenant support | Superset of `createDatafnClient` |
| `toSvelteStore` | Static signal → Svelte store | First Svelte binding | — |
| `toReactiveSvelteStore` | Reactive signal factory → Svelte store | Fix signal death on switch | Superset of `toSvelteStore` |
| `clientStore` (todo app) | Svelte writable holding client | Feed `toReactiveSvelteStore` | Reimplements `subscribeClient` |
| `switchMode` (todo app) | Manual destroy+recreate | Toggle sync/local-only | Reimplements `SwitchableClient.switchContext` |

## Observed Errors/Symptoms

### Symptom 1: No offline awareness in sync engine or UI

- No `navigator.onLine` check anywhere in `datafn/client/src/` (confirmed by grep: zero matches).
- No `window.addEventListener("online", ...)` or `window.addEventListener("offline", ...)` listeners.
- When the browser goes offline, the push loop silently fails and backs off. The pull loop emits `sync_failed` events and stops until the next trigger (visibility change, focus, timer).
- There is no observable "connectivity state" signal that a UI component can subscribe to.
- The user has no way to know the app is offline except by noticing data isn't syncing.

### Symptom 2: Todo app uses manual mode-switching instead of SwitchableClient

- `datafn/examples/todo-app/client/src/lib/datafn.ts` exports `client`, `clientStore`, and `switchMode` — a hand-rolled pattern that duplicates `SwitchableClient`'s `subscribeClient` and `switchContext`.
- `App.svelte` line 82 uses `$: client = $clientStore` to keep a reactive reference — this is the workaround that `SwitchableClient`'s Proxy makes unnecessary.
- `App.svelte` line 88 references `initialClient` for `onMount` logic, creating a stale-reference risk if the client is switched before mount completes.

### Symptom 3: Doubled API surface confuses consumers

- `@datafn/client` exports both `createDatafnClient` and `createSwitchableClient`. Consumers must choose between them upfront and migrate if they later need switching.
- `@datafn/svelte` exports both `toSvelteStore` and `toReactiveSvelteStore`. Consumers who start with `toSvelteStore` silently break when they add mode/tenant switching.
- `wrapSubscribeClient` exists solely as a bridge between the two patterns — it wouldn't be needed if there was one unified API.

## Root Causes

### Root Cause 1: SyncEngine has no browser connectivity awareness

**Location:** `datafn/client/src/sync/engine.ts`, lines 96–124 (`start()`), 268–281 (`onVisibilityChange`/`onWindowFocus`)

**Current code:**

```typescript
// Lines 109-118: Only registers visibility and focus listeners
if (typeof document !== "undefined" && document.addEventListener) {
  document.addEventListener("visibilitychange", this.boundOnVisibilityChange);
}
if (typeof window !== "undefined" && window.addEventListener) {
  window.addEventListener("focus", this.boundOnWindowFocus);
}
```

**Expected behavior:** The sync engine should:
1. Listen for `window.addEventListener("online", ...)` and `window.addEventListener("offline", ...)` events.
2. When offline: pause the push interval (don't waste CPU/battery on doomed requests), stop pull attempts, and emit a `sync_offline` event the UI can observe.
3. When online: resume the push loop, trigger an immediate pull, and emit a `sync_online` event.
4. Expose a reactive `connectivity` signal or state (e.g., `syncEngine.isOnline` or a `connectivity_changed` event) so framework adapters can surface it.

**Actual behavior:** The engine is completely unaware of connectivity. It runs the push timer regardless, each push attempt fails after retries (burning up to 4 network requests with backoff delays before giving up), then the push interval itself backs off. There is no proactive pause and no event emitted.

**Impact:** Poor UX — users see stale data with no explanation. Wasted battery/network on doomed requests. No way for the UI to show "You're offline" without custom application code.

**Evidence:** `grep -r "navigator.onLine\|online.*event\|offline.*event" datafn/client/src/` returns zero matches.

### Root Cause 2: Todo app reimplements SwitchableClient manually

**Location:** `datafn/examples/todo-app/client/src/lib/datafn.ts`, lines 184–205

**Current code:**

```typescript
export let client = makeClient("sync");

export const clientStore = writable(client);

export function switchMode(mode: AppMode) {
  client = makeClient(mode);
  clientStore.set(client);
  return client;
}
```

**Expected behavior:** The todo app should use `createSwitchableClient` (which already exists in `@datafn/client`) and its built-in `subscribeClient` / `switchContext` to handle mode switching. This would eliminate the need for `clientStore`, `switchMode`, and the mutable `export let client`.

**Actual behavior:** The app maintains three exports (`client`, `clientStore`, `switchMode`) that reimplement the same capabilities as `SwitchableClient`:
- `client` (mutable module-level reference) = `SwitchableClient.client` (stable Proxy)
- `clientStore` (Svelte writable) = `SwitchableClient.subscribeClient` (lifecycle observer)
- `switchMode()` (destroy + recreate) = `SwitchableClient.switchContext` (managed lifecycle with queue serialization)

The manual version lacks the switch queue serialization, the destroyed guard, and the proper lifecycle event emission that `SwitchableClient` provides.

**Impact:** DX confusion — the example app teaches the wrong pattern. Risk of stale references (`initialClient` used in `onMount` at `App.svelte` line 88). Missing serialization for rapid mode toggles.

**Evidence:** `SwitchableClient` was implemented in issue `2026-02-12-p8x2k4m7` but the todo app was never migrated to use it.

### Root Cause 3: Dual client API — `createDatafnClient` vs `createSwitchableClient`

**Location:** `datafn/client/src/index.ts`, lines 5–17

**Current code:**

```typescript
export {
  createDatafnClient,
  type DatafnClient,
  type DatafnClientConfig,
  type DatafnRemoteAdapter,
} from "./client.js";

export {
  createSwitchableClient,
  type SwitchableClient,
  type SwitchableClientConfig,
} from "./switchableClient.js";
```

**Expected behavior:** A single client factory that supports both simple and switchable use cases. The `SwitchableClient` Proxy overhead is negligible (one property-access indirection), and apps that never switch simply never call `switchContext`.

**Actual behavior:** Two separate factories with different config shapes and different return types:
- `createDatafnClient`: accepts `storage: DatafnStorageAdapter | DatafnStorageFactory`, returns `DatafnClient<S>`.
- `createSwitchableClient`: accepts `storage: DatafnStorageFactory`, `initialAuth: AuthContext`, returns `SwitchableClient<S>` (which wraps a `DatafnClient<S>`).

The `SwitchableClient` interface has `{ client, switchContext, currentContext, destroy, subscribeClient }` — a different shape from `DatafnClient`. This means switching from one to the other is a breaking change in consumer code.

**Impact:** Consumers must choose upfront. Choosing `createDatafnClient` first (simpler) and later needing switching requires changing every import and call site. The two return types don't share an interface.

### Root Cause 4: Dual Svelte adapter — `toSvelteStore` vs `toReactiveSvelteStore`

**Location:** `datafn/svelte/src/toSvelteStore.ts`, lines 31–54 and 96–142

**Current code (toSvelteStore):**

```typescript
export function toSvelteStore<T>(signal: DatafnSignal<T>): DatafnSvelteStore<T> {
  return readable(
    {
      data: signal.get(),
      loading: signal.loading,
      error: signal.error,
      refreshing: signal.refreshing,
    },
    (set) => {
      const unsubscribe = signal.subscribe((value: T) => { ... });
      return unsubscribe;
    }
  );
}
```

**Current code (toReactiveSvelteStore):**

```typescript
export function toReactiveSvelteStore<T, C = any>(
  clientRef: ClientRef<C>,
  signalFactory: (client: C) => DatafnSignal<T>,
): DatafnSvelteStore<T> {
  return readable(
    { data: undefined as unknown as T, loading: true, error: null, refreshing: false },
    (set) => {
      let currentSignal: DatafnSignal<T> | null = null;
      let currentUnsubSignal: (() => void) | null = null;
      const unsubClient = clientRef.subscribe((client) => {
        currentUnsubSignal?.();
        currentSignal?.dispose();
        currentSignal = signalFactory(client);
        // ... subscribe to new signal ...
      });
      return () => { unsubClient(); currentUnsubSignal?.(); currentSignal?.dispose(); };
    },
  );
}
```

**Expected behavior:** One function that handles both static and reactive use cases. `toReactiveSvelteStore` is strictly a superset — if the client never changes, the factory runs once and behaves identically to `toSvelteStore`.

**Actual behavior:** Two exported functions. `toSvelteStore` silently breaks when the client switches (signals go dead, store stops updating). Consumers who start with `toSvelteStore` discover this only at runtime.

**Impact:** API confusion. Silent breakage. Every consumer will eventually need `toReactiveSvelteStore` anyway — the static version is a trap.

## Proposed Fixes

### Fix 1: Add connectivity awareness to SyncEngine

1. Add `online`/`offline` event listeners in `SyncEngine.start()`:
   ```typescript
   if (typeof window !== "undefined") {
     window.addEventListener("online", this.boundOnOnline);
     window.addEventListener("offline", this.boundOnOffline);
   }
   ```
2. When `offline` fires: pause the push interval, set `this.isOnline = false`, emit `connectivity_changed` event.
3. When `online` fires: resume push interval, trigger immediate `pullNow()` + `processPush()`, set `this.isOnline = true`, emit `connectivity_changed` event.
4. Check `navigator.onLine` before each push attempt as a fast-fail (skip the request entirely if offline).
5. Expose connectivity state via the event bus so framework adapters can create reactive stores (e.g., a Svelte store for "isOnline").
6. Clean up listeners in `SyncEngine.stop()`.

### Fix 2: Migrate todo app to SwitchableClient

1. Replace `datafn.ts`'s manual `makeClient` + `switchMode` + `clientStore` with `createSwitchableClient`.
2. Use `wrapSubscribeClient(subscribeClient)` as the `clientRef` for `toReactiveSvelteStore` calls in `App.svelte`.
3. Replace `switchMode()` calls with `switchContext()` (or a thin wrapper that adjusts sync config).
4. Remove the mutable `export let client` and `clientStore = writable(client)`.
5. Use the `SwitchableClient.client` Proxy for all imperative mutations — no `$: client = $clientStore` needed.

**Note:** `SwitchableClient` currently requires `initialAuth: AuthContext` and `storage: DatafnStorageFactory`. For the todo app (no auth), `initialAuth` should be made optional (default to `{}`), and storage factory should accept a simple adapter as well.

### Fix 3: Unify to one client factory

1. Merge `SwitchableClient` capabilities into `createDatafnClient`:
   - Return type includes `switchContext`, `subscribeClient`, `currentContext` alongside the existing `DatafnClient` surface.
   - Internally, always use the Proxy pattern.
   - `switchContext` and `subscribeClient` are always available; apps that don't switch simply never call them.
2. Accept `storage` as either `DatafnStorageAdapter` (wrapped in a factory internally) or `DatafnStorageFactory`.
3. Make `initialAuth` / `authContext` optional (default to `{}` or omitted).
4. Deprecate `createSwitchableClient` — keep as a re-export of `createDatafnClient` for one version cycle.
5. Update `@datafn/client` `index.ts` to export the unified type.

### Fix 4: Unify to one Svelte store adapter

1. Rename `toReactiveSvelteStore` to `toSvelteStore` (replacing the old static version).
2. The new `toSvelteStore` takes `(clientRef, signalFactory)` — the reactive version.
3. Remove the old `toSvelteStore(signal)` signature entirely.
4. Remove `wrapSubscribeClient` — the unified client's `subscribeClient` already conforms to `ClientRef`.
5. Update `@datafn/svelte` `index.ts` accordingly.

## Notes

- The `@datafn/client` and `@datafn/svelte` packages are pre-1.0 with no known external consumers. A breaking API consolidation is low-risk now but becomes increasingly costly as adoption grows.
- The `SwitchableClient` Proxy overhead is negligible — one property-access indirection per call. In a browser context with DOM rendering, IndexedDB I/O, and network calls, this is unmeasurable.
- Fix 3 (unified client) and Fix 4 (unified Svelte adapter) should be implemented together to avoid an intermediate state where the client is unified but the Svelte adapter still has two variants.
- Fix 1 (offline awareness) is independent and can be implemented separately.
- Fix 2 (todo app migration) depends on Fix 3 being completed first (so the todo app can use the unified client API), OR it can be done as an intermediate step using `createSwitchableClient` directly.
- The `SwitchableClient` currently requires `initialAuth: AuthContext` which makes it awkward for apps without authentication (like the todo app). Making `initialAuth` optional is a prerequisite for Fix 2/Fix 3.
- For Fix 1, the `navigator.onLine` API is not 100% reliable (it can report `true` when behind a captive portal). The implementation should treat it as a hint: skip requests when definitely offline, but don't assume connectivity means the server is reachable. The existing retry-with-backoff logic remains the authoritative mechanism.
