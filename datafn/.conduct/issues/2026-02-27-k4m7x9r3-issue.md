### User-reported issue description (verbatim)

> The newly generated schema using latest datafn CLI didn't generate a namespace column (`__ns`) which it should have. DataFn is almost always used in a multi-user context, so namespace isolation should be the default behavior rather than requiring developers to discover and set `multiTenant: true`. The current default of `false` is a security footgun — forgetting the flag silently produces a schema with no data isolation between users/tenants.

## Summary

**Severity: Medium** — The `multiTenant` flag in the datafn schema defaults to `false`/`undefined`, meaning the `__ns` namespace column and index are only generated when developers explicitly set `multiTenant: true`. Since datafn is fundamentally a multi-user backend framework, namespace isolation is a core requirement for virtually all use cases. The current default inverts the expected behavior: developers must opt-in to security rather than opt-out. Forgetting the flag produces a schema with no row-level data isolation — a silent security vulnerability.

---

## Observed Errors / Symptoms

**Symptom:** Generated Drizzle schema (`datafn-schema.drizzle.ts`) contains no `__ns` column on any table, and no namespace index. All tables are flat with no tenant discrimination.

**Generated output (actual):**
```ts
export const todos = pgTable("todos", {
  completed: boolean("completed").notNull().default(false),
  createdAt: bigint("created_at", { mode: "number" }).notNull(),
  id: text("id").primaryKey(),
  // ... no __ns column
});
```

**Expected output (for a multi-user app):**
```ts
export const todos = pgTable("todos", {
  __ns: text("__ns").notNull(),
  completed: boolean("completed").notNull().default(false),
  createdAt: bigint("created_at", { mode: "number" }).notNull(),
  id: text("id").primaryKey(),
  // ...
}, (table) => [
  index("idx_todos___ns").on(table.__ns),
]);
```

**No error is thrown** — the schema generates successfully without the column. This is the core problem: the failure mode is silent.

## Root Causes

### RC-1: `multiTenant` defaults to `undefined` (falsy) in schema validation

**Location:** [datafn/core/src/schema.ts:191-198](datafn/core/src/schema.ts#L191-L198)

```ts
// Pass through multiTenant flag (default: false/undefined)
const multiTenant = (s as any).multiTenant === true ? true : undefined;

return ok({
  resources: normalizedResources,
  relations: relations as DatafnSchema["relations"],
  ...(multiTenant ? { multiTenant } : {}),  // Only included when explicitly true
});
```

The validation function treats `multiTenant` as opt-in. When the flag is absent (the default case), it is excluded from the validated schema entirely. This means downstream consumers (codegen, server middleware) see `undefined` and skip namespace isolation.

**The default should be inverted:** `multiTenant` should default to `true` unless explicitly set to `false`.

### RC-2: Codegen gates `__ns` generation on strict `=== true` check

**Location:** [datafn/cli/src/drizzle-codegen.ts:35](datafn/cli/src/drizzle-codegen.ts#L35)

```ts
const isMultiTenant = schema.multiTenant === true;
```

This is correct behavior given RC-1, but it means the entire namespace column/index generation path is skipped when `multiTenant` is not explicitly `true`. Four code blocks are gated on this flag:
- Line 55-58: `__ns` column on resource tables
- Line 70-72: `__ns` index on resource tables
- Line 111-117: `__ns` column on join tables
- Line 166-169: `__ns` index on join tables

### RC-3: `DatafnSchema` type declares `multiTenant` as optional with no default semantics

**Location:** [datafn/core/src/types.ts](datafn/core/src/types.ts)

```ts
export type DatafnSchema = {
  resources: DatafnResourceSchema[];
  relations?: DatafnRelationSchema[];
  /** When true, Drizzle codegen adds __ns column + index for row-level namespace isolation. */
  multiTenant?: boolean;
};
```

The JSDoc says "When true" — implying opt-in. The type itself is `boolean | undefined`, defaulting to the unsafe path.

### RC-4: Server-side namespace wrapping also gated on this flag

**Location:** [packages/db/src/adapter/row-level-namespace.ts](packages/db/src/adapter/row-level-namespace.ts), [datafn/server/src/server.ts](datafn/server/src/server.ts)

The row-level namespace adapter wrapper that filters queries by `__ns` is also only applied when `multiTenant` is true. This means the server routes serve unscoped data to all users — a data leak.

### RC-5: The spec designed it as opt-in

**Location:** [datafn/.conduct/specs/2026-02-26-new-k7r4m9x2-spec/SPEC.md](datafn/.conduct/specs/2026-02-26-new-k7r4m9x2-spec/SPEC.md)

The spec explicitly documents:
```ts
export default defineSchema({
  multiTenant: true, // NEW: declares multi-tenant mode
  resources: [...],
});
```

The spec designed namespace isolation as a feature to opt into, rather than recognizing it as a fundamental requirement for any multi-user datafn deployment. This is the upstream design decision that led to the current behavior.

## Proposed Fixes

### Fix A (Recommended): Invert the default — `multiTenant` defaults to `true`

1. **`datafn/core/src/schema.ts`**: Change validation to default `multiTenant` to `true`:
   ```ts
   const multiTenant = (s as any).multiTenant === false ? false : true;
   ```

2. **`datafn/core/src/types.ts`**: Update JSDoc to reflect new default:
   ```ts
   /** Defaults to true. Set to false to disable row-level namespace isolation (single-tenant mode). */
   multiTenant?: boolean;
   ```

3. **`datafn/cli/src/drizzle-codegen.ts`**: Change check to treat `undefined` as `true`:
   ```ts
   const isMultiTenant = schema.multiTenant !== false;
   ```

4. **Server-side namespace wrapping**: Same inversion — apply namespace wrapper unless `multiTenant === false`.

5. **Update `defineSchema` type**: Optionally rename the field or add `singleTenant?: boolean` as an alias for clarity.

### Fix B (Alternative): Keep opt-in but add a CLI warning

If backwards compatibility is a concern, keep the default but emit a loud CLI warning when `multiTenant` is not set:
```
⚠️  WARNING: multiTenant is not set. All data will be unscoped.
    Add `multiTenant: true` to your schema for row-level namespace isolation.
```

This is a weaker fix — it still allows the insecure default but at least surfaces it.

### Fix C: Regenerate todo-app example schema

After Fix A or B, regenerate the todo-app's Drizzle schema so it serves as a correct reference implementation with `__ns` columns.

## Notes

- This is a design-level issue, not a bug in the implementation. The codegen, validation, and server all work correctly given the current design — the problem is that the default is wrong for datafn's use case.
- Inverting the default is a breaking change for any existing deployment that relies on `multiTenant` being `undefined`/`false`. However, since the namespace feature was just introduced (spec `2026-02-26-new-k7r4m9x2`), the blast radius is minimal — no production deployments exist yet with the old default.
- The `singleTenant` mode (no `__ns`) is still valid for edge cases like single-user desktop apps, embedded databases, or internal tools with no auth. These should explicitly opt out.
