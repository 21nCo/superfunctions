## Summary

**Severity: Critical/High** — Two related issues prevent many-many relation changes from propagating to other clients via pull, and create a maintenance/correctness hazard across the codebase.

**Issue 1 (Pull Gap):** The client's `pullNow()` and WebSocket `hello` only build cursors from `schema.resources` — they never include join store keys like `join_task_tags_tag`. Since the server's `executePullCanonical` only fetches changes for resources present in `request.cursors`, join deltas recorded by `extractJoinDeltas()` during push are invisible to other clients. Many-many relation changes pushed by Client A will never arrive at Client B through incremental pull.

**Issue 2 (Duplicated Derivation):** The join store name pattern `join_{from}_{relation}_{to}` is derived independently in **7+ locations** across client and server with no shared utility. One location (`export.ts`) uses the wrong field (`relation.field` instead of `relation.relation`), which is a latent correctness bug. The `@datafn/core` package exports no join store name utility despite being the natural home for shared logic.

---

## Observed Errors/Symptoms

- Client A performs a `relate` mutation (e.g. assigning tags to a todo)
- Push succeeds — join deltas are correctly recorded on the server in the changelog under resource key `join_todos_tags_tag`
- Client B calls `pullNow()` — its cursors map contains only `{ todos: "5", tags: "5" }` — no `join_todos_tags_tag` entry
- Server `executePullCanonical` iterates `Object.entries(request.cursors)` and never queries the `join_todos_tags_tag` changelog
- Client B receives an empty join delta set — the relation change is silently lost
- Same issue on WebSocket reconnect: `hello` message sends cursors without join stores, so the server cannot detect that join changes are pending
- Export/import may silently export join data under the wrong store name when `relation.field !== relation.relation`

## Root Causes

### Root Cause 1: `pullNow()` cursors exclude join store keys

**Location:** `datafn/client/src/sync/engine.ts` (lines 587–593)

**Current code:**

```typescript
// Lines 587-593: Build cursors only from schema.resources
for (const res of this.schema.resources) {
  if (res.isRemoteOnly) continue;
  
  // Get per-table cursor, default to "0" if not set
  const cursor = await this.storage.getCursor(res.name) || "0";
  cursors[res.name] = cursor;
}
```

**Expected behavior:** The cursors map should also include entries for all join store keys derived from `schema.relations` (for many-many relations). For example, if the schema defines a many-many relation `todos ↔ tags`, the cursors map should include `join_todos_tags_tag: "0"`.

**Actual behavior:** Only `schema.resources` entries are iterated. Join store keys are never included in the cursors map.

**Impact:** The server's `executePullCanonical` (pull.ts:255) iterates `Object.entries(request.cursors)` and only fetches changes for resources in that map. Join deltas recorded under `join_*` resource keys are never queried.

### Root Cause 2: WebSocket `hello` cursors exclude join store keys

**Location:** `datafn/client/src/sync/engine.ts` (lines 186–192)

**Current code:**

```typescript
// Lines 186-192: Same pattern — only schema.resources
for (const res of this.schema.resources) {
  if (res.isRemoteOnly) continue;
  
  const cursor = await this.storage.getCursor(res.name) || "0";
  cursors[res.name] = cursor;
}
```

**Expected behavior:** Same as Root Cause 1 — should include join store keys.

**Actual behavior:** Identical to `pullNow()`. When the WS reconnects and sends `hello`, the server has no way to know the client's join store cursor positions.

### Root Cause 3: Post-push cursor advancement does include join stores — but pull never uses them

**Location:** `datafn/client/src/sync/engine.ts` (lines 908–914)

After a successful push, the client correctly advances per-table cursors from the push response — including join store keys (since `push.ts` now records `resourceSeqs` for join deltas at line 400). However, this stored join cursor is never read back by `pullNow()` or `hello`, so it has no effect on subsequent pulls.

```typescript
// Lines 908-914: This correctly stores join store cursors from push response...
if (pushResult.cursors) {
  for (const [resource, cursor] of Object.entries(pushResult.cursors)) {
    await setCursorMonotonically(this.storage, resource, cursor);
  }
}
// ...but pullNow() at line 587 never reads them back
```

### Root Cause 4: `export.ts` uses wrong field for join store name derivation

**Location:** `datafn/client/src/export.ts` (lines 78–84)

**Current code:**

```typescript
function resolveJoinStoreName(relation: any): string {
  // Match the server-side join store naming convention
  // Format: join_{from}_{fromField}_{to}
  const fromResource = relation.from;
  const field = relation.field;           // <-- BUG: should be relation.relation
  const toResource = relation.to;
  return `join_${fromResource}_${field}_${toResource}`;
}
```

**Expected behavior:** Should use `relation.relation` (the relation name), matching every other derivation site in the codebase.

**Actual behavior:** Uses `relation.field`, which is a different schema property (not always equal to `relation.relation`). This produces wrong join store names, so export reads from a non-existent store and import writes to a mismatched store name.

**Evidence — canonical pattern comparison:**

| Location | Pattern | Uses |
|---|---|---|
| `client/src/offline/relations.ts:64` | `join_${from}_${relName}_${to}` | `relationName` param (correct) |
| `client/src/adapters/indexedDbStorage.ts:52` | `join_${from}_${relName}_${to}` | `relationName` param (correct, duplicate) |
| `server/src/execution/mutation/relations.ts:302` | `join_${mut.resource}_${relName}_${to}` | loop variable `relName` (correct) |
| `server/src/execution/sync/clone.ts:205` | `join_${relation.from}_${relation.relation}_${relation.to}` | `relation.relation` (correct) |
| `server/src/execution/sync/reconcile.ts:126` | `join_${relation.from}_${relation.relation}_${relation.to}` | `relation.relation` (correct) |
| `client/src/sync/engine.ts:763` | `join_${relation.from}_${relation.relation}_${relation.to}` | `relation.relation` (correct) |
| `client/src/sync/cloneUp.ts:510` | `join_${f}_${relName}_${t}` | `rel.relation ?? "rel"` (correct) |
| **`client/src/export.ts:84`** | **`join_${from}_${field}_${to}`** | **`relation.field`** (**BUG**) |

### Root Cause 5: No shared utility for join store name derivation

**Location:** `datafn/core/src/index.ts` — no join store utility exported

The core package (`@datafn/core`) exports types, schema validation, DFQL normalization, and KV utilities — but has no join store name derivation function. The pattern `join_{from}_{relation}_{to}` is independently derived in 7+ locations across client and server:

1. `client/src/offline/relations.ts:59` — exported `getJoinStoreName()` (canonical implementation)
2. `client/src/adapters/indexedDbStorage.ts:46` — local `getJoinStoreName()` (exact duplicate of #1)
3. `client/src/export.ts:78` — local `resolveJoinStoreName()` (**uses wrong field**)
4. `client/src/sync/engine.ts:763` — inline in `reconcileNow()`
5. `client/src/sync/cloneUp.ts:510` — inline in `enumerateJoinStores()`
6. `server/src/execution/mutation/relations.ts:302` — inline in `extractJoinDeltas()`
7. `server/src/execution/sync/clone.ts:205` — inline in `executeClone()`
8. `server/src/execution/sync/reconcile.ts:126` — inline in `executeReconcile()`

Additionally, the server uses a separate naming convention for the **actual DB table**: `__datafn_join_{from}_{relation}` (without `_{to}` suffix), which is distinct from the logical client store key. This dual naming adds to the confusion — clone.ts:207 and reconcile.ts:128 both have the DB table derivation inline too.

## Proposed Fixes

### Fix 1: Add join store cursors to `pullNow()` and WS `hello`

In `engine.ts`, after iterating `schema.resources` to build the cursors map, also iterate `schema.relations` for many-many relations and add their join store keys:

```typescript
// After the existing schema.resources loop:
if (this.schema.relations) {
  for (const relation of this.schema.relations) {
    if (relation.type !== "many-many") continue;
    const joinStoreKey = getJoinStoreName(relation.from, relation.relation, relation.to);
    const cursor = await this.storage.getCursor(joinStoreKey) || "0";
    cursors[joinStoreKey] = cursor;
  }
}
```

Apply the same change to both the `pullNow()` cursor-building block (line 587) and the WS `onopen` hello cursor-building block (line 186).

### Fix 2: Create shared `getJoinStoreKey()` in `@datafn/core`

Add a shared utility function to `datafn/core/src/`:

```typescript
/**
 * Derive the logical join store key used by clients and change tracking.
 * Format: join_{fromResource}_{relationName}_{toResource}
 */
export function getJoinStoreKey(from: string, relation: string, to: string): string {
  return `join_${from}_${relation}_${to}`;
}

/**
 * Derive the actual DB table name for a join table.
 * Format: __datafn_join_{fromResource}_{relationName}
 * (can be overridden by relation.joinTable in schema)
 */
export function getJoinTableName(from: string, relation: string): string {
  return `__datafn_join_${from}_${relation}`;
}

/**
 * Enumerate all join store keys for a schema's many-many relations.
 * Useful for building cursor maps, reconcile payloads, etc.
 */
export function enumerateJoinStoreKeys(
  relations: DatafnRelationSchema[],
  resourceFilter?: Set<string>,
): string[] {
  const keys: string[] = [];
  for (const rel of relations) {
    if (rel.type !== "many-many") continue;
    const from = rel.from as string;
    const to = rel.to as string;
    if (resourceFilter && !resourceFilter.has(from)) continue;
    keys.push(getJoinStoreKey(from, rel.relation, to));
  }
  return keys;
}
```

Then replace all 7+ inline derivations with imports from `@datafn/core`.

### Fix 3: Fix `export.ts` `resolveJoinStoreName`

Replace `relation.field` with `relation.relation` — or better, delete `resolveJoinStoreName()` entirely and import the shared utility from Fix 2.

## Notes

- The **server-side pull implementation already handles join store changes correctly** (pull.ts:284-312) — it checks `resource.startsWith("join_")` and routes to the `joins` bucket. The only problem is the client never sends join store cursors, so the server never queries for them.
- The **push change tracking already records join deltas under the correct join store key** (push.ts:396-408 via `extractJoinDeltas`). These deltas sit in the changelog waiting to be fetched, but no client ever asks for them.
- The **apply logic already handles join deltas correctly** (apply.ts:201-229) — it processes `result.joins` upserts and deletes. The data just never arrives because pull never requests it.
- The **clone path works correctly** because clone.ts directly queries the DB for join rows and returns them under the logical store key, bypassing the cursor-based changelog mechanism entirely.
- The `reconcileNow()` method already handles join stores correctly (engine.ts:759-777) — it iterates `schema.relations` and builds join store keys inline. This is the exact pattern that `pullNow()` and `hello` need to adopt.
- This issue was uncovered during investigation of the spurious `{id}` upsert bug (`2026-02-24-r7k3m9x4-issue`), which is now fixed. The spurious upsert fix means relation mutations no longer corrupt primary resource records, but the join delta propagation gap remains.
- Since the library is not yet used externally, protocol changes are safe without backward-compatibility concerns.
