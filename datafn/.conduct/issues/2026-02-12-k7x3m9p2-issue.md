## Summary

The todo-app example crashes with `Store not found: todos` on any mutation because `IndexedDbStorageAdapter` is constructed without the schema. Without the schema, the `onupgradeneeded` handler skips creating per-resource IndexedDB object stores (`todos`, `categories`, join tables). When the client later attempts to write to these stores, `getStore()` finds them missing and throws. This is a **critical** bug — it makes the entire offline/local-first mutation path non-functional.

## Observed Errors / Symptoms

- **Error**: `Uncaught (in promise) Error: Store not found: todos`
- **Location in stack**: `IndexedDbStorageAdapter.getStore()` at `indexedDbStorage.ts:285-286`
- **Trigger**: Any mutation (insert, replace, merge, delete) against any schema resource
- **Scope**: Affects all resources, not just `todos` — `categories` and join stores are equally missing

## Root Causes

### Root Cause 1: Example app does not pass schema to IndexedDbStorageAdapter

**Location**: `datafn/examples/todo-app/client/src/lib/datafn.ts`, line 140

**Current code**:

```typescript
// line 140
storage: new IndexedDbStorageAdapter("todo-app-db"),
```

**Expected behavior**: The adapter should receive the schema so it can create per-resource object stores during `onupgradeneeded`.

**Actual behavior**: Only `dbName` is passed. The constructor's `schema` parameter defaults to `undefined`:

```typescript
// datafn/client/src/adapters/indexedDbStorage.ts, lines 124-128
constructor(
  dbName: string = DB_NAME,
  resources?: string[],
  schema?: DatafnSchema,
) {
```

Without `schema`, the entire resource-store creation block is skipped:

```typescript
// datafn/client/src/adapters/indexedDbStorage.ts, line 177
if (this.schema) {
  // 1. Resource Stores — SKIPPED when schema is undefined
  for (const resource of this.schema.resources) {
    if (!db.objectStoreNames.contains(resource.name)) {
      const store = db.createObjectStore(resource.name, { keyPath: "id" });
      // ... index creation ...
    }
  }
  // 2. Join Stores (Many-Many) — also SKIPPED
}
```

Only the built-in stores (`kv`, `meta`, `changelog`) are created, since they live outside the `if (this.schema)` guard.

**Impact**: No resource object stores exist. Every call to `getStore("todos", ...)` or `getStore("categories", ...)` throws:

```typescript
// datafn/client/src/adapters/indexedDbStorage.ts, lines 283-286
const db = await this.dbPromise;
if (!db.objectStoreNames.contains(storeName)) {
    throw new Error(`Store not found: ${storeName}`);
}
```

**Evidence**: The stack trace confirms the throw originates at `getStore` → `upsertRecord` → `handleOfflineMutation`.

### Root Cause 2 (Systemic): `createDatafnClient` does not wire schema into the storage adapter

**Location**: `datafn/client/src/client.ts`, lines 364-425

**Current code**:

```typescript
// lines 410-412
} else {
  // Direct storage adapter
  resolvedStorage = config.storage;
```

`createDatafnClient` receives **both** the schema and the storage adapter, but never connects them. The schema is validated, enriched with built-in KV (line 343), and used throughout the client — but the storage adapter is used as-is, with no check that it has the necessary stores.

**Expected behavior**: Since `createDatafnClient` has full knowledge of the schema and the storage adapter, it should either:
- Validate that the adapter's stores match the schema (fail-fast with a clear error), or
- Automatically provide the schema to the adapter

**Actual behavior**: The adapter is used blindly. The mismatch between schema resources and actual IndexedDB stores is only discovered at mutation time, deep in the call stack, with a cryptic error message.

**Impact**: This is a **pit of failure** in the API design. Every consumer of `IndexedDbStorageAdapter` must independently remember to pass the schema. There is no safety net at the `createDatafnClient` level.

### Root Cause 3 (Edge case): Stale IndexedDB prevents store creation on re-runs

**Location**: `datafn/client/src/adapters/indexedDbStorage.ts`, lines 13-14, 136

**Current code**:

```typescript
const DB_VERSION = 2;
// ...
const request = indexedDB.open(dbName, DB_VERSION);
```

IndexedDB only fires `onupgradeneeded` when the version increases. If a user has previously opened the database (even without schema, creating only `kv`, `meta`, `changelog`), the database is already at version 2. On subsequent runs — even after fixing the constructor call to include the schema — `onupgradeneeded` will **not** fire, so the resource stores still won't be created.

**Expected behavior**: Adding the schema parameter should cause stores to be created.

**Actual behavior**: The fix only works on a fresh database. Existing databases require the user to manually delete them via DevTools, or the adapter must detect and handle this case.

**Impact**: Confusing developer experience — "I added the schema but it still doesn't work" — requires clearing IndexedDB manually.

## Proposed Fixes

### Fix 1 — Immediate (example app, one-line)

Pass the schema to the adapter:

```typescript
storage: new IndexedDbStorageAdapter("todo-app-db", undefined, schema),
```

### Fix 2 — API improvement: Static factory method (Option C)

Add a primary factory method to `IndexedDbStorageAdapter` that requires schema:

```typescript
static create(options: { dbName: string; schema: DatafnSchema }): IndexedDbStorageAdapter {
  return new IndexedDbStorageAdapter(
    options.dbName,
    options.schema.resources.map(r => r.name),
    options.schema,
  );
}
```

This makes the correct usage the obvious usage. The raw constructor can remain for backward compatibility but the factory becomes the documented API.

### Fix 3 — Safety net: Validation in `createDatafnClient` (Option B)

After resolving storage in `createDatafnClient`, run `healthCheck()` and throw a descriptive error if resource stores are missing:

```typescript
// After resolving storage, before returning client
if (resolvedStorage) {
  const health = await resolvedStorage.healthCheck();
  if (!health.ok) {
    throw createClientError(
      "STORAGE_INIT",
      `Storage adapter health check failed: ${health.issues.join("; ")}. ` +
      `Ensure schema is passed to IndexedDbStorageAdapter: ` +
      `IndexedDbStorageAdapter.create({ dbName, schema })`,
      { issues: health.issues },
    );
  }
}
```

### Fix 4 — Handle stale databases (Root Cause 3)

In the `IndexedDbStorageAdapter` constructor or an `ensureStores()` method, after opening the DB, check if expected resource stores exist. If not, close the DB, increment the version, and reopen to trigger `onupgradeneeded`:

```typescript
// After initial open, verify stores exist
const db = await this.dbPromise;
if (this.schema) {
  const missing = this.schema.resources.filter(
    r => !db.objectStoreNames.contains(r.name)
  );
  if (missing.length > 0) {
    db.close();
    // Reopen with bumped version to trigger onupgradeneeded
    this.dbPromise = this.openWithVersion(DB_VERSION + 1);
  }
}
```

**Recommended implementation order**: Fix 1 (immediate unblock) → Fix 2 (better API) → Fix 3 (safety net) → Fix 4 (stale DB handling).

## Notes

- The `createForUser()` static method also accepts `schema` as an optional parameter, making it equally susceptible to this bug when schema is omitted.
- The `validResources` parameter (2nd constructor arg) only controls `validateTableName()` checks — it does **not** create object stores. Even passing resource names without schema would not fix this.
- IndexedDB's constraint that object stores can only be created during `onupgradeneeded` makes lazy initialization non-trivial. The static factory (Fix 2) that ensures schema is present at construction time is the cleanest approach.
- The `healthCheck()` method already checks for missing resource stores (lines 706-712), but it's never called during client initialization — only available as an opt-in diagnostic.
