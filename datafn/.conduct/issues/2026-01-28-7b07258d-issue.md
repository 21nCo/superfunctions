## Summary

The `IndexedDbStorageAdapter` on the client side does not support multi-tenant or multiple user account scenarios. The adapter accepts a `dbName` parameter in its constructor (defaults to `"datafn_client_db"`), but there is no mechanism to automatically isolate data per user or tenant. Users must manually construct database names with user/tenant identifiers (e.g., `new IndexedDbStorageAdapter(\`my-app-db_${userId}\`)`), which is error-prone and requires manual user context management. Unlike other superfunctions codebases (e.g., `nucleus`, `devving`) that use patterns like `${databaseName}_${user}` for automatic user-based database isolation, datafn's client has no built-in support for this. The solution is to add an `AuthContextProvider` interface to `@superfunctions/auth` and allow `createDatafnClient` to accept this provider, which can extract user/tenant context and automatically construct isolated database names. This is a **Medium** severity issue affecting data isolation, security, and developer experience for multi-user applications.

## Observed Errors/Symptoms

1. **No Multi-User Data Isolation**: All users share the same IndexedDB database when using the default `dbName`, causing data leakage between users.

2. **Manual Database Name Construction Required**: Users must manually extract user IDs and construct database names like `new IndexedDbStorageAdapter(\`my-app-db_${userId}\`)`, which is error-prone and requires managing user context outside of datafn.

3. **No User Context in Client Initialization**: The `createDatafnClient` function has no way to access user/tenant context, making automatic database name construction impossible.

4. **Inconsistent with Other Superfunctions**: Other codebases (e.g., `nucleus/client/persistence/indexeddb/indexeddb.local.ts`) use patterns like `${databaseName}_${user}` for automatic user-based isolation, but datafn doesn't follow this pattern.

5. **Security Risk**: If users forget to include user ID in database name, multiple users' data will be stored in the same database, violating data isolation requirements.

6. **Poor Developer Experience**: Developers must manually handle user context extraction, database name construction, and client recreation when users switch accounts.

## Proposed Fixes

### Fix 1: Add AuthContextProvider Interface to @superfunctions/auth

**Location**: `packages/auth/src/types.ts`

Add the interface:
```typescript
/**
 * Provider for extracting authentication context on the client side
 * Used by client libraries like datafn to isolate data per user/tenant
 */
export interface AuthContextProvider<TContext = any> {
  /**
   * Get current authentication context (user ID, tenant ID, etc.)
   * This context is used to construct isolated storage identifiers
   * 
   * @returns The authentication context (e.g., { userId: string, tenantId?: string })
   */
  getContext(): Promise<TContext> | TContext;
}
```

```typescript

  AuthProviderConfig,
  AuthContextProvider, // Add this
```

### Fix 3: Use AuthContextProvider in createDatafnClient

**Location**: `client/src/client.ts:107-337`

Update `createDatafnClient` to use the provider:
```typescript
export function createDatafnClient<S extends DatafnSchema>(
  config: DatafnClientConfig<S>,
): DatafnClient<S> {
  // ... existing validation ...

  // Extract auth context if provider is configured
  let authContext: { userId: string; tenantId?: string } | undefined;
  if (config.authContextProvider) {
    const context = await config.authContextProvider.getContext();
    authContext = context as { userId: string; tenantId?: string };
  }

  // Resolve storage adapter
  let storage: DatafnStorageAdapter | undefined;
  if (config.storage) {
    if (typeof config.storage === 'function') {
      // Factory function - pass auth context
      if (!authContext) {
        throw createClientError(
          "DFQL_INVALID",
          "storage factory function requires authContextProvider",
          { path: "storage" },
        );
      }
      storage = config.storage(authContext);
    } else {
      // Direct adapter
      storage = config.storage;
    }
  }

  // ... rest of client creation ...
}
```

## Notes

- **Design Decision**: The `AuthContextProvider` interface is intentionally simple with just a `getContext()` method. This keeps it framework-agnostic and allows auth libraries to implement it easily.

- **Storage Factory Pattern**: Using a factory function `(context) => DatafnStorageAdapter` allows the storage adapter to be constructed with user context, enabling automatic database name construction.

- **Backward Compatibility**: The `authContextProvider` is optional, and `storage` can still be a direct adapter instance. This ensures existing code continues to work without changes.

- **Database Name Format**: Following the pattern from other superfunctions, database names should be `${baseName}_${userId}` or `${baseName}_${tenantId}_${userId}` for multi-tenant scenarios.

- **User Switching**: When a user logs out and a new user logs in, a new client instance should be created with the new user's context. The old client's storage will remain isolated in the previous user's database.

- **AuthFn Integration**: Libraries like `authfn` should implement `AuthContextProvider` to provide a standard way to extract context. The implementation might look like:
  ```typescript
  const auth = createAuthFn({ ... });
  
  // authfn should provide:
  auth.contextProvider = {
    getContext: () => {
      const session = auth.getSession(); // Get current session
      return {
        userId: session?.userId || 'anonymous',
        tenantId: session?.tenantId,
      };
    }
  };
  ```

- **Error Handling Consideration**: If `getContext()` throws or returns invalid context (e.g., missing userId), the client initialization should fail with a clear error message.

- **Performance Consideration**: `getContext()` should be fast since it's called during client initialization. Consider caching if the auth library's context extraction is expensive.

- **Comparison with Server**: This issue is about client-side multi-user support. Server-side multi-tenant support (if needed) would be a separate concern handled by the server's `authorize` callback and database adapter.
