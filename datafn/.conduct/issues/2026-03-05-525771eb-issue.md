# Summary
The merge path currently uses a defensive post-update read (`findOne`) to avoid false-success outcomes, which ensures reliability but adds an extra database call on successful merge updates. Severity is **Medium**: correctness is preserved, but performance/regression risk remains until adapter contracts are uniformly strict and verifiable across adapters/dialects.

# Observed Errors/Symptoms
- No functional correctness failure in the current implementation for tested paths.
- Architectural symptom: successful merge update paths now do two DB operations (`update` + `findOne`) in both mutation and push execution.
- This introduces avoidable read amplification in high-write merge workloads.

# Root Causes

## Root Cause 1: Reliability is currently enforced at server layer via fallback read instead of adapter-contract certainty

- **Location**: `datafn/server/src/execution/mutation/merge-decision.ts:83-91`, `112-120`
- **Current code (problematic for performance)**:
```ts
await update();
if (findOne) {
  const updatedRow = await findOne();
  if (!updatedRow) {
    throw { name: "NotFoundError", message: "Record not found after update" };
  }
}
```
- **Expected behavior**:
  - Merge success/failure should be determined by a strict adapter update contract (zero match => typed not-found) without mandatory verification reads on success.
- **Actual behavior**:
  - Server performs verification read after update success to guard against adapter ambiguity.
- **Impact**:
  - Every successful merge update in push/mutation can incur an extra read.
  - Higher DB load and latency under merge-heavy traffic.
- **Evidence**:
  - `merge-decision.ts` explicitly calls optional `findOne` after both initial update and update-retry success.

## Root Cause 2: Merge execution paths wire fallback read unconditionally

- **Location**:
  - `datafn/server/src/execution/mutation/execute.ts:69-95`
  - `datafn/server/src/execution/sync/push.ts:239-265`
- **Current code (problematic for performance)**:
```ts
findOne: async () =>
  db.findOne({ model: ..., where: [{ field: "id", operator: "eq", value: ... }], namespace })
```
- **Expected behavior**:
  - Either no fallback read where adapter contract is guaranteed, or capability-gated fallback only on adapters lacking strict zero-row semantics.
- **Actual behavior**:
  - Both paths always pass `findOne`, making fallback read active by default.
- **Impact**:
  - Global performance penalty regardless of adapter capability maturity.
- **Evidence**:
  - Both execution paths provide `findOne` callback to shared merge helper unconditionally.

## Root Cause 3: Adapter contract compliance is currently unevenly trusted, requiring server compensation

- **Location**:
  - `packages/db/src/adapters/drizzle/index.ts:217-231`
  - historical context validated by `datafn/server/__tests__/merge-sql-regression.test.ts`
- **Current code**:
```ts
const row = Array.isArray(res) ? res[0] : (res as any);
if (!row) throw new NotFoundError(model, where);
```
- **Expected behavior**:
  - All adapters/dialects provide equivalent zero-row update signaling (`NotFoundError` or canonical equivalent).
- **Actual behavior**:
  - Drizzle path is hardened, but server still assumes potential adapter inconsistency and keeps fallback read globally.
- **Impact**:
  - Contract confidence remains incomplete at platform level, so server-level overhead persists.
- **Evidence**:
  - Drizzle adapter now enforces not-found; server still keeps fallback verification.

# Proposed Fixes
1. Define and enforce a strict adapter contract for `update` across all `@superfunctions/db` adapters/dialects:
   - `update` MUST throw typed not-found on zero matched rows.
   - Add adapter contract tests per adapter/dialect matrix.
2. Add explicit capability flag (example: `capabilities.operations.strictUpdateNotFound`) or equivalent contract marker.
3. Make merge helper fallback read conditional:
   - Disable `findOne` verification when adapter contract capability is true.
   - Keep fallback only for legacy/non-compliant adapters.
4. Remove unconditional `findOne` wiring from push/mutation once coverage proves contract reliability.
5. Add performance regression tests/benchmarks for merge-heavy workloads before and after fallback removal.

# Testing Checklist
- Adapter contract tests (all adapters):
