## Summary

**Severity: Medium** (performance degradation, unnecessary network round-trips)

Every pull operation triggers 2 redundant HTTP `/query` requests to the remote server — one per KV signal (`pref:theme` and `pref:sort`). These queries should execute locally against IndexedDB but instead route to the remote server because the built-in `kv` resource's hydration state is never set to `"ready"`. The root cause is a gap in the hydration plan system: when a hydration plan specifies `bootResources`, **only** those listed resources are cloned. The built-in `kv` resource (auto-injected by `ensureBuiltinKv()`) is not included and therefore never transitions from `"notStarted"` to `"ready"`. The query router in `executeQuery()` treats `"notStarted"` as a remote-fallback state, causing every KV signal refresh to hit the server.

---

## Observed Errors/Symptoms

1. **Two HTTP `/query` calls on every pull** — Network tab shows POST requests to the remote `/datafn` endpoint with KV query payloads during each pull cycle.
2. **Payloads observed:**
   - `{"resource":"kv","version":1,"filters":{"id":{"eq":"kv:pref:sort"}},"select":["id","value"]}`
   - `{"resource":"kv","version":1,"filters":{"id":{"eq":"kv:pref:theme"}},"select":["id","value"]}`
3. **No functional breakage** — the queries return correct data, but the round-trip is wasteful and adds latency.
4. **Repeats on every pull** — not just the first one; every subsequent pull interval triggers the same redundant queries.

## Root Causes

### RC-1: Hydration plan excludes built-in `kv` resource — never cloned, hydration state stuck at `"notStarted"`

**Location:** `datafn/examples/todo-app/client/src/lib/datafn.ts:84-86` (config) and `datafn/client/src/sync/engine.ts:355-379` (initializeSync)

**Current code — client config:**
```ts
// datafn/examples/todo-app/client/src/lib/datafn.ts:84-86
hydration: {
  bootResources: ["todos", "categories"],
},
```

**Current code — initializeSync:**
```ts
// datafn/client/src/sync/engine.ts:355-360
async initializeSync() {
  if (this.hydrationPlan?.bootResources || this.hydrationPlan?.backgroundResources) {
    await this.initializeWithHydrationPlan();  // <-- takes the plan path
    return;
  }
  // ... default path (cloneNow for ALL resources) is SKIPPED
}
```

**Current code — initializeWithHydrationPlan:**
```ts
// datafn/client/src/sync/engine.ts:385-418
private async initializeWithHydrationPlan() {
  const { bootResources = [], backgroundResources = [] } = this.hydrationPlan!;
  // Only clones bootResources (todos, categories)
  // "kv" is NOT in either list → never cloned
}
```

**Expected behavior:** The built-in `kv` resource should be included in the clone/hydration process automatically, since it's a framework-injected resource that users don't explicitly manage.

**Actual behavior:** `kv` is never cloned. Its hydration state remains `"notStarted"` forever.

**Impact:** All KV queries route to the remote server instead of executing locally.

**Evidence:** The `ensureBuiltinKv()` call at `client.ts:372` adds `kv` to the schema, but nothing ensures it gets included in the hydration plan. The default `initializeSync` path (line 362-378) clones ALL non-remote-only resources, but the hydration plan path only clones explicitly listed resources.

### RC-2: Query router falls through to remote for `"notStarted"` hydration state

**Location:** `datafn/client/src/query.ts:125-172`

**Current code:**
```ts
// datafn/client/src/query.ts:125-172
const hydrationState = await storage.getHydrationState(resource);

if (hydrationState === "ready" && schema) {
  // → Local execution
  let result = await executeLocalQuery(storage, schema, query, schemaIndex);
  // ...
}

if (hydrationState === "hydrating") {
  // → Remote fallback (clone in progress)
  const response = await remote.query(transformedQuery);
  // ...
}

// → Remote fallback for: notStarted or missing resource  ← THIS PATH
const response = await remote.query(transformedQuery);
```

**Expected behavior:** For a resource that HAS local storage configured but was never cloned, querying the remote is the only correct fallback. This code is correct in isolation.

**Actual behavior:** Combined with RC-1, this means every KV signal refresh after a pull goes to the remote server.

**Impact:** 2 unnecessary HTTP requests per pull cycle, adding latency and server load.

### RC-3: `sync_applied` event triggers signal refresh even when KV data hasn't changed

**Location:** `datafn/client/src/signals/querySignal.ts:344-360` and `datafn/client/src/sync/engine.ts:754-765`

**Current code — event emission:**
```ts
// datafn/client/src/sync/engine.ts:761-763
resources: lastResult.records
  ? Object.keys(lastResult.records).sort()
  : [],
```

**Current code — signal event listener:**
```ts
// datafn/client/src/signals/querySignal.ts:354-358
if (phase === "clone" || phase === "pull") {
  const affectedResources: string[] = ctx?.resources ?? [];
  if (affectedResources.length === 0 || affectedResources.some(r => footprint.has(r))) {
    scheduleRefresh();
  }
}
```

**Expected behavior:** KV signals should only refresh when KV data actually changed in the pull.

**Actual behavior:** Two scenarios cause unnecessary refresh:
1. If the pull result includes `kv` in `records` (because KV data changed), the signal correctly refreshes — but then routes to remote (RC-1 + RC-2).
2. If the pull result has NO records at all (`resources: []`), the `affectedResources.length === 0` guard triggers ALL signals to refresh, including KV — a broadcast-style invalidation that's wasteful.

**Impact:** Even pulls with zero KV changes trigger KV signal refreshes. Combined with RC-1/RC-2, each such refresh becomes an HTTP call.

### RC-4 (Defense gap): `applyCloneResult` doesn't set `"ready"` for resources with no server data

**Location:** `datafn/client/src/sync/apply.ts:59-87` and `datafn/client/src/sync/engine.ts:424-429`

**Current code — cloneResources pre-sets hydrating:**
```ts
// datafn/client/src/sync/engine.ts:427-429
for (const table of tables) {
  await this.storage.setHydrationState(table, "hydrating");
}
```

**Current code — applyCloneResult only processes present resources:**
```ts
// datafn/client/src/sync/apply.ts:70-87
for (const [resource, records] of Object.entries(data)) {
  await storage.setHydrationState(resource, "hydrating");
  for (const record of records) {
    await storage.upsertRecord(resource, record);
  }
  // ...
  await storage.setHydrationState(resource, "ready");
}
```

**Expected behavior:** If a resource was requested for cloning, it should transition to `"ready"` even if the server returned zero records for it (the resource is fully hydrated — it just has no data yet).

**Actual behavior:** If the server omits a resource from the clone response `data` (e.g., `kv` has no records yet), `applyCloneResult` never processes it. The resource stays at `"hydrating"` (set by `cloneResources` at line 428), which is a stuck intermediate state.

**Impact:** Even if RC-1 is fixed by including `kv` in the hydration plan, if the server returns no KV data, the resource would get stuck at `"hydrating"` instead of transitioning to `"ready"`. Queries for `"hydrating"` resources also route to remote (query.ts:142-154). This affects ANY resource with zero records, not just `kv`.

## Proposed Fixes

### Fix 1 (Primary — addresses RC-1): Auto-include built-in resources in hydration plan

In `SyncEngine.initializeWithHydrationPlan()`, automatically append any schema resources not already listed in `bootResources` or `backgroundResources` that are:
- Not `isRemoteOnly`
- Built-in / framework-injected (like `kv`)

```ts
// In initializeWithHydrationPlan(), after reading hydrationPlan:
const allPlannedResources = new Set([...bootResources, ...backgroundResources]);
const unplannedResources = this.schema.resources
  .filter(r => !r.isRemoteOnly && !allPlannedResources.has(r.name))
  .map(r => r.name);

// Append unplanned resources to boot (they're small — kv is typically tiny)
const effectiveBootResources = [...bootResources, ...unplannedResources];
```

**Potential secondary issues with this fix:**
- **Server must handle `kv` in clone requests:** The server's `/clone` endpoint must support the `kv` table. If it doesn't recognize `kv`, the clone could fail entirely, breaking initialization. Need to verify server-side clone handling for built-in resources.
- **Increases initial clone payload slightly:** Adding `kv` to boot resources means it's cloned before the app renders. For most apps this is negligible (KV stores are small), but for apps with many built-in resources in the future, boot time could increase.
- **User expectations for hydration plan:** Users may explicitly omit resources from the hydration plan for a reason (e.g., they don't want to clone `kv` at all). Auto-including could surprise developers who carefully curated their boot/background lists. Consider making this opt-out rather than mandatory.

### Fix 2 (Defense — addresses RC-4): Set `"ready"` for all requested clone tables

In `cloneResources()`, after `applyCloneResult()` completes, ensure all requested tables are set to `"ready"`:

```ts
// After applyCloneResult:
for (const table of tables) {
  const state = await this.storage.getHydrationState(table);
  if (state !== "ready") {
    await this.storage.setHydrationState(table, "ready");
  }
}
```

**Potential secondary issues with this fix:**
- **False "ready" state for partially cloned resources:** If the clone failed partway through (e.g., server returned some tables but not others due to an error), force-setting `"ready"` could mask the fact that data is incomplete. However, the current code already throws on clone failure (line 465), so if we reach the post-apply code, the clone succeeded.
- **Hydration state transition validation:** The storage adapter validates state transitions (e.g., can't go from `"hydrating"` to `"ready"` might have constraints). Need to verify the IndexedDB adapter allows this transition. Looking at `indexedDbStorage.ts:650`, it does check current state — but `"hydrating" → "ready"` is a valid forward transition.
- **`applyCloneResult` already sets `"ready"` per-resource:** There would be redundant `setHydrationState("ready")` calls for resources that WERE in the response. Minor overhead but harmless.

### Fix 3 (Performance — addresses RC-3): Don't broadcast-refresh on empty resources

Change the signal event listener to NOT refresh when `affectedResources` is empty:

```ts
// querySignal.ts:356 — change from:
if (affectedResources.length === 0 || affectedResources.some(r => footprint.has(r))) {
// to:
if (affectedResources.some(r => footprint.has(r))) {
```

**Potential secondary issues with this fix:**
- **Missed refreshes after no-op pulls:** If a pull returns no records but still indicates the server state is fresh, signals won't refresh. This is correct behavior — no data changed, so no refresh needed. However, if the server uses pulls as a "confirm you're up to date" mechanism without sending records, signals would never learn they're stale.
- **First pull after clone:** If the first pull after a clone returns no new records (nothing changed), signals created during the clone phase might not refresh. They should already have been refreshed by the clone's `sync_applied` event though, so this should be safe.
- **Edge case with server-side deletes returning empty records:** If the server deletes all records for a resource but the pull result puts deletions in `deleted` rather than `records`, `Object.keys(lastResult.records)` might not include that resource. The signal wouldn't refresh and would show stale data. However, looking at the engine code, `records` and `deleted` are separate — the `resources` array only comes from `records`, not `deleted`. This is a **pre-existing bug** unrelated to this fix, but removing the `length === 0` safety net would make it slightly worse.

## Notes

- **This is not specific to the example app.** Any datafn client using a hydration plan without explicitly listing `kv` in `bootResources` or `backgroundResources` will have this issue. Since `kv` is a built-in resource that users don't define in their schema, it's unreasonable to expect them to include it in their hydration plan.
- **The default path (no hydration plan) is correct.** `initializeSync()` without a hydration plan calls `cloneNow()` which clones ALL non-remote-only resources including `kv`. The bug only affects the hydration plan path.
- **`applyPullResult` intentionally doesn't touch hydration state.** Pull is incremental — it only applies deltas. Setting hydration state during pull would be semantically incorrect because a pull doesn't guarantee full data presence for a resource. The correct place to set `"ready"` is during clone.
- **Future built-in resources would have the same issue.** If datafn adds more framework-injected resources beyond `kv`, they would also be excluded from hydration plans. The fix should be generic (auto-include all non-user-defined resources) rather than hardcoding `kv`.
