## Summary

**Severity: High** — Breaks the primary query pattern used by the todo-app example and any client that requests relation expansion alongside all base fields.

The DFQL server-side validation (`validateSelectTokens`) rejects the bare `"*"` wildcard token in `select` arrays, returning `DFQL_UNKNOWN_FIELD`. Additionally, the server-side execution engine (`materializeSelect`) has no handling for `"*"` even if validation were to pass. However, the client-side offline query engine fully supports `"*"` and the official example app (`todo-app`) relies on `select: ["*", "tags.*"]` in three places. This is a spec gap that the client implementation outgrew — the original DFQL spec never defined `"*"` as a valid select token, but the client organically needed it to express "all base fields plus specific relation expansions."

The `select[0]` token is `"*"`. The server validation treats it as an unknown field name because `"*"` is not in the resource's `fieldNames` set or `relationNames` set.

## Root Causes

### Root Cause 1: Server validation rejects bare `"*"` as unknown field

**Location:** `datafn/server/src/validation/query.ts`, lines 272–328 (`validateSelectTokens`)

**Current code (problematic):**
```typescript
for (let i = 0; i < select.length; i++) {
    const token = select[i];
    if (typeof token !== "string") continue;

    const parts = token.split(".");
    const baseName = parts[0];
    const directive = parts.slice(1).join(".") || undefined;

    // HTREE support
    const isHtreeToken = baseName === "parent" || baseName === "children";

    if (isHtreeToken) { /* ... htree handling ... */ }

    // Check if it's a field or relation
    if (!fieldNames.has(baseName) && !relationNames.has(baseName)) {
      return vErr(
        parts.length > 1 ? "DFQL_UNKNOWN_RELATION" : "DFQL_UNKNOWN_FIELD",
        parts.length > 1 ? `Unknown relation: select[${i}]` : `Unknown field: select[${i}]`,
        `select[${i}]`,
      );
    }
    // ...
}
```

**Expected behavior:** The `"*"` token should be recognized as a valid wildcard meaning "include all base fields" and should pass validation.

**Actual behavior:** `"*"` is split into `parts = ["*"]`, `baseName = "*"`. Since `"*"` is not in `fieldNames` and not in `relationNames`, it falls through to the `DFQL_UNKNOWN_FIELD` error.

**Impact:** All queries using `select: ["*", ...]` fail with a 400 error. This blocks the primary use case of "all fields plus relation expansion."

**Evidence:** The error message `Unknown field: select[0]` directly matches this code path.

### Root Cause 2: Server execution engine ignores `"*"` even if validation passed

**Location:** `datafn/server/src/execution/query/select.ts`, lines 122–340 (`materializeSelect`)

**Current code (problematic):**
```typescript
const result: Record<string, unknown> = {};
const includedFields = new Set<string>();

for (const token of select) {
    if (isNestedSelectToken(token)) { /* ... nested handling ... */ }

    const parsed = parseSelectToken(token);

    if (parsed.baseName === "parent" || parsed.baseName === "children") { /* ... htree ... */ }

    // Base field (no directive)
    if (!parsed.directive) {
      const relation = findRelation(schema, resource, parsed.baseName);
      if (relation) {
        result[parsed.baseName] = getRelationIds(record, relation, store);
        includedFields.add(parsed.baseName);
      } else {
        // Regular field — sets result["*"] = record["*"] → undefined
        result[parsed.baseName] = record[parsed.baseName];
        includedFields.add(parsed.baseName);
      }
      continue;
    }
    // ...
}
```

**Expected behavior:** When `token === "*"`, the function should include all schema-defined base fields in the result (equivalent to the "no select" path at lines 112–120).

**Actual behavior:** `parseSelectToken("*")` returns `{ baseName: "*", directive: undefined }`. The function falls into the "base field, no directive" branch, tries `findRelation(schema, resource, "*")` (returns null), then does `result["*"] = record["*"]` which sets a literal `"*"` key to `undefined`. All base fields are silently omitted from the response.

**Impact:** Even if the validation bug were fixed alone, the server would return records missing all base fields — only relation-expanded data would be present.

**Evidence:** Compare with the "no select" path (lines 112–120) which correctly iterates `resourceSchema.fields` and includes all fields. The `"*"` token should trigger equivalent behavior.

### Root Cause 3: Spec gap — bare `"*"` was never specified but was organically needed

**Location:** `datafn/.conduct/intent/dfql.intent.md`, line 121

**Spec language:**
> "Not specifying `select` selects all base fields on the record (no relation expansion)."

**From `datafn/.conduct/specs/2026-01-18-spec/REQUIREMENTS.md`, QUERY-003:**
> "If `select` is omitted, the response includes all base fields for the resource and no relation expansions."

**The gap:** The spec defined two orthogonal behaviors:
1. **Omit `select`** → all base fields, no relations
2. **Provide `select`** → only explicitly listed fields/relations

But it never addressed the composite case: "I want all base fields AND specific relation expansions." The only spec-compliant way to achieve this is to list every field by name: `select: ["id", "text", "completed", "priority", "createdAt", "updatedAt", "tags.*"]` — which is fragile, verbose, and breaks when fields are added to the schema.

The client-side offline engine (`datafn/client/src/offline/relations.ts`, line 254) independently solved this by supporting the `"*"` wildcard:

```typescript
if (token === "*" || token === "#" || token === "*#" || token === "#*") {
    baseFields.add("*"); // Keep all fields
    continue;
}
// ...
if (baseFields.has("*")) {
    Object.assign(result, record);  // Copy all fields
}
```

The todo-app example was then written using this client-side convention (`select: ["*", "tags.*"]`), which works in offline/local mode but fails when the query is forwarded to the server.

## Timeline: How This Gap Emerged

| Date | Event | What happened |
|---|---|---|
| **2026-01-18** | Original DFQL spec (PHASE_02) | `select` semantics defined: omit = all fields, explicit field names, relation tokens (`rel.*`, `rel.#`, `rel.*#`, `children.**`). No bare `"*"` wildcard. |
| **2026-01-18** | REQUIREMENTS.md QUERY-003 | "If `select` is omitted, the response includes all base fields." The assumption: if you want all fields, just omit `select`. |
| **2026-01-18** | Server PHASE_02 implementation | `materializeSelect` in `select.ts` implemented per spec: omitted select → all fields; explicit tokens → specific fields/relations. No `"*"` case. |
| **2026-01-19** | Change spec PHASE_11 | Added `omit`, ids-only tokens, nested traversal (`tasks.tags.*`). Still no bare `"*"`. |
| **~2026-01-24** | Client offline engine implementation | `materializeSelect` in `client/src/offline/relations.ts` was implemented with `"*"` support (line 254). The developer recognized that `select: ["tags.*"]` without `"*"` would mean "only return the tags relation, no base fields" — making it impossible to request "everything + relations" without listing every field. |
| **~2026-02-11** | Server validation tightened | `validateSelectTokens` was added/enhanced in `validation/query.ts` with schema-bounded checking. It validates tokens against `fieldNames` and `relationNames` sets, with special cases for htree tokens. No special case for `"*"`. |
| **~2026-02-12** | Todo-app example written | `App.svelte` uses `select: ["*", "tags.*"]` in three places (lines 70, 76, 82), relying on the client-side convention. Works offline via the client engine. |
| **2026-02-21** | Bug reported | Server returns 400 when the todo-app sends `select: ["*", "tags.*"]` to the server query endpoint. The client-side convention was never propagated to the server validation or execution. |

**Root pattern:** The client-side implementation independently evolved a pragmatic extension (`"*"` wildcard) that the original DFQL spec didn't define. The server-side validation was written strictly to spec. No cross-layer integration test caught the divergence because client offline queries don't hit the server validation path.

## Notes

- **Fix 1 (validation) was already applied as a hotfix** in this session by adding `if (token === "*") continue;` to `validateSelectTokens`. Fix 2 (execution) has NOT been applied yet and is required for the feature to work end-to-end.
- The client-side offline engine also supports `"#"`, `"*#"`, and `"#*"` as bare select tokens (line 254 of `relations.ts`). The server should consider whether these bare tokens also need support, though they appear less commonly used.
- No existing test (unit or integration) covers the `"*"` token in select on either client or server. The divergence was invisible because client offline queries bypass server validation entirely.
- The `DfqlQuery` type in `core/src/dfql.ts` defines `select` as `string[]` with no constraints, so there is no type-level enforcement of valid tokens.
