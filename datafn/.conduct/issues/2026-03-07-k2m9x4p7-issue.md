# Summary
`/datafn/push` fails for `kv` `merge` mutations when the target row does not already exist. The merge fallback create path uses update-only capability injection payload (missing `createdAt`), which violates `kv.createdAt NOT NULL`, causing per-mutation `INTERNAL` failure in push results. Severity: **High** because this breaks routine sync writes for preference KV entries in the example app.

# Observed Errors/Symptoms
- Push request accepted at envelope level (`ok: true`) but mutation is not applied.
- `result.errors[0]` contains:
  - `code: INTERNAL`
  - `message: Internal error`
  - `path: $`
- Server log includes concrete DB failure:
  - `null value in column "created_at" of relation "kv" violates not-null constraint`
- Affected mutation shape:
  - `resource: "kv"`, `operation: "merge"`, `record: { value: "light" }`

# Root Causes
## 1) Push merge path uses update-only capability injection even when merge falls back to create
- Location:
  - `datafn/server/src/execution/sync/push.ts:274-294`
- Current code (problematic snippet):
```ts
const mergeData = injectCapabilityFieldsOnUpdate(strippedRecord, resolvedCapabilities, actorId);
const mergeResult = await executeSchemaAwareMerge({
  schema,
  resource: mut.resource,
  id: mut.id,
  delta: mergeData,
  update: async () => targetDb.update(...),
  create: async (record) => targetDb.create({ model: mut.resource, data: record, namespace }),
});
```
- Expected behavior:
  - When merge requires create fallback, create payload must include required creation fields (`createdAt`, and audit fields where applicable).
- Actual behavior:
  - `delta` is built with update semantics only; create fallback receives that delta and inserts without `createdAt`.
- Impact:
  - Any merge-to-create on resources with `createdAt NOT NULL` can fail (KV in example app fails immediately).
- Evidence:
  - Server error log shows `created_at` null constraint violation.

## 2) Merge decision helper reuses provided delta for create fallback without augmenting creation fields
- Location:
  - `datafn/server/src/execution/mutation/merge-decision.ts:98-105`
- Current code (problematic snippet):
```ts
const decision = decideMergeMode(schema, resource, id, delta);
...
await create(decision.createRecord);
```
- Expected behavior:
  - Callers should supply create-complete data when fallback mode is `create`, or helper should enforce/create a dedicated create payload path.
- Actual behavior:
  - Caller-provided delta is used as-is for create fallback.
- Impact:
  - Caller bug in merge payload preparation directly becomes DB-level constraint failure.
- Evidence:
  - `createRecord` is derived from `delta` via `{ id, ...delta }` and inserted.

## 3) Example KV schema enforces NOT NULL created timestamp
- Location:
  - `datafn/examples/todo-app/server/src/datafn-schema.drizzle.ts:21-26`
- Current code (relevant snippet):
```ts
export const kv = pgTable("kv", {
  ...
  createdAt: bigint("created_at", { mode: "number" }).notNull(),
  updatedAt: bigint("updated_at", { mode: "number" }).notNull(),
});
```
- Expected behavior:
  - Merge-create should include both timestamps when timestamps capability is active.
- Actual behavior:
  - Insert attempt can lack `createdAt`.
- Impact:
  - Constraint violation and failed KV sync writes.

# Proposed Fixes
1. In push merge execution, split payloads by mode:
   - `updateData = injectCapabilityFieldsOnUpdate(...)`
   - `createData = injectCapabilityFieldsOnInsert(...)`
   - Ensure merge fallback create path uses `createData` (not `updateData`).
2. Keep readonly stripping behavior before capability injection so client-provided system fields remain non-authoritative.
3. Return a more precise mutation error for this path where possible (if detectably creation-field violation) instead of generic `INTERNAL` to improve diagnostics.
4. Add regression tests for push merge fallback create on timestamp/audit-enabled resources (`kv`-like shape).
