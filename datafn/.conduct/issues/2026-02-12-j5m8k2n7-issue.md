## Summary

The datafn example app (todo-app) throws **Unknown table: kv** on load because the client augments the app schema with the built-in KV resource via `ensureBuiltinKv()`, then runs a storage validation probe for every resource in that augmented schema (including `"kv"`). The `IndexedDbStorageAdapter` is created with the **app-only** schema (e.g. `todos`, `categories`), so its `validResources` set does not include `"kv"`. The adapter physically creates the `kv` object store in IndexedDB (KV-001) but rejects any access to it in `validateTableName()`, causing the probe and any later `client.kv` usage to throw. The fix is **adapter-side**: ensure the IndexedDB adapter always treats the built-in `"kv"` resource as valid when `validResources` is set (e.g. add `KV_RESOURCE_NAME` to the set in `create()` and in the constructor path that builds it from schema).

## Observed Errors / Symptoms

1. **Uncaught (in promise) Error: Unknown table: kv** — thrown from `indexedDbStorage.ts:360` inside `validateTableName()`.
2. **Stack trace**: `validateTableName` → `getRecord` → `client.ts:447` (storage validation loop).
3. **When**: On creating a datafn client with `IndexedDbStorageAdapter.create({ dbName, schema })` where `schema` is the app schema (e.g. only `todos`, `categories`). The failure occurs during the client’s storage validation phase, before the first query/mutation.
4. **Affected**: datafn example todo-app and any app that uses IndexedDB storage without passing a schema that already includes the built-in KV resource.

## Root Causes

### Root Cause 1: validResources is built only from the schema passed to the adapter (no built-in KV)

**Location**: `datafn/client/src/adapters/indexedDbStorage.ts`, lines 111–116 and 156–158.

**Current code**:

```typescript
// Lines 111-116 — create() builds resources only from options.schema
  static create(options: {
    dbName: string;
    schema: DatafnSchema;
  }): IndexedDbStorageAdapter {
    const resources = options.schema.resources.map((r) => r.name);
    return new IndexedDbStorageAdapter(options.dbName, resources, options.schema);
  }

// Lines 156-158 — constructor sets validResources from that list only
    if (resources) {
      this.validResources = new Set(resources);
    }
```

**Expected behavior**: The adapter should allow access to every store it actually creates and uses. The adapter creates the `kv` object store in `onupgradeneeded` (lines 279–284) and the client always adds the KV resource to the effective schema via `ensureBuiltinKv()`, so the adapter should treat `"kv"` as a valid resource.

**Actual behavior**: `validResources` contains only the resource names from the schema passed at construction (e.g. `["todos", "categories"]`). The built-in `"kv"` resource is never added, so `validateTableName("kv")` throws.

**Impact**: Storage validation in the client fails when it probes the `kv` resource; any use of `client.kv` would also throw. Example app cannot start with IndexedDB storage when using the typical pattern of passing the app schema to `IndexedDbStorageAdapter.create()`.

**Evidence**: Error message `Unknown table: kv`; stack trace points to `getRecord(resource.name, "__storage_probe__")` in the client’s validation loop (client.ts:444–447) where `resource.name` is `"kv"` from the client’s augmented schema.

**Expected behavior**: The client correctly ensures the built-in KV resource exists in the schema and validates that storage has a store for every non-remote-only resource. The adapter should accept the `"kv"` resource for this probe.

**Actual behavior**: The client passes the augmented schema (with `kv`) into the validation loop. The adapter was created with the raw app schema, so it rejects the `"kv"` probe.

**Impact**: Same as above — validation fails and the promise rejection surfaces as "Unknown table: kv".

### Root Cause 3: Adapter creates the kv store but does not allow it in validResources

**Location**: `datafn/client/src/adapters/indexedDbStorage.ts`, lines 279–284 (store creation) and 358–361 (validation).

**Current code**:


**Expected behavior**: If the adapter creates and uses the `kv` store, it should allow `"kv"` as a valid resource name so that client validation and `client.kv` work without requiring the app to pass a schema that includes KV.

**Actual behavior**: The `kv` store is created in IndexedDB, but `validResources` is built only from the constructor’s `resources`/schema, so `"kv"` is not in the set and all access to the `kv` resource is rejected.

**Impact**: Inconsistent contract: the adapter creates a store it then refuses to use by name.

## Proposed Fixes

### Recommended: Adapter-side fix (in datafn/client)

**Approach**: Ensure the IndexedDB adapter always treats the built-in `"kv"` resource as valid whenever `validResources` is set, so that storage validation and `client.kv` work without requiring apps to pass a schema that includes KV.

1. **In `IndexedDbStorageAdapter.create()`** (`indexedDbStorage.ts`):
   - After building `resources` from `options.schema.resources`, add the built-in KV resource name if not already present, e.g. import `KV_RESOURCE_NAME` from `@datafn/core` and ensure `resources` includes it before passing to the constructor.
   - Example: `const resources = [...options.schema.resources.map((r) => r.name)]; if (!resources.includes(KV_RESOURCE_NAME)) resources.push(KV_RESOURCE_NAME);`

2. **In `IndexedDbStorageAdapter` constructor** (when building `validResources` from `resources`):
   - When setting `this.validResources = new Set(resources)`, ensure the set includes `KV_RESOURCE_NAME` (e.g. add it after the set is created so that even when `create()` is not used and resources are passed from elsewhere, the adapter still allows `kv` if it creates the store).

3. **In `createForUser()`** (if `resources` is derived from schema):
   - When `schema` is provided and `resources` is not, derive resources from schema and apply the same rule: include `KV_RESOURCE_NAME` in the list passed to the constructor.

This keeps the contract consistent: the adapter creates the `kv` store (KV-001) and always allows access to it, regardless of the app schema. No change required in the example app or other consumers.

### Alternative: App-side fix (example app only)

**Approach**: Pass the same schema the client uses (including built-in KV) when creating the adapter, e.g. `IndexedDbStorageAdapter.create({ dbName: "todo-app-db", schema: ensureBuiltinKv(schema) })` with `ensureBuiltinKv` imported from `@datafn/core`. This fixes the example app but forces every app using IndexedDB to remember to pass the augmented schema; easy to forget and duplicates client logic. **Not recommended** as the primary fix.

## Notes

- The same pattern (client augments schema with built-in resources, adapter only knows app schema) could affect other built-in resources in the future; the adapter-side fix for KV is the right precedent.
- `ensureStores()` in the adapter only checks `this.schema.resources` and relations for missing stores; it does not currently ensure the `kv` store exists in the same way. The KV store is created in `onupgradeneeded` unconditionally, so after the adapter-side fix, no change to `ensureStores()` is required for this issue.
