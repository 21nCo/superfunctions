## Summary

**Severity: Critical/High** — When a client pushes a `relate`, `unrelate`, or `modifyRelation` mutation, the server's change-tracking code records a changelog entry for the **primary resource** with `op: "upsert"` and a record containing **only `{ id }`**. This is because `mut.record` is empty/undefined for relation operations (relation data lives in `mut.relations`). When other clients pull this change, the `"upsert"` op causes `storage.upsertRecord()` — a full record replacement — which overwrites the complete record (with all its fields like `name`, `completed`, etc.) with just `{ id: "..." }`. This results in **silent data loss** on every client that pulls a relation mutation from another client.

---

## Observed Errors/Symptoms

- Client A performs a `relate` mutation (e.g. assigning a tag to a todo)
- Client B pulls and receives a change entry: `{ op: "upsert", resource: "todos", record: { id: "todo:abc" } }`
- Client B's IndexedDB record for `todo:abc` is **replaced** with just `{ id: "todo:abc" }` — all other fields (`name`, `completed`, `createdAt`, etc.) are destroyed
- The todo appears blank/broken in Client B's UI
- The join table changes (the actual relation data) may propagate correctly, but the primary resource record is corrupted
- Same behavior occurs for `unrelate` and `modifyRelation` mutations

## Root Causes

### Root Cause 1: Push change-tracking records `{ id }` as "upsert" for the primary resource on relation mutations

**Location:** `datafn/server/src/execution/sync/push.ts` (lines 456–478)

**Current code:**

```typescript
// Lines 456-462: Build change record
const changeRecord =
  mut.operation === "delete"
    ? null
    : {
        id: mut.id,
        ...coerceDateFields(schema, mut.resource, mut.record || {}),
      };

// Lines 465-470: Determine op type
const changeOp =
  mut.operation === "delete" ? "delete" :
  mut.operation === "insert" ? "insert" :
  mut.operation === "merge" ? "merge" :
  mut.operation === "replace" ? "replace" :
  "upsert"; // relate/modifyRelation/unrelate fall back to upsert

// Lines 472-478: Record the change
await changeTracking.recordChange({
  serverSeq,
  resource: mut.resource,
  id: mut.id,
  op: changeOp,
  record: changeRecord,
});
```

**Expected behavior:** Relation mutations should not record a primary resource "upsert" change, because:
- For **many-many** relations: the primary resource is not modified at all — only join rows change
- For **many-one** relations: only a FK field on the source record changes
- For **one-many** relations: the FK field changes on the **target** resource, not the source

**Actual behavior:** Every relation mutation records a change entry `{ op: "upsert", record: { id: "..." } }` for the primary resource, because `mut.record` is `undefined`/`{}` for relation operations. The `|| {}` fallback produces an empty object, and only `id: mut.id` is present.

**Impact:** Other clients that pull this change call `storage.upsertRecord(resource, { id })`, which is a full replacement — destroying all existing fields on the record.

**Evidence — data flow trace:**

1. Client A pushes: `{ operation: "relate", resource: "todos", id: "todo:abc", relations: { tags: "tag:1" } }`
2. `mut.record` is `undefined` → `changeRecord = { id: "todo:abc" }`
3. `changeOp = "upsert"` (fallback)
4. Changelog stores: `{ serverSeq: 10, resource: "todos", id: "todo:abc", op: "upsert", record: { id: "todo:abc" } }`
5. Client B pulls, receives this in `records.todos` array
6. `applyPullResultCanonical` calls `storage.upsertRecord("todos", { id: "todo:abc" })` — **full replacement**
7. Client B's record `{ id: "todo:abc", name: "Buy milk", completed: false }` → `{ id: "todo:abc" }` — **data loss**

### Root Cause 2: Same issue exists in standalone mutation execution path

**Location:** `datafn/server/src/execution/mutation/execute.ts` (lines 370–394)

**Current code:**

```typescript
const changeOp =
  mutation.operation === "delete" ? "delete" :
  mutation.operation === "insert" ? "insert" :
  mutation.operation === "merge" ? "merge" :
  mutation.operation === "replace" ? "replace" :
  "upsert"; // relate/modifyRelation/unrelate fall back to upsert

  mutation.operation === "delete"
    ? null
    : mutation.operation === "replace" && resolvedRecord !== undefined
      ? { id: mutation.id, ...resolvedRecord }
      : { id: mutation.id, ...(mutation.record || {}) };

await changeTracking.recordChange({
  serverSeq,
  resource: mutation.resource,
  id: mutation.id,
  op: changeOp,
  record: changeRecord,
});
```

**Actual behavior:** Identical pattern: `mutation.record || {}` is empty for relation operations, producing `{ id }` with `op: "upsert"`.

**Impact:** Same data loss on pull for mutations executed via the standalone `executeMutation` path.

### Root Cause 3: Pull and client apply have no guard against id-only upserts

**Location:** `datafn/server/src/execution/sync/pull.ts` (lines 307–308) and `datafn/client/src/sync/apply.ts` (lines 178–181)

**Pull server code** (pull.ts:307-308):
```typescript
} else if ((change.op === "insert" || change.op === "replace" || change.op === "upsert") && change.record) {
  records[resource].push(change.record);
}
```

The `change.record` check passes because `{ id: "..." }` is truthy.

**Client apply code** (apply.ts:178-181):
```typescript
for (const [resource, resourceRecords] of Object.entries(records)) {
  for (const record of resourceRecords) {
    await storage.upsertRecord(resource, record);
  }
}
```

No check for whether the record is an id-only stub. `upsertRecord` is a full replacement per IndexedDB `put()` semantics.

**Impact:** The id-only record flows unobstructed from changelog → pull response → client apply → IndexedDB full replacement.

### Why the join deltas ARE correct (for context)

The join table changes are handled correctly in a separate code path (push.ts:480-501):

```typescript
if (
  mut.operation === "relate" ||
  mut.operation === "modifyRelation" ||
  mut.operation === "unrelate"
) {
  const joinDeltas = extractJoinDeltas(mut, schema);
  for (const delta of joinDeltas) {
    const joinSeq = await changeTracking.getNextServerSeq();
    // ... records change for join store key
  }
}
```

The join deltas correctly record `upsert`/`delete` changes to the `join_*` store. The problem is the **additional** spurious change recorded for the primary resource at lines 472-478.

## Proposed Fixes

### Fix Option A: Skip primary resource changelog entry for many-many relation mutations

For `many-many` relate/unrelate/modifyRelation, the primary resource is not modified — only join rows change. The fix is to **not record a primary resource change entry** for these operations. The join deltas (already correctly recorded) are the only changes that need to propagate.

In `push.ts` (lines 449-478) and `execute.ts` (lines 370-394):
- Before recording the primary resource change, check if the operation is `relate`/`modifyRelation`/`unrelate`
- For **many-many**: skip the primary resource change entirely (only join deltas matter)
- For **many-one**: record a `merge` change with the FK field that was actually modified (e.g. `{ id, categoryId: "cat:1" }`)
- For **one-many**: record a `merge` change on the **target** resource (not the source) with the FK field (e.g. on the target: `{ id: targetId, todoId: "todo:abc" }`)

### Fix Option B: Read-after-write for relation mutations

After executing the relation mutation on the DB, read back the full record and store it in the changelog. This is simpler but adds a DB read per mutation:
- In `push.ts`: after `executeRelate()` succeeds, do `db.findOne({ model: mut.resource, where: ... })` and use the full record in `changeTracking.recordChange()`
- Same for `execute.ts`

### Fix Option C: Do not record primary resource change for any relation mutation (simplest)

Since relation operations change **relationships** (join rows or FK fields) and not the primary record's own data, the primary resource changelog entry is fundamentally wrong. The fix is to simply not create it. All relation data propagation should happen through:
1. **many-many**: join table deltas (already working)
2. **many-one/one-many**: separate FK field changes recorded as `merge` ops on the correct resource

## Notes

- The **client-side offline optimistic apply** (`mutate.ts`) is NOT affected — it correctly handles relation mutations by updating FK fields or join rows without touching the primary record's other fields.
- The data loss only occurs on **other clients** that pull the change, not on the originating client (which applied the mutation optimistically and correctly).
- The join table deltas (`extractJoinDeltas` in push.ts) are correctly implemented and do propagate. The bug is specifically the **additional** primary resource "upsert" entry.
- This is the same class of bug as the merge-data-loss issue (`2026-02-24-m7k9x2p4-issue`) — both stem from the changelog recording insufficient/incorrect data for the `record` field and using generic `"upsert"` as the op type.
- The `ChangeEntry.op` type was recently expanded (FIX-A in the merge issue fix) to support `"insert" | "merge" | "replace" | "delete"`, but relation operations were left as the `"upsert"` fallback. A dedicated handling for relation ops was not added.
- Since the library is not yet used externally, protocol changes are safe without backward-compatibility concerns.
