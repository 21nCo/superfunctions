## User-Reported Issue Description

> How does multi-tenancy work in the current datafn implementation? If I want to provide a tenant switcher on UI for users to switch between organizations or spaces — is there a better approach than destroy-and-recreate? Like a datafn-provided built-in function to switch?

## Summary

`createDatafnClient` binds to a single `AuthContext` and storage adapter for its entire lifetime. There is no `client.switchContext()`, `client.switchTenant()`, or any built-in mechanism to change the active tenant at runtime. The only way to switch tenants in a multi-tenant UI is to manually call `client.destroy()`, create a new client with the new auth context, rebind all UI subscriptions/signals, and restart sync. This is error-prone, requires significant boilerplate in every multi-tenant app, and creates a class of bugs around stale references to the old client. A `createSwitchableClient()` utility that wraps the destroy/create cycle behind a stable proxy reference is the recommended solution.

## Observed Errors / Symptoms

This is not a crash or error — it's a missing capability:

1. **No `switchContext` or `switchTenant` method** on `DatafnClient`
2. **Auth context resolved once at creation** — `createDatafnClient` is synchronous and resolves `authContext` immediately (lines 378-394 of `client.ts`), storing it in a closure-scoped `resolvedAuthContext` variable that cannot be updated
3. **Storage adapter bound at creation** — `resolvedStorage` is set once (lines 364-425 of `client.ts`) and used for the entire client lifetime
4. **All internal state is closure-scoped** — `eventBus`, `signalRegistry`, `syncEngine`, `debouncerMap`, `crossTabRelay` are all created once in `createDatafnClient` and captured in closures. No mechanism exists to reset or swap them
5. **`destroyed` flag is one-way** — once `destroy()` is called (line 781), the flag is set to `true` and `guardDestroyed()` prevents all further operations. There is no `undestroy` or `reinitialize`

## Root Causes

### Root Cause 1: Client lifecycle is one-shot — no reinitializtion path

**Location**: `datafn/client/src/client.ts`, lines 246-968

**Current code (relevant excerpts)**:

```typescript
// Line 246 — createDatafnClient is synchronous, returns a fully bound client
export function createDatafnClient<S extends DatafnSchema>(
  config: DatafnClientConfig<S>,
): DatafnClient<S> {

// Lines 364-409 — storage and auth resolved ONCE
  let resolvedStorage: DatafnStorageAdapter | undefined;
  let resolvedAuthContext: AuthContext | undefined;
  if (config.storage) {
    if (typeof config.storage === "function") {
      // ... resolves authContext and creates storage adapter ONCE ...
      resolvedStorage = config.storage(authContext);
    } else {
      resolvedStorage = config.storage;
    }
  }

// Line 651 — destroyed flag is one-way
  let destroyed = false;
```

**Expected behavior**: For multi-tenant apps, the client should offer a way to switch the active tenant (auth context + storage) without requiring the consuming app to manage the full destroy/create/rebind lifecycle.

**Actual behavior**: The client is a one-shot construction. Switching tenants requires:
1. Calling `client.destroy()` — which closes storage, stops sync, disposes all signals, and sets `destroyed = true`
2. Creating an entirely new client via `createDatafnClient()`
3. Rebinding all UI references — every `client.todos`, `client.kv`, `client.subscribe(...)`, and every Svelte store / React hook that holds a reference to the old client must be updated
4. Restarting sync / hydration

**Impact**: Every multi-tenant app using datafn must implement the same boilerplate destroy-create-rebind pattern. Bugs arise from:
- Forgetting to call `destroy()` (leaks IndexedDB connections, sync timers)
- Holding stale references to the old client in UI components
- Race conditions between the old client's in-flight operations and the new client's initialization
- Signals from the old client continuing to fire into disposed subscriptions

### Root Cause 2: Framework adapters have no tenant-switch awareness

**Location**: `datafn/svelte/src/toSvelteStore.ts`

**Current code**:

```typescript
// toSvelteStore binds to a single signal permanently
export function toSvelteStore<T>(signal: DatafnSignal<T>): DatafnSvelteStore<T> {
  return readable(
    {
      data: signal.get(),
      loading: signal.loading,
      error: signal.error,
      refreshing: signal.refreshing,
    },
    (set) => {
      const unsubscribe = signal.subscribe((value: T) => {
        set({ data: value, loading: signal.loading, error: signal.error, refreshing: signal.refreshing });
      });
      return unsubscribe;
    }
  );
}
```

**Expected behavior**: Framework adapters should be able to react to tenant switches — invalidating stores and rebinding to the new client's signals.

**Actual behavior**: `toSvelteStore` subscribes to a single signal at creation time. When the underlying client is destroyed and a new one is created, the Svelte store goes stale. The app developer must manually dispose and recreate every store derived from `toSvelteStore`.

**Impact**: Framework-level reactivity breaks on tenant switch. Every component that uses `toSvelteStore` must be aware of tenant switches and handle rebinding — violating the principle that the framework adapter should handle this transparently.

### Root Cause 3: IndexedDB adapter is inherently stateful — true hot-swap is not possible

**Location**: `datafn/client/src/adapters/indexedDbStorage.ts`

**Current code**:

```typescript
// Constructor opens the DB and holds the connection for the adapter's lifetime
constructor(dbName, resources?, schema?) {
  this.dbPromise = this.openDatabase(DB_VERSION).then((db) =>
    this.ensureStores(db),
  );
}

// close() terminates the connection
async close(): Promise<void> {
  const db = await this.dbPromise;
  db.close();
}
```

**Expected behavior**: N/A — this is a constraint, not a bug.

**Actual behavior**: An `IndexedDbStorageAdapter` holds a single `IDBDatabase` connection. You cannot "re-point" it to a different database (different tenant). Switching tenants genuinely requires closing the old adapter and creating a new one.

**Impact**: Any tenant-switching solution must accept that the storage adapter is destroyed and recreated. The question is whether the **user** manages this lifecycle or **datafn** does.

## Proposed Fix — `createSwitchableClient()` (Recommended: Option C)

A thin wrapper utility that manages the destroy/create lifecycle behind a stable Proxy reference:

### API Design

```typescript
import { createSwitchableClient } from "@datafn/client";

const { client, switchContext, currentContext } = createSwitchableClient({
  schema,
  clientId: getOrCreateClientId(),
  storage: (ctx) => IndexedDbStorageAdapter.create({
    dbName: `my-app_${ctx.tenantId}_${ctx.userId}`,
    schema,
  }),
  initialAuth: { userId: "user-123", tenantId: "tenant-a" },
  sync: {
    mode: "sync",
    remote: "http://localhost:3000/datafn",
    offlinability: true,
  },
});

// `client` is a Proxy — always delegates to the current underlying real client
// `switchContext` handles the full destroy → create → hydrate cycle
// `currentContext` returns the active AuthContext

await switchContext({ userId: "user-123", tenantId: "tenant-b" });
// client.todos, client.kv, etc. now point to tenant-b's data
```

### Implementation Sketch

```typescript
export interface SwitchableClientConfig<S extends DatafnSchema> {
  schema: S;
  clientId: string;
  storage: DatafnStorageFactory;
  initialAuth: AuthContext;
  sync?: DatafnSyncConfig;
  plugins?: DatafnPlugin[];
  generateId?: DatafnClientConfig<S>["generateId"];
  /** Called after the new client is created and before sync starts */
  onSwitch?: (newContext: AuthContext, oldContext: AuthContext) => void | Promise<void>;
}

export interface SwitchableClient<S extends DatafnSchema> {
  /** Proxied client — always delegates to the current underlying client */
  client: DatafnClient<S>;
  /** Switch to a new auth context. Destroys old client, creates new one. */
  switchContext(auth: AuthContext): Promise<void>;
  /** Get the current auth context */
  currentContext(): AuthContext;
  /** Destroy the switchable client and its underlying client */
  destroy(): Promise<void>;
}

export function createSwitchableClient<S extends DatafnSchema>(
  config: SwitchableClientConfig<S>,
): SwitchableClient<S> {
  let currentAuth = config.initialAuth;
  let realClient = createDatafnClient({
    schema: config.schema,
    clientId: config.clientId,
    authContext: currentAuth,
    storage: config.storage,
    sync: config.sync,
    plugins: config.plugins,
    generateId: config.generateId,
  });

  // Proxy that always delegates to the current realClient
  const proxy = new Proxy({} as DatafnClient<S>, {
    get(_target, prop) {
      return (realClient as any)[prop];
    },
  });

  return {
    client: proxy,

    async switchContext(auth: AuthContext) {
      const oldAuth = currentAuth;

      // 1. Destroy old client (flushes, stops sync, closes storage)
      await realClient.destroy();

      // 2. Create new client for the new context
      currentAuth = auth;
      realClient = createDatafnClient({
        schema: config.schema,
        clientId: config.clientId,
        authContext: auth,
        storage: config.storage,
        sync: config.sync,
        plugins: config.plugins,
        generateId: config.generateId,
      });

      // 3. Notify callback
      if (config.onSwitch) {
        await config.onSwitch(auth, oldAuth);
      }

      // 4. Start sync if applicable
      if (config.sync?.mode === "sync") {
        await realClient.sync.start();
      }
    },

    currentContext() {
      return currentAuth;
    },

    async destroy() {
      await realClient.destroy();
    },
  };
}
```

### Why Option C over alternatives

| Approach | Pros | Cons |
|----------|------|------|
| **A: `client.switchContext()`** | Single call, no proxy | Requires rearchitecting all client internals (closure-scoped state, signal registry, event bus). Signals hold stale refs. High risk. |
| **B: Reactive auth context** | Most ergonomic | Fundamentally changes lifecycle model. Every internal component needs mid-flight context change handling. Massive scope. |
| **C: `createSwitchableClient` proxy** | Stable reference, no internal changes, thin utility | Proxy indirection, signals still need invalidation on switch |

Option C is the sweet spot: it solves the user-facing problem (stable client reference, managed lifecycle) without touching the core client internals. It can be implemented as a standalone utility in `@datafn/client` and optionally wrapped further by framework adapters (`@datafn/svelte`, `@datafn/react`).

### Framework adapter extension (future)

For Svelte, a `createSwitchableSvelteClient` could wrap the switchable client and automatically invalidate stores:

```typescript
// @datafn/svelte
export function createSwitchableSvelteClient<S extends DatafnSchema>(
  config: SwitchableClientConfig<S>,
) {
  const switchable = createSwitchableClient(config);
  const clientStore = writable(switchable.client);

  return {
    client: clientStore, // Svelte store — components react to changes
    async switchContext(auth: AuthContext) {
      await switchable.switchContext(auth);
      clientStore.set(switchable.client); // Triggers Svelte reactivity
    },
    destroy: switchable.destroy,
  };
}
```

## Notes

- The IndexedDB adapter's statefulness (one connection per adapter) is a hard constraint — true hot-swap of storage is not possible. Any solution must accept the destroy/create cycle for the storage layer.
- The Proxy approach in Option C means `===` identity checks against the client object will still pass (same proxy reference), but property access is forwarded. This works well for Svelte/React patterns where you pass `client` through context.
- `clientId` should remain stable across switches (it identifies the device, not the tenant). The storage factory uses `tenantId` + `userId` for isolation, not `clientId`.
- The `onSwitch` callback can be used to show loading spinners, clear UI caches, or trigger analytics events.
- Concurrent `switchContext` calls should be serialized to avoid race conditions (e.g., user clicks tenant-B then tenant-C rapidly). The implementation should queue or debounce switches.
- This utility could live in `@datafn/client` directly (no separate package needed) since it only depends on `createDatafnClient` and existing types.
