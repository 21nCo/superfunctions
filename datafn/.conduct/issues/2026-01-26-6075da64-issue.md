## Summary

The IndexedDB storage adapter implementation deviates from the original specification in two significant ways: (1) It uses a single "records" object store with composite key `[resource, id]` instead of per-resource stores as specified in PHASE_09, and (2) Schema-defined indices (e.g., `base: ["createdAt"]`) are not used to create IndexedDB indices, despite the implementation milestone being marked as completed. The single-store approach was a pragmatic MVP choice that simplifies schema management and enables efficient resource-based queries via composite key ranges. However, the missing schema-based indexing causes queries on indexed fields to fall back to full table scans with in-memory filtering, which is acceptable for MVP scale but will not scale for larger datasets. This is a **Medium** severity issue affecting query performance and maintainability.

## Observed Errors/Symptoms

1. **Spec Drift - Storage Structure**: PHASE_09.md specified "records (per resource)" suggesting separate object stores per resource, but implementation uses a single "records" store.

2. **Missing Schema-Based Indices**: Schema definitions include `indices: { base: ["createdAt"] }` but these are not used to create IndexedDB indices. Queries filtering or sorting by `createdAt` perform O(n) scans instead of O(log n) index lookups.

3. **Performance Degradation**: The `findRecords()` method (lines 263-278) falls back to listing all records and filtering in-memory for any field other than "id", regardless of whether that field is declared as indexed in the schema.

4. **Documentation Mismatch**: `implementation.md` line 107 marks "Implement schema-to-table creation + indexing based on DFQL schema" as completed (`[x]`), but schema indices are not actually implemented.

## Root Causes

### Issue 1: Single "records" Store Instead of Per-Resource Stores

**Location**: `client/src/adapters/indexedDbStorage.ts:61-68`

**Spec Requirement** (PHASE_09.md, line 49):
```
- define DB schema (object stores + indexes) for:
  - records (per resource)  ← Spec suggests per-resource stores
  - join rows (per relation)
  - meta (cursors + hydration)
  - changelog
```

**Current Implementation**:
```typescript
// Records store: Key [resource, id]
// This effectively groups by resource and allows range queries
if (!db.objectStoreNames.contains("records")) {
  const store = db.createObjectStore("records", {
    keyPath: ["resource", "id"],
  });
  store.createIndex("by_resource", "resource", { unique: false });
}
```

**Expected Behavior**: Per the spec, each resource should have its own object store (e.g., "todos", "users", etc.) for better isolation and potentially per-resource indexing strategies.

**Actual Behavior**: All resources share a single "records" store with composite key `[resource, id]`. The `resource` field is part of the key path, enabling efficient resource-based queries via key ranges, but all resources are stored together.

**Impact**: 
- **Positive**: Simpler schema management (no need to create/destroy stores when resources change), single transaction scope for cross-resource operations, natural sorting by resource then id
- **Negative**: All resources share one store (less isolation), cannot have resource-specific indexing strategies, schema changes don't require store migrations but also don't benefit from store-level optimizations

**Evidence**: 
- Spec clearly states "records (per resource)" in PHASE_09.md line 49
- Implementation comment (line 61-62) explains the design choice: "This effectively groups by resource and allows range queries"
- Code uses composite key `[resource, id]` and `by_resource` index to enable resource filtering
- No documentation found explaining why this deviation was made

### Issue 2: Schema Indices Not Implemented in IndexedDB

**Location**: `client/src/adapters/indexedDbStorage.ts:58-96` (store creation), `client/src/adapters/indexedDbStorage.ts:263-278` (findRecords fallback)

**Intent/Milestone** (implementation.md, line 107):
```
- [x] Implement schema-to-table creation + indexing based on DFQL schema
```

**Current Implementation**:
```typescript
// Only hardcoded indices exist:
store.createIndex("by_resource", "resource", { unique: false });
store.createIndex("by_relation", "relationKey", { unique: false });
store.createIndex("by_client_mutation", ["clientId", "mutationId"], { unique: true });

// Schema indices are NOT used:
// Example schema: { indices: { base: ["createdAt"] } }
// No IndexedDB index is created for "createdAt"
```

**Expected Behavior**: When a schema defines `indices: { base: ["createdAt"] }`, the adapter should create an IndexedDB index on the `createdAt` field to enable efficient queries and sorting.

**Actual Behavior**: Schema indices are completely ignored. Only three hardcoded indices exist: `by_resource`, `by_relation`, and `by_client_mutation`. Queries on schema-indexed fields fall back to full table scan:

```typescript
async findRecords(
  resource: string,
  field: string,
  value: unknown,
): Promise<Record<string, unknown>[]> {
  // Optimization for ID lookup
  if (field === "id") {
    const record = await this.getRecord(resource, value as string);
    return record ? [record] : [];
  }

  // Fallback: list all and filter
  // Since this is client-side, scanning usually acceptable for typical local datasets
  const all = await this.listRecords(resource);
  return all.filter((r) => r[field] === value);  // ← O(n) scan, no index used
}
```

**Impact**: 
- Queries filtering or sorting by schema-indexed fields (e.g., `createdAt`) perform O(n) full table scans instead of O(log n) index lookups
- Performance degrades linearly with dataset size
- Schema indices serve no functional purpose - they're only hints that are ignored
- Audit note acknowledges this as "known trade-off" for MVP (audit.md, line 22)

**Evidence**: 
- `implementation.md` line 107 marks schema indexing as completed, but no code reads schema to create indices
- `findRecords()` method explicitly falls back to full scan (lines 274-277)
- Comment acknowledges "scanning usually acceptable for typical local datasets" (line 275)
- Audit report notes: "Pre-loading Performance: The current DB store implementation pre-loads all records for a resource during execution, which is correct for MVP semantics but unscalable for large tables (known trade-off)." (audit.md, line 22)

## Notes

- **Single Store Rationale** (inferred from code comments): The composite key `[resource, id]` approach enables efficient resource-based queries using IndexedDB key ranges. The comment at line 61-62 suggests this was an intentional design choice for simplicity and efficiency.

- **Schema Indices Status**: The milestone was marked complete, but the actual implementation only covers the adapter structure, not the schema-based indexing feature. This appears to be a case where the checkbox was marked before the feature was fully implemented, or the feature scope was reduced during implementation.

- **Performance Trade-off**: The audit explicitly notes this as a "known trade-off" for MVP (audit.md, line 22). The `findRecords()` method comment (line 275) acknowledges "scanning usually acceptable for typical local datasets", indicating this was a conscious decision to prioritize simplicity over performance for MVP.

- **Migration Complexity**: If schema-based indexing is added later, existing databases would need a migration to:
  1. Read schema from client config or adapter initialization
  2. Create new indices in `onupgradeneeded` handler
  3. Increment `DB_VERSION` to trigger upgrade
  4. Handle field name mapping (camelCase in schema vs snake_case in DB if applicable)

- **Alternative Approaches Considered**: The codebase shows other projects (nucleus, memotron) use per-resource stores with indices like `createdAt` and `updatedAt` (see `nucleus/client/persistence/indexeddb/indexeddb.local.ts` lines 166-167). This suggests the single-store approach was a datafn-specific design choice, possibly to simplify the adapter interface.

- **Query Execution Impact**: The server-side `DbDataStore` also pre-loads all records (see `server/src/execution/db-store.ts` line 22), suggesting this full-scan approach is consistent across both client and server implementations for MVP.
