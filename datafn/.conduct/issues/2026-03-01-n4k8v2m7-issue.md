## Summary

KV mutations pushed via `/datafn/push` fail with `INTERNAL` because the upsert uses `conflictTarget: "id"`, which produces PostgreSQL `ON CONFLICT (id)`. The `kv` table has a **composite primary key** `(__ns, id)`, so there is no unique constraint on `id` alone. PostgreSQL rejects the statement with: *"there is no unique or exclusion constraint matching the ON CONFLICT specification"*. The row-level namespace wrapper is intended to transform `conflictTarget: "id"` to `["__ns", "id"]`, but the debug log shows the adapter receiving `conflictTarget: 'id'`, so either the transformation is not applied or not reaching the Drizzle adapter. The fix is to pass a composite conflict target (`["__ns", "id"]`) from the push handler when the schema has multi-tenant namespace isolation.

## Root Causes

### Root Cause 1: Push passes `conflictTarget: "id"` but table has composite PK `(__ns, id)`

**Location:** `datafn/server/src/execution/sync/push.ts` lines 239–246

**Current code:**
```typescript
await db.upsert({
  model: mut.resource,
  where: [{ field: "id", operator: "eq", value: mut.id }],
  create: { id: mut.id, ...coercedData },
  update: coercedData,
  namespace,
  conflictTarget: "id",
});
```

**Expected behavior:** For multi-tenant schemas, the conflict target must match the table’s primary key. The `kv` table (and all multi-tenant tables) use `PRIMARY KEY (__ns, id)`.

**Actual behavior:** Push passes `conflictTarget: "id"`. The Drizzle adapter uses this to build `ON CONFLICT (id)`, which does not match any unique constraint.

**Impact:** PostgreSQL rejects the upsert; the error is caught and returned as `INTERNAL`.

**Evidence:** Server log shows `conflictTarget: 'id'`; `datafn-schema.drizzle.ts` defines `primaryKey({ columns: [table.__ns, table.id] })` for `kv`.

---

### Root Cause 2: Namespace wrapper conflictTarget transformation not effective for push path

**Location:** `packages/db/src/adapter/row-level-namespace.ts` lines 211–224

**Current code:**
```typescript
let conflictTarget = params.conflictTarget;
if (conflictTarget) {
  conflictTarget = Array.isArray(conflictTarget)
    ? [col, ...conflictTarget]
    : [col, conflictTarget];
}
const result = await adapter.upsert({
  ...params,
  where,
  create,
  update,
  conflictTarget,
});
```

**Expected behavior:** When push passes `conflictTarget: "id"`, the wrapper should transform it to `["__ns", "id"]` before calling the underlying adapter, so Drizzle generates `ON CONFLICT (__ns, id)`.

**Actual behavior:** The debug log from the Drizzle adapter factory shows `conflictTarget: 'id'`, suggesting either:
- The wrapper is not in the call chain for this path, or
- The transformed `conflictTarget` is not reaching the Drizzle adapter.

**Impact:** The Drizzle adapter receives `"id"` and produces invalid SQL.

**Evidence:** `packages/db/src/adapter/factory.ts` line 206 logs `context.log.debug('upsert', params)`; user’s log shows `conflictTarget: 'id'`.

### Root Cause 3: KV table schema uses composite primary key

**Location:** `datafn/examples/todo-app/server/src/datafn-schema.drizzle.ts` lines 17–23; `datafn/cli/src/drizzle-codegen.ts` lines 69–72

**Current schema:**
```typescript
export const kv = pgTable("kv", {
  __ns: text("__ns").notNull(),
  id: text("id").notNull(),
  value: jsonb("value"),
}, (table) => [
  primaryKey({ columns: [table.__ns, table.id] }),
  index("idx_kv___ns").on(table.__ns),
]);
```

**Expected behavior:** `ON CONFLICT` must target `(__ns, id)` to match the primary key.

**Actual behavior:** Upsert targets `(id)` only, which has no unique constraint.

**Impact:** PostgreSQL rejects the statement.

## Proposed Fixes

### Fix A (recommended): Push handler passes composite conflict target for multi-tenant schemas

**File:** `datafn/server/src/execution/sync/push.ts`

Derive `conflictTarget` from schema:

```typescript
const isMultiTenant = schema.multiTenant !== false;
const conflictTarget = isMultiTenant ? ["__ns", "id"] : "id";

await db.upsert({
  model: mut.resource,
  where: [{ field: "id", operator: "eq", value: mut.id }],
  create: { id: mut.id, ...coercedData },
  update: coercedData,
  namespace,
  conflictTarget,
});
```

**Pros:** Explicit, caller-controlled, no dependency on wrapper behavior.  
**Cons:** Duplicates schema knowledge in the push handler.

---

### Fix B: Verify and fix namespace wrapper transformation

Ensure the row-level namespace wrapper correctly transforms `conflictTarget` and that the wrapped adapter is used for push. Add logging in the wrapper to confirm the transformed `conflictTarget` is passed to the underlying adapter.

**Pros:** Centralizes logic in the adapter layer.  
**Cons:** Requires tracing the adapter chain and possibly fixing wrapper or wiring.

---

### Fix C: Drizzle adapter derives composite conflict target when __ns is in create

If the Drizzle adapter detects `__ns` in the `create` payload and no explicit `conflictTarget`, derive `["__ns", "id"]` for tables with composite PK.

**Pros:** Adapter-level fix.  
**Cons:** Adapter would need schema/table metadata; higher complexity.

## Notes

- Issue `2026-03-01-m4k7x9v2` added `conflictTarget: "id"` to the push upsert, assuming the namespace wrapper would transform it to `["__ns", "id"]`. The current failure indicates that either the transformation is not applied on this path or the adapter receives the untransformed value.
- The `kv` table uses a composite primary key `(__ns, id)` per `2026-03-01-x7k3m9v4` and the Drizzle codegen. The conflict target must match this constraint.
- The push handler catches the PostgreSQL error and returns a generic `INTERNAL` message; the real error is logged via `logger?.error("Push operation failed", ...)`.
