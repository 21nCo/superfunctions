## User-Reported Issue Description

> http://localhost:3000/datafn/push is failing with 400 error and the api call is happening continuously without exponential backoff in the example todo app.

(With requested addition: document the recommended solution of backing off the interval when push keeps failing so the next round is delayed more.)

## Summary

When the DataFn client’s sync push fails (e.g. server returns 400), the **per-attempt** retries use exponential backoff (1s, 2s, 4s), but the **push loop** uses a fixed `pushInterval` (e.g. 2s in the todo app). After a round of push fails, the next round is scheduled by the same fixed interval, so the client keeps hitting `/datafn/push` repeatedly over time. There is no interval backoff when push keeps failing, which makes the behaviour look “continuous” and can hammer a failing or misconfigured server. Severity: **Medium** — degraded behaviour under persistent push failure (e.g. 400), unnecessary load and poor UX.

## Observed Errors / Symptoms

- **HTTP 400** from `POST /datafn/push` (e.g. in the todo app against `http://localhost:3000/datafn`).
- **Behaviour**: The push API is called repeatedly; the user perceives “continuous” calls and “no exponential backoff” because:
  - Within a single round there *is* backoff between the 4 attempts (~1s, 2s, 4s).
  - After the round exhausts retries, the **next round** starts after only `pushInterval` (e.g. 2s), with no extra delay when push has been failing repeatedly.
- **Example**: With `pushInterval: 2000` and `pushMaxRetries: 3`, the client does up to 4 attempts per round with backoff, then ~2s later starts another round, so failed push requests continue at a steady cadence.

## Root Causes

### RC-1: Push loop uses a fixed interval; no backoff of the interval when push keeps failing

**Location**: `datafn/client/src/sync/engine.ts` — `start()` (lines 99–101) and `processPush()` (no reschedule of timer on failure).

**Current code**:

```typescript
// start():
if (this.pushInterval) {
  this.timer = setInterval(() => this.processPush(), this.pushInterval);
}
```

When `processPush()` runs and `pushWithRetries()` returns `null` (all retries failed), the engine does not reschedule or lengthen the next run. The only driver for the next push is the same `setInterval` with fixed `pushInterval`. Success path can schedule an immediate next batch via `setTimeout(() => this.processPush(), 0)` when the batch is full, but the failure path does not adjust the interval.

**Expected behaviour**: When push repeatedly fails (e.g. multiple rounds in a row), the next round should be delayed more (e.g. exponential backoff of the interval) so the client does not keep calling the server at a fixed short interval.

**Actual behaviour**: The next round always occurs after `pushInterval` (e.g. 2s), regardless of how many times push has failed.

**Impact**: Under persistent push failure (e.g. 400), the client continues to hit `/datafn/push` at a steady rate, which feels like “continuous” calls and no meaningful backoff at the loop level.

**Evidence**: No code in `engine.ts` adjusts the timer or schedules a delayed next `processPush()` when `pushResult === null`; the only scheduling is the fixed `setInterval` and the success-path `setTimeout(..., 0)` for a full batch.

---

### RC-2: 4xx (e.g. 400) is retried like any other error

**Location**: `datafn/client/src/sync/engine.ts` — `pushWithRetries()` (lines 848–919).

**Current code**:

The catch block retries on **any** thrown error. When the HTTP transport returns `{ ok: false, error: {...} }` for 400, the engine throws and then retries with per-attempt backoff. There is no check for client error (e.g. `response.error` or 4xx) to skip retries.

**Expected behaviour**: Client errors (e.g. 400 Bad Request) should not be retried, or at least not with the same policy as transport errors, since retrying is unlikely to succeed.

**Actual behaviour**: Every failure (including 400) is retried up to `pushMaxRetries` times with exponential backoff within the round.

**Impact**: Wasted attempts and extra load on the server for failures that will not resolve by retrying; combined with RC-1, this contributes to the impression of “continuous” failing calls.

---

### RC-3: Root cause of 400 is environment-specific

**Location**: Server and/or client request (todo app example: `datafn/examples/todo-app/client/src/lib/datafn.ts`, `datafn/examples/todo-app/server`).

The **400** itself is a server response indicating a bad or invalid request. Common causes include: server not running or wrong URL, schema/validation mismatch, missing or invalid body, auth/config issues, or server-side bugs (e.g. internal table resolution as in other documented issues). The sync engine does not cause the 400; it only reacts to it. Fixing the 400 requires investigating the specific server and request (logs, response body, route config).

**Impact**: Until the 400 is fixed, push will keep failing; RC-1 and RC-2 determine how aggressively the client retries and how soon the next round runs.

## Proposed Fixes

1. **Fix the 400**  
   Investigate server logs, response body, and client request (URL, schema, body) for the todo app (and any other environment) and fix the underlying cause so `/datafn/push` returns success or a clear, actionable error.

2. **Back off the interval when push keeps failing (recommended)**  
   - When a round of push exhausts retries and returns `null`, do **not** rely only on the fixed `setInterval` for the next run.
   - Introduce an **interval backoff** (e.g. exponential): e.g. track consecutive push failures and schedule the next `processPush()` with a delay that increases (e.g. `min(pushInterval * multiplier^consecutiveFailures, maxPushInterval)`), with optional jitter.
   - On first success after failures, reset the consecutive-failure count so the next interval returns to the configured `pushInterval`.
   - This keeps per-attempt retry backoff as-is (RET-001) and adds a second layer of backoff at the loop level, so the next round is delayed more when push keeps failing.

3. **Optionally: do not retry on 4xx**  
   In `pushWithRetries()`, when the response indicates a client error (e.g. `response.ok === false` and `response.error` with a 4xx code or `retryable === false`), skip retries and return `null` immediately so the engine does not waste attempts and can apply interval backoff sooner.

## Testing Checklist

- With server returning 400 for push: confirm that after one or more failed rounds, the **next** round is delayed (e.g. interval backoff), and that delay increases with consecutive failures (e.g. 2s, then 4s, then 8s, up to a cap).
- After a successful push following failures: confirm the next round uses the normal `pushInterval` again (backoff reset).
- With server returning 200 for push: confirm behaviour unchanged (no unnecessary delays).
- If 4xx no-retry is implemented: confirm 400 (or 4xx) results in no retries within the round and only one request per round until interval backoff triggers the next round.

## Notes

- The todo app uses `pushInterval: 2000`, `pushMaxRetries: 3`, and does not set `pushRetryBackoff` (defaults are used). So per-attempt backoff is ~1s, 2s, 4s; the missing piece is backoff of the **interval** when push keeps failing.
- `cloneUp`’s `pushBatchWithRetry()` in `datafn/client/src/sync/cloneUp.ts` has no backoff between retries (immediate retries); that is a separate improvement and not the cause of the “continuous” behaviour in the periodic push loop described here.
