## Summary

Sync fails at startup with `Unknown table: __global_cursor__` because the IndexedDB storage adapter validates every argument to `getCursor` and `setCursor` as a **table (resource) name** via `validateTableName()`. The sync engine uses a special cursor key `__global_cursor__` (not a table) to store the global sync cursor. When the adapter is created with a schema (e.g. `IndexedDbStorageAdapter.create({ dbName, schema })`), `validResources` is set from the schema (e.g. `todos`, `categories` only). Since `__global_cursor__` is not in that set, `validateTableName("__global_cursor__")` throws. This is a **high** severity bug: sync cannot start for any app using the recommended schema-based adapter creation path.

## Observed Errors / Symptoms

- **Error**: `Error: Unknown table: __global_cursor__`
- **Location in stack**: `IndexedDbStorageAdapter.validateTableName` at `indexedDbStorage.ts:360`, called from `getCursor` at line 588 (and similarly from `setCursor` at 598).
- **Trigger**: Sync start — during clone/hydration, `applyCloneResult` → `setCursorMonotonically` calls `storage.getCursor("__global_cursor__")` and/or `storage.setCursor("__global_cursor__", ...)`.
- **Scope**: Any client that uses `IndexedDbStorageAdapter.create({ dbName, schema })` (e.g. the todo-app example) and enables sync.

## Root Causes

### Root Cause 1: Cursor keys are validated as table names in getCursor/setCursor

**Location**: `datafn/client/src/adapters/indexedDbStorage.ts`, lines 358–361 (validateTableName), 588 (getCursor), 598 (setCursor)

**Current code**:

```typescript
// lines 358–361
private validateTableName(table: string) {
  if (this.validResources && !this.validResources.has(table)) {
    throw new Error(`Unknown table: ${table}`);
  }
}

// line 588 (getCursor)
async getCursor(resource: string): Promise<string | null> {
  this.validateTableName(resource);  // ← treats "resource" as table name
  const store = await this.getStore("meta", "readonly");
  // ...
}

// line 598 (setCursor)
async setCursor(resource: string, cursor: string | null): Promise<void> {
  this.validateTableName(resource);  // ← same
  // ...
}
```

**Expected behavior**: Cursor storage is keyed by **cursor keys**, which include both per-resource names (e.g. `todos`, `categories`) and the internal key `__global_cursor__`. The adapter should allow the sync engine to read/write the global cursor under `__global_cursor__` without treating it as a table name.

**Actual behavior**: Every string passed to `getCursor`/`setCursor` is validated with `validateTableName()`. When `validResources` is set (e.g. from schema in `IndexedDbStorageAdapter.create({ schema })`), it contains only schema resource names. `__global_cursor__` is not a resource name, so validation throws.

**Impact**: Sync initialization fails as soon as clone/apply logic tries to get or set the global cursor. The example app (and any app using schema-based adapter creation) cannot start sync.

**Evidence**: Stack trace shows `getCursor` → `validateTableName` → throw. Sync code uses `__global_cursor__` in:
- `datafn/client/src/sync/apply.ts` line 9: `export const GLOBAL_CURSOR_KEY = "__global_cursor__";`
- `datafn/client/src/sync/cloneUp.ts` lines 356, 439, 443: `getCursor("__global_cursor__")`, `setCursor("__global_cursor__", ...)`

### Root Cause 2: validResources is derived only from schema resources

**Location**: `datafn/client/src/adapters/indexedDbStorage.ts`, lines 114–116, 156–158

**Current code**:

```typescript
// create() — line 115
const resources = options.schema.resources.map((r) => r.name);
return new IndexedDbStorageAdapter(options.dbName, resources, options.schema);

// constructor — lines 156–158
if (resources) {
  this.validResources = new Set(resources);
}
```

So `validResources` contains only names from `schema.resources` (e.g. `todos`, `categories`). There is no allowance for internal cursor keys such as `__global_cursor__`.

**Expected behavior**: Either internal cursor keys are excluded from table-name validation, or they are explicitly allowed when validating cursor/hydration keys.

**Actual behavior**: No special handling for `__global_cursor__`; it is validated like any other string and rejected.

**Impact**: Reinforces Root Cause 1: when using the recommended `create({ schema })` path, the global cursor key is never valid.

## Proposed Fixes

1. **Recommended (minimal change)**  
   In `IndexedDbStorageAdapter`, for `getCursor` and `setCursor` only: skip table-name validation when the key is the known internal cursor key `__global_cursor__`. For example:
   - Import or define `GLOBAL_CURSOR_KEY = "__global_cursor__"` (or match the constant from `apply.ts`).
   - In `getCursor(resource)` and `setCursor(resource, ...)`, call `validateTableName(resource)` only when `resource !== GLOBAL_CURSOR_KEY` (or when `resource` is not in a small set of allowed internal cursor keys).
   - This keeps table-name validation for actual resource names while allowing the sync engine to use `__global_cursor__`.

2. **Alternative**  
   Introduce a separate allowlist for “cursor keys” that includes `__global_cursor__` plus all entries in `validResources`, and in `getCursor`/`setCursor` validate against that allowlist instead of `validResources` alone. Same net effect; slightly more extensible if more internal keys are added later.

3. **Do not** add `__global_cursor__` to `validResources` as if it were a table — it is not a table; it is a key in the `meta` store. Keeping the distinction avoids confusion and accidental use as a resource store name.

No change is required in the example app’s `datafn.ts` or in sync/apply logic; the fix belongs in the adapter.

## Notes

- The memory adapter uses the same `validateTableName(resource)` pattern in getCursor/setCursor; if it ever gets a `validResources`-like restriction, it would need the same allowance for `__global_cursor__`.
- When `validResources` is not set (e.g. adapter constructed without a resource list), `validateTableName` is a no-op, so the issue only appears when using schema-based creation.
- Spec and audit docs (e.g. REQUIREMENTS.md, EXPLANATION.md) already describe `__global_cursor__` as the global cursor key; the implementation should align with that contract in the adapter.
