## User-Reported Issue Description

> Push fails with `TypeError: db.run is not a function` when running the datafn example todo-app server with Drizzle + Postgres. Sequence store getCurrent fails, falling back to database, then Push failed. Error occurs at `packages/db/dist/adapters/drizzle/internal.js:48:22` in `ensureTable`. The example app uses Postgres (`drizzle(pool, { schema })`); the internal CRUD implementation assumes a SQLite-style `db` (run/all) which Postgres Drizzle does not provide.

## Summary

After the fix from spec `2026-02-12-fix-r8k4m2x9-spec` (internal table resolution via `Adapter.internal`), the Drizzle adapter’s **internal CRUD** implementation in `packages/db/src/adapters/drizzle/internal.ts` uses a **SQLite-only** execution API: `db.run()` for DDL/writes and `db.all()` for reads. The Drizzle **Postgres** (and MySQL) drivers do not expose `run` or `all`; they use a different API (e.g. `db.execute()` with different result shapes). When the DataFn server runs with Drizzle + Postgres (e.g. the todo-app example), the first use of internal tables (e.g. `__datafn_meta` in `ensureTable`) calls `db.run(...)` and throws `TypeError: db.run is not a function`, causing every push to fail. The oversight originated in the spec and test design: the spec and phase plan described only the SQLite API, and test vectors only exercised Drizzle with `dialect: "sqlite"`, so Postgres/MySQL were never required or tested.

**Flow**: Client push → server `executePush` → `ChangeTrackingService.getCurrentServerSeq` / `DatabaseSequenceStore.getCurrent` → `ensureInternalTable("__datafn_meta", ...)` → `adapter.internal.ensureTable` → `createDrizzleInternalCrud(...).ensureTable` → `db.run(drizzleSql.raw(ddl))` → throw.

**Behavioural symptoms**:

- Push returns failure; sync keeps retrying.
- Any server path that lazily ensures internal tables (sequence store, change tracking, idempotency, seed) fails when the adapter is Drizzle + Postgres (or MySQL).

## Root Causes

### RC-1: Drizzle internal CRUD assumes SQLite-style `db` API (run/all)

**Location**: `packages/db/src/adapters/drizzle/internal.ts` (e.g. lines 61, 77, 91, 118, 137, 151)

**Current code** (representative):

```typescript
// ensureTable
const ddl = `CREATE TABLE IF NOT EXISTS ${name} (${colDefs.join(', ')})`;
await db.run(drizzleSql.raw(ddl));   // ← SQLite/better-sqlite3 API

// create
await db.run(query);

// findOne / findMany
const rows = await db.all(query);

// update / delete
const result = await db.run(query);
```

**Expected behaviour**: Execution API should be **dialect-dependent**: SQLite-style drivers expose `run`/`all`; Postgres/MySQL Drizzle drivers use a different API (e.g. `db.execute()` or driver-specific execution) with different return shapes.

**Actual behaviour**: The code unconditionally uses `db.run` and `db.all`. These exist only on SQLite-style Drizzle backends (e.g. better-sqlite3). The Drizzle node-postgres (and MySQL) instances do not have `run` or `all`, so any call throws.

**Impact**: All internal table operations (ensureTable, create, findOne, findMany, update, delete) fail when the Drizzle adapter is configured with `dialect: "postgres"` or `dialect: "mysql"`, breaking push, change tracking, idempotency, and seed.

**Evidence**: Stack trace points to `internal.js:48` (ensureTable); `datafn/examples/todo-app/server/src/db.ts` uses `drizzle(pool, { schema })` with `dialect: "postgres"`.

---

### RC-2: Spec and phase plan specified only the SQLite execution API

**Location**: Spec `datafn/.conduct/specs/2026-02-12-fix-r8k4m2x9-spec/`

**Spec (REQUIREMENTS.md)**:

- **ICRUD-003** (line 60): “DDL is dialect-appropriate (Postgres, SQLite, MySQL)” — requires dialect-appropriate DDL but does **not** require dialect-appropriate **execution API** for raw SQL.
- **DRZ-001** (lines 67–68): “The Drizzle adapter MUST implement InternalCrud using **`db.run(sql`...`)`** from drizzle-orm for DDL and by dynamically constructing raw SQL for CRUD.” This describes only the **SQLite** execution API. There is no requirement that Postgres/MySQL use a different method (e.g. `db.execute()` and result mapping).

**Phase plan (phases/PHASE_01.md)**:

- Tasks state: “Execute via **`db.run(sql`...`)`**” and “Implement CRUD using **`db.all(sql`...`)`** for reads and **`db.run(sql`...`)`** for writes” — again only the SQLite API, with no branching by dialect.

**Expected behaviour**: Spec and phase plan should require “per-dialect execution API” for Drizzle internal CRUD (e.g. “for SQLite use db.run/db.all; for Postgres/MySQL use the driver’s execute API and map results accordingly”).

**Actual behaviour**: Spec and phase plan described a single API (`db.run`/`db.all`), so implementors had no mandate to branch by dialect.

**Impact**: Implementation correctly followed the spec and phase plan; the gap is in the spec, not in “wrong” execution.

---

### RC-3: Test vectors only exercised Drizzle + SQLite

**Location**: `datafn/.conduct/specs/2026-02-12-fix-r8k4m2x9-spec/TEST_VECTORS.md`

**Current content** (TV-DRZ-INTERNAL-001):

```typescript
const adapter = drizzleAdapter({ db, dialect: "sqlite" });
```

**Expected behaviour**: At least one test vector (or acceptance test) should cover Drizzle internal CRUD with **Postgres** (or MySQL), e.g. Drizzle+Postgres or the todo-app with Postgres.

**Actual behaviour**: The only Drizzle internal CRUD test uses `dialect: "sqlite"`. No vector or test covers Drizzle+Postgres/MySQL.

**Impact**: All specified tests pass with a SQLite-only implementation; the Postgres failure is only discovered in real use (e.g. todo-app with Postgres).

## Where the Spec Went Wrong (Summary)

| Artifact | What went wrong |
| -------- | ----------------- |
| **REQUIREMENTS.md ICRUD-003** | Requires “dialect-appropriate” DDL but does not tie that to “per-dialect execution API” for raw SQL. |
| **REQUIREMENTS.md DRZ-001** | Specifies only `db.run(sql...)` (SQLite API); does not require different execution for Postgres/MySQL. |
| **REQUIREMENTS.md DRZ-001** | Acceptance criteria say “for the configured dialect” for DDL but do not require dialect-specific **execution** paths. |
| **TEST_VECTORS.md TV-DRZ-INTERNAL-001/002** | Only use `dialect: "sqlite"`; no vector for Postgres or MySQL. |
| **phases/PHASE_01.md** | Tasks prescribe `db.run`/`db.all` without “when dialect is SQLite; for Postgres/MySQL use …”. |
| **Audit** | Audit confirmed “DDL is dialect-appropriate” and “Drizzle uses db.run” without verifying that Postgres/MySQL paths exist or are tested. |

## Proposed Fixes

### Implementation (packages/db)

- In `packages/db/src/adapters/drizzle/internal.ts`, make execution **dialect-aware**:
  - **SQLite**: Keep using `db.run()` and `db.all()` when the Drizzle `db` exposes them (e.g. better-sqlite3).
  - **Postgres / MySQL**: Use the driver’s execution API (e.g. `db.execute(sql)` or equivalent for raw SQL). Map result shapes (e.g. rowCount/rowsAffected, row arrays) to what internal CRUD expects (counts for run, rows for all).
- Ensure `createDrizzleInternalCrud(db, dialect)` receives the correct `dialect` and branches on it for execution and result handling.

### Spec and test design (datafn/.conduct/specs)

- **REQUIREMENTS.md**  
  - In **DRZ-001**: Explicitly require “per-dialect execution API”: e.g. “For SQLite use `db.run`/`db.all` where available; for Postgres and MySQL use the driver’s raw execution API (e.g. `db.execute`) and map results to the same semantics (row counts, row arrays).”  
  - In **ICRUD-003** or DRZ-001: Add an acceptance criterion that internal CRUD works for **each** supported dialect (postgres, sqlite, mysql), not only one.
- **TEST_VECTORS.md**  
  - Add a test vector (or reference an acceptance test) for Drizzle internal CRUD with **Postgres** (e.g. TV-DRZ-INTERNAL-003 or “todo-app with Drizzle+Postgres push succeeds”). Optionally add one for MySQL if supported.
- **Phase plan (PHASE_01.md)**  
  - Update Drizzle tasks to say: “For SQLite use db.run/db.all; for Postgres/MySQL use db.execute (or driver equivalent) and map result shapes.”

### Audit

- Future audits for adapter behaviour should require evidence that **each** supported dialect is implemented and tested (e.g. Drizzle internal CRUD for postgres and sqlite, not only sqlite).

## Notes

- The bug is a **regression in scope**: spec `2026-02-12-fix-r8k4m2x9-spec` fixed internal table **resolution** (routing through `adapter.internal` instead of user CRUD) but the **implementation** of Drizzle’s `internal` assumed a single (SQLite) execution API.
- Prisma and Kysely internal CRUD use driver-agnostic raw APIs (`$executeRaw`/`$queryRaw`, `db.schema` + `sql`) and are not affected; only the Drizzle internal module is SQLite-API bound.
- Investigation was based on user-reported error, stack trace, and review of spec/phase/test vectors; no code was modified except creating this issue file.
