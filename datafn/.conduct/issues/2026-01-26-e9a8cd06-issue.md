## Summary

The `DatafnSignal` interface currently only exposes `get()` and `subscribe()` methods, but does not provide access to loading, error, or refreshing states. This creates a poor developer experience as applications cannot show loading indicators, handle errors gracefully, or indicate when data is being refreshed after mutations. The implementation internally tracks a `status` variable with "idle" | "loading" | "error" states and has logic to detect refresh operations, but these are not exposed through the public API. A previous specification (2026-01-24-audit-fix-comprehensive-spec) included these properties but they were never implemented. This is a **Medium** severity issue affecting developer experience and application UX.

## Observed Errors/Symptoms

1. **No Loading State**: Applications cannot detect when initial data fetch is in progress. The signal returns `undefined` initially, but there's no way to distinguish between "not yet loaded" and "loading".

2. **No Error State**: When queries fail, errors are thrown but not captured in a reactive state. Applications cannot display error messages or handle errors gracefully in the UI.

3. **No Refreshing State**: When mutations trigger automatic refreshes (via `mutation_applied` events), there's no way to indicate to users that data is being updated. The refresh happens silently in the background.

4. **Example App Workaround**: The todo app example (`examples/todo-app/client/src/App.svelte`) attempts to use `$todos?.loading` and `$todos?.error` (lines 74, 76), but these properties don't exist, causing the code to fail at runtime with "Cannot read properties of undefined".

**Location**: `client/src/signals/querySignal.ts:54, 94-98`

**Impact**:

## Proposed Fixes

### Fix 1: Extend DatafnSignal Interface

Update `core/src/types.ts` to include state properties:

```typescript
export interface DatafnSignal<T> {
  get(): T;
  subscribe(handler: (value: T) => void): () => void;
  readonly loading: boolean;
  readonly error: DatafnError | null;
  readonly refreshing: boolean;
}
```

### Fix 2: Implement State Properties in querySignal

Modify `client/src/signals/querySignal.ts` to:

1. Create reactive state for `loading`, `error`, and `refreshing`
2. Track `refreshing` separately from `loading` using the `isRefresh` parameter
3. Expose these as properties on the returned signal object
4. Notify subscribers when state changes, not just when value changes
5. Store error object when fetch fails (currently errors are thrown but not stored)

### Fix 3: Update Svelte Adapter

Modify `svelte/src/toSvelteStore.ts` to handle the new properties. The store should expose:
- The query result value (current behavior)
- Loading state
- Error state  
- Refreshing state

This may require returning a store that wraps the signal value with state, or creating separate stores for each property.

### Fix 4: Update Example App

Once the properties are available, update `examples/todo-app/client/src/App.svelte` to properly use:
- `$todos.loading` for initial load state
- `$todos.error` for error display
- `$todos.refreshing` for refresh indicator (optional, could show subtle indicator)
- `$todos.data` for the actual data array

## Notes

- The internal `status` variable tracks "idle" | "loading" | "error" but this doesn't map cleanly to the desired API. We need:
  - `loading`: true when `inFlight && !isRefresh`
  - `refreshing`: true when `inFlight && isRefresh`
  - `error`: stored error object (currently errors are thrown, not stored)
  
- The `toSvelteStore` adapter may need to be redesigned to expose multiple reactive values. Options:
  1. Return an object store with `{ value, loading, error, refreshing }`
  2. Create separate stores for each property
  3. Use Svelte's `derived` stores to compute state from signal
  
- Error handling currently throws errors on initial fetch but silently swallows refresh errors. The new API should capture both types of errors.

- The `isRefresh` parameter is passed to `fetchQuery` but not tracked separately. We need to track whether the current in-flight request is a refresh or initial load.

- Consider backward compatibility: existing code that only uses `get()` and `subscribe()` should continue to work.
