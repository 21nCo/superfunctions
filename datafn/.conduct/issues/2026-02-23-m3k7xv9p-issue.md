## Summary

Issue `2026-02-23-k7x9m4vr` ("Unify Client/Svelte API Surface") was implemented, successfully merging `SwitchableClient` into `createDatafnClient` (Fix 3) and replacing `toReactiveSvelteStore` as the sole `toSvelteStore` (Fix 4). However, the implementation left three concrete DX problems because the original issue underspecified Fix 4's API design:

1. **`toSvelteStore` requires a manually constructed `ClientRef` object** — consumers must write `{ subscribe: client.subscribeClient.bind(client) }` because `toSvelteStore` expects a `ClientRef<C>` (object with `subscribe`) but `DatafnClient` exposes `subscribeClient` (different name). The removed `wrapSubscribeClient` helper was replaced with inline ceremony that's worse.

2. **Every signal factory uses `(c as any)` casts** — the factory callback in `toSvelteStore(clientRef, (c) => ...)` receives `c` typed as `DatafnClient<DatafnSchema>`. Because `DatafnSchema` has `name: string` (not literal `"todos"` | `"categories"`), `ResourceNames<DatafnSchema>` resolves to `string`, producing an index signature `{ [key: string]: DatafnTable }` instead of named properties `.todos`, `.categories`. While `c.todos` may technically work via the index signature, the implementing agent used `(c as any)` defensively on all 6 signal stores.

3. **`defineSchema()` and explicit `: DatafnSchema` annotations erase literal resource names** — even the "type-safe" `defineSchema` helper returns `DatafnSchema` (line 125 of `core/src/types.ts`), so there is no path to get literal resource names into the client type. The todo app's `const schema: DatafnSchema = {...}` doubly erases them.

## Root Causes

### Root Cause 1: `toSvelteStore` doesn't accept a `DatafnClient` directly — requires `ClientRef` wrapper

**Location:** `datafn/svelte/src/toSvelteStore.ts`, lines 14–16 and 54–57

**Current code:**

```typescript
// Lines 14-16: ClientRef type
export type ClientRef<C> = {
  subscribe(fn: (client: C) => void): () => void;
};

// Lines 54-57: toSvelteStore signature
export function toSvelteStore<T, C = any>(
  clientRef: ClientRef<C>,
  signalFactory: (client: C) => DatafnSignal<T>,
): DatafnSvelteStore<T> {
```

**`DatafnClient` type (for comparison):**

```typescript
// datafn/client/src/client.ts, line 279:
subscribeClient(fn: (client: DatafnClient<S>) => void): () => void;
```

**The mismatch:** `ClientRef` has a method called `subscribe`. `DatafnClient` has a method called `subscribeClient`. The `DatafnClient.subscribe` method is the *event bus* subscriber — completely different purpose. So you can't pass a `DatafnClient` as a `ClientRef` directly.

**Why `wrapSubscribeClient` was removed without a replacement:** Issue `2026-02-23-k7x9m4vr` Fix 4 said "Remove `wrapSubscribeClient` — the unified client's `subscribeClient` already conforms to `ClientRef`." This is structurally true — `subscribeClient` has the right `(fn) => () => void` signature. But because the *property name* differs (`subscribeClient` vs `subscribe`), consumers must manually bridge:

```typescript
const clientRef = { subscribe: client.subscribeClient.bind(client) };
```

**Dependency constraint:** `@datafn/svelte` depends on `@datafn/core`, NOT `@datafn/client`. So `toSvelteStore` cannot reference the `DatafnClient` type directly. This is why it uses the generic `ClientRef<C>` approach. The fix must work within this constraint (no circular dependencies).

**Impact:** Every consumer app must write the `{ subscribe: ... .bind(...) }` boilerplate.

**Expected behavior:** `toSvelteStore(client, (c) => c.table("todos").signal(...))` — pass the client directly, no wrapper needed.

### Root Cause 2: `toSvelteStore` generic default `C = any` silently swallows type information

**Location:** `datafn/svelte/src/toSvelteStore.ts`, line 54

**Current code:**

```typescript
export function toSvelteStore<T, C = any>(
```

**Why this matters:** If TypeScript fails to infer `C` from the `clientRef` argument for any reason (e.g., the `.bind()` in the manual construction loses specificity, or the argument doesn't match `ClientRef<C>` cleanly), `C` silently defaults to `any`. The factory callback `(c) => ...` then receives `c: any`, which compiles without error but provides zero type safety. The developer gets no warning that inference failed.

**Expected behavior:** `C` should have no default, or should default to `never` so that inference failure is a compile error, not a silent `any`.

### Root Cause 3: Schema literal types erased at two levels — `defineSchema` return type and explicit annotations

**Location (A):** `datafn/core/src/types.ts`, lines 120–127

**Current code:**

```typescript
export function defineSchema<
  const T extends {
    readonly resources: readonly DatafnResourceBase[];
    readonly relations?: readonly DatafnRelationSchema[] | DatafnRelationSchema[];
  }
>(schema: T & { readonly resources: ValidateResources<T["resources"]> }): DatafnSchema {
  return schema as unknown as DatafnSchema;
}
```

The input captures `const T` (preserving literal types like `name: "todos"`), but the return type is `DatafnSchema` — which has `resources: DatafnResourceSchema[]` where `name: string`. All literal type information is erased.

**Location (B):** `datafn/examples/todo-app/client/src/lib/datafn.ts`, line 8

**Current code:**

```typescript
export const schema: DatafnSchema = {
  resources: [
    { name: "todos", ... },
    { name: "categories", ... },
  ],
  ...
};
```

The explicit `: DatafnSchema` annotation widens `"todos"` to `string`.

**Type flow consequence:**

1. `schema` is typed as `DatafnSchema` → `schema.resources[number].name` is `string`
2. `createDatafnClient({ schema })` infers `S = DatafnSchema`
3. `ResourceNames<DatafnSchema>` = `DatafnSchema["resources"][number]["name"]` = `string`
4. `DatafnClient<DatafnSchema>` includes `{ [Name in string]: DatafnTable<DatafnSchema, string> }` — an index signature
5. `c.todos` is technically `DatafnTable<DatafnSchema, string>` via the index signature, but there is no autocomplete, no named-property checking, and agents/developers reach for `(c as any)` out of uncertainty

**Expected behavior:** `defineSchema` should return a type that preserves literal resource names so that `DatafnClient<typeof schema>` has `.todos` and `.categories` as named properties with autocomplete.

### Root Cause 4: Deprecated `createSwitchableClient` not properly marked with JSDoc `@deprecated`

**Location:** `datafn/client/src/switchableClient.ts` — the completion report says "@deprecated JSDoc" was added, but the actual exports in `datafn/client/src/index.ts` only have a plain comment:

```typescript
// Switchable client — @deprecated: createDatafnClient now includes switchContext/subscribeClient/currentContext
export {
  createSwitchableClient,
  type SwitchableClient,
  type SwitchableClientConfig,
} from "./switchableClient.js";
```

A plain `//` comment is NOT a JSDoc `@deprecated` tag. IDEs (VS Code, Cursor, WebStorm) will not show deprecation warnings (strikethrough, hover tooltip) for these exports. Consumers have no signal that they should use `createDatafnClient` instead.

**Expected behavior:** The `createSwitchableClient` function and the `SwitchableClient`/`SwitchableClientConfig` types should have proper `/** @deprecated Use createDatafnClient instead */` JSDoc annotations on their declarations in `switchableClient.ts`.

## Proposed Fixes

### Fix 1: Add overload to `toSvelteStore` that accepts objects with `subscribeClient`

**File:** `datafn/svelte/src/toSvelteStore.ts`

Add a function overload that detects a `subscribeClient` method on the first argument and wraps it internally. This uses structural typing — no need to import `DatafnClient` from `@datafn/client`:

```typescript
type HasSubscribeClient<C> = {
  subscribeClient(fn: (client: C) => void): () => void;
};

// Overload 1: Accept a DatafnClient (or anything with subscribeClient)
export function toSvelteStore<T, C extends HasSubscribeClient<C>>(
  client: C,
  signalFactory: (client: C) => DatafnSignal<T>,
): DatafnSvelteStore<T>;

// Overload 2: Accept a ClientRef (existing behavior, for Svelte writable stores etc.)
export function toSvelteStore<T, C>(
  clientRef: ClientRef<C>,
  signalFactory: (client: C) => DatafnSignal<T>,
): DatafnSvelteStore<T>;

// Implementation
export function toSvelteStore<T, C>(
  clientOrRef: ClientRef<C> | HasSubscribeClient<C>,
  signalFactory: (client: C) => DatafnSignal<T>,
): DatafnSvelteStore<T> {
  // Normalize: if the argument has subscribeClient, wrap it as a ClientRef
  const clientRef: ClientRef<C> =
    "subscribeClient" in clientOrRef
      ? { subscribe: (clientOrRef as HasSubscribeClient<C>).subscribeClient.bind(clientOrRef) }
      : (clientOrRef as ClientRef<C>);

  return readable(
    // ... existing implementation unchanged ...
  );
}
```

**Result in consumer code:**

```typescript
// Before (current):
const clientRef = { subscribe: client.subscribeClient.bind(client) };
const allTodosStore = toSvelteStore(clientRef, (c) =>
  (c as any).todos.signal({ sort: ["-createdAt"] })
);

// After:
const allTodosStore = toSvelteStore(client, (c) =>
  c.table("todos").signal({ sort: ["-createdAt"] })
);
```

No wrapper object, no `.bind()`, and `c` is properly typed as `DatafnClient<S>`.

**Important type detail:** The `HasSubscribeClient<C>` self-referential generic ensures that when you pass a `DatafnClient<S>`, `C` is inferred as `DatafnClient<S>` (not as the intersection type of `HasSubscribeClient`), because `DatafnClient<S>.subscribeClient` takes `(fn: (client: DatafnClient<S>) => void)` — the `C` resolves to the full client type.

### Fix 2: Remove `C = any` default from `toSvelteStore`

**File:** `datafn/svelte/src/toSvelteStore.ts`, line 54

Change:
```typescript
export function toSvelteStore<T, C = any>(
```

To (in the overloads and implementation):
```typescript
// No default for C — inference failure becomes a compile error, not silent any
export function toSvelteStore<T, C>(
```

If `C` cannot be inferred, TypeScript will require the consumer to specify it explicitly, which surfaces the problem immediately instead of silently falling back to `any`.

### Fix 3: Make `defineSchema` return a narrowed type preserving literal resource names

**File:** `datafn/core/src/types.ts`, lines 120–127

Change the return type from `DatafnSchema` to a type that preserves the literal `name` values:

```typescript
type NarrowedSchema<T extends { resources: readonly DatafnResourceBase[] }> = DatafnSchema & {
  resources: T["resources"];
};

export function defineSchema<
  const T extends {
    readonly resources: readonly DatafnResourceBase[];
    readonly relations?: readonly DatafnRelationSchema[] | DatafnRelationSchema[];
  }
>(schema: T & { readonly resources: ValidateResources<T["resources"]> }): NarrowedSchema<T> {
  return schema as unknown as NarrowedSchema<T>;
}
```

This preserves `T["resources"]` in the return type, so `defineSchema({resources: [{name: "todos", ...}]}).resources[number].name` is `"todos"`, not `string`.

### Fix 4: Migrate todo app to use `defineSchema` and remove `: DatafnSchema` annotation

**File:** `datafn/examples/todo-app/client/src/lib/datafn.ts`, line 8

Change:

To:

With Fix 3 applied, `typeof schema` now preserves literal resource names. `createDatafnClient({ schema })` infers `S` with literal names. `DatafnClient<S>` has `.todos` and `.categories` as named properties. The `(c as any)` casts in `App.svelte` become unnecessary.

## Notes

- **This issue is a direct follow-up to `2026-02-23-k7x9m4vr`.** That issue's Fix 4 said "Remove `wrapSubscribeClient` — the unified client's `subscribeClient` already conforms to `ClientRef`" without specifying how consumers should create the `ClientRef` without boilerplate or type loss. The implementing agent (claude-sonnet-4-6) followed the spec faithfully, producing working code with poor DX.
- **Fix 1 requires no new package dependencies.** The `HasSubscribeClient<C>` type is structural — `@datafn/svelte` doesn't need to import anything from `@datafn/client`. It just checks for the shape `{ subscribeClient: (fn) => () => void }`.
- **Fix 3 is a breaking change to `defineSchema`'s return type** (narrows from `DatafnSchema` to `DatafnSchema & { resources: T["resources"] }`). This is safe because the narrowed type is assignable to `DatafnSchema`, so existing code that accepts `DatafnSchema` will still work. Code that uses `typeof defineSchema(...)` will get a *more specific* type, which can only cause errors if the code was relying on the widened type (unlikely).
- **The `(c as any)` casts may be technically unnecessary even without Fix 3.** When `S = DatafnSchema`, the mapped type `{ [Name in string]: DatafnTable<DatafnSchema, string> }` produces an index signature. `c.todos` should resolve to `DatafnTable<DatafnSchema, string>` via that index signature. The implementing agent likely used `as any` defensively without verifying whether the index signature path type-checked. However, the DX is still poor (no autocomplete, no named properties) — Fix 3 remains the right solution.
- **Event handler `as any` casts** (App.svelte lines 54, 59 — `(event as any).resource`) are a separate issue: `DatafnEvent` in `@datafn/core` doesn't type `resource`, `action`, `ids` as properties on all event variants. This is out of scope for this issue but worth noting.
- **Fixes should be applied in order:** Fix 3 (defineSchema return type) → Fix 4 (todo app schema migration) → Fix 1 (toSvelteStore overload) → Fix 2 (remove C = any) → Fix 5 (remove as-any from App.svelte) → Fix 6 (JSDoc deprecated). Fix 1 and Fix 3 are independent of each other, but Fix 5 depends on both.
