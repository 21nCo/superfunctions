# LogFn step-output forwarding checkpoint

Scope: original 2026-02-05 `specs/2026-02-05-new-c8f2n1xq-spec/REQUIREMENTS.md` RUNNER-005:325 and INT-004:423 require step output through LogFn. The runner already uses the real LogFn pipeline into its private durable spool. This slice adds an actual host-configured LogFn sink path for admitted control-plane output; it does not relabel optional dashboard streaming as mandatory, infer shell termination, or rerun commands.

## Storage and delivery contract

`LogFnStepOutputDispatcher` visits a finite page of ten runs and claims at most one line per run. Shared-adapter revision CAS commits the claim before sink invocation. Stable IDs hash namespace, run, dispatch and flattened event ordinal. Packet sequence/digest validation, runner authentication, redaction rejection, per-job 1 MiB/4096-event admission and authoritative log HTTP reads remain unchanged.

There is no duplicate persistent payload and no growing per-line receipt collection. Each job ledger holds a versioned delivered prefix and at most one claim/unknown receipt. Confirmed delivery advances the prefix; it must not be deleted while bytes remain, because doing so would replay old output. This constant-sized checkpoint is the receipt compaction policy. The existing global run/runner/database-history capacity limitation is still open; this does not bound total disk/WAL or invent a run-deletion policy.

The real `@logfn/core` pipeline invokes a host-supplied Sink, observes async completion/flush and rejects dropped/truncated/changed output. Context contains a stable event ID, run ID, redacted job key, fixed step key and ordinal. Raw dispatch IDs encode job names and are deliberately excluded; tokens, execution credentials and raw sink errors are never emitted. The built server opts in with `CIFN_STEP_OUTPUT_LOGS=console`, independently of lifecycle forwarding. Default is off. The deprecated hypothetical LogFn HTTP-query adapter remains unsupported; no fake receiver service is introduced.

Ambiguous failures park unknown and block later lines in that job; other independent jobs can progress. Lease expiry, receipt database failure or owner crash never authorize replay. Explicit operator reconciliation can confirm delivery or retry while bytes exist; retry can duplicate a previously accepted effect. No public HTTP reconciliation route or unauthenticated receipt access is added. `close()` closes admission and joins admitted sink I/O. Arbitrary custom sinks still require their own deadlines; shutdown cannot forcibly cancel them.

## Expiry, migration and retained uncertainty

The existing read, append and periodic-purge expiry paths all use the same expiry transition. Bytes are removed at the original expiry. A fixed tombstone records confirmed-delivered and expired-undelivered counts plus at most one unresolved event identity. An in-flight receipt becomes unknown. After expiry retry returns false; explicit `delivered` or `undelivered` resolves the retained uncertainty without resurrecting output. No automatic deletion of unknown claims or silent conversion to success occurs.

New sink invocation checks both claim and payload deadlines. Bytes already passed to arbitrary sink I/O or copied by an in-flight caller cannot be revoked; storage expiry is not a hard process-memory/remote-retention guarantee. Old expired ledgers have no recoverable counts and report `historicalCountUnavailable`. Existing unexpired admitted packets are eligible from ordinal zero; drain old writers before relying on this protocol. No retroactive fence against old binaries or historical delivery inference is claimed.
