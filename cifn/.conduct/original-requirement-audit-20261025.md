# Original CiFn requirement audit, 2026-10-25

Audit starting head: `cf15a21074f4fec88b0b162b52d543ada17e70fc`. This is a source-and-checkpoint mapping, not a declaration that the original full specification is complete. `tracker.csv` marks the original work items complete, but those legacy flags do not establish current production readiness.

`original-requirement-map.csv` enumerates all **159 statement-bearing requirement IDs** from the 2026-02-05 initial specification, 2026-02-07 audit specification and 2026-02-15 Python SDK specification. IDs are date-qualified because the audit specification reuses IDs with different meanings (for example original RUNNER-005 is status/LogFn reporting; the later RUNNER-005 is redaction). Each row identifies original source/line, current implementation surface, evidence and an explicit assessment. “Source surface present” means a full requirement vector has not been revalidated by this pass. It must not be treated as a green completion mark.

## Strong existing checkpoint evidence

- Durable SQLite run/job/step state, authenticated runner claims, cancellation/adjudication and replay without shell reexecution have native restart/race and installed HTTP evidence in the durable storage/dispatch/execution, step-status and adjudication checkpoint documents.
- Library-backed LogFn lifecycle and admitted step output have persisted claim/receipt/unknown-outcome behavior and actual installed local sinks. Optional streaming or external forwarding is not substituted for the original named LogFn integration.
- Repository checkout/config resolution, signature verification, event/branch admission and explicit host-approved fork identities have owned local Git, HTTP/SQLite and fresh-package evidence. This does not establish arbitrary untrusted-fork isolation or private provider credentials.
- Per-job Docker filesystem continuity, authoritative exec inspection and explicit retained-container cleanup have actual cached-image native and installed evidence. This does not establish automatic crash completion, a hostile-code sandbox or a particular invented receipt TTL.
- Python typing/schema/normal-CI evidence exists from the recorded checkpoint. This pass does not upgrade that to complete fresh Python sync/thread, SDK-to-built-server and platform coverage. CLI/dashboard/deployment surfaces likewise need their own end-to-end acceptance.

## Consequential open original requirements

1. **Archive/provider safety and integration** — Feb5 RUN-005, RUN-006, INT-002; Feb7 INT-002. The original local artifact/cache helper accepted traversal paths, source symlinks and untrusted extraction manifest paths. Three owned-filesystem regressions reproduced outside-workspace reads/writes before this slice. The current confinement changes address that concrete prerequisite across all four paths. They do not supply missing remote FileFn support: `executeRemoteShellJob` rejects every provider except checkout; `FileFnArtifactsAdapter.getFileId()` returns null and `list()` returns an empty array, so its `downloadByKey()` always misses. Full remote upload/download, durable artifact reference acknowledgement, cache transport and actual FileFn interoperability remain required.
2. **Actual scheduling** — Feb5 PIPE-004 and INT-001. The ignored-expression baseline is now replaced by actual FlowFn Scheduler evaluation and built-server registration (see `cron-flow-readiness.md`). Actual UTC due-time, stop/restart and SQLite queued-run acceptance are covered. Distributed schedule ownership and durable occurrence reconciliation remain open; manual trigger tests alone never established those guarantees.
3. **Declared provider execution** — Feb5 RUN-008, RUNNER-003, INT-006; Feb7 RUNNER-001, INT-006/007. The remote runner rejects TestFn/artifact/cache; HostFn now has an explicit trusted-host policy and durable execution acceptance (see `remote-hostfn-readiness.md`). Local TestFn has actual SDK/subprocess evidence, and the local HostFn shell interpolation baseline is now addressed by supervised argv execution (see `hostfn-argv-readiness.md`). Remaining remote provider integration and independent deployment receipt evidence are still required; no live deployment was attempted in this audit.
4. **Production ecosystem and operational proof** — actual FlowFn/SecFn/FileFn service contracts, private-provider permissions, original load targets, CLI/native browser dashboard, Docker Compose/HostFn packaging and deployment remain distinct. Source HTTP adapters and local mocks do not prove them. No external services were contacted to close these gates.

The selected bounded implementation is archive confinement, because it fixes reproduced writes/reads outside the original workspace contract before enabling more provider delivery. It preserves the outstanding original requirements above rather than redefining them as optional. Original specs do not prescribe autonomous Docker recovery or numeric receipt TTL; those operational improvements are not substituted for the named missing provider/scheduler requirements.
