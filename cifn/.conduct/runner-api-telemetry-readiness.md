# Durable runner and API telemetry checkpoint

Original requirement: the 2026-02-05 specification, `specs/2026-02-05-new-c8f2n1xq-spec/REQUIREMENTS.md`, OBS-001 (line 494) requires runner registration/heartbeat, pipeline parse errors and API errors alongside run/job/step events. OBS-002 prohibits secrets. This extends the real LogFn lifecycle delivery checkpoint, without reclassifying optional streaming or closing the remaining original integration/readiness requirements.

## Behavior

Runner registration and every accepted heartbeat append an encrypted event in the same shared-adapter revision CAS as the runner mutation. Public runner projections retain their original fields and exclude delivery records/claims. A namespace-wide encrypted API error ledger admits fixed allowlisted code, route template, method and status; no raw URL/query/body/header/parser exception is captured. Request-local context isolates concurrent error classification. Pipeline validation failure atomically admits `pipeline.parse_error` and `api.error`.

Hono waits for durable admission before returning an error. The built Node server does the same for pre-router body/Request failures, with route `unmatched`. Normal 400/401/413/422/500 semantics remain when admitted; storage or capacity failure returns sanitized `503 UNAVAILABLE`. Successful requests do not consume API error capacity. Errors arising before a host has a Request (for example HTTP parser protocol rejection), disconnected clients with no possible response, and other custom transport boundaries are not covered by application response telemetry. Memory storage remains development-only without durable telemetry guarantees.

Typed run/runner/API owners share the existing claimed delivery, unknown parking, explicit reconciliation and delivered-only pruning protocol. Stable event identities include an unambiguous owner domain; existing run IDs remain unchanged. Sink work stays outside database transactions. No automatic retry of an unknown sink result is introduced. The real LogFn pipeline/sink remains the delivery path, not a callback placeholder replacing the library.

## Bounds, maintenance and upgrades

Each owner retains at most 25,000 records and 8 MiB including reserved receipt metadata. `apiTelemetryMaxEvents` / `CIFN_API_TELEMETRY_MAX_EVENTS` can select a namespace API cap from 1 through 25,000; the chosen cap is persisted and incompatible reopen configuration fails. API parse+error admission cannot partially fill the ledger. Receipts and explicit pruning remain possible at capacity. Unknown/pending/in-flight obligations are never pruned. Runner heartbeat admission rejects once its retained ledger fills; hosts must dispatch/reconcile/prune. These are admitted per-owner bounds, not a global database/WAL/history disk quota.

The bounded cross-owner scan reads eleven indexed rows and returns at most ten owners plus a keyset cursor. Carry cursors through the whole namespace, reset saved dispatcher cursors on this upgrade, and repeat after wrap; no unbounded scan is hidden in a tick. Apply the shared schema's `cifn_state_telemetry(namespace,id)` index for custom adapters; built SQLite creates it idempotently. Native EXPLAIN confirms index use. Existing run-only inspection/reconciliation/pruning APIs remain supported; generic typed-owner APIs cover new owners. Drain older control-plane writers before relying on this coverage. There is no historical backfill, automatic retention scheduler or retroactive fence against old binaries.
