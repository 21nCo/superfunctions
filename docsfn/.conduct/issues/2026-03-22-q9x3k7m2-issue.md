## Summary

**Severity: Medium-High**

After the rendering pipeline fix (`2026-03-22-m4k8v2p9-completion`), `docsfn/docs` still contains three categories of library-level code that every docsfn consumer would need to duplicate. The root cause is architectural: `@docsfn/core` has a single entry point that bundles Node.js APIs (`node:path`, `node:url`, `node:fs/promises` via `config.ts`) alongside browser-safe types and rendering types. This makes it impossible for `DocsContent.svelte` (from `@docsfn/svelte`) to be used client-side in SvelteKit/Vite because importing `@docsfn/core` triggers Vite's `__vite-browser-external` error. The docs site works around this by maintaining parallel implementations of core types, the content renderer, and the page layout.

## Root Causes

### RC-1: `@docsfn/core` has no browser-safe sub-entry point

- **Location**: `docsfn/core/src/index.ts` (lines 1-24)
- **Current code**:
  ```ts
  export * from "./types";
  export * from "./config";       // <-- imports node:path, node:url, node:fs/promises
  export * from "./provider";
  export * from "./manifest";
  export * from "./markdown";     // <-- browser-safe (types + marked)
  export * from "./sanitize";     // <-- browser-safe
  // ... etc
  ```
- **Expected behavior**: Types like `CompiledContentBlock`, `CompiledContentArtifact`, and render-only utilities should be importable from `@docsfn/core/types` or `@docsfn/core/browser` without pulling in Node.js modules.
- **Actual behavior**: Any `import { CompiledContentBlock } from "@docsfn/core"` in client-side code fails Vite bundling because the barrel export re-exports `config.ts` which imports `node:*` modules.
- **Impact**: This is the **fundamental cause** of all three downstream duplications below. It was explicitly acknowledged in the completion report for issue `2026-03-22-r7k4m2n9-issue` as a follow-up.

### RC-2: Duplicated types — `compiled-docs-types.ts`

- **Location**: `docsfn/docs/src/lib/compiled-docs-types.ts` (25 lines)
- **Current code**:
  ```ts
  /** Mirrors @docsfn/core CompiledContentArtifact shape for client-safe typing (no core import). */
  export type PresentCompiledBlock =
    | { type: "heading"; level: number; text: string; html: string; slug: string }
    | { type: "paragraph"; text: string; html: string }
    | { type: "list"; ordered: boolean; items: Array<{ text: string }>; html: string }
    // ... identical to CompiledContentBlock in @docsfn/core/src/markdown.ts
  ```
- **Canonical source**: `docsfn/core/src/markdown.ts` lines 9-50 — defines `CompiledContentBlock` with the exact same shape.
- **Expected behavior**: The docs site should `import type { CompiledContentBlock } from "@docsfn/core/types"` (type-only import, tree-shakeable).
- **Actual behavior**: Types are manually mirrored. Any new block type added to core (e.g., `table`, `details`, `embed`) must be manually added here too, or the docs site silently drops those blocks.
- **Impact**: Version skew risk. Silent feature loss when core evolves. Maintenance burden on every consumer.

### RC-3: Duplicated content renderer — `PresentCompiledDocs.svelte`

- **Location**: `docsfn/docs/src/lib/components/PresentCompiledDocs.svelte` (53 lines)
- **Canonical source**: `docsfn/svelte/src/DocsContent.svelte` (100 lines)
- **Comparison**:

  | Feature | `DocsContent.svelte` (library) | `PresentCompiledDocs.svelte` (docs site) |
  |---------|-------------------------------|----------------------------------------|
  | Block rendering | `{@html block.html}` for heading/paragraph/list/callout | Identical |
  | Tab state | `activeTabs: Record<number, string>` | Identical |
  | Code blocks | `data-docsfn-code="true"` | Identical |
  | Mermaid | `data-docsfn-mermaid="true"` | Identical |
  | Component slots | `components` prop with `<svelte:component>` | Falls back to `<div data-docsfn-component>` only |
  | Page actions slot | `<slot name="page-actions" />` | Missing |
  | Compile-on-render | `compileSvelteContent()` fallback | Not needed (pre-compiled) |
  | Trust assertion | `assertCompiledContentTrusted()` | Missing |

- **Expected behavior**: `DocsContent` from `@docsfn/svelte` should be usable directly.
- **Actual behavior**: `DocsContent.svelte` imports `compileSvelteContent` and `assertCompiledContentTrusted` from `@docsfn/core`, which triggers the `node:*` Vite error on client. The docs site maintains a stripped-down copy without those imports.
- **Impact**: Bug fixes and new features (component slots, page actions, trust assertions, new block types) in the library renderer don't reach the docs site. Two consumers (docs pages + blog posts) both use the duplicate.

### RC-4: Duplicated page layout — `docs/[...slug]/+page.svelte`

- **Location**: `docsfn/docs/src/routes/docs/[...slug]/+page.svelte` (lines 26-178, ~100 lines of layout + CSS)
- **Canonical source**: `docsfn/svelte/src/DocsLayout.svelte` (73 lines)
- **Comparison**: The docs site `+page.svelte` reimplements the exact 3-column grid layout (sidebar / main / TOC) with:
  - Mobile sidebar toggle with backdrop overlay
  - Responsive breakpoint at 1024px
  - Sticky TOC with scroll
  - Grid template `16rem 1fr 14rem`

  `DocsLayout.svelte` provides the same structure (sidebar-col / main / toc-col) with slots, but the docs site doesn't use it.
- **Expected behavior**: `<DocsLayout surface={data.surface}>` wrapping the content.
- **Actual behavior**: 100 lines of layout HTML + CSS duplicated in the consumer.
- **Impact**: Medium — layout is less likely to diverge than rendering, but still represents unnecessary boilerplate for every new docsfn consumer site.

## Observed Symptoms

1. `docsfn/docs/src/lib/compiled-docs-types.ts` exists as a parallel type file with comment "Mirrors @docsfn/core"
2. `PresentCompiledDocs.svelte` is used in both docs pages and blog posts instead of library `DocsContent`
3. `+page.svelte` for docs routes contains ~100 lines of layout CSS that mirrors `DocsLayout.svelte`
4. The completion report for the prior issue explicitly acknowledged this: _"The compilation-side issue (client bundle node:* pollution in DocsContent.svelte) should be fixed in a follow-up by splitting @docsfn/core into a browser-safe sub-entry or lazily importing the compilation functions."_

## Proposed Fixes

### Fix 1: Create browser-safe sub-entry in `@docsfn/core` (ROOT FIX)

Split `@docsfn/core` exports so browser-safe code is importable without Node.js deps:

```jsonc
// package.json exports
{
  ".": "./dist/index.js",           // full (server-only)
  "./types": "./dist/types.js",     // types + enums only
  "./browser": "./dist/browser.js"  // types + markdown types + sanitize (no node:*)
}
```

Or alternatively, make `DocsContent.svelte` use dynamic imports for the compile function:
```ts
// Only import compile when actually needed (not for pre-compiled content)
$: compiledContent = compiled ?? (await import("@docsfn/core")).compileSvelteContent({...});
```

### Fix 2: Delete `compiled-docs-types.ts` (depends on Fix 1)

Replace all imports of `PresentCompiledBlock` / `PresentCompiledDocs` with `CompiledContentBlock` / `CompiledContentArtifact` from `@docsfn/core/types` or `@docsfn/core/browser`.

### Fix 3: Delete `PresentCompiledDocs.svelte` (depends on Fix 1)

Replace usage in:
- `docsfn/docs/src/routes/docs/[...slug]/+page.svelte` — use `<DocsContent compiled={data.compiled} />`
- `docsfn/docs/src/routes/blog/[slug]/+page.svelte` — use `<DocsContent compiled={data.compiled} />`

### Fix 4: Use `DocsLayout` from `@docsfn/svelte` (independent)

Replace the custom 3-column layout in `+page.svelte` with:
```svelte
<DocsLayout surface={data.surface} sidebar={data.sidebar}>
  <DocsContent compiled={data.compiled} />
</DocsLayout>
```

This may require enhancing `DocsLayout.svelte` to include the mobile sidebar toggle (it currently lacks it) and the scoped CSS (it currently has no styles — relies on theme.css classes).

## Notes

- The prior completion report (`2026-03-22-m4k8v2p9-completion`) explicitly called this out as a follow-up in its Notes section, confirming this is a known architectural debt.
- Fix 1 (browser-safe sub-entry) is the prerequisite for Fixes 2 and 3. Fix 4 is independent and can be done in parallel.
- The `DocsLayout.svelte` component currently has no `<style>` block — it relies on CSS classes from `theme.css`. The docs site's layout has scoped styles. Fix 4 may require adding mobile sidebar toggle logic and styles to `DocsLayout.svelte`.
- The `DocsContent.svelte` component has features the docs site copy lacks (component slots, page-actions slot, trust assertion). Switching to the library version would gain these features for free.
