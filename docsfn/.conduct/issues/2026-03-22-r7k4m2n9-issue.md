## Summary

**Severity: Critical/High**

docsfn's markdown compiler (`@docsfn/core`) and both framework component libraries (`@docsfn/svelte`, `@docsfn/react`) ship a fundamentally broken content rendering pipeline. The block compiler stores paragraph, heading, callout, and component body text as **raw markdown strings** but the `DocsContent` components in both Svelte and React render those strings as **literal text** — not as HTML. Inline formatting (`**bold**`, `` `code` ``, `[links](url)`), GFM tables, and images never render. Lists (`- item`, `1. item`) are not recognized as a block type and get merged into paragraph text with spaces. Additionally, no default theme CSS is shipped, so sidebar, breadcrumb, pagination, and TOC components render as unstyled inline elements. Every consumer must independently solve both problems.

## Observed Errors / Symptoms

1. **Inline markdown not rendered**: Heading and paragraph text containing `**bold**`, `` `code` ``, `[links](url)`, `*italic*`, `~~strikethrough~~` renders literally as those characters in the browser.
2. **Lists rendered as paragraph text**: Markdown lists (`- item\n- item`) are consumed by the paragraph fallback in `parseBlocks` and joined with spaces into a single `<p>` tag.
3. **No layout styling**: Sidebar links appear inline (no `display: block`), breadcrumbs have no flex layout, pagination has no grid, TOC has no list styling. The components emit `docsfn-*` class names but no CSS targets them.
4. **Workaround in docs site**: `docsfn/docs` works around all three problems via a local `PresentCompiledDocs.svelte` + `md-render.ts` (runtime `marked` + `isomorphic-dompurify`) and ~350 lines of hand-written `app.css`. This workaround is not available to other consumers.

## Root Causes

### RC-1: Block compiler has no `list` block type

**Location**: `docsfn/core/src/markdown.ts`, lines 8–46 (`CompiledContentBlock` union), lines 155–165 (`isBlockStart`), lines 432–443 (paragraph fallback)

**Current code** (`CompiledContentBlock`):

```typescript
export type CompiledContentBlock =
  | { type: "heading"; ... }
  | { type: "paragraph"; text: string; }
  | { type: "code"; ... }
  | { type: "mermaid"; ... }
  | { type: "tabs"; ... }
  | { type: "callout"; ... }
  | { type: "component"; ... };
```

`isBlockStart` does not check for list markers (`/^[-*+]\s/` or `/^\d+\.\s/`). Lines starting with `-`, `*`, `+`, or `1.` fall through to the paragraph accumulator, which joins consecutive non-block lines with spaces.

**Expected behavior**: Lists should be a first-class block type (ordered and unordered), parsed into structured items, and rendered as `<ul>/<ol>` by `DocsContent`.

**Actual behavior**: `- Install\n- Configure\n- Deploy` becomes `{ type: "paragraph", text: "- Install - Configure - Deploy" }` and renders as a single `<p>`.

**Impact**: Every Markdown document with bullet or numbered lists renders incorrectly.

### RC-2: Paragraph / heading / callout text stored as raw markdown, rendered as literal text

**Location (Svelte)**: `docsfn/svelte/src/DocsContent.svelte`, lines 51–53, 58–61

```svelte
{#if block.type === "heading"}
  <svelte:element this={`h${block.level}`} id={block.slug}>{block.text}</svelte:element>
{:else if block.type === "paragraph"}
  <p>{block.text}</p>
...
{:else if block.type === "callout"}
  <aside data-docsfn-callout={block.kind}>
    <p>{block.text}</p>
  </aside>
```

**Location (React)**: `docsfn/react/src/DocsContent.tsx`, lines 37–43, 58–63

```tsx
if (block.type === "heading") {
  return React.createElement(headingTag, { id: block.slug }, block.text);
}
if (block.type === "paragraph") {
  return <p>{block.text}</p>;
}
if (block.type === "callout") {
  return (
    <aside data-docsfn-callout={block.kind}>
      <p>{block.text}</p>
    </aside>
  );
}
```

In both cases, `block.text` is a raw markdown string containing inline markers. Svelte's `{block.text}` and React's `{block.text}` escape HTML, so `**bold**` renders as the literal characters `**bold**`.

**Expected behavior**: Inline markdown in text fields should be converted to HTML and rendered as rich content.

**Actual behavior**: Raw markdown strings displayed verbatim.

**Impact**: All inline formatting, links, and inline code across every content page is broken.

### RC-3: No `html` field produced at compile time

**Location**: `docsfn/core/src/markdown.ts`, `CompiledContentBlock` type and `parseBlocks` function

The compiler emits only `text: string` for paragraphs, headings, and callouts. There is no pre-rendered `html` field that consumers could use directly. This forces every consumer to independently add a runtime markdown-to-HTML step (currently `marked` + DOMPurify in the docs site workaround).

**Expected behavior**: The compiler should produce a sanitized `html` field alongside `text` at compile time, so `DocsContent` can use `{@html block.html}` / `dangerouslySetInnerHTML` without needing a runtime markdown library.

**Actual behavior**: Only raw `text` is available. `@docsfn/svelte` lists `marked` as a dependency but never uses it in `DocsContent`. `@docsfn/react` lists `markdown-to-jsx` as a dependency but never uses it either.

---

### RC-4: No default theme CSS shipped by `@docsfn/svelte` or `@docsfn/react`

**Location**: `docsfn/svelte/package.json` (exports map), `docsfn/react/package.json` (exports map)

Both packages export only JavaScript/TypeScript entry points. No CSS file is included in the package `exports`. Components use `docsfn-sidebar-link`, `docsfn-sidebar-group-trigger`, `docsfn-breadcrumbs-list`, `docsfn-pagination-links`, `docsfn-toc-list`, etc. as class names, but no stylesheet defines rules for them.

The docs site compensates with ~350 lines in `docsfn/docs/src/app.css` covering: sidebar layout (flex column, link padding, group nesting, active state), breadcrumb flexbox, pagination grid, TOC styling, content typography (heading sizes, paragraph margins, inline code, link colors), and dark mode variables.

**Expected behavior**: `@docsfn/svelte` (and `@docsfn/react`) should ship an importable default theme CSS file that targets the documented `docsfn-*` class hooks and `--docsfn-*` custom properties.

**Actual behavior**: Every consumer must write all chrome and typography CSS from scratch.

---

### RC-5: `theme.ts` generates CSS variables but under different names than `app.css` consumes

**Location**: `docsfn/core/src/theme.ts` lines 37–55, vs. `docsfn/docs/src/app.css` lines 3–23

`generateThemeCSS` produces variables like `--docsfn-primary`, `--docsfn-background`, `--docsfn-foreground`, `--docsfn-muted`, `--docsfn-border`.

The docs site `app.css` uses `--docsfn-color-primary`, `--docsfn-color-bg`, `--docsfn-color-fg`, `--docsfn-color-muted`, `--docsfn-color-border`, etc.

These naming conventions are misaligned. A consumer using `generateThemeCSS` would produce variables that no component CSS references.

## Proposed Fixes

### Fix 1: Add `list` as a first-class block type in `@docsfn/core`

Add to `CompiledContentBlock`:

```typescript
| {
    type: "list";
    ordered: boolean;
    items: Array<{ text: string; html: string }>;
  }
```

Update `isBlockStart` to recognize list markers (`/^[-*+]\s/`, `/^\d+[.)]\s/`). Add a `parseListBlock` function in `parseBlocks` that accumulates consecutive list lines (supporting nested lists) and emits a structured `list` block. Update both `DocsContent` components to render `<ul>/<ol>` with `<li>` elements.

### Fix 2: Add `html` field to text-bearing blocks at compile time

For `paragraph`, `heading`, `callout`, and `list` item blocks, run inline markdown rendering at compile time inside `parseBlocks` or `compileMarkdown`. Use `marked.parseInline` (already a dependency) for phrasing content and `marked.parse` for block content (callout bodies, component bodies). Sanitize the output using an extended version of the existing `sanitize.ts`.

Updated block types:

```typescript
| { type: "heading"; level: number; text: string; html: string; slug: string; }
| { type: "paragraph"; text: string; html: string; }
| { type: "callout"; kind: ...; text: string; html: string; }
```

`text` is kept for search indexing and plain-text consumers. `html` is the default rendering path.

### Fix 3: Update `DocsContent` components to use `html` field

**Svelte** (`DocsContent.svelte`):

```svelte
{#if block.type === "heading"}
  <svelte:element this={`h${block.level}`} id={block.slug}>{@html block.html}</svelte:element>
{:else if block.type === "paragraph"}
  <div class="docsfn-paragraph">{@html block.html}</div>
{:else if block.type === "list"}
  <svelte:element this={block.ordered ? 'ol' : 'ul'}>
    {#each block.items as item}
      <li>{@html item.html}</li>
    {/each}
  </svelte:element>
{:else if block.type === "callout"}
  <aside data-docsfn-callout={block.kind}>{@html block.html}</aside>
```

**React** (`DocsContent.tsx`): same pattern using `dangerouslySetInnerHTML={{ __html: block.html }}`.

This makes both components work correctly out of the box with zero configuration.

### Fix 4: Ship default theme CSS from `@docsfn/svelte` and `@docsfn/react`

Extract the docs site's `app.css` chrome rules (sidebar, breadcrumbs, pagination, TOC, content typography, dark mode variables) into:

- `docsfn/svelte/src/theme.css` — full default theme
- `docsfn/svelte/src/theme-base.css` — structural only (layout, display, flex — no colors/fonts)

Expose via package `exports` in `package.json`:

```json
{
  "exports": {
    ".": { ... },
    "./theme.css": "./dist/theme.css",
    "./theme-base.css": "./dist/theme-base.css"
  }
}
```

Consumer zero-config usage:

```svelte
<script>
  import "@docsfn/svelte/theme.css";
</script>
```

Same pattern for `@docsfn/react`.

### Fix 5: Align `theme.ts` variable names with the CSS convention

Either update `generateThemeCSS` to produce `--docsfn-color-*` names matching what the theme CSS consumes, or update the theme CSS to use the `--docsfn-*` names that `generateThemeCSS` produces. The former is recommended since the `--docsfn-color-*` convention is already used across the docs site and is more descriptive.

### Fix 6: Remove workaround from `docsfn/docs`

After fixes 1–5, delete:

- `docsfn/docs/src/lib/md-render.ts`
- `docsfn/docs/src/lib/components/PresentCompiledDocs.svelte`
- `docsfn/docs/src/lib/compiled-docs-types.ts` (if it only serves the workaround)

Remove `marked` and `isomorphic-dompurify` from `docsfn/docs/package.json` dependencies. Update `+page.svelte` to use `DocsContent` directly. Replace the bulk of `app.css` with `import "@docsfn/svelte/theme.css"`, keeping only site-specific overrides.

## Notes

- `@docsfn/svelte` already lists `marked ^12.0.0` as a dependency but never uses it — likely intended for this purpose originally.
- `@docsfn/react` already lists `markdown-to-jsx ^7.3.2` as a dependency but never uses it — same situation.
- The compile-time `html` approach (Fix 2) is preferred over runtime rendering because it keeps the browser bundle lean, avoids SSR issues with DOMPurify, and only needs to sanitize once.
- A plugin/theme-package system (`docsfn.config.ts → theme: "name"`) is not recommended at this stage. CSS imports are simpler, more debuggable, and consistent with how Tailwind, Shiki, and similar tools work. Third-party theme packages can simply export a CSS file targeting the same `docsfn-*` hooks.
- The `components` prop on `DocsContent` (for custom MDX-like component rendering) is already the correct escape hatch for consumers who need to override specific block rendering.
