## Summary

Both docsfn example apps (SvelteKit and Next.js) implement custom hand-rolled HTML for every UI surface — sidebar, breadcrumbs, pagination, TOC, search status, version switcher, and content rendering — instead of using the production-ready component libraries shipped in `@docsfn/svelte` and `@docsfn/react`. Most critically, **markdown content is dumped as raw text into `<pre>` tags** instead of using the `<DocsContent>` component that compiles markdown into structured, rendered blocks. This makes the examples misleading as reference implementations and fails to validate that the component library works end-to-end.

**Severity: Medium** — Does not break core functionality but significantly undermines the value of example apps as onboarding references and integration tests for the component library.

---

## Observed Errors/Symptoms

1. **Raw markdown displayed in `<pre>` tags** — Users see unrendered markdown source instead of formatted content
2. **No `@docsfn/svelte` or `@docsfn/react` component imports** — Neither example app imports a single UI component from the component libraries
3. **Hand-rolled sidebar, breadcrumbs, pagination, TOC** — Each example reimplements these from scratch with custom HTML/CSS
4. **No search dialog** — Search is displayed as a static status text, not the interactive `<DocsSearch>` dialog with Cmd+K, scope filtering, and keyboard navigation
5. **No API reference rendering** — API routes dump `JSON.stringify(spec)` into a `<pre>` tag instead of using `<ApiReferenceRenderer>`
6. **Blog content is raw markdown** — Blog posts use `<pre>{data.post.body}</pre>`
7. **Embedded pages are raw markdown** — Embedded route uses `<pre>{data.page.body}</pre>`

## Root Causes

### Root Cause 1: SvelteKit Example — Raw Markdown in `<pre>` Instead of `<DocsContent>`

**Location:** `examples/sveltekit-docs-site/src/routes/docs/[...slug]/+page.svelte`, line 84

**Current code:**
```svelte
<pre class="docs-example-content">{data.routeEntry.page.body}</pre>
```

**Expected behavior:** Use the `<DocsContent>` component from `@docsfn/svelte` which compiles markdown into structured blocks (headings, paragraphs, code blocks, callouts, tabs, mermaid diagrams):
```svelte
<DocsContent content={data.routeEntry.page.body} compatPreset={data.compatPreset} />
```

**Actual behavior:** Raw markdown source text is displayed verbatim in a preformatted block.

**Impact:** The primary purpose of a docs site — rendering content — is completely broken. Users evaluating docsfn see raw markdown and assume the tool doesn't handle rendering.

**Evidence:** The `DocsContent.svelte` component at `svelte/src/DocsContent.svelte` is fully implemented with support for headings, paragraphs, code blocks, mermaid, callouts, tabs, and custom components.

## Proposed Fixes

### Fix 1: SvelteKit Example — Replace Hand-Rolled UI with Component Library

Replace the entire `+page.svelte` content with:

```svelte
<script lang="ts">
  import {
    DocsLayout,
    DocsContent,
    DocsSearch,
    TopBar,
    Breadcrumbs,
    Pagination,
    VersionSwitcher,
    ApiReferenceRenderer,
  } from "@docsfn/svelte";
  import type { PageData } from "./$types";

  export let data: PageData;
</script>

<DocsLayout surface={data.surface}>
  <svelte:fragment slot="topbar">
    <TopBar surface={data.surface}>
      <DocsSearch searchArtifact={data.searchArtifact} />
      <VersionSwitcher surface={data.surface} />
    </TopBar>
  </svelte:fragment>

  <Breadcrumbs surface={data.surface} />

  {#if data.routeEntry.kind === "page"}
    <article>
      <h1>{data.routeEntry.page.title}</h1>
      {#if data.routeEntry.page.description}
        <p>{data.routeEntry.page.description}</p>
      {/if}
      <DocsContent
        content={data.routeEntry.page.body}
        compatPreset={data.compatPreset}
      />
    </article>
  {:else if data.routeEntry.kind === "api"}
    <ApiReferenceRenderer api={data.routeEntry.api} />
  {/if}

  <Pagination surface={data.surface} />
</DocsLayout>
```

### Fix 2: SvelteKit Example — Simplify `+page.ts` Load Function

Remove the manual `flattenSidebarLinks()` function — `<DocsSidebar>` (used internally by `<DocsLayout>`) handles the sidebar tree directly from `surface.sidebar`.

### Fix 3: SvelteKit Blog Route — Use `<DocsContent>` or `<EmbeddedPage>`

```svelte
<script lang="ts">
  import { DocsContent } from "@docsfn/svelte";
  export let data;
</script>

<article>
  <h1>{data.post.title}</h1>
  <DocsContent content={data.post.body} />
</article>
```

### Fix 4: SvelteKit Embedded Route — Use `<EmbeddedPage>`

```svelte
<script lang="ts">
  import { EmbeddedPage } from "@docsfn/svelte";
  export let data;
</script>

<EmbeddedPage
  title={data.page.title}
  description={data.page.description}
  content={data.page.body}
  headings={data.page.headings ?? []}
/>
```

### Fix 5: Next.js Example — Mirror the Same Fixes with React Components

Replace hand-rolled JSX with `<DocsLayout>`, `<DocsContent>`, `<DocsSidebar>`, `<Breadcrumbs>`, `<Pagination>`, `<DocsSearch>`, `<TopBar>`, `<ApiReferenceRenderer>`, `<ThemeProvider>`, `<BlogList>` from `@docsfn/react`.

### Fix 6: Pass Search Artifact Through to Components

Both examples load `searchArtifact` in the layout server load but only display a count. The artifact should be passed to `<DocsSearch>` component for actual search functionality.

## Notes

- The examples appear to have been written as "structural data flow demos" before the component library was completed, and were never updated afterward.
- The `@docsfn/svelte` components depend on `@uifn/svelte` for primitives (Dialog, ScrollArea, Tabs, DropdownMenu). Ensure this dependency is available in the example app.
- The React component library also includes `<ThemeProvider>` and `<BlogList>` which have no Svelte equivalents — this may indicate the Svelte component library is slightly behind React.
- The `compatPreset` field is already loaded in both examples but not passed to any rendering component — it should be forwarded to `<DocsContent>` for fumadocs compatibility.
