# Asynchronous verified issue links

This closes the reporter's asynchronous issue-link display gap through WatchFn's authenticated read-only status route. It does not change standalone `captureBug()` acknowledgment or schedule provider writes in the browser.

Enable `issueStatus.enabled` to poll after accepted reporter submissions. Default bounds are 10 reads, 1-second spacing and a 15-second total deadline; validated limits allow 1–30 attempts, 100–10000ms spacing and 10–60000ms total duration. Linked or reconciliation states stop immediately; attempt exhaustion returns the latest status/null. HTTP/parser failures, cancellation and deadlines reject without resubmitting or marking an accepted report unsent. Reporter close, replacement and Catch stop cancel active reads/delays. A provider that ignores AbortSignal cannot hold the polling promise past the total deadline or update the UI later.

Endpoint clients use BrowserClient's actual status reader and derive `/mount/issues/status` from `/mount/ingest`. Ambiguous paths require explicit `watch.issueStatusEndpoint`. The same full Watch API key authorizes status, ingestion and query; this is not a new credential scope. An injected `issueStatus.read` or Watch-client `readBugIssueStatus` can call an authorized application backend so the browser need not possess that key. Backend authorization remains the application's responsibility. Both network and injected receipts must bind the requested app/report and coherent state/link. Only expected-provider HTTPS GitHub/Linear issue URLs without credentials/query/fragment are rendered; unverified or dangerous links never become DOM hrefs. Immediate injected-client issue receipts receive the same link checks.

The UI keeps accepted reports accepted while showing waiting, unavailable, operator-attention or verified-link state. It does not offer delivery retry on a status error. `pollIssueStatus` is also available programmatically; standalone capture never calls it automatically.

Validation includes eleven focused SDK tests for independent acknowledgment, attempts/terminal states, deadline and stop with a signal-ignoring provider, ignored late receipts, forged identity/URLs, provider mutation of expected identity, actual endpoint/header reuse and configuration limits. The native BotFn acceptance now uses the mounted `/watch` route and actual Chrome reporter: it observes pending state, runs the real server worker, then sees the verified provider link. HTTP503 and a dangerous fake receipt preserve acceptance without links or resubmission. Closing during a hanging status request cancels polling; all six accepted reports remain unique, are delivered by the server worker, and retain linkage through SQLite close/reopen. Actual BotFn GitHub authentication and issue requests still go only to a local protocol fixture.

The separate Python flat-report service remains unchanged; it is not the canonical browser client. Hosted provider permissions, worker deployment, retention, tenant-specific query/auth design, provider transport/memory limits and v1.1 issue-close synchronization remain open. Bounded status reads do not remove the existing BotFn client's unbounded provider-response parsing or Linear cancellation limitations.

Full SDK suite: 103 tests across 10 files; source typecheck and dual runtime/declaration builds pass. Fresh browser/DrawFn/CatchFn tarballs pass ESM and CommonJS status/polling runtime checks plus strict Node16/NodeNext public declaration emission, including React props sharing the root CatchFn class. This revealed and corrected CatchFn's preexisting conditional-export mismatch: require consumers now resolve the generated `.d.cts` declarations instead of ESM `.d.ts`; runtime entry points remain unchanged. No dependency or lockfile changes were needed.
