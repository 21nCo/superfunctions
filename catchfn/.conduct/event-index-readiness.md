# Canonical indexed Watch storage

The Catch branch now includes WatchFn's schema-owned event projections, required type/app/time and type/app/severity indexes, issue/session/replay indexes, conservative query pushdown and bounded offline backfill. This closes the missing canonical index implementation from the original Persistence & Storage section without adding a separate report service or transport. The full payload remains authoritative, and BotFn intake/link writes maintain projections atomically with the canonical event.

Existing deployments must apply the additive Watch schema migration before starting new writers. Historical null/unknown projection versions remain visible through a compatibility scan until offline backfill completes. Stop writers, workers and queries during backfill; follow its storage-ID cursor until null. Projection version 1 is an internal completeness invariant, not a field for application writers to set independently. Read the [migration contract, SQLite DDL and limitations](../../watchfn/.conduct/event-index-readiness.md).

The three Catch acceptance scripts now create numeric epoch columns and every declared index. The actual loopback HTTP/SQLite script checks the projection values from built Catch ingestion, combines type/app/severity/session and exact time-range filters, and repeats filtered retrieval after closing/reopening SQLite. Its authentication, retries, ambiguous-response at-least-once behavior and storage-failure assertions remain intact. The actual Chrome/BotFn script covers delayed verified issue links, cancellation, errors and SQLite reopen; the cross-origin browser delivery script covers CORS and transport behavior against the same indexed schema.

Validation: all 103 Catch SDK tests, TypeScript checks and CJS/ESM/declaration builds pass. The HTTP/SQLite, Chrome/BotFn and cross-origin Chrome acceptance commands pass. These runs use the freshly built Watch core from the identical merged source in the sibling Watch checkout via `CATCHFN_WATCH_CORE`; the Catch checkout's scoped install still lacks the optional adapter packages needed for Watch's complete multi-entry build. No dependency/lock changes or provider messages were needed.

Watch's own new native scenario migrates an old two-column SQLite table with 1005 rows, proves old reports remain queryable before backfill, verifies bounded/idempotent traversal and unchanged payload bytes, reopens the file, and confirms SQLite selects the type/app/time index. Its 179 core tests, types/build, and actual BotFn HTTP/native regressions also pass; details are recorded with the Watch change.

## Scope clarification and remaining requirements

The original Catch specification explicitly says “Future: Python SDK to open bug reports from backend contexts.” Therefore canonical Python client parity is deferred work, not an unmet v1 deliverable. The existing Python package remains a separate flat-report server, and its historical Python 3.8 compatibility claim remains unresolved against shared dependencies requiring 3.10. It is not evidence of canonical Watch delivery.

Retention defaults/bug-specific TTL, scalable broad queries and tag/aggregation execution, hosted provider/database validation, migration operations and deployment remain open. The supplied upload callback implements the original provided-endpoint alternative for large attachments; Watch does not currently provide a file channel, and this change does not invent one. Indexes do not establish tenant isolation or production readiness. Existing Watch API-key authority and trusted-application limits continue to apply.

The subsequent [canonical retention checkpoint](event-retention-readiness.md) implements the explicit default/bug TTL policy, with protected unresolved issue evidence and retained receipt tombstones. General non-app metric retention and production operations remain open.
