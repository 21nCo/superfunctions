# Canonical bug-report TTL acceptance

Catch's canonical Watch storage now implements the original v1 retention requirement: configured reports inherit Watch's 30-day retention default, with a server-owned bug-report TTL override. This does not modify the separate flat-report service or introduce a new browser/Python transport.

Hosts configure a fixed app allowlist and TTL policy on Watch, apply the nullable `receivedAt` schema migration, and schedule bounded `cleanupRetention` passes. The clock is the application host's `Date.now()`, not client event time or the database server clock; ingest and cleanup hosts need synchronized clocks. Historical reports remain protected until an explicit offline migration-anchor backfill. See [the complete policy, migration and failure contract](../../watchfn/.conduct/event-retention-readiness.md).

Unresolved issue deliveries are protected beyond TTL. Only linked canonical payloads with matching receipt target/project/issue ID/URL may expire; their outbox receipts and content fingerprints remain indefinitely. Exact replays remain acknowledged without resurrecting a payload or creating another provider issue. Conflicting replays still fail, and authenticated status remains available to Catch polling. Removing receipt history or changing namespaces would break that guarantee and is outside this payload-retention operation.

The actual built SDK/Chrome acceptance script now enables a short fixture-only bug TTL but schedules cleanup only after existing widget/delivery checks. It traverses six linked reports in two-row cleanup pages, proves a second pass deletes nothing, replays the original accepted HTTP envelope without a new provider create or payload, closes/reopens SQLite, and calls built Catch's `pollIssueStatus` against the actual mounted Watch endpoint. The verified issue link remains available while all six payloads are absent and six receipt records remain. Existing lost-ack deduplication, authorization/route rejection, real Chrome widget polling/cancellation and provider protocol checks still pass.

The canonical HTTP/SQLite and cross-origin Chrome acceptance scripts also pass against the new schema with retention unconfigured, preserving existing at-least-once behavior. All 103 Catch SDK source tests, TypeScript checks and CJS/ESM/declaration builds pass at this checkpoint. Watch's 188 source tests, type/build checks, three native BotFn scenarios, and 1005-row historical migration/arrival initialization pass. Tests use the freshly built Watch core from the identical merged source in the sibling checkout via `CATCHFN_WATCH_CORE`; no hosted provider issue or message is created.

Reproduction: build the Watch core and Catch SDK prerequisites, then run `CATCHFN_WATCH_CORE=/absolute/path/to/watchfn/typescript/dist/index.mjs node catchfn/typescript/scripts/botfn-acceptance.mjs` from the repository root. Local better-sqlite3/Kysely and Chrome are required. The HTTP and cross-origin scripts are `watchfn-acceptance.mjs` and `browser-delivery-acceptance.mjs` in the same directory.

Remaining gates include protected/unresolved data and receipt archival operations, production scheduling, general non-app metric/hybrid retention, broad-query/tag/aggregation scalability, hosted database/provider evidence and deployment. These accepted limitations do not constitute full readiness. Canonical Python SDK work remains explicitly future scope in the original specification.
