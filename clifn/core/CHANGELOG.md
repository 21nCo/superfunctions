# Changelog

## 0.4.0

- `runAction` accepts `jsonStyle: 'lines' | 'document'` (CLI-12, D8). With `mode: 'json'` and `jsonStyle: 'document'`, stdout receives exactly one JSON document per run, `{"ok":true,"data":...,"diagnostics"?}` or `{"ok":false,"error":{"code","message","details"?},"diagnostics"?}`, followed by a newline; `diagnostics` is redacted and omitted when empty. Every `debug`/`info`/`success`/`warn`/`error` message, and a spinner's `succeed`/`fail` message, is a JSON line on stderr; `quiet` and `verbose` apply as before. `output.json()` and `output.table()` are collected instead of printed: when the action returns no `data`, the last `json` value becomes `data` (`null` without one), and a warning on stderr names every call that was not used.
- Document-mode `data` (including the `json()` fallback), error `details` and diagnostics are resolved in one pass that follows `JSON.stringify` (every getter and `toJSON` runs as often as it would there, with its member key). Error details and diagnostic details are redacted once they are completely resolved, so a `toJSON` cannot bring a sensitive field back; `data` is printed without redaction. Where `JSON.stringify` would throw or never finish, the document stays printable: bigints become strings, an object already being serialized prints `"[Circular]"`, and a `toJSON` that keeps returning fresh objects leading back to the same value prints 64 nested projections and then `"[Circular]"` in place; this cap is the only difference for finite chains, so a chain deeper than 64 projections of one value is cut the same way. The only size limit is the engine's maximum string length, where `JSON.stringify` itself throws: one document counts a lower bound of its text (punctuation, keys and strings with their quotes, number and literal text, the error code and message) across `data` or the error and then each diagnostic, and an array counts `2n + 1` characters before its first item is read, so an oversized sparse or proxy array fails at once. Data that `JSON.stringify` can print is printed byte for byte. Past the limit, `data` gives the `CLIFN_RUNNER_FAILED` serialization-failure document, error details are left out with the code and exit code kept, diagnostic details are left out with the diagnostic's code, severity and message kept (a diagnostic whose other members do not fit is dropped with a warning on stderr), and an error message is replaced by a fixed short one; an omitted member gives its share back. If escapes still make the text too long, the diagnostics, then the error details, then the error message are shed before the serialization-failure document is used. A value, or its JSON text, that does not fit the heap exhausts it as it would in `JSON.stringify`; that is outside this limit.
- Document-mode error codes, in order: a string `error.code` matching `^[A-Z][A-Z0-9_]{1,63}$`; a message that is exactly `^CLIFN_[A-Z0-9_]+$` (as the credential store throws), reported with a fixed description; otherwise `CLIFN_RUNNER_FAILED`. A plain-object `details` is included after `redactValue`. The exit code is an integer `error.exitCode` from 1 to 125, else 1.
- Added `@clifn/core/terminal`, also exported from the root (D9): `resolveTerminal({ env?, stdin?, stdout?, stderr?, json? })` returns `{ color, interactive, ci }`, and `resolveRunnerOptions(flags, { env?, streams? })` turns parsed `json`, `quiet`, `verbose`, `color` (`true`, `false` or `'auto'`), `yes` and `nonInteractive` flags into runner options (`jsonStyle: 'document'` with `json`). Colour is resolved per stream: `stderrColor` (errors and the spinner) follows the terminal rules, and in text mode `color` (stdout) also needs a TTY stdout unless `--color` or `FORCE_COLOR` asks for it. `RunnerOptions` and `OutputOptions` accept an optional `stderrColor`, which defaults to `color`.
- `createPrompt({ ask?, output?, nonInteractive? })`: `nonInteractive: true` makes every prompt throw `PromptInputError` with code `CLIFN_PROMPT_NON_INTERACTIVE`; an options object that names `output` or `nonInteractive` writes the default asker's question to `output`, else stderr. `PromptInputError` takes an optional code; its code type stays `"CLIFN_PROMPT_INPUT_ERROR"` unless another code is passed.
- No existing export, default or output changed: text mode, the default `'lines'` JSON style, `createPrompt()`, `createPrompt({})`, `createPrompt({ ask })` and the `prompt` singleton print the same bytes to the same streams as before.

## 0.3.0

- Added `@clifn/core/paths` (CLI-13, D7), also exported from the root: `resolveAppPaths(appName, { platform?, env?, homedir? })` returns the config, state and cache directories (XDG on Linux and macOS, `%APPDATA%` / `%LOCALAPPDATA%` on Windows; relative or empty environment values fall back to the defaults), and `ensureAppDir(dir)` creates a missing directory with mode `0o700`. App names follow `^[a-z0-9][a-z0-9._-]{0,63}$`; anything else throws `InvalidAppNameError` (`CLIFN_INVALID_APP_NAME`). A non-absolute home directory throws `InvalidHomeDirectoryError` when a default directory needs it.
- `createCredentialStore` accepts `{ appName }` (`<config>/credentials`) or `{ path }`; `createProjectConfig` accepts `{ appName, fileName? }` (`<config>/config.json` by default), `{ cwd?, fileName }` or `{ path }`; `{ appName }` stores resolve for the current platform (`env` and `homedir` may be passed through). Only own properties of the options object are read (inherited keys are ignored), and an optional key set to `undefined` takes its default; malformed options (a selector set to `undefined` or a non-string, a key from another form, an unknown key, or a `platform` other than the current one) throw `InvalidStoreOptionsError` (`CLIFN_INVALID_STORE_OPTIONS`). On Windows a UNC value needs a real server and share, and device or extended-length (`\\.\`, `\\?\`) values are not used.
- On Windows an app name cannot end with `.` or be a device name (`con`, `nul.txt`, ...), so two names never share a directory. Object-form store targets must name a file (no empty path, root, trailing separator or NUL in `path`, `fileName` or `cwd`; environment values with a NUL fall back like relative ones; no drive in `fileName` after normalization; on Windows no `:`, control or `<>"|?*` character, device name or trailing dot or space in a file segment; a device name is matched after trailing ASCII spaces only, so `aux\u00a0.json` is a file), options are read from their own property descriptors before any getter runs, a malformed `platform` reports `CLIFN_INVALID_STORE_OPTIONS`, and loading the package no longer fails when the home or working directory is unavailable.
- No existing export, default or output changed: the string and no-argument forms keep their paths, including the Conduct defaults.

## 0.2.0

- Added the consumer compatibility baseline (CLI-11): `tests/consumer-contract.table.ts` lists every `@clifn/core` import that `@extfn/cli`, `@plugfn/cli`, `@mailfn/cli`, `@devfn/cli` and `@devfn/config` use; `consumer-contract.test.ts` checks each runtime symbol's kind from the built subpath, `consumer-contract.test-d.ts` checks the types and option shapes those consumers rely on, and `consumer-scan.test.ts` fails when a consumer imports a symbol or subpath the table does not list.
- Declared `engines.node` `>=20`. The runtime `ini` dependency moves from `^5.0.0` to `^4.1.3`, whose engines admit every Node 20 release; `ini` 5.0.0 only narrowed the engines range to `^18.17.0 || >=20.5.0` and ships the same code.
- Added a `typecheck` script; `test` now runs once (`vitest run`) and includes the type-level contract tests.
- No export, default or output changed.

## 0.1.0

- Added a Conduct v0.3 compatibility note documenting stable public subpath imports.
- Confirmed public import guidance for `credentials`, `config`, `client`, `ui`, `stdio`, and `prompt`.
