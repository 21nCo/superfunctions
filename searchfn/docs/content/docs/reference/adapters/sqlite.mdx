title: SQLite Adapter
description: Server-side full-text search on SQLite FTS5 for Node, libSQL/Turso and Cloudflare D1.
---

The SQLite Adapter stores a SearchFn index in SQLite [FTS5](https://www.sqlite.org/fts5.html) tables inside a database you already have. It talks to SQLite through an injected driver, so the same package runs on Node with `better-sqlite3`, on libSQL or Turso with `@libsql/client`, and on Cloudflare Workers with a D1 binding.

## When to Use

- Server-side search without running a separate search service
- Cloudflare Workers apps that keep their data in D1
- Apps on SQLite, libSQL or Turso that want search next to their data
- `@datafn/server` deployments on any of those backends

For the on-device Swift SQLite index, see [Apple: SQLite adapter](/docs/documentation/apple/sqlite-adapter).

## Installation

```bash
npm install @searchfn/adapter-sqlite
```

Install the driver you use as well. `better-sqlite3` and `@libsql/client` are optional peer dependencies; D1 needs no package. The package is ESM-only: load it with `import`, not `require()`.

## Drivers

| Binding | Driver | Transactions |
| --- | --- | --- |
| `fromBetterSqlite3(db)` | `better-sqlite3` `Database` | `db.transaction()` |
| `fromLibsql(client)` | `@libsql/client` `Client` (file, embedded replica or Turso URL) | `client.batch(..., "write")` |
| `fromD1(env.DB)` | Cloudflare D1 binding | `db.batch()` |

The adapter never closes the driver: the code that opened the database owns it.

### Custom drivers

Any object with this shape works:

```typescript
interface SqliteDriver {
  exec(sql: string): Promise<void>;
  all<T>(sql: string, params?: readonly (string | number | null)[]): Promise<T[]>;
  run(sql: string, params?: readonly (string | number | null)[]): Promise<{ changes?: number }>;
  batch?(statements: { sql: string; params?: readonly (string | number | null)[] }[]): Promise<void>;
}
```

`batch()` must run its statements in one transaction. The adapter checks the index generation in the same batch as the writes, rebuild and cleanup that depend on it, which is what keeps several adapter instances on one database consistent. All three bindings above provide it.

Without `batch()` the adapter runs statements one by one. That gives no protection against concurrent use: every operation on the database must then be serialized by the caller (one adapter instance, no overlapping calls), otherwise a write that overlaps a rebuild can be lost from the index. An error part-way through a write can also leave the index out of step with the stored documents; call `rebuild(resource)` to repair it.

## Usage

### Node (better-sqlite3)

```typescript
import Database from "better-sqlite3";
import { SqliteAdapter, fromBetterSqlite3 } from "@searchfn/adapter-sqlite";

const adapter = new SqliteAdapter({ driver: fromBetterSqlite3(new Database("app.db")) });

await adapter.initialize({
  resources: [{ name: "bookmarks", searchFields: ["title", "notes"] }],
});

await adapter.index({
  resource: "bookmarks",
  documents: [
    { id: "b1", fields: { title: "Subset bookmarks", notes: "sync design" }, metadata: { __ns: "team-a" } },
  ],
});

const ids = await adapter.search({
  resource: "bookmarks",
  query: "subs book",
  prefix: true,
  fieldBoosts: { title: 3 },
  namespaceFilter: ["team-a"],
});
```

### libSQL / Turso

```typescript
import { createClient } from "@libsql/client";
import { SqliteAdapter, fromLibsql } from "@searchfn/adapter-sqlite";

const client = createClient({ url: process.env.TURSO_URL!, authToken: process.env.TURSO_TOKEN });
const adapter = new SqliteAdapter({ driver: fromLibsql(client) });
```

### Cloudflare D1

```typescript
import { SqliteAdapter, fromD1 } from "@searchfn/adapter-sqlite";

export default {
  async fetch(request: Request, env: { DB: D1Database }) {
    const adapter = new SqliteAdapter({ driver: fromD1(env.DB) });
    const ids = await adapter.search({ resource: "bookmarks", query: "subset", prefix: true });
    return Response.json(ids);
  },
};
```

See [Deploy: Cloudflare Workers](/docs/documentation/deploy/cloudflare-workers) for a full Worker.

### With DataFn

```typescript
import { createDatafnServer } from "@datafn/server";
import { createSearchProvider } from "@searchfn/datafn-provider";
import { SqliteAdapter, fromD1 } from "@searchfn/adapter-sqlite";

const server = await createDatafnServer({
  schema,
  database,
  searchProvider: createSearchProvider(new SqliteAdapter({ driver: fromD1(env.DB) })),
});
```

The server calls `initialize()` with each resource's `indices.search` fields at startup, updates the index after mutations, and passes the request namespace as `namespaceFilter` on search queries. The server sends every mutation to the search provider, including mutations of resources without `indices.search`; the adapter ignores those, so their records are never stored or returned by cross-resource search.

## Configuration

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `driver` | `SqliteDriver` | — | Required. Use `fromBetterSqlite3`, `fromLibsql`, `fromD1` or your own driver. |
| `tablePrefix` | `string` | `"searchfn"` | Prefix for adapter-owned tables. Letters, digits and underscores, up to 48 characters. |
| `maxBatchSize` | `number` | `500` | Documents per write transaction. Larger `index()` calls are split into several transactions. |
| `defaults` | `SearchDefaults` | — | `prefix` and `fieldBoosts` used when a query omits them. |
| `observability` | `ObservabilityInput` | — | Logger and instrumentation. |

## Behavior

### Queries

- Text is tokenized with FTS5's `unicode61 remove_diacritics 2` tokenizer, so matching ignores case and diacritics (`cafe` matches `Café`).
- Every query term must match (terms are ANDed). A term may match in any searched field.
- With `prefix: true`, every term matches as a prefix (`subs` matches `subset`).
- Query text is always matched literally. FTS5 operators and syntax in user input (`AND`, `NEAR`, quotes, `*`, `column:`) are not interpreted. Only the first 32 distinct terms are used.
- `fields` limits matching to those declared fields. Unknown field names are ignored; if none are known, the result is empty. An empty `fields` list selects no fields and returns no results, as does an empty `resources` list in `searchAll()`; omit either option to search every field or the default resources.
- Results are ordered by BM25 (`bm25()`), highest first, with ties broken by resource name (in `searchAll()`) and then document id, both in JavaScript string order (`<`, UTF-16 code units), the order the SearchFn client and `@datafn/server` use when they merge results. The same order applies before every `limit` and `limitPerResource` cut, so a smaller limit always returns a prefix of a larger one, also through those consumers. `fieldBoosts` sets the per-field BM25 weight (default `1`); weights must be finite and `>= 0`.
- `namespaceFilter` and `regionFilter` match the `__ns` and `__region` document metadata. When a filter is set, documents without that metadata are excluded.

### Fuzzy search

Fuzzy search is not supported. The adapter reports `fuzzy: false` and ignores the `fuzzy` option (or a `fuzzy` default) instead of failing: the query runs as an exact or prefix match. The first such query logs a warning once per adapter instance, through the `observability` logger when one is configured and `console.warn` otherwise. Use `prefix: true` for search-as-you-type.

### Storage

For a table prefix `searchfn`, the adapter creates:

- `searchfn_resources`: one row per resource with its declared fields and current index generation.
- `searchfn_r<id>_docs`: the stored documents (id, an id sort key, id type, namespace, region and all fields as JSON).
- `searchfn_r<id>_fts_<generation>`: the FTS5 index, one column per declared search field.

Table names come from an internal integer id, so resource and field names are never used as SQL identifiers. Every value is a bound parameter; each write binds one JSON parameter, which keeps D1 below its per-statement parameter limit. Writes are split so that no bound JSON value exceeds 512 KiB, and a single document or id that does not fit on its own is rejected with `DFQL_INVALID` before anything in the call is written.

### Writes and idempotency

- `initialize()` creates tables idempotently. Calling it again with the same fields, in any order, changes nothing.
- When the declared fields change, `initialize()` rebuilds the FTS index from the stored documents in one transaction, including fields that were stored but not indexed before. Every write checks the published index generation in the same transaction, and every search reads it with the results, so other adapter instances on the same database detect the new generation on their next operation and reload. They never read or write a retired index, even if its table still exists.
- `index()` upserts. Re-indexing a document replaces its fields and metadata; within one call the last document with a given id wins. Number ids come back as numbers. Documents are keyed by the string form of their id, so `5` and `"5"` are the same document and the last write sets the returned type.
- After `initialize()`, the adapter registers and searches only the resources it declared: `search()` returns no results for any other resource, `searchAll()` searches declared resources only (and drops undeclared names from `resources`), and `clear()` and `rebuild()` on them are no-ops. `index()` and `remove()` on an undeclared resource are no-ops unless the resource is already registered in the database (by another instance or an earlier declaration); then they still apply, so its index never misses a change and declaring it again cannot return stale or deleted records. Each `initialize()` call replaces the declared set.
- On an instance that was never initialized, `index()` registers an unknown resource with the field names in that call, and `searchAll()` without `resources` searches every resource in the database.
- `remove()` and `clear()` are idempotent, and both are no-ops for unknown resources.
- `rebuild(resource)` recreates the FTS index from the stored documents in one transaction, using the field list stored in the database (not one cached by this instance), and drops every older index generation, plus any table left behind by an interrupted rebuild from a driver without `batch()`. That cleanup runs in the same transaction, after the generation check, so it never drops an index another instance published. It is idempotent.

### Lifecycle

`dispose()` makes the adapter reject further calls until `initialize()` is called again and succeeds; a failed `initialize()` leaves it disposed. It does not close the driver, and the stored index persists.

## Testing

The package runs the shared adapter conformance suite against `better-sqlite3`, `@libsql/client` and D1 inside workerd (`@cloudflare/vitest-pool-workers`). The D1 tests use a local database and need no Cloudflare account.
