# DevFn configuration reference

DevFn discovers `devfn.config.ts`, `.js`, `.mjs`, `.cjs`, or `.json` while walking upward from the current directory. JavaScript-family manifests are executable code, require digest-bound trust, and must be self-contained (no imports or `require()`). JSON is data-only.

## Top-level manifest

| Field | Required | Meaning |
| --- | --- | --- |
| `version: 1` | yes | Manifest schema version. |
| `project.id` | yes | Stable semantic project identity. |
| `project.name` | no | Human display name. |
| `defaultProfile` | no | Profile selected when `--profile` is omitted. Without it, a `profiles.default` entry is required. |
| `runtimeDir` | no | Repository-relative generated-state root; defaults to `.devfn`. |
| `ports` | no | Named `PortSpec` map. |
| `processes` | no | Named native process map. |
| `services` | no | Named Docker Compose service map. |
| `profiles` | yes | Named selections of processes/services plus non-secret environment and proxy choice. |
| `hostnames` | no | Explicit local hostname routes to named ports. |
| `prerequisites` | no | Required command/version diagnostics, optionally profile-scoped. |
| `environmentOutputs` | no | Repository-relative dotenv or JSON runtime files and owner-only permission modes. |
| `policy` | no | Repository-relative organization policy JSON path. |

Every repository-relative path rejects absolute paths, `..` escape, and runtime symlink escape. References to ports, processes, services, profiles, dependencies, and hostname targets must resolve during validation. An explicitly configured but missing policy is an error; only the conventional unconfigured policy path is optional.

## Ports

A port can specify `protocol` (`tcp` or `udp`), `preferred`, `range: [start, end]`, `exact`, `ephemeral`, `exposure` (`loopback` or `public`), conventional container `internal` port, contiguous `block` name, and exported `env` key.

- `exact: true` requires `preferred` and fails closed on collision.
- `ephemeral: true` cannot be combined with fixed preferences.
- Requirements sharing `block` receive a contiguous allocation.
- Public ports require `devfn up --allow-public`.

## Native processes

`adapter` is one of `command`, `npm`, `pnpm`, `turbo`, `wrangler`, `xcode`, or `extfn`. A process can specify `command`, package-manager `script`, repository-relative `cwd`, non-secret literal `env`, inherited `envAllowlist`, redacted `secretEnv`, named `ports`, `dependsOn`, `health`, `shutdownTimeoutMs`, and `exposure` (`local` or `public`).

Turbo, Wrangler, and ExtFn resolve project-local binaries with offline npm execution; pnpm runs through Corepack so the repository's `packageManager` pin is honored. Adapters never download a missing tool during startup. `doctor` reports the missing prerequisite instead. Discovery marks Yarn and Bun as proposed and emits no guessed npm process; add an explicit command adapter after review.

Local-process exposure verification requires `lsof` on macOS and Linux; Windows uses `netstat`. Run `devfn doctor` before startup to detect a missing listener-inspection tool.

Sensitive-looking keys cannot be literal manifest values. Numbered keys such as `API_TOKEN2` and compact names ending in an unambiguous credential word such as `MYPASSWORD`, `GITHUBTOKEN`, `MYAPIKEY`, or `MYACCESSKEY` follow the same rule. They must be inherited by name in `envAllowlist` and repeated in `secretEnv`, which activates streaming redaction before logs are persisted. PostgreSQL `PGPASSWORD` and qualified `pg_pass`/`pg_pwd` casing variants follow this rule. URL userinfo and credential-bearing headers such as `Authorization: Bearer` are rejected in resolved literals and argv, including when assembled from templates. Curl short-option clusters and cookie assignments receive the same validation; ordinary `--cookie theme=dark` and `--cookie=theme=dark` values are allowed. Public processes require `--allow-public`.

## Compose services

A service uses `adapter: "compose"`, Compose `service`, optional repository-relative `file`, project-name prefix, named host-port-to-container-port mappings, dependencies, health, `persistent`, non-secret `env`, `envAllowlist`, and `secretEnv`. DevFn adds a digest of the exact project prefix and opaque owner to the Compose project name, keeping separate accepted prefixes and owners isolated.

DevFn writes a generated override with loopback host mappings unless the named port explicitly selects public exposure. It starts only the requested service with `--no-deps`. Services declaring `secretEnv` use Docker's `none` logging driver and therefore cannot use log-pattern health checks. Ordinary cleanup stops/removes only invocation-owned containers and never passes a volume-deletion flag.

## Health checks

- HTTP: `{ type: "http", port: "app", path: "/health", expectedStatus: 200, timeoutMs: 120000 }`
- TCP: `{ type: "tcp", port: "postgres" }`
- Command: `{ type: "command", command: ["node", "scripts/ready.mjs"] }`
- Log: `{ type: "log", pattern: "ready on" }`

HTTP URLs are returned only for explicitly routed hostnames or ports named by HTTP health checks. Other services remain transport allocations visible through `devfn ports`; DevFn does not invent an HTTP URL for a database or arbitrary TCP listener.

## Startup endpoint and template resolution

`@devfn/core` exports `resolveEndpointTemplates({ config, plan, ownerId, ports, composeNetworks? })`. It is a pure resolver: `ownerId` is an opaque lifecycle owner supplied by the caller, and `ports` contains the selected profile's leased port numbers. `composeNetworks` maps selected service names to effective Docker network names. Supply it to publish Compose DNS URLs; absent network evidence omits those URLs and rejects references to them. The orchestrator reads the effective networks from `docker compose config` before creating state. It returns generated values, the profile environment, direct URLs, and resolved environment and command arguments for each selected node. The current CLI supplies its existing worktree instance ID as the owner. Callers of the resolver may use more than one owner per checkout. The resolver does not derive an owner from a path or start resources.

For each selected port, DevFn generates `DEVFN_PORT_<NAME>` (uppercase, punctuation replaced by `_`) and its configured `ports.<name>.env` alias. An HTTP health port, or a selected proxy hostname target, also gets `DEVFN_URL_<NAME>` as a direct loopback endpoint for host processes and owner-only output files. For Compose services on the same Compose project network, that key instead names the sibling service and its internal port, such as `http://web:8080`; `composeUrls` exposes these container-context values separately from `directUrls`. The leased host port remains in `DEVFN_PORT_<NAME>`. A route's HTTPS setting does not change its direct HTTP upstream; an explicitly direct HTTPS health endpoint retains HTTPS. Once all nodes are ready, the receipt's public `urls` may prefer installed proxy routes. A TCP or UDP allocation without an HTTP declaration has no invented URL.

Generated reserved values cannot be overridden. Profile literals establish defaults; a process or service literal with the same exact key wins for that node. Differently cased keys that collide after case folding are rejected. Selected inherited keys and platform base keys follow the same case-folded collision rule before startup, so macOS, Linux and Windows resolve the same map. Profile references resolve against generated and profile values before node overrides, so a node override does not retroactively change another profile value. The generated `DEVFN_*` namespace is reserved. `HOST` is reserved in profiles and local native processes: a local native process always receives `HOST=DEVFN_HOST=127.0.0.1`. An explicitly public native process may set or inherit `HOST` after public exposure is authorized. A Compose service may set `HOST` to its container bind address, including `0.0.0.0`. Local native node values, command argv and command-health argv may reference either generated bind key. These local process bind keys are not profile or Compose template inputs. Port environment aliases cannot use reserved keys. Colliding normalized port keys are rejected. The owner-only environment output file contains the resolved profile and generated non-secret values; node-specific values go only to that node.

Use `{{env.NAME}}` to refer explicitly to a generated or previously declared environment key in a profile value, node value, process `command` argument, package-manager `script`, or command-health argument. References inside each environment map may be forward references; cycles and missing references fail before any lease, file, process, or service mutation, while a self-reference to a generated port alias resolves to its generated value. Profile values can refer to generated values; node values and argv can also refer to resolved profile and node values. Compose service environment references use the container-context URL for sibling services; Compose command-health argv runs on the host and uses host-side direct URLs. Inherited `envAllowlist` values are delivered only through the existing process or Compose secret channel and cannot be template sources. Sensitive keys must be declared in `secretEnv`; credential values must not be placed in literals or argv. Empty or NUL argv values and malformed `{{...}}` references are rejected for all selected command sources. All other characters, including `$`, backticks, semicolons, pipes and ampersands, stay literal argv data; DevFn does not invoke a shell.

HTTP readiness that names a leased `port` probes its direct loopback URL at startup, status and retry, even when a `url` is also configured. The configured URL's path and query are retained; an HTTPS proxy route uses its direct HTTP upstream, while a genuinely direct HTTPS endpoint keeps HTTPS. A separate `path` is checked for credentials and validated against the configured URL origin before a leased origin is substituted, then appended by the existing URL path rule. URL-only readiness remains an explicit URL check, except that a URL aimed at a selected proxy route is rejected before startup: that route is installed only after nodes are ready. Compose interpolation receives the same resolved generated, profile and service values before `docker compose up`; Compose files must explicitly map those values into container `environment` entries when the container needs them. Each Compose service receives container-context sibling URLs only for services in the same owner-specific project with a shared effective Compose network. The default network counts when Compose assigns it; disjoint explicit networks and network namespace modes do not provide sibling DNS. Independent projects are allowed; an unreachable reference is rejected before mutation. An unmanaged pre-existing container is reused only when its effective environment matches the current Compose configuration, allowing only unchanged image defaults beyond the current keys; removed generated, profile, and service literals are rejected before startup. A native dependent can use a Compose service's leased host URL after that service becomes ready. URL userinfo and sensitive query, fragment or path assignment keys in manifest environment, argv, or effective health URLs are rejected without printing credentials, including URL forms normalized by Node's URL parser and percent-encoded values; credential argv flags such as `--token` are also rejected. Aliases `key`, `pass`, `pwd`, `auth`, `sig`, `token`, `secret`, `password`, and `credential` are sensitive at separator or camel/acronym boundaries, including qualified forms such as `db_password`, `DB_PASS`, and `DBSig`. Compact forms use the documented qualifiers in the core package README; ordinary words such as `monkey` and `compass` remain data. Pass credentials through `envAllowlist` and `secretEnv`. A ready receipt fingerprints declared startup inputs, selected port declarations, and the effective Compose service and referenced volume, network and config definitions. Compose resolves default and include-scoped interpolation and env files before fingerprinting; inherited host variables in selected Compose source require an explicit envAllowlist entry, and credential-named and secretEnv values are redacted before hashing. An effective source or env-file change degrades status and causes a safe owned restart on retry; changes discarded by Compose merge rules and byte-equivalent restoration retain the same fingerprint. Missing optional Compose env files are allowed; required files must exist. Existing v0.1 receipts without startup or port-spec fingerprints keep their prior readiness path.

For native commands, package scripts and command-health argv, a colon-delimited credential pair following `--user`, `--username`, `--proxy-user`, `-u` or `-U` is rejected in split, equals and attached forms. Plain user names remain valid. Percent-encoded credential URLs and headers are also rejected; encoding does not turn them into safe non-secret literals. This inspection does not invoke a shell or alter argument bytes.

Form arguments with credential-named fields and JSON bodies with credential-named keys are rejected in those same three argv sources, including nested objects, JSON-escaped keys, percent-encoded bodies, incomplete JSON bodies and shell-quoted JSON in package scripts. Ordinary non-secret JSON remains argv data. Deliver credentials through `envAllowlist` and `secretEnv` instead of embedding them in a command or readiness check.

Before reusing an unmanaged Compose container with `--no-recreate`, DevFn also compares Compose's effective service config hash with the hash persisted on that container. A changed command, published port, image, or other startup setting is rejected even when the environment is unchanged. Missing or malformed hash evidence fails closed before `up`.

## Profiles and hostnames

Profiles select named processes/services, add non-secret environment, and opt into the shared proxy with `proxy: true`. Dependencies are included transitively and started topologically. Cycles fail before mutation.

A hostname maps a route name to `target`, optional `hostname` template, `tls` (`off` or `internal`), and optional `profiles` filter. Templates accept `{project}` and `{instance}`. The route uses a stable DNS-safe component derived from an opaque owner; owners differing only by case receive distinct route names; the original owner value remains in ownership records and `DEVFN_INSTANCE_ID`. A configured static hostname receives an owner-derived label before `.localhost`, so two owners cannot publish the same route. Every resolved name must end in `.localhost` unless the route explicitly refers to a machine-registered domain.

`devfn domains register dev.example.test --tls internal` records a user-owned development domain in the machine state directory, bound to the current repository identity and project. Registration requires every current name-resolution answer for the domain to be loopback, so a reserved name such as `dev.example.test` must already resolve to loopback through local DNS or a hosts-file entry; a new or changed selected route must also resolve exclusively to loopback before startup and Caddy reload. Existing routes stay installed when another instance stops, even if their DNS later becomes unavailable. DNS with no answers, mixed local/public answers, or a nonloopback answer fails closed for route activation. The command does not edit DNS, `/etc/hosts`, the OS resolver, or a trust store. `devfn domains list` and `devfn domains unregister <domain>` inspect or remove registrations; removal refuses domains with active or pending routes. A registration cannot contain or be contained by any other registration, including one owned by the same repository. Public routing and remote targets have separate contracts.

A manifest can select `domain: "dev.example.test"` only after explicit machine registration. `host` optionally chooses a single DNS label shared by several path routes; otherwise the route key is used. Registered host labels can contain at most 40 characters. The worktree hostname is `<host>-<readable-worktree-name>-<stable-suffix>.<domain>`, with a 20-hex-character digest of the canonical worktree path as the suffix. The readable worktree name is shortened as needed so the whole first label fits DNS's 63-character limit; the suffix is always kept intact, so a long worktree directory name appears truncated in its hostname. The primary Git worktree also gets `<host>.<domain>` as its canonical alias. Both forms use one label under the domain, so one wildcard certificate can cover them. The suffix makes collisions between same-named worktrees extremely unlikely without depending on activation order. A registered route inherits its TLS mode from the machine registration; the manifest cannot override it. Default `.localhost` routes and their v0.1 owner-derived names remain unchanged.

`path` defaults to `/`, with `match: "prefix"`; `match: "exact"` selects only that path. A prefix matches its segment boundary (`/api` and `/api/...`, not `/apix`). `stripPrefix: true` strips a non-root prefix before proxying. Exact routes precede prefixes; longer prefixes precede shorter ones. Duplicate host/path/match routes fail before Caddy reload, and a host with only selected paths returns 404 elsewhere. All upstreams remain loopback.

Internal TLS uses the existing Caddy internal CA. Clients must explicitly trust that CA if they need verified HTTPS; DevFn never installs it. Selected TLS hosts redirect HTTP to HTTPS, while unknown HTTP hosts return 404. `--tls certificate --cert /absolute/cert.pem --key /absolute/key.pem` uses explicit PEM files. DevFn validates the key pair, validity dates, and DNS subject alternative name coverage of every generated hostname before publishing a route; a legacy common name alone does not count. A wildcard certificate may be needed for worktree names; a certificate for the registered base alone is insufficient. DNS-01 is rejected until a validated provider adapter is available. There is no implicit ACME, public certificate issuance, or CA installation.

## OAuth callback relay

An identity provider such as Google accepts only exact, pre-registered redirect URIs, while each worktree has its own hostname. `devfn oauth-relay start <registered-domain> [--host auth]` starts one machine-wide relay process and routes `https://<host>.<domain>` (with the platform HTTPS port, 8443 on macOS) to it through the DevFn Caddy. Register `https://auth.<domain>[:port]/<callback-path>` with the provider once. The domain must already be registered to the repository running the command; the command installs nothing else, and `devfn oauth-relay stop` removes the route before stopping the process. Like a profile with proxy routes, the relay claims the Caddy listener ports in the machine registry before it starts, as the reserved lifecycle owner `devfn-oauth-relay` with the relay process recorded as its owner: an existing sibling lease on either listener port refuses the start and names its instance and service, and while the relay route exists other worktrees stopping their routes are covered by its claim. The same claim leases the relay's loopback backend port, which the relay process binds exactly, so it cannot take a port another DevFn lifecycle has leased but not yet bound, and no DevFn lease can take it while the claim lasts; a running relay whose claim has ended is replaced by the next `start`. `devfn oauth-relay status` reports whether the process and route are live and whether ticket state is readable, never any state or code.

The relay changes no OAuth step. Each worktree's own OAuth client still generates and validates its state, nonce and PKCE verifier, exchanges the code itself and issues its own session. The client integration interface is `OAuthRelayClient` from `@devfn/proxy/oauth-relay`:

1. At sign-in, generate state, nonce and PKCE as usual, then call `await relay.authorize({ state, callbackUrl })`. `callbackUrl` is the worktree's own callback URL on one of its live DevFn routes, normally the request origin plus the callback path. It returns `redirectUri`, the registered relay URI with the same path.
2. Send `redirect_uri=redirectUri` in the authorization request and the identical value in the token exchange.
3. The provider redirects the browser to the relay. The relay consumes the state's single-use ticket and answers `303 See Other` to the bound `callbackUrl` with the provider's query unchanged. Validate state, exchange the code and validate the nonce there as usual, then set host-only session cookies (no `Domain` attribute) so worktree sessions stay separate.

`relay.redirectUri(callbackPath)` returns the same registered URI without registering a state. Like `authorize`, it answers only while `oauth-relay/service.json` names a verifiably running relay process; a missing record or a recorded relay that is no longer running fails with `DEVFN_OAUTH_RELAY_UNAVAILABLE`, so a crashed relay's leftover record never yields a URI.

`authorize` binds the state to the calling owner, by default `DEVFN_INSTANCE_ID`, and to the exact committed route that serves `callbackUrl` (route ID, hostname, path, target port and activation time). It is refused for another owner's route, a non-DevFn destination, a URL with credentials, query, fragment, percent-encoding or dot segments, a redirect URI off the relay origin, a state that is shorter than 22 or not unreserved URL characters, or a state already bound to an unexpired ticket, consumed or not. Tickets expire after 600 seconds by default (`expiresInSeconds`, at most 900); the store then forgets the state, so it may be registered again. DevFn passes every process it launches, and that process's command health check at startup and in `status`, `DEVFN_STATE_DIR`, the lifecycle's resolved machine state directory (including `--state-dir` and `XDG_STATE_HOME`, which processes do not otherwise receive), and `OAuthRelayClient` reads that directory by default, then the default machine state directory; an explicit `stateDir` option overrides both. Compose services do not receive `DEVFN_STATE_DIR` and cannot read the host state directory, so call `OAuthRelayClient` from a native process. The ticket store keeps only a SHA-256 digest of each state, never a code, verifier or token; the relay process logs nothing.

A callback is forwarded only by the relay process that `oauth-relay/service.json` names as running for the relay origin; a missing record answers `DEVFN_OAUTH_RELAY_UNAVAILABLE` and an unreadable one `DEVFN_OAUTH_RELAY_STATE_INVALID`, before any ticket is touched. It is forwarded only once, only when it arrives on the relay host and the registered path, carries exactly one `state` and exactly one `code` or `error`, and the bound route is still committed and unchanged with a verifiably running owner. Registration and forwarding read route state and owner evidence as one snapshot under the routing lock every route and lease transition holds, so a route replaced, removed or still in transition is refused rather than raced. Owner evidence must be affirmative: a ready lifecycle of the owner holds the active lease on the route's target port, and the process or container recorded on that lease is verified running. An unverifiable identity (including a process recorded without a birth signature), a launch whose identity is not yet recorded, a lease that names the owner's lifecycle but records another instance or project, or a lifecycle started by a release without an owner journal is refused (`stale-owner`); restart such a lifecycle with this release. Malformed owner evidence of the owner (an owner journal flag other than `true`, a launch list that is not a list, or a recorded process or container whose identity fields are malformed) answers `DEVFN_OAUTH_RELAY_STATE_INVALID` and is never rewritten; other owners' evidence is judged on its own. A pending route journal left by an interrupted routing command refuses every callback until the next DevFn routing command recovers it. A ticket is consumed by the first attempt that reaches it, even one that is then rejected, so a replay, including a concurrent one, is refused. Rejections answer `DEVFN_OAUTH_RELAY_REJECTED: <reason>` (`malformed`, `unknown-state`, `replayed`, `expired`, `wrong-origin`, `stale-owner`, `route-stopped`, `target-mutated`, `target-invalid` or `capacity`). Unreadable ticket, route or registry state answers `DEVFN_OAUTH_RELAY_STATE_INVALID`: the relay fails closed and leaves the file for inspection rather than rewriting it. A ticket is stored only in a form the store reads back, so a redirect or callback URL longer than 2048 characters is refused at registration (`malformed`) and cannot make other owners' tickets unreadable. Only `GET` query callbacks are relayed; form-post response modes are not.

Owners are opaque: a later named runtime can register with its own owner identity through the same interface. `devfn-oauth-relay` is the reserved route owner of the relay itself. The relay process is recorded in `oauth-relay/service.json` and on its registry claim before it is committed, and on its route once committed: a relay whose starter is interrupted before the commit exits with it, so no relay runs unrecorded, and an uncommitted relay has no route. The relay process leads its own process group, and the relay counts as stopped only when the group of every recorded identity is verified gone; an unreadable record, an unverifiable identity, or a live process that a route or claim records but the service record does not name keeps the route and refuses `start` until `devfn oauth-relay stop`. A process left in a relay's group after the relay itself exited cannot be verified as the relay's, so it keeps the route, record and listener claim, `start` is refused and `stop` signals none of it and fails with `DEVFN_OAUTH_RELAY_UNAVAILABLE` naming the group; stop that process yourself, then run `stop` again. `stop` removes the route first and stops every recorded relay process group through its verified leader, forcing members that outlive a graceful stop, only after Caddy applied that removal; when Caddy cannot apply it (`DEVFN_PROXY_UNAVAILABLE` or `DEVFN_PROXY_RELOAD_FAILED`), `stop` fails before signalling any relay process and leaves the relay running, recorded and routed, so no callback is sent to a freed port; make the DevFn Caddy available (`devfn doctor` reports it) and run `stop` again. Every relay command applies one route rule first, under the relay's service lock: a committed or pending relay route may exist only while it reaches the live recorded relay (its hostname, loopback port and process). `start`, `status`, `ports gc` and orphan recovery remove any other relay route and confirm it gone while the live relay keeps running (the next `start` routes it again); once the relay is verifiably stopped they also end its record and listener claim, after its route. A relay route is always removed and confirmed gone before any relay process is signalled or its claim or backend lease released. `start` replaces a running relay whose claim ended the way `stop` retires one: route first, so a replacement whose claim or launch then fails leaves no relay route, and a removal that fails leaves the old relay running and recorded. A `start` whose route activation fails follows the same rule: any relay route left in committed or pending state (Caddy may have reloaded before the failure; the proxy keeps such an activation's journal until a reload of the committed routes confirms what Caddy serves), or unreadable route state, is removed and confirmed gone before the new relay is stopped and its record, claim and backend lease released; if that removal cannot be confirmed, the new relay keeps running, recorded and claimed, and `start` fails with `DEVFN_OAUTH_RELAY_UNAVAILABLE` naming both failures; run `stop` once Caddy is available. When the route is gone but the new relay's process group does not stop, or cannot be verified, the relay keeps its record and listener claim, and `start` fails with `DEVFN_OAUTH_RELAY_UNAVAILABLE` naming the start failure, the stop failure and the relay PID; run `stop` once it can be stopped (a process left in the group without its leader is yours to stop first). An invalid `--host` label is refused as `DEVFN_OAUTH_RELAY_REJECTED` (reason `malformed`) before any state is read. With an unreadable record it still removes the route and stops the processes the route and claims name, then fails with `DEVFN_OAUTH_RELAY_STATE_INVALID` and leaves the record for inspection; remove it once no relay process runs. Once the relay is verified gone, the next DevFn route transition that changes routes (a `devfn up` or `devfn down` of a profile with routes, an activation rollback, or the recovery of an interrupted routing command's journal) drops its route; a lifecycle without routes never touches Caddy for it; `devfn oauth-relay status`, `devfn ports gc` or the next `oauth-relay start` also removes its record and ends its listener claim. `ports gc` skips the relay while a relay command holds it. A relay command or callback killed while it holds a relay lock delays other worktrees only for a few seconds: the lock is recovered once its holder is verified dead. Restarting the relay replaces its route and keeps pending tickets. Neither touches other owners' routes or tickets. Until one of those runs, a crashed relay's route still points Caddy at its former loopback port: DevFn leases cannot take that port while the route or the relay's claim remains, but a non-DevFn local process that binds it in that window would receive callbacks, including authorization codes. PKCE keeps such a code unusable without the worktree's verifier; run `devfn oauth-relay status` after a relay crash to close the window. An earlier DevFn release's `devfn ports gc` keeps the relay route while the relay process recorded in the registry runs. Owner evidence is the lease and the recorded identity, not the listening socket: DevFn does not check, per callback, that the owner's process still holds the port. A live owner that closed its listener has its own worktree route serving whatever binds that port, session cookies included, so the relay adds no exposure there; keep worktree processes bound to their leased ports for as long as they run.

AuthFn maps onto this interface without AuthFn changes. Its social callback URI is its environment `baseUrl` plus base path, used for both the authorization request and the token exchange, so an `AuthFnEnvironmentResolver` that returns the relay origin as `baseUrl` makes both use the registered URI. Leave the cookie `domain` unset so AuthFn's session cookies stay host-only on the worktree host that receives the forwarded callback. `POST /social/start` returns the flow's `stateId`, which is its OAuth `state`; register it with `authorize` before navigating to the returned `redirectTo`. A flow whose state was never registered is rejected at the relay, so a missed registration fails closed. The DevFn tests prove the contract with a fake provider and generic client fixtures; a real AuthFn and Google journey is networking acceptance evidence (DEV-9), not part of these tests.

## Public tunnel routes

A profile can publish selected `hostnames` routes on the public internet through a machine-registered tunnel binding:

```ts
profiles: { share: { processes: ["web"], proxy: true, tunnel: { binding: "preview", routes: ["web"] } } }
```

`devfn up --profile share --allow-public` is required on every start; without it DevFn fails with `DEVFN_PUBLIC_EXPOSURE_CONFIRMATION_REQUIRED` before reading tunnel state, starting a connector or calling the provider. Selecting a binding, or any other external resource, never grants public exposure, and a manifest cannot create a binding or name credentials. Only the listed routes are public; each must be a route of that profile, and the profile must use the proxy.

`devfn tunnel register <name> --nonproduction --domain <public domain> --account-id <id> --zone-id <id> --tunnel-id <uuid> --credentials-file <path> --api-token-env <NAME>` records a pre-existing nonproduction Cloudflare named tunnel and public domain in machine state, bound to the repository and project. DevFn never creates a tunnel or zone and never stores a credential: the binding keeps the path of the tunnel credentials file (an owner-only regular file whose content DevFn never reads) and the name of the environment variable holding an API token limited to that zone's DNS records and to reading the account's Cloudflare Tunnels. A public domain cannot overlap a loopback development domain or another binding, in either registration order, and a tunnel can back only one binding. `devfn tunnel list`, `status <name>` and `unregister <name>` inspect or remove bindings (their JSON output shows credential reference variable names, never values); removal is refused while a binding publishes routes, runs a connector or has a withdrawal outstanding.

Each public hostname is `<host>-<readable-worktree-name>-<stable-suffix>.<public domain>`, using the route's `host` label or key and the same worktree label as registered domains, one label under the binding domain, so a single edge certificate for `*.<public domain>` covers every worktree. Cloudflare Universal SSL covers only a zone's apex and its first-level subdomains: a binding whose public domain is the zone apex needs nothing more, while one below the apex needs an advanced or custom edge certificate for `*.<public domain>`. DevFn does not provision or check edge certificates. The name depends only on the worktree identity and binding, so `devfn tunnel urls [--profile <name>]` prints the deterministic public URLs before anything starts, and the endpoint resolver generates each selected route's URL as `DEVFN_PUBLIC_URL_<ROUTE>` (uppercase, punctuation replaced by `_`) for environment and argv templates; a ready receipt records them as `publicUrls` and its published hostnames as `tunnel`.

Public routes are served by the DevFn Caddy on a separate loopback listener, port 8444, with internal TLS. That listener is an explicit allowlist: each public host serves only its selected paths (404 elsewhere), a request whose Host header differs from its TLS server name is refused with 421, any other name Caddy holds a certificate for, including every local route, gets 403, and an unknown server name fails the TLS handshake. DevFn's own 404 and 403 responses there carry `Devfn-Public-Origin: fallback` or `deny`. Local routes never render on it, so neither a wildcard DNS record nor a forged Host header reaches a private route through the tunnel. Public validation is independent of the loopback DNS checks for registered domains: before any provider change DevFn verifies, over TLS to the public origin, that each hostname's certificate verifies against the DevFn Caddy internal root for exactly that name, that the request reaches that host's allowlisted site (whatever status the application returns, but never the deny response) and that a forged Host is refused, and that the binding's tunnel exists in its account and is locally configured (a remotely managed tunnel's dashboard ingress would replace the allowlist); then it creates or confirms one proxied CNAME per hostname to the binding's tunnel, marked with the comment `devfn-tunnel:<binding>`, and reads it back. A wildcard record to the binding's tunnel at the public domain or any ancestor of it, such as `*.<public domain>` or `*.<zone>`, is refused, because removing a name's own record could not end its reachability. A record DevFn did not create is never changed or deleted, and a publish that fails removes only records it created after reading that none existed; a failed read stops it first. The connector configuration lists exactly the published hostnames, each forwarded to the public origin with that hostname as TLS server name and Host header, certificate verification against the internal root (`noTLSVerify: false`), and a final `http_status:404` rule; `cloudflared tunnel ingress validate` and `ingress rule` check it offline, under an empty home directory, before it runs.

One connector per binding serves every worktree's public routes. It runs through the DevFn process wrapper, which leads its own process group and starts the connector only after its birth identity is journaled, with an explicit environment: a private empty home directory and no ambient credentials, API token or `TUNNEL_*` settings. A change starts the new connector and waits for its readiness before stopping the old one, so other worktrees stay published. No connector starts while any other recorded connector, except the running one it replaces, may still run: one whose process group cannot be verified stays recorded, keeps the routes it may serve outstanding and blocks every launch until you stop that group. Every transition is journaled under the binding's lock: a failed or interrupted publish withdraws only the DNS records it created, repairs a published name's missing record and keeps the previous connector; an uncommitted name that a connector it started may already route stays journaled as that lifecycle's withdrawal until no connector routes it, while a DevFn-owned record for it that existed before the publish is kept; and names a lifecycle stops publishing are withdrawn only after the new set is committed. A new connector replaces the running one in the same journal write that commits the new set, so an interrupted change leaves the previous connector serving the previous set. A publish whose commit write fails before it replaces the journal is rolled back like any failed publish; once that write replaces the journal the publish stands, also when syncing the replacement to disk then fails, and a replaced connector whose stop could not yet be recorded is stopped by the next command. Journal writes are synced to disk before they replace the previous state. An old connector still serving published routes after its replacement exited is kept and replaced again rather than stopped.

A withdrawal removes the names' DNS records and reads them back, then replaces a running connector with one without them; it never reduces another worktree's service and never starts a connector where none runs. Public exposure of a lifecycle has ended once no recorded connector may still route its names; confirmed DNS removal alone is not enough, because cached resolutions and established connections still reach a connector that routes them. Public routes are published after all nodes are ready and withdrawn from every binding before any process stops, including the prior lifecycle of a replacement. A start that does not keep a ready lifecycle for replacement first withdraws any public routes its lifecycle still publishes, also when its worktree receipts are gone, and starts nothing and takes no port while that exposure cannot end. A ready public lifecycle whose connector no longer runs or publishes its names is not reported as already running; `up` replaces it and publishes again. While exposure has not ended, such as while an old connector still routes the names until its replacement starts or a connector cannot be verified stopped, nothing is stopped and no port is released. Once it has, local teardown completes. A part still outstanding, such as a DNS removal that keeps failing, stays journaled and is retried by every later command of that binding. `devfn down` reports it as `publicOutstanding` with a `degraded` state, and `devfn tunnel status <name>` lists it as `outstanding`. A start that moves to another binding reports what the old binding still journals as `tunnel.outstanding` in its receipt. `devfn ports gc` withdraws the routes of a lifecycle that can no longer run and keeps the proxy routes, and so the ports, of an owner whose exposure may continue. It collects every other lease before it reports those owners.

DevFn writes a per-lifecycle publish marker under `tunnel-owners/` before its first provider or connector change on a binding and removes it once nothing is outstanding there. A lifecycle without one never published, so its start and stop read no tunnel state, as in DevFn v0.1; a lifecycle with one fails closed if that binding's state cannot be read. A connector that exited is restarted only by the next publish or by `devfn tunnel recover <name> --allow-public`, after the binding's tunnel is verified and, for recovery, each route's DevFn-owned DNS record is confirmed or recreated and read back, and only for the routes of the publishing lifecycle and of lifecycles that may still run by their registry evidence and pass the public-origin check again; the routes of any other lifecycle, such as one that ended without `devfn down`, are withdrawn instead of being made public again. Malformed tunnel state fails closed with `DEVFN_TUNNEL_STATE_INVALID` and is left for inspection. Real Cloudflare exposure, edge certificates and cleanup readback are networking acceptance evidence, not part of the fixture tests.

### ngrok bindings

The same selected-route, consent and ownership contract applies to ngrok; only the provider adapter differs. `devfn tunnel register <name> --provider ngrok --nonproduction --authtoken-env <NAME> ...` records the names of the environment variables that hold a nonproduction ngrok agent authtoken and API key; DevFn never stores either value, never creates an ngrok domain and never installs `ngrok`, which must already be in an absolute `PATH` directory. A binding has one of two endpoint kinds:

- **Reserved** (`--domain <domain> --api-key-env <NAME>`): the account must already reserve the wildcard domain `*.<domain>`. Public hostnames follow the same `<host>-<readable-worktree-name>-<stable-suffix>.<domain>` rule, so their URLs are deterministic before start: `devfn tunnel urls` prints them and the endpoint resolver generates `DEVFN_PUBLIC_URL_<ROUTE>` for every selected public route of the profile, which environment and argv templates, and selected Compose interpolation (`${DEVFN_PUBLIC_URL_<ROUTE>}`), may reference like any other generated value. Replacement (`devfn restart`) and crash recovery resolve the same URLs. Before any connector starts, DevFn reads the account through the API, using the key only to list reserved domains and online tunnels: the wildcard must be reserved, and a hostname already served by an online tunnel that does not carry exactly this registration's `devfn-tunnel:<binding>:<registration ID>` metadata is a conflict that DevFn leaves unchanged. Registration assigns a fresh random registration ID, so a binding of the same name registered on another machine or state directory, which derives the same hostnames for the same worktree path, never counts as owned: pooling would otherwise split public traffic between two developers' origins. The same read is repeated once a launched connector is ready and before its publish or recovery commits, because another registration's agent may have come online between the first read and the launch: a foreign tunnel then stops the new connector and its agent, the transition fails with `DEVFN_TUNNEL_CONFLICT`, nothing is committed and the previous connector keeps serving. An agent of another registration that joins the pool after that readback, or that the account's tunnel listing does not show yet, is not detected until a later publish or recovery of that hostname reads the account; live listing behaviour is networking acceptance evidence (DEV-9).
- **Ephemeral** (`--ephemeral`, no domain): ngrok assigns each endpoint's URL only once the connector runs. A profile must select such a binding explicitly with `tunnel: { binding, routes, ephemeral: true }`; a binding of the other kind is refused either way. `devfn tunnel urls` lists the routes under `assignedAfterStart` instead of printing a URL, no `DEVFN_PUBLIC_URL_<ROUTE>` is generated, and any reference to one in a profile, node, argv, health command or Compose interpolation fails before any lease, process or connector starts, rather than starting a consumer without its URL. The assigned URLs reach only runtime outputs: the ready receipt's `publicUrls` (with `tunnel.urlTiming: "post-start"`) and `devfn tunnel status <name>` (`urls`, by origin hostname). Every restart of the binding's connector assigns new URLs, including the make-before-break restart caused by another worktree publishing or withdrawing routes on the same binding. Such a restart does not change any other lifecycle's readiness: a ready lifecycle stays ready while the running connector serves each of its route hostnames at a URL of its own, and `devfn status` then reports each route's current URL, from its own hostname with the route's path, as `publicUrls`, with `publicUrlsChanged: true` once they differ from the receipt's `publicUrls`, which record them at start. A route hostname without a URL, or sharing another one's, is `degraded`. `devfn up` on such a ready lifecycle keeps it, including its processes and the shared connector, and records the current URLs in its receipt; `devfn tunnel status` always reports the current ones by hostname. An agent that reports one URL for two endpoints is never treated as ready, since that URL would serve only one of the routes. The application receives the DevFn-internal origin name (`*.<binding>.ngrok.devfn.internal`) as its Host header.

ngrok keeps no DNS record for DevFn to create or delete: a hostname is publicly reachable exactly while an agent runs an endpoint for it. DevFn therefore journals and withdraws ngrok routes like Cloudflare routes, but public reachability is governed only by its connector: a withdrawal has ended once no recorded connector may still route the names. The connector is a DevFn process that runs an origin bridge on a free loopback port and, beside it, the ngrok agent with a generated configuration: one HTTPS-only endpoint per published hostname, named after it, sending that hostname as the Host header, with traffic inspection and the agent's local API off (that API could start endpoints DevFn did not select) and the binding's metadata marker; reserved endpoints are pooled so a replacement connector can start before the one it replaces stops. `ngrok config check` validates the generated configuration offline, under an empty home directory, before it runs. The ngrok agent forwards plain HTTP and cannot pin the origin's TLS server name or root, so the bridge provides the Cloudflare connector's origin guarantees: a request whose Host is not one of the connector's hostnames, or whose request target is not a plain path (an absolute URL could name another host to the origin), is answered `404` with `Devfn-Public-Origin: deny` and never reaches the public origin, and an allowlisted request, including a WebSocket upgrade, is forwarded over TLS to the public origin with that hostname as TLS server name and Host only once the origin certificate verifies against the DevFn Caddy internal root for exactly that name. The public origin listener, its strict SNI and Host checks and its deny fallback are the same as for Cloudflare. The agent receives only `PATH`, the private home directory and `NGROK_AUTHTOKEN`, resolved from the binding's reference when the connector starts; the DevFn process wrapper redacts the authtoken from the connector log, and provider errors report status and error codes only. The connector is ready once the agent reports every endpoint started, a reserved one at exactly its own hostname; a connector whose agent exits stops as well, so a dead agent never looks ready. An agent left behind would keep its public endpoints forwarding to a freed loopback port that any local process could bind, so a connector that exits, including through its own failure, kills its agent first, and one killed outright, which runs no code, cannot leave an unknown agent: on POSIX the agent waits behind a gate until the connector has recorded its process identity in a file keyed by that connector launch's random ID, and a connector that dies before that never starts it. DevFn reads, signals through and removes only the record of the launch it is settling, never one a later connector wrote, even at a reused readiness port. Until such an orphaned agent is stopped, `devfn tunnel status` reports the connector `unverified` and its names stay published or outstanding; every later tunnel command of the binding (publish, withdrawal, `devfn down`, `devfn tunnel recover`) first stops it through that verified identity, and only then reports names unrouted or starts another connector. Windows has no such gate, so an agent whose connector is killed before recording it is not found there. A replacement connector starts on a fresh `connector.log`; the one it replaces keeps writing to the previous log, moved to `connector.log.1`. `devfn tunnel status <name>` reports each binding's `capabilities`: URL timing, whether DevFn manages DNS records (`dns: "connector-only"` for ngrok), and the provider gaps above. Fixture tests exercise the adapter, bridge and lifecycle with a stand-in agent; they are not a live ngrok account result. A real ngrok sandbox journey, including the agent's endpoint logs and cleanup, is networking acceptance evidence (DEV-9).

## Organization policy

`devfn.policy.json` supports `fallbackRange`, `hostnameSuffix`, and entries with `name`, exactly one of `port`/`range`, `kind` (`protected`, `preferred`, or `excluded`), optional `project`, and `description`. `devfn ports report` combines the policy with the entire machine registry into Markdown; it is not limited to the current project or profile. `--output` must remain inside the repository.
