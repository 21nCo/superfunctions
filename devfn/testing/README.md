# @devfn/testing

Deterministic fixture manifests, temporary projects, and fake listeners for allocator, lifecycle, crash-recovery, and CLI contract tests.

## Networking qualification harness

`@devfn/testing/networking` holds the versioned matrix (`devfn.networking-qualification/v1`) that DevFn's networking contract must pass on real hosts, and the harness that runs it. Each scenario names its deferred-matrix row, the prerequisites it needs, the assertions a live run must observe, the disposable resources it may create, and the local contract tests that cover the same behavior. Those tests are fixture evidence only; they never count as a live pass.

The rows are: native and Compose endpoint wiring before start, two simultaneous worktrees, hostname/path isolation, internal TLS and registered domains (1); Google OAuth sign-in in two worktrees through one relay redirect URI (2); Cloudflare and ngrok reserved/ephemeral public journeys (3); startup failure, concurrent change, crash, one-worktree stop and proxy/tunnel reload (4); and the opaque-owner endpoint interface (5). The DEV-2 networking outcome needs every scenario passed on both macOS and Linux at the exact head (`gate`).

From a built checkout (`npx turbo run build --filter=@devfn/cli --filter=@devfn/testing`):

```sh
node devfn/testing/dist/networking/cli.js plan [--approval approval.json] [--browser-operator]
node devfn/testing/dist/networking/cli.js run --head <sha> --out receipt.json [--scenario <id>]... [--row <n>]... [--approval approval.json] [--browser-operator]
node devfn/testing/dist/networking/cli.js gate --head <sha> macos.json linux.json
```

`plan` only probes. `run` drives the built DevFn CLI against a new state directory under a temporary run root, using generic fixture repositories and worktrees. It exits 0 only when every selected scenario passed. `run` refuses to start unless `--head` is the HEAD of a clean checkout in which every tracked `devfn/*/src` file has a `dist` output at least as new; the receipt records that provenance and `gate` requires it. Every DevFn command of the run, including the deliberately killed start, and the Caddy it starts get `XDG_DATA_HOME`, `XDG_CONFIG_HOME` and `XDG_STATE_HOME` under the run root, so the run's internal CA and Caddy configuration never touch the operator's.

- A scenario is `passed` only when its driver observed every planned assertion and none failed, every resource it created was removed and read back absent, and the operator's own DevFn state and the OS trust stores are unchanged. Each operator allocation, route, registered domain and tunnel binding is compared by name and by a digest of its material fields, so a retargeted route or a changed binding under the same name is a change; on macOS the user and admin trust settings are compared too. Otherwise it is `failed`. `blocked` means a prerequisite or driver was unavailable (`EXTERNAL_ACCEPTANCE_GATE: …`), and `unsupported` means the host is not macOS or Linux. Neither is a pass, and Windows is never qualified.
- Prerequisites are read-only probes that fail closed. They check Node.js 22+, the built CLI, git, Caddy (on Linux, also its existing permission to bind 80 and 443), and `lsof` and `ps` for process read-back. The DevFn proxy ports (2019, the probed platform's listener ports and 8444) must be free, because another runtime holding them is never touched. They also check Docker Compose against a local engine only: the endpoint from `DOCKER_HOST` or the current Docker context must be a local socket, and the run pins it for every DevFn and `docker` command (remote targets are a separate capability). They also check the approved resources. The harness never installs tools, trust roots, port permissions or resolver entries. A registered domain must already resolve only to loopback.
- Every resource is recorded in `<run root>/inventory.json` before it is created, and only inside the approved scope: the run root, an approved domain, or a run-prefixed binding or hostname. Cleanup runs even when a driver fails. Nothing is reaped before the read-back that would report it. A lifecycle is read back after `devfn down`, so a process that outlived it, a lease, a route of its owner or a Compose container or network of its owner fails the scenario; the run's shared Caddy, OAuth relay and tunnel connectors are left to their own resources while they are recorded. The relay and connector processes recorded before `oauth-relay stop` or `tunnel unregister` must be gone afterwards, and a binding is absent only when its provider holds nothing carrying its marker. A checkout that still runs processes is kept and fails its read-back. A public name is recorded before `devfn up` can publish it (for an ngrok URL assigned after start, the origin name DevFn derives for the route, with the URL attached once assigned). It is absent only when DevFn no longer routes it and a provider read-back (Cloudflare DNS, or the ngrok endpoint and tunnel lists by name and marker) holds nothing for it; an unreadable provider is never absence. Run-level resources (the run's Caddy and any process left in the run root) are read back into the receipt, and leftovers, including Compose containers and networks of the run's own owners, are removed only after that. On SIGINT, SIGTERM or SIGHUP the run writes no receipt. It first kills in-flight DevFn commands, refuses any further creation and ends every wait, waits for the running scenario to return, then runs one cleanup and read-back of what the ledger lists and reports what remains. The run root is kept for inspection when anything is not confirmed absent.
- Errors are never evidence: a timeout, refused connection or DNS failure leaves an assertion failed or unobserved. Each check passes only on the shipped component's own answer: the public origin's 403 with `Devfn-Public-Origin: deny` for a route's own name, its 421 for a forged Host and its marked `fallback` 404, the local proxy's empty 404, Caddy's 308 to HTTPS, the relay's 403 `DEVFN_OAUTH_RELAY_REJECTED: replayed`, and for a mismatched Host the provider edge's own refusal (a Cloudflare `error code: 1xxx` answer other than 1033, or a 4xx with an `ngrok-error-code` header). The exported `ANSWERS` predicates are tested against the failure answers.
- The receipt (`networking-qualification-contract`, mode 0600) records the host, provenance, prerequisites, each observation and cleanup read-back, run-level cleanup, the endpoint interface version and the limitations of every provider binding the run registered. Credential values from approved variables are redacted.

The approval file names nonproduction resources and the environment variables that hold credentials, never their values. Unknown fields, production, expired approvals and malformed names are refused:

```json
{
  "version": 1, "nonproduction": true, "approvedBy": "owner", "expiresAt": "2026-12-31T00:00:00Z",
  "domain": "dev.example.test",
  "oauth": { "provider": "google", "clientIdEnv": "QUAL_GOOGLE_CLIENT_ID", "clientSecretEnv": "QUAL_GOOGLE_CLIENT_SECRET", "relayHost": "auth", "redirectUri": "https://auth.dev.example.test:8443/oauth/callback" },
  "cloudflare": { "domain": "preview.example.test", "accountId": "<32 hex>", "zoneId": "<32 hex>", "tunnelId": "<uuid>", "credentialsFile": "/abs/tunnel.json", "apiTokenEnv": "QUAL_CF_TOKEN" },
  "ngrokReserved": { "domain": "ngrok.example.test", "authtokenEnv": "QUAL_NGROK_AUTHTOKEN", "apiKeyEnv": "QUAL_NGROK_API_KEY" },
  "ngrokEphemeral": { "authtokenEnv": "QUAL_NGROK_AUTHTOKEN", "apiKeyEnv": "QUAL_NGROK_API_KEY" }
}
```

The OAuth redirect URI must be the relay origin on this host plus the fixture callback path: `https://<relayHost>.<domain>/oauth/callback`, with port 8443 on macOS and the default port on Linux. Both ngrok entries need an API key variable, which the run uses only to read endpoints back. With `--browser-operator`, the run prints each worktree's login URL and waits up to 10 minutes. A person or browser agent completes the Google sign-in, and opening the URLs needs an explicit trust decision in that browser for the DevFn internal CA. The fixture apps report outcomes and session hosts, never codes or tokens. A consumed callback URL stays in the app's memory until the harness replays it once, as soon as the app reports it and well inside the relay ticket lifetime; nothing writes it to disk or the receipt. The crash scenario waits out the five-minute stale window of a killed start's lifecycle lock, and so does an interrupted run's cleanup when the interrupt killed a start.
