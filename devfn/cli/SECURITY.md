# DevFn security

- Every DevFn manifest can declare lifecycle commands, so the CLI refuses to load JSON, TypeScript, or JavaScript until the user records trust for its exact digest with `--trust`. JSON is parsed directly from the verified bytes; executable manifests run from a private copy of those same bytes and must be self-contained, with imports and `require()` rejected so dependency files cannot bypass the digest boundary.
- Runtime children inherit a small base environment plus explicit `envAllowlist` entries. Sensitive-looking keys must also be listed in `secretEnv`; a detached wrapper redacts those effective values before native-process logs are persisted. Literal values are rejected only when their key looks sensitive, so review every manifest literal. Compose logging is disabled for services with `secretEnv` because Docker otherwise retains historical unredacted logs. Secrets are not persisted in the registry or lifecycle receipt.
- Generated environment and state files use owner-only modes (default `0600`); their directories use `0700`. Existing files are explicitly re-permissioned after each write.
- Local ports and proxy targets bind to loopback unless a manifest explicitly selects public exposure. Profiles containing public processes, ports or tunnel routes require the separate `--allow-public` confirmation on every start; selecting a tunnel binding alone grants nothing. A public Cloudflare tunnel must never be inferred: bindings are registered per machine, must be asserted nonproduction, and store only a credentials file path and the name of the environment variable holding a DNS-scoped API token. The tunnel reaches only a public origin listener that serves the selected routes, refuses a Host header that differs from the TLS server name and denies every other name, including all local routes.
- Repository-relative process, Compose, runtime, policy, and output paths are validated against lexical and symlink path escape.
- PID ownership uses a birth signature where the host exposes one, read the same way whatever time zone or locale DevFn runs in (macOS `ps` is pinned to `TZ=UTC0 LC_ALL=C`); a signature an earlier release recorded in the caller's time zone is never compared as text, but judged by the record's own UTC time: a process that started after the record was written is a reused PID, one that started no later is the recorded owner, and a record without a time stays unverified. A process that started within two seconds after the record time, the allowance for wall-clock adjustment, is also unverified rather than reused: DevFn neither signals it nor retires its leases, routes or claims, and teardown reports a cleanup error until the PID is free or a later run can decide. An earlier release's active port lease is judged by its activation time, written just after its owner's identity was read. A recorded process is judged with its whole process group: when the recorded wrapper or launcher exited but processes remain in its group, DevFn treats it as possibly running, keeps its leases, routes, listener claims and owner journal, does not signal the leaderless group, and reports a cleanup error until it is gone. Stopping a verified process waits until its whole group is gone and forces members that ignore termination. A member that has exited but was not reaped (a zombie, as every orphan stays under a container PID 1 that does not reap) counts as gone: it runs nothing, and its PID and group ID cannot be reused until it is reaped. A member DevFn cannot list or signal counts as possibly running, so on Linux a group is proven gone only when every `/proc` entry can be read and parsed and `/proc` is not mounted with `hidepid`; otherwise it stays possibly running. Processes that leave their group (for example by `setsid`) and Windows process trees after their leader exits are outside this check. DevFn refuses to stop a reused PID, and never signals a live PID whose start identity cannot be read: `down`, restart and replacement then report a cleanup error, leave the receipt `degraded` and keep its leases, routes and owner journal until a later `down` can verify or stop it. Teardown also stops owners the registry journal records that the receipt does not list, and finds the containers of an interrupted Compose launch by its Compose project and service labels; a container that ran before the launch is left running. A process still running after its stop was refused on identity grounds is a cleanup error, not a stopped owner.
- Compose launches: `docker compose up` runs only after its launcher's identity is journaled, and an interrupted launch is resolved only once that launcher and every process in its process group are gone, so a Compose run that outlived DevFn cannot send Docker a new request after `down` reports stopped. The Docker daemon may still finish a create or start request the killed launcher had already sent, so the label scan then repeats, re-reading the state of every container it already stopped, and resolves only after a one-second settle period in which nothing the launch created remains and nothing it started runs; after five passes it reports a cleanup error and keeps the launch journal, leases and routes. A daemon request delayed beyond that final scan is not observable to DevFn: a container it creates after `down` reports stopped is outside this guarantee and is not tracked by DevFn.
- `down` stops only the exact worktree instance. Ordinary shutdown removes no persistent Docker volumes.
- `.localhost` remains the default hostname suffix. Other development domains require explicit machine registration for the repository and project; a repository manifest cannot register one. Each selected alias must resolve only to loopback, and registration does not change DNS, a hosts file, or the OS resolver. Public routing needs separate validation.
- DevFn manages only a Caddy process it started itself and refuses to overwrite an unrelated Caddy admin endpoint. Internal TLS uses Caddy's local CA without installing its trust root; clients must trust that CA explicitly. Explicit certificate mode requires a valid matching key and a DNS subjectAltName covering every selected alias before proxy reload. DNS-01 is unavailable until a validated adapter exists and is rejected rather than configured implicitly.
- Caddy listeners and ports:
  - Listener binding: Caddy binds only to available 127.0.0.1 and ::1 loopback interfaces. Registered DNS answers for other loopback addresses are rejected because Caddy does not bind them. If an external process occupies a listener, proxy startup fails rather than binding a public interface. DevFn runs the Caddy found in an absolute `PATH` directory, never one in a relative entry such as `.`, and validates, reloads and runs a configuration with that same binary.
  - Platform ports: on macOS, an unprivileged process cannot bind loopback port 80 or 443, so DevFn uses HTTP 8080 and HTTPS 8443 and includes those ports in published URLs and redirects. Linux uses 80 and 443, so its URLs omit the port; binding them requires `net.ipv4.ip_unprivileged_port_start` at or below 80 or `cap_net_bind_service` on the Caddy binary. DevFn does not change system permissions.
  - Owner verification: a setcap Caddy hides its sockets from same-user inspection, so DevFn verifies it by PID start identity and by comparing its live admin configuration with the committed one.
  - Claim retirement: a listener claim left by an expired, interrupted, or failed lifecycle is retired only after the instance has no committed or pending routes, TCP connections are refused and both TCP and UDP binds succeed on 127.0.0.1 and ::1, and a live owner's configuration excludes the port. A refused connection alone proves nothing, because a firewall rule can refuse connections to a listening port. A denied privileged bind can be cleared only when a verified owner's configuration excludes the port; any other bind failure keeps the claim.
  - `devfn ports gc`: removes proxy routes only for instances with no running command whose recorded process and container owners, including those of failed or interrupted invocations, are all verified dead; a live PID whose start identity cannot be read, lease age and occupied ports are not evidence.
  - Failed start and activation: activation succeeds only after Caddy confirms that every listener started. A failed Caddy start returns only after the Caddy DevFn spawned has exited; if it cannot be stopped, its owner record, when one was written, is kept, the error names its PID, and the failed lifecycle keeps its listener claim until the listener is proven gone. A failed or timed-out reload, or a spawned Caddy that does not exit, is never taken as proof that Caddy kept its previous routes: Caddy may already serve the candidate. Its activation journal stays, marked uncertain, and every reader of pending route state counts its routes as possibly live until a reload of the committed routes succeeds. After a failed reload, that reload is tried at once and by the next routing command; a spawned Caddy that does not exit is rolled back by the next routing command. Neither replays the activation, and a route preflight first rolls a marked journal back the same way, so a rejected activation never blocks another owner's routes once Caddy reloads. The journal is marked before it is published and before Caddy reloads or starts, so this holds even when nothing can be written after the failure, and an interrupted activation is rolled back too; only an unmarked journal, such as one an earlier release left, is replayed. Like every transition, it leaves out routes of services verified gone, which own no route ID or hostname for a transition or its preflight, and only the routes Caddy confirmed are committed; a recovered journal is likewise never rewritten before Caddy confirms it. While it fails, commands that change routes fail rather than treat the routes as gone. A lifecycle that no route state names changes no routes: its teardown never touches Caddy or another owner's journal, so it is not held by that journal. A lock left by a routing operation whose holder is verified dead is recovered after one minute, within the three minutes a waiting command allows. Locks are taken by creating their directory, which never replaces an existing lock, including one an earlier release is creating; its owner record is then added without replacing another holder's, and a holder removes only a lock recording itself. A stale lock is taken over in place, never removed first, and once a holder is recorded its owner record is never missing, so neither a new command nor a creator that has not yet recorded itself can take the lock meanwhile. Only one command at a time takes over a given dead holder's record, and only while it is still the record judged dead; a command killed mid-takeover is superseded once it is verified dead, however many were killed before it, within the waiting command's budget. An owner record or takeover marker that cannot be read, or is not a well-formed DevFn owner record, counts as a live command's and needs manual removal once no DevFn command runs. Earlier releases do not follow this rule and still move a stale lock aside to recover it, so one acting on an outdated judgment can hold the lock alongside a command of this release, as two earlier releases already can; stop older DevFn commands before relying on stale-lock recovery. A lock without an owner record, left by a creator killed before recording itself, is taken only after five minutes, the time earlier releases also wait for its creator to record itself.
  - Claims and migration: a profile with selected proxy routes claims both listener ports before service startup; existing sibling TCP or UDP leases on either port block that activation. While a proxy claim is active, other DevFn profiles cannot lease those ports. A TCP port that another instance's committed or pending route targets cannot be leased for TCP by any other instance, including one that already holds it, until that route is replaced or removed. To migrate an existing v0.1 service on a listener port, stop its profile, change its exact or preferred service port in the manifest, and restart it before enabling proxy routes. DevFn reports the owning instance and service, leaves the existing profile running, and does not move a lease automatically. Without an active proxy claim, a profile without proxy routes keeps its v0.1 exact, preferred, and stable port behavior.
  - Certificate snapshots: activated explicit certificates are copied into owner-only machine state so an unrelated worktree can stop after the source certificate disappears; replace the source and reactivate the affected route to update it. A failed replacement restores the prior routes with the snapshots they were served with, not the current source files, and reports a failed restore instead of claiming the routes were kept. A replacement killed before the prior teardown loses that rollback copy: the prior lifecycle reports `degraded`, `devfn down` removes this worktree's routes, and the next `up` revalidates the certificate source files.
- Volume deletion, database reset, and other destructive operations are outside ordinary lifecycle commands and require separate explicit tooling and confirmation. Public tunnel routes are published only by a lifecycle start with `--allow-public` and withdrawn by `devfn down`, `devfn ports gc` and `devfn tunnel recover`.
