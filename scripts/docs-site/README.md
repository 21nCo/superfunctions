# Shared DocsFn site runtime

The new per-function sites supply their config and Vite raw-content globs to `createDocsSiteRuntime`. Each factory call owns its own manifest/search/compiled-content cache. Keep this module server-only; layout loaders return only site/navigation metadata, and search is loaded from `/docs/search.json` when needed.

`Search.svelte` uses DocsFn's search runtime with a native modal dialog. It supports the visible trigger, Ctrl/Cmd+K, Escape, keyboard-focusable result links, loading state, and errors without the published UI dialog's SSR limitation.

Each site resolves the shared module's DocsFn imports through the scoped Vite resolver so it uses the versions pinned by that site. In a workspace checkout, build the affected site from the repository root with `npm exec -- turbo run build --filter=<consumer-package>` so its `^build` prerequisites are prepared; `npm run build` in `<function>/docs` alone is enough only for a standalone install. After changing shared code, build all consumers and verify desktop search (including a result navigation and Escape) plus the mobile Menu drawer. Keep the responsive open-drawer override when using the current published theme.

Each new-site PR includes this shared directory at the same repository path so it can land independently. All factory wrappers reference this one canonical directory. After merge, edit it directly rather than duplicating provider logic in individual sites.

Only sites whose factory wrappers import this directory consume this runtime. Check those imports when planning cross-site validation.

Bundled files have no reliable filesystem modification time; the provider omits `updatedAt` instead of inventing one. YAML frontmatter uses the same gray-matter parser as the filesystem provider. Front matter is YAML-only: `front-matter.mjs` rejects every engine label other than the bare `---` delimiter, `yaml` or `yml` before gray-matter runs (both the whole opener line and the label gray-matter dispatches from it) (its `js` engine evaluates code), in both the bundled runtime and the LLM prebuild. The prebuild wraps the published filesystem provider: each listing copies every Markdown collection it is about to read (resolved from the same canonical configuration the provider receives, with the same default directories and missing-directory rules), each from its own source directory alone, into its own tree in a private temporary snapshot, checks those exact bytes, lets the provider parse only the snapshot and removes it afterwards, so a source edit after the check cannot reach the parser. Before the provider runs, the wrapper checks the final configuration it hands over: the root and every docs, pages and blog directory must resolve inside that snapshot, otherwise the build fails closed; under a missing content root each configured Markdown directory is replaced by a missing directory inside the snapshot, so the provider still reports the missing root and never sees a live source directory. Entries and diagnostics keep their source paths, in the native or forward-slash form the provider reports, so path-based rules such as `DOCSFN_HTML_UNSAFE_ALLOWLIST` still apply. The snapshot is staged in the real path of the temporary directory (`TMPDIR`, or `TEMP`/`TMP` on Windows), resolved once, so a relative value or one that leaves through a symbolic link and `..` is checked and used as the same directory. On POSIX the build refuses a temporary directory whose real path contains a backslash, and the final check rejects a snapshot root or Markdown directory containing one: the provider lists files with fast-glob, which rewrites every backslash to a path separator, so it would silently read a different (sibling) path; point `TMPDIR` at a directory without one. For the same reason it fails closed when any file or directory name in a docs, pages, blog, API or assets directory contains a backslash, naming the source path; rename it. After listing, every docs, pages and blog entry the provider returns must be one of the snapshotted, checked files, otherwise the build fails. The build refuses to run when that directory lies inside a docs, pages, blog, API or assets directory, because a staging tree there would be listed as content; point it elsewhere. It also refuses to run when any of those directories contains a `docs-llms-snapshot-*` staging tree left by an interrupted or concurrent build, instead of listing it; remove the leftover tree. Binary static files stay in SvelteKit’s static passthrough.

Search-enabled consumers declare the published Core's `@searchfn/client` peer. In a workspace checkout, run `npm exec -- turbo run build --filter=<consumer-package>` from the repository root before direct `npm test` or native checks: `^build` prepares the physically imported SearchFn workspaces as well as the consumer's other declared prerequisites. A standalone install resolves published packages, whose dist files are already present. Do not substitute a root SDK pin or mocked search implementation.

Run `npm test` in a new-site workspace to check generated LLM files and the shared provider/cache contracts. Initialization failures are retryable; concurrent successful requests reuse one cache.
