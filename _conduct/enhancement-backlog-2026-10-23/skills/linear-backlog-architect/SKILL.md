# Linear Backlog Architect

Shape a product outcome or an existing Linear backlog into executable, reviewable issues for an agent implementation loop. Use this skill when asked to decompose a feature, audit issue scope, sequence sub-issues, or prepare issues for automated delivery. For an idea that only needs durable capture and product/architecture documents, use `21n/add-to-backlog` instead.

## Modes and authority

- **Plan or audit:** read the relevant repository, architecture, issue descriptions/discussion, existing backlog, and loop configuration. Return a proposed issue tree, dependency graph, and readiness findings without changing Linear or the execution queue.
- **Publish:** when the user has asked to create or revise issues, make the approved outcome concrete in Linear. This request authorizes the corresponding issue, document, and relation writes; do not ask again for routine details that are supported by the project context. If the destination or a product decision needed to write truthful acceptance criteria remains ambiguous, ask only about that decision.
- **Queue:** update a delivery loop's ordered issue/dependency configuration only when the user has also authorized adding this work to that loop. Publishing issues does not itself start implementation, dispatch cards, merge PRs, or mark issues Done.

Use Composio CLI for all Linear reads and writes in the `21n` workspace, with the configured account when selecting Linear tools. Before issue creation or document association, retrieve the published `21n/create-and-associate-linear-issue@1.0.0` skill and follow its destination, duplicate, partial-write, and read-back rules. Use the relevant Linear relation tools for parent/child and blocked-by links, then read them back. After an ambiguous write response, inspect Linear before retrying; never create a second issue to repair an uncertain first write.

## Build the delivery shape

1. Establish the outcome, current architecture and repository boundaries, decisions already made, and evidence that will establish completion. Distinguish facts, proposals, assumptions, and unresolved product choices. Preserve existing issue IDs, discussion, links, and any active PR scope.
2. Use a parent issue for the outcome when several PR-sized pieces belong together. The parent describes the integrated result and completion gate; executable children describe one coherent behavior or invariant each. Do not dispatch an umbrella issue as if it were another implementation slice. For a genuinely single-PR outcome, one issue is enough.
3. Split where pieces have different behavior, subsystem ownership, validation, release risk, or review context. Keep a tightly coupled invariant together when splitting would leave an invalid intermediate state. Do not split by arbitrary file counts, and do not create bookkeeping children that cannot be independently verified. Apply a size budget: an executable issue should land as a PR of about 1,500 changed non-test lines and about 3,000 changed lines including tests, across at most two subsystems. Count generated schemas, golden or snapshot fixtures, and lockfile churn as non-test lines: the loop's splitter does, and reviewers read them. When they dominate an issue, give the generator or fixture set its own issue. Record the estimate (non-test lines, total lines, subsystems) in each readiness note. Give native or platform-specific code (launchd, Windows, C helpers), storage migrations, and each concurrency, ownership, or security invariant (locks and claims, single-use tokens, OAuth state, credential handling) their own issues unless they are inseparable from one atomic invariant; these attract repeated review findings and stall review loops when bundled. An issue over budget is `needs split` unless its readiness note justifies it as one atomic invariant. For an issue within 20% of the budget, include an ordered fallback slice outline (paths and acceptance items per slice) so the loop's splitter has a plan ready if review stalls.
4. For every executable issue, write a compact contract: user/system trigger and expected behavior; scope and explicit exclusions; owned boundary, owned files or directories, and relevant interfaces/invariants; concrete acceptance checks with observable evidence; verification surface (unit, integration, UI, CI, external/manual); the platforms and runtimes its tests must run on (a test that skips a platform CI runs is reported as a coverage defect, so list any deliberate skip as an exclusion); dependencies; and any migration, rollback, or rollout gate that actually applies. Write every product or policy default the change implies as a decision in the issue, for example who may call a route, how a forged or missing caller is treated, or whether a deprecated alias stays. Review otherwise raises each one as an owner question mid-loop. Name a deferred manual acceptance issue explicitly rather than treating unrun manual testing as proof.
5. Draw a directed acyclic graph of **real prerequisites**. Use Linear blocked-by relations for required ordering; parent/child links are hierarchy, not dependency. Distinguish a preferred execution order from a blocker. Parallel children need stable shared interfaces, compatible base branches, disjoint owned files, and a stated integration point; issues that edit the same hot files run in sequence so an open PR is not left conflicting with a moving base. If stacked PRs are necessary, identify the base and the merge/rebase sequence.
6. Carry cross-cutting requirements into each affected child's acceptance criteria and, where needed, a final integrated acceptance issue. Do not put all implementation into one broad cross-cutting ticket.

## Defer external acceptance to the end

A loop card that needs a live credential, account, sandbox, device, or deployed environment parks until a person supplies it, and blocks every later issue behind it. Shape the backlog so that implementation never waits on external access:

1. **Implementation issues accept on code contracts only.** Their acceptance evidence is what the loop can produce unattended: unit, integration and contract tests, fixtures, fakes or recorded responses, local services, and CI. Each one names the trailing acceptance issue that owns its live checks in one sentence the convergence evaluator can quote verbatim, for example: "Screen-reader verification is deferred to SKI-31 and is not claimed by this issue." Without that sentence, a missing live check is reported as a verification gap that holds the PR. Do not write "verify against the real provider" into an implementation issue.
2. **Trailing acceptance issues, one per external boundary.** After every implementation issue, add one acceptance issue per independently provisioned boundary: a provider sandbox, a hosting or database environment, an authenticated browser journey, a platform or host (for example Windows), assistive technology (a screen-reader session such as VoiceOver or NVDA), manual or visual review, an owner sign-off, a recovery/rollback drill. Each lists its concrete checks, the implementation issues it covers (blocked-by each of them), and the disposable-resource cleanup it must prove. A boundary closes as soon as its own access exists; one missing credential must not hold every other live check. Add a final integrated acceptance issue only for checks that genuinely span boundaries, blocked-by the per-boundary issues.
3. **Owner provisioning issue.** List every nonproduction credential, account, sandbox, device, or allow-listed scope the acceptance issues need in one issue assigned to the owner: what each item is, which account or workspace it belongs to, where it must be registered (Composio alias, ignored local settings, provider console), and how the loop proves it is usable with a read-only probe. Make each acceptance issue blocked-by the provisioning items it needs. The provisioning issue is never queued for the implementation loop.
4. **Queue configuration.** For the shared loop, map each implementation issue's deferred live checks to its acceptance issue in the project's `externalAcceptance` configuration (`requiredByIssue`, `resourcesRequiredByIssue`, `deferredLiveAcceptanceByIssue` or the project's equivalent) at queue time, rather than waiting for an owner exception after a card stalls. Queue an acceptance issue only once its provisioning items are verified, unless the user asks to queue it now.
5. **Mid-flight discovery.** If an implementation issue already in review turns out to need external access, propose moving those checks to a new or existing trailing acceptance issue (with its provisioning item) instead of holding the PR, and record it as a scope amendment on the issue.

## Beta builds for owner acceptance

When a parent delivers something the owner installs, such as a macOS app or an npm package or CLI, and the repository has a beta pipeline (for Subset, the **Beta builds** workflow), shape the end of the backlog around one beta handoff per completed delivery, not a beta per merge:

1. **Owner beta acceptance issue.** Make the owner-run acceptance issue that installs the build blocked-by every implementation issue of the parent. Give it a `## Beta targets` section naming each target as the pipeline spells it (for example `macos/breaks` or `npm/usage`). Also give it a `## What to verify` section: short numbered steps the owner performs on the installed beta, each with the observable result that passes it. Write the steps for a person, not a test runner; they become the "what to verify" list of the handoff message. Provisioning, assistive-technology and other boundaries keep their own issues as above.
2. **Version.** The pipeline builds no beta of a target whose version is already released live. Put the version bump in the first implementation issue that changes the target, and say so in its scope.
3. **Queue configuration.** For the shared Hermes loop, add `betaHandoff` to the project config at queue time. It holds:
   - the targets, each with its dev landing page, and the package name for npm targets;
   - `ownerAcceptanceIssues`: the owner beta acceptance issue and the other owner-run acceptance issues;
   - the owner's Slack destination: by default `#out-queue` in the 21n workspace (channel `C0CB0D1EWKA`, Composio account `21n`).

   When every ordered issue is complete, the loop's `beta-handoff.mjs` builds the betas from the base branch and verifies them. It then posts the summary, download links, what to verify and what is pending to that channel and to the parent issue. Do not queue the owner acceptance issues for implementation.
4. **One handoff per delivery.** Put the parent's implementation issues in one project order so the handoff fires once, when the feature is complete. Issues appended later, such as a fix round after owner testing, get their own handoff when they complete. Do not ask the loop for intermediate betas.

## Bound heuristic acceptance

Detection, redaction, parsing, sanitizing, matching or validating untrusted or free-form input has no natural end: each review round finds another form. An issue that says "detects credentials" or "handles all inputs" can loop indefinitely. For such an issue, the acceptance evidence names a closed set:

- the exact forms or grammar covered, with one test vector per form;
- the adversarial or performance bounds (for example linear time on the listed inputs);
- explicit non-goals for forms outside the set.

A review finding outside the closed set is not a blocker for that issue: the loop records it in the hardening follow-up issue the parent names (see "Base and follow-up hygiene"). If the closed set cannot be agreed before dispatch, the issue is `needs decision`.

## Base and follow-up hygiene

1. **Base health.** Before queueing, confirm the target base branch is green: CI passes, no test is flaky or close to its timeout, every required check actually runs (code analysis quotas, secrets, runners), and the repository has what CI needs. Otherwise add a small "stabilize base" issue first and make the queued issues blocked-by it. Never fold a pre-existing base failure into a feature issue.
2. **Follow-up bucket.** Each parent has one Backlog issue, "<parent> review follow-ups", linked to the parent. The loop defers minor review findings and out-of-set heuristic findings there instead of holding a PR or creating one issue per finding. It is never queued automatically.

## Prerequisite capability check

For every adapter, provider, service, schema, or shared module that an issue's scope relies on, confirm that it already exists on the target base branch or is delivered by an earlier issue in the DAG. Otherwise mark the issue `needs decision` and state the options (add a prerequisite issue, defer that part to a later issue, or narrow the scope). Settle these before queueing; a decision discovered during review costs whole review cycles.

## Readiness decision

Before publishing or queueing, assess every executable issue for: a bounded, coherent PR outcome within the size budget; known prerequisite contract and a passed prerequisite capability check; observable acceptance evidence that the loop can produce without live external access; live checks deferred to named trailing acceptance issues; heuristic work bounded by a closed acceptance set; product defaults written as decisions; a green base branch; no unresolved decision that would change the implementation contract; and compatibility with the current repository and loop. An acceptance issue is `ready` only when its provisioning items are verified; otherwise mark it `needs access` with the missing items. Mark it `ready`, `needs decision`, or `needs split`, with the reason. A parent outcome is `container`, not an executable `ready` issue. A large issue may be ready if it is one atomic invariant and the reviewer can assess it as one change.

Return an ordered table with proposed or existing issue IDs, parent, outcome, dependencies, parallelism, size estimate, readiness, verification, and the acceptance issue owning its live checks; then the owner provisioning list and, for an installable deliverable, the beta targets and `betaHandoff` settings. Include the smallest useful issue descriptions, a dependency DAG, and any decision required from the user. For an existing backlog, propose changes only to unstarted issues by default; report active PR work separately rather than rewriting its acceptance contract mid-review.

## Publishing and verification

Search the chosen project/team for equivalent issues first. Preserve a supplied existing issue and its discussion; if a likely duplicate is found for a new issue, resolve reuse versus distinct creation with the user as the shared Linear skill requires. Create or amend only the issues in scope, then add parent/child and blocked-by relations. Confirm each issue's ID, URL, team, project, state, description, parent, dependencies, and required links by reading Linear back. Check the team setting for parent/sub-issue auto-close before relying on a manual completion gate; if auto-close could mark a parent Done without the owner's go, report that conflict and do not claim the gate is protected.

For the shared Hermes Linear loop (`thyaravind/automations`, `projects/<id>.json`), queue only executable ready issues, keep the existing config's order/dependency conventions, run its config and focused tests, and dry-run the coordinator. Preserve existing dirty work and active cards. Do not start the coordinator or dispatch new work unless that action was requested. Report the published IDs, verified relations, queue changes, tests, and any remaining unverified external behavior.

## Split mode

The loop's splitter may invoke this skill with a frozen reference branch, the original issue and a checkpoint `splitPlan`. Then: keep the original issue as the `container` parent and preserve its discussion; create one executable child per slice in plan order, each with `## Outcome`, `## Scope` (the reference-branch paths it ports), `## Acceptance evidence` (the original issue's acceptance items that slice owns, plus the inherited open families by ID), `## Verification` (builds and tests alone on the base; its diff contains only reference-branch code plus minimal glue, checked by the loop's slice-subset verifier) and `## Dependencies` (the previous slice). Link each child blocked-by its predecessor, read everything back, and return the child IDs in order. Do not change the frozen PR, its ledger or its branch.
