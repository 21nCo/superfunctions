`@superfunctions/oauth-flow` is the high-level orchestration package for teams that want a complete OAuth lifecycle instead of assembling every lower-level piece manually. It wraps the hardest parts of the flow into one service: starting an install, validating the callback, persisting tokens, refreshing connections, disconnecting providers, and emitting lifecycle events. That makes it the fastest path from “we need OAuth in our app” to a working integration surface.

For external application teams, this package is often the right default because it keeps the flow logic in one place while still letting you choose providers, storage, hooks, and HTTP transport. For library authors or platform teams with unusual orchestration needs, it also serves as a reference implementation for how the lower-level packages fit together.

## What It Is

`@superfunctions/oauth-flow` exports `createOAuthFlowService()` together with the types used by the resulting service. The service supports `start()`, `handleCallback()`, `refresh()`, and `disconnect()`. Internally it composes [`oauth-core`](/docs/authentication/oauth-core) for state and callback invariants, [`oauth-http`](/docs/authentication/oauth-http) for token transport, and [`oauth-storage`](/docs/authentication/oauth-storage) for state and token persistence.

## When To Use It

Use this package when your application needs a real OAuth installation lifecycle and you want sensible defaults without losing important hooks. It is a good fit for SaaS integrations, marketplace installs, developer portals that connect customer accounts to providers, and any service that needs refresh-token maintenance or disconnect cleanup. If you only need authentication at request time, `@superfunctions/auth` is enough. If you need custom orchestration around a lower-level policy engine, the `oauth-core` path gives you more control.

## Install

```bash
npm install @superfunctions/oauth-flow @superfunctions/oauth-providers @superfunctions/oauth-storage
```

## Quick Start

The quickest setup is to provide one or more provider descriptors, runtime secrets, and storage adapters.

```ts
import { createOAuthFlowService } from "@superfunctions/oauth-flow";
import { getOAuthProviderDescriptor } from "@superfunctions/oauth-providers";
import {
  MemoryOAuthStateStore,
  MemoryTokenVault,
} from "@superfunctions/oauth-storage";

const flow = createOAuthFlowService({
  providers: {
    github: getOAuthProviderDescriptor("github"),
  },
  providerRuntimeConfig: {
    github: {
      clientId: process.env.GITHUB_CLIENT_ID!,
      clientSecret: process.env.GITHUB_CLIENT_SECRET!,
      allowlistedRedirectUris: ["https://app.example/oauth/github/callback"],
    },
  },
  stateStore: new MemoryOAuthStateStore(),
  tokenVault: new MemoryTokenVault(),
});
```

From there, your app can start an install and later complete the callback with the same service.

```ts
const started = await flow.start({
  providerId: "github",
  tenantId: "tenant_1",
  userId: "user_1",
  connectionId: "github-primary",
  redirectUri: "https://app.example/oauth/github/callback",
});

const connected = await flow.handleCallback({
  code: "oauth-code",
  state: started.stateId,
  redirectUri: "https://app.example/oauth/github/callback",
});
```

## Core Concepts

The package draws a clear line between subject identity, provider configuration, and token persistence. `start()` captures the subject (`tenantId`, `userId`, optional `connectionId`) together with the provider choice and redirect URI. `handleCallback()` consumes the stored state, exchanges the authorization code, and writes the resulting token record. `refresh()` and `disconnect()` then operate on that connection-centric token record over time.

The second concept is hooks and events. Identity hooks let your application react when a connection is created or removed, while emitted events provide a stable stream of lifecycle outcomes such as `oauth.flow.started` and `oauth.flow.refresh.failed`. That makes the package useful beyond a single web request: the same service can feed analytics, auditing, or support tooling.

## Real-World Example

An application that offers customer-managed provider connections usually needs a full lifecycle: launch install, persist the connection, refresh the token in the background, and let users disconnect later. `@superfunctions/oauth-flow` is designed for exactly that surface.

```ts
import { createOAuthFlowService } from "@superfunctions/oauth-flow";
import { getOAuthProviderDescriptor } from "@superfunctions/oauth-providers";
import {
  MemoryOAuthStateStore,
  MemoryTokenVault,
} from "@superfunctions/oauth-storage";

const flow = createOAuthFlowService({
  providers: { github: getOAuthProviderDescriptor("github") },
  providerRuntimeConfig: {
    github: {
      clientId: process.env.GITHUB_CLIENT_ID!,
      clientSecret: process.env.GITHUB_CLIENT_SECRET!,
      allowlistedRedirectUris: ["https://app.example/oauth/github/callback"],
    },
  },
  stateStore: new MemoryOAuthStateStore(),
  tokenVault: new MemoryTokenVault(),
  identityHooks: {
    async onConnected(result) {
      console.log("connected", result.connectionId, result.providerId);
    },
    async onDisconnected(input) {
      console.log("disconnected", input.connectionId);
    },
  },
});

await flow.refresh({
  connectionId: "github-primary",
  providerId: "github",
  redirectUri: "https://app.example/oauth/github/callback",
});

await flow.disconnect({
  connectionId: "github-primary",
  providerId: "github",
  revokeRemote: true,
});
```

That example shows why `oauth-flow` is the high-level path in this category: your application code coordinates business events and HTTP routes, while the package handles replay protection, token merging during refresh, revocation attempts, and cleanup flags.

## Troubleshooting

If `start()` fails before producing an authorization URL, inspect the configured provider ID and redirect allowlist before you look at token transport. If `handleCallback()` reports a replay or mismatch error, verify that the callback request used the same redirect URI and state issued by `start()`. If refresh fails but the old token record should remain valid, check your application’s error handling rather than assuming the token was overwritten; the service is designed to keep the prior record intact when refresh exchange fails.
