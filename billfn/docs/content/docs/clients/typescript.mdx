title: TypeScript
description: Use the typed HTTP client for browser or server-side consumers.
---

`@billfn/client` wraps the HTTP routes with a typed transport surface and keeps the server’s envelope shape intact.

## Install

```bash
npm install @billfn/client
```

## Create a Client

```ts
import { createBillFnClient } from "@billfn/client";

const client = createBillFnClient({
  baseUrl: "https://billing.example.com/billfn",
});
```

The default `baseUrl` is `/billfn`.
The default `credentials` mode is `"include"`.

## Example: Create a Checkout

```ts
const response = await client.createCheckout({
  planKey: "pro",
  provider: "dodo",
  interval: "month",
});

if (response.ok) {
  const checkoutUrl = response.data.checkoutSession.checkoutUrl;
  if (checkoutUrl) {
    window.location.href = checkoutUrl;
  }
}
```

The server decides who the checkout is for through its `auth.resolveSubject`
(the client sends the browser's cookies by default). A `subject` field is used
only by a server that sets `auth.allowClientSubject` for trusted callers.

A server that checks a CSRF header on writes (as in
[Server setup](/docs/server/setup#recommended-production-wiring)) needs the
client to send it. Pass a `fetch` that adds the header:

```ts
const client = createBillFnClient({
  fetch: (input, init) =>
    fetch(input, {
      ...init,
      headers: { ...(init?.headers as Record<string, string> | undefined), "x-csrf-token": readCsrfToken() },
    }),
});
```

`readCsrfToken` stands for however your app exposes its CSRF token to the
page (a meta tag or a readable cookie), and the header name must match the
server's check.

Without `priceId`, checkout uses the plan's first price for the provider and
interval that has no `eligibility` tag. To sell another catalog price of the
plan, such as an introductory discount, pass its `priceId`:

```ts
await client.createCheckout({
  planKey: "pro",
  provider: "dodo",
  interval: "month",
  priceId: "price_pro_dodo_month_intro",
});
```

The server sells only catalog prices and never reads an amount from the
request. A `priceId` that is not a price of the plan for that provider (and
interval, when given) fails with `400 BILLFN_VALIDATION_ERROR`. A price with an
`eligibility` tag that the host does not approve for the account fails with
`403 BILLFN_PRICE_NOT_ELIGIBLE`; see
[Server setup](/docs/server/setup#discounted-prices).

## Available Methods

- `getCatalog()`
- `getEntitlements(query?)`
- `getUsage(query?)`
- `createCheckout(input)`
- `verifyCheckout(input)`
- `cancelSubscription(input)`
- `changeSubscription(input)`
- `resumeSubscription(input)`
- `refundCharge(input)` (the server answers 403 unless its `refunds.authorize` hook approves the request)
- `syncSubscription(input)`
- `restorePurchases(input)`
- `enqueueReconciliationJob(input)`
- `getReconciliationJob(jobId)`
- `runReconciliationJob(jobId)`

## Error Handling

The client returns the same envelope shape as the server:

```ts
if (!response.ok) {
  console.error(response.error.code, response.error.message);
}
```

That makes it easier to surface provider or validation errors without losing metadata such as `status` and `retryable`.

The HTTP client also synthesizes a few transport-level envelopes when no valid BillFn response is available:

- `BILLFN_NETWORK_ERROR`
- `BILLFN_EMPTY_RESPONSE`
- `BILLFN_INVALID_RESPONSE`
