---
title: Lifecycle events
description: Deliver entitlement, checkout, renewal, cancellation and grant events to host handlers through a durable outbox.
---

BillFn emits lifecycle events for plan emails and session updates. Each event is stored in the `lifecycleEvents` outbox before it is delivered, and it is delivered **at least once** to the `onEvent` handler. Every delivery of an event carries the same `id`, so deduplicate by it.

```ts
import { createBillFn } from "@billfn/core";

const billfn = createBillFn({
  db,
  catalog,
  providers,
  async onEvent(event) {
    if (await processedEvents.has(event.id)) return;
    switch (event.type) {
      case "checkout.completed":
        await mail.sendWelcome(event.billingAccountId, event.data.planKey);
        break;
      case "entitlement.changed":
        await sessions.refreshEntitlements(event.billingAccountId);
        break;
    }
    await processedEvents.add(event.id);
  },
});
```

Without `onEvent`, BillFn records no events. Configure the handler in every process that writes billing state (the server that mounts the router, webhook ingestion and the reconciliation worker); an event is recorded only by a process that has a handler.

## Events

| Type | When | `data` |
| --- | --- | --- |
| `entitlement.changed` | A subscription write changes the account's paid plan, status, features or limits; a grant starts or is revoked; a grant expired (from the `lifecycle-events` job) | `cause` (`subscription`, `grant.started`, `grant.revoked`, `grant.expired`), `planKey`, `status`, `subscriptionId` or `grantId`; for a subscription, `features`, `limits`, `previousPlanKey` and `previousStatus` |
| `checkout.completed` | A checkout session moved to succeeded (verification or webhook); once per checkout session. A later write of a succeeded session (a renewal webhook, a restore, a repeated verification) adds none | `checkoutSessionId`, `subscriptionId`, `provider`, `planKey`, `priceId` |
| `subscription.renewed` | An `active` subscription's period end moved later, including a trial converting to a paid period; once per period end | `subscriptionId`, `provider`, `planKey`, `priceId`, `currentPeriodStart`, `currentPeriodEnd`, `previousPeriodEnd` |
| `subscription.canceled` | A subscription that intended to renew (`autoRenew` on, live or held by a payment problem or pause) stopped renewing: canceled now (`status: "canceled"`) or set to end at `currentPeriodEnd` (`autoRenew: false`, as for a Dodo cancel at the next billing date), also during a hold. Reported once: a later hold, resume, expiry or final cancellation adds none. A hold alone (`past_due`, `paused`), `pending`, an expiry or a failure is not a cancellation | `subscriptionId`, `provider`, `planKey`, `priceId`, `status`, `autoRenew`, `currentPeriodEnd` |
| `grant.started` | A trial or comp was granted. A refused second trial or a repeated revoke adds no grant event | `grantId`, `kind`, `planKey`, `startsAt`, `expiresAt` |
| `grant.expiring` | A grant that is not revoked expires within 3 days: from the `lifecycle-events` job, or with the grant's creation when it already expires within 3 days; once per grant | `grantId`, `kind`, `planKey`, `expiresAt` |

Every event also has `billingAccountId`, `occurredAt` and `attempt` (the delivery attempt, from 1).

`entitlement.changed` describes the source that changed. A paid subscription that is not `inactive` supersedes a grant, so a grant event can leave the account's effective entitlements unchanged; read `getEntitlements` (or `subscriptionProvider.getEntitlementSnapshot`) for the current state rather than applying the payload.

## Delivery

- **After the call.** The service call that records an event (a checkout verification, webhook, cancel, sync, grant create, entitlements read, `subscriptionProvider` or `quotaProvider` read, job run, and so on) delivers it once the call settles. A handler failure never fails that call, and the call waits for the delivery at most 10 seconds: a slower handler finishes in the background, and an event it does not finish is delivered again after its claim lapses.
- **Retries.** A handler that throws, or does not settle within 5 minutes, is retried with exponential backoff (30 seconds, doubling, at most an hour) until 24 hours after the event was recorded (for a staged event, after it was made `pending`). A failure after that marks the event `failed`. A delivery that never completed (its dispatcher stopped mid-delivery, for example at a Workers time limit) counts as a failed attempt once its claim lapses: it is retried after that attempt's backoff, and once the 24 hours have passed the next dispatch marks the event `failed` with `lastError` "delivery did not complete" instead of calling the handler again. Once an event was attempted, no handler is called at or after the 24-hour mark: a retry backs off to at most that mark, and the dispatch of an event due then marks it `failed`, keeping its last error. An event never attempted (its process stopped before the first dispatch) gets one attempt whenever the next dispatch runs, and is marked `failed` if that attempt fails.
- **Due events.** `billfn.services.events.dispatch({ limit })` delivers due events, oldest due first (default 100). The `lifecycle-events` reconciliation job also does this; schedule it every few minutes so retries run.
- **Racing dispatchers.** A dispatcher claims an event with a compare-and-set before calling the handler, so of two dispatchers racing on an event one delivers it.
- **Crashes.** An event commits before any delivery, so a process that stops after the commit leaves it pending for the next dispatch. A claim lasts 5 minutes: an event whose dispatcher stopped mid-delivery is delivered again, with the same `id`, after the claim lapses and its backoff passed. A handler that runs longer than 5 minutes counts as failed and can be delivered again while it still runs.

A handler's side effects should therefore be idempotent per `event.id`; BillFn does not deduplicate them for you.

## Operations

`billfn.services.events.list({ status, billingAccountId, limit })` lists outbox events, newest first. `status: "failed"` lists the events that ran out of retries, with `attempts`, `lastError` and `failedAt`. BillFn also tracks the metrics `billfn.event.recorded`, `billfn.event.delivered`, `billfn.event.retry_scheduled`, `billfn.event.failed` and `billfn.event.dropped` (tagged with the event type), and `billfn.event.dispatch_deferred` when the delivery after a call could not reach the outbox. Without transactions, `billfn.event.stage_recovered` and `billfn.event.stage_discarded` count the staged events a dispatch settled (see Consistency), and `billfn.event.stage_unsettled` the applied writes that could not make theirs pending.

## The `lifecycle-events` job

```ts
await billfn.enqueueReconciliationJob({ kind: "lifecycle-events" });
```

Each run first dispatches due events, so no other step can delay delivery or the failed marking. It then records `entitlement.changed` (cause `grant.expired`) for grants that expired in the last 7 days (and were not revoked before they expired) and `grant.expiring` for grants that expire within 3 days, then the missing events of up to 50 grant changes flagged pending (see [Consistency](#consistency)), and then dispatches again, so events these steps record are delivered in the same run (or by the next one if that dispatch stops). A failed sweep or repair is left to the next run; a run that lost its lease ends before its next write.

The work of each run is bounded, and the next run resumes where it stopped:

- **Expiry sweeps.** Each of the two sweeps reads grants in expiry order (then by id) and stores the position after the last page it finished in the `reconciliationCursors` table. A run reads at most 200 grants per sweep, and the next run starts after the stored position, so it never rereads a grant an earlier run finished. A page's events are recorded before the position moves past it, so a run that stops mid-page leaves that page to the next run, which records only the events still missing. When two runs read the same position, the first to move it carries on and the other stops that sweep. A grant created already within 3 days of its expiry records `grant.expiring` with its creation (unless it is revoked by the time that event is recorded), since the sweep may already be past its expiry time. A `grant.expiring` or `entitlement.changed` (cause `grant.expired`) whose grant was revoked before it expired, as when a write races the revoke, is dropped at delivery without calling the handler (`billfn.event.dropped`), also after an attempt that failed or stopped. A grant write that becomes visible only after a position passed its expiry (a slow write, or an instance whose clock is behind) still gets these events once: after moving a position past a page, the sweep reads that page's range again and records grants that appeared since, and a grant created after that sees the moved position when its creation is recorded and records the events itself. The grant stays flagged pending until that check succeeds (with transactions it runs right after the commit), so a check that fails or a process that stops before it is left to the job's repair. Reading a page again is bounded too: at most 200 grants per sweep per run, and a run that stops or runs out while doing it leaves where it stopped to the next run.
- **Grant event repair.** The run reads only the grants flagged pending (the oldest 50), never an account's other grants, and renews its lease before each row it writes (each lifecycle event, each billing event and each flag clear), so a run that lost its lease to another stops before its next write and leaves the rest to that run or a later one.

Both grant events are recorded once per grant, so running the job often is safe. Run it often enough for the sweeps to keep up: each run handles at most 200 grants entering each window, so with more grants than that expiring per interval, run it more often (every few minutes for retries anyway). A grant that expired more than 7 days before the sweep reaches it gets no `entitlement.changed`.

## Consistency

With an adapter that supports transactions, a grant and its lifecycle events commit together; a creation also sets `eventsPending` until its check of the expiry sweeps' positions after the commit succeeds, and the `lifecycle-events` job's repair runs that check for a flagged one. Without transactions, a grant's events are recorded before its billing event, and the grant write sets its `eventsPending` field, which is cleared once the billing events the stored grant derives are recorded (for a revoke, its creation's too). The next grant call or entitlements read for the account, or a `lifecycle-events` job run (which reads the flagged grants, so its work follows the changes that lack events, however long ago they were made), records any that a failed write or a stopped process left out. Their ids derive from the stored grant, so each is recorded once, and a grant change that never applied records none.

Subscription and checkout events are recorded with the write that causes them: `subscription.renewed` and `subscription.canceled` with the subscription write, `entitlement.changed` with the entitlement snapshot write, and `checkout.completed` with the checkout session write. With transactions each write and its events commit together, so a failed event write fails the write and the call, and the retry (a webhook redelivery, sync or reconciliation job) still finds the change and records its events. A process that stops after a write committed leaves its events committed with it. A subscription import's binding reports no `subscription.renewed` or `subscription.canceled` while it is pending: acceptance can still refuse and delete it. Its acceptance reports the plan through `entitlement.changed` when it changes the account's entitlements.

Without transactions the events are first recorded with status `staged`, which no dispatcher delivers. The write then stores their ids in the `lifecycleEventIds` field of the row it writes, in the same single-row update, so the row itself proves that the write applied. That update applies only over the marker the call read. Before a write replaces a marker, it makes the events the marker names `pending`.

- **The write applied.** Its events become `pending` and are delivered, so a handler that reads billing state (such as `getEntitlements`) reads the committed write.
- **Anything else**: the write failed (possibly after it applied, as when a driver error follows a commit), lost a race with another write of the same row, or the process stopped. The events stay `staged`. Once 5 minutes have passed, a dispatch makes each one `pending` if its row (the subscription, the entitlement snapshot or the checkout session) still names it. Otherwise the write may still be on its way (it stalled), so the event stays `staged`, and later dispatches check it again with backoff (5 minutes, growing to an hour). It is deleted only 24 hours after its latest stage. A later write of the row would already have made the events of the marker it replaced pending, so a deleted event is one whose write did not apply within 24 hours. A write that applied therefore delivers its events once, however the call ended, and one that never applied delivers none.

The retry, whether a lost race retried within the call or a webhook redelivery, sync or reconciliation job, records a change that did not apply again. The `id` derives from the change: the provider change for `subscription.canceled`, the period end for `subscription.renewed`, the subscription state and the entitlements replaced for `entitlement.changed`, and the session for `checkout.completed`. For the first three it also derives from the payload, and the `checkout.completed` payload derives from the session's own purchase, so one `id` always names one payload. A write retried over a newer row records the same event, not a second one. Of two writes that race to report one change with different payloads, only the one that applies is delivered, with its own payload: the other stages another `id`, which no row names. A staged event that a failed write left behind is deleted 24 hours later, once a retry under another id applied the change.

## Events after a deploy

Events describe changes, so deploying `onEvent` emits none for existing state: a session that succeeded earlier, a subscription that renewed or was canceled earlier, and a grant whose billing event was recorded earlier report nothing, also when a later write rewrites them. The only events about earlier state are these:

- `grant.expiring` for each grant that is not revoked and expires within 3 days of the first run (spread over several runs when there are more than 200).
- `entitlement.changed` (cause `grant.expired`) for each grant that expired in the 7 days before the first run, also before the deploy.
- Without transactions, an entitlements read or grant call for an account records `grant.started` and its `entitlement.changed` (or a revocation's `entitlement.changed`) for a grant of that account whose billing event was never recorded, whenever the change was made. The job repairs only grants written from the deploy on.
