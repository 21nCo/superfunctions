---
title: Lifecycle events
description: Deliver entitlement, checkout, renewal, cancellation and grant events to host handlers through a durable outbox.
---

BillFn emits lifecycle events for plan emails and session updates. Each event is stored in the `lifecycleEvents` outbox before it is delivered, and it is delivered **at least once** to the `onEvent` handler. Every delivery of an event carries the same `id`, so deduplicate by it.

```ts
import { createBillFn } from "@billfn/core";

const billfn = createBillFn({
  db,
  catalog,
  providers,
  async onEvent(event) {
    if (await processedEvents.has(event.id)) return;
    switch (event.type) {
      case "checkout.completed":
        await mail.sendWelcome(event.billingAccountId, event.data.planKey);
        break;
      case "entitlement.changed":
        await sessions.refreshEntitlements(event.billingAccountId);
        break;
    }
    await processedEvents.add(event.id);
  },
});
```

Without `onEvent`, BillFn records no events. Configure the handler in every process that writes billing state (the server that mounts the router, webhook ingestion and the reconciliation worker); an event is recorded only by a process that has a handler.

## Events

| Type | When | `data` |
| --- | --- | --- |
| `entitlement.changed` | A subscription write changes the account's paid plan, status, features or limits; a grant starts or is revoked; a grant expired (from the `lifecycle-events` job) | `cause` (`subscription`, `grant.started`, `grant.revoked`, `grant.expired`), `planKey`, `status`, `subscriptionId` or `grantId`; for a subscription, `features`, `limits`, `previousPlanKey` and `previousStatus` |
| `checkout.completed` | A checkout session succeeded (verification or webhook); once per checkout session | `checkoutSessionId`, `subscriptionId`, `provider`, `planKey`, `priceId` |
| `subscription.renewed` | An `active` subscription's period end moved later, including a trial converting to a paid period; once per period end | `subscriptionId`, `provider`, `planKey`, `priceId`, `currentPeriodStart`, `currentPeriodEnd`, `previousPeriodEnd` |
| `subscription.canceled` | A renewing subscription stopped renewing: canceled now (`status: "canceled"`) or set to end at `currentPeriodEnd` (`autoRenew: false`, as for a Dodo cancel at the next billing date). An expiry or failure is not a cancellation | `subscriptionId`, `provider`, `planKey`, `priceId`, `status`, `autoRenew`, `currentPeriodEnd` |
| `grant.started` | A trial or comp was granted | `grantId`, `kind`, `planKey`, `startsAt`, `expiresAt` |
| `grant.expiring` | A grant that is not revoked expires within 3 days (from the `lifecycle-events` job); once per grant | `grantId`, `kind`, `planKey`, `expiresAt` |

Every event also has `billingAccountId`, `occurredAt` and `attempt` (the delivery attempt, from 1).

`entitlement.changed` describes the source that changed. A paid subscription that is not `inactive` supersedes a grant, so a grant event can leave the account's effective entitlements unchanged; read `getEntitlements` (or `subscriptionProvider.getEntitlementSnapshot`) for the current state rather than applying the payload.

## Delivery

- **After the call.** The service call that records an event (a checkout verification, webhook, cancel, sync, grant create, entitlements read, `subscriptionProvider` or `quotaProvider` read, job run, and so on) delivers it once the call settles. A handler failure never fails that call, and the call waits for the delivery at most 10 seconds: a slower handler finishes in the background, and an event it does not finish is delivered again after its claim lapses.
- **Retries.** A handler that throws is retried with exponential backoff (30 seconds, doubling, at most an hour) until 24 hours after the event was recorded. A failure after that marks the event `failed`.
- **Due events.** `billfn.services.events.dispatch({ limit })` delivers due events, oldest due first (default 100). The `lifecycle-events` reconciliation job also does this; schedule it every few minutes so retries run.
- **Racing dispatchers.** A dispatcher claims an event with a compare-and-set before calling the handler, so of two dispatchers racing on an event one delivers it.
- **Crashes.** An event commits before any delivery, so a process that stops after the commit leaves it pending for the next dispatch. A claim lasts 5 minutes: an event whose dispatcher stopped mid-delivery is delivered again, with the same `id`, after the claim lapses. A handler that runs longer than 5 minutes can also be delivered again meanwhile.

A handler's side effects should therefore be idempotent per `event.id`; BillFn does not deduplicate them for you.

## Operations

`billfn.services.events.list({ status, billingAccountId, limit })` lists outbox events, newest first. `status: "failed"` lists the events that ran out of retries, with `attempts`, `lastError` and `failedAt`. BillFn also tracks the metrics `billfn.event.recorded`, `billfn.event.delivered`, `billfn.event.retry_scheduled` and `billfn.event.failed` (tagged with the event type), and `billfn.event.dispatch_deferred` when the delivery after a call could not reach the outbox. Without transactions, `billfn.event.stage_recovered` and `billfn.event.stage_discarded` count the staged events a dispatch settled (see Consistency), and `billfn.event.stage_unsettled` the writes that could not settle theirs.

## The `lifecycle-events` job

```ts
await billfn.enqueueReconciliationJob({ kind: "lifecycle-events" });
```

Each run records `grant.expiring` for grants that expire within 3 days, records `entitlement.changed` (cause `grant.expired`) for grants that expired in the last 7 days, and then dispatches due events. Both grant events are recorded once per grant, so running the job often is safe. Run it at least daily; a grant that expired more than 7 days before any run gets no `entitlement.changed`.

## Consistency

With an adapter that supports transactions, a grant and its lifecycle events commit together. Without transactions, a grant's events are recorded before its billing event, and the next grant call or entitlements read for the account records any that a failed write left out.

Subscription and checkout events are recorded with the write that causes them: `subscription.renewed` and `subscription.canceled` with the subscription write, `entitlement.changed` with the entitlement snapshot write, and `checkout.completed` with the checkout session write. With transactions each write and its events commit together, so a failed event write fails the write and the call, and the retry (a webhook redelivery, sync or reconciliation job) still finds the change and records its events. A process that stops after a write committed leaves its events committed with it.

Without transactions the events are first recorded with status `staged`, which no dispatcher delivers, and then the write runs:

- **The write applied.** Its events become `pending` and are delivered, so a handler that reads billing state (such as `getEntitlements`) reads the committed write.
- **The write failed or lost a race** with another write of the same row. Its staged events are deleted and never delivered. The retry, whether a lost race retried within the call or a webhook redelivery, sync or reconciliation job, records the change again. The `id` derives from the change: the provider change for `subscription.canceled`, the period end for `subscription.renewed`, the subscription state and the entitlements replaced and written for `entitlement.changed`, and the session for `checkout.completed`. So a write retried over a newer row records the same event, not a second one.
- **The process stopped** between staging an event and settling it. The event stays `staged`. Once 5 minutes have passed, a dispatch checks it against the stored state and makes it `pending` only if the write applied: the subscription reached the renewed period end or stopped renewing, the snapshot holds the changed entitlements, or the checkout session succeeded. Otherwise it is deleted. A write that stopped after it applied therefore still delivers its event, and one that never applied delivers none.

Because a stopped write is judged by the stored state, a stop combined with another write of the same row before that check can still decide it either way. One example is a cancellation that applied and was resumed within those 5 minutes: its staged event is deleted.
