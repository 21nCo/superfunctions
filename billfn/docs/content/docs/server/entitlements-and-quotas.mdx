description: Use BillFn’s normalized providers to gate features and enforce storage or usage limits.

The most important consumer surface in BillFn is not the raw subscription row. It is the normalized read model:

- `subscriptionProvider`
- `quotaProvider`
- `GET /entitlements`
- `GET /usage`

## Subscription Provider

`subscriptionProvider` gives other functions a stable way to answer feature and plan questions.

```ts
const subscription = await billfn.subscriptionProvider.getActiveSubscription({
  principalId: "user_123",
});

const entitlements = await billfn.subscriptionProvider.getEntitlementSnapshot({
  principalId: "user_123",
});

const canSync = await billfn.subscriptionProvider.hasFeature(
  { principalId: "user_123" },
  "sync",
);
```

## Trials and Comps

`billfn.services.grants` grants a plan's entitlements without payment until an expiry. It is an operator service, not a public route; `@billfn/admin` exposes it as the `grant-entitlement` and `revoke-grant` actions.

```ts
await billfn.services.grants.create({
  billingAccountId: "ba_user_user_123",
  subject: { principalId: "user_123" }, // creates the billing account when missing
  planKey: "nucleus",
  kind: "trial", // or "comp"
  expiresAt: new Date(Date.now() + 14 * 24 * 60 * 60 * 1000).toISOString(),
  operator: { id: "authfn", type: "service" },
});
```

- A trial makes the entitlements `trialing`, a comp `active`, for the grant's plan until `expiresAt`. The snapshot carries `grant: { id, kind, expiresAt }`.
- A billing account gets one trial ever: a second fails with `BILLFN_CONFLICT` and `details.reason` `trial_already_granted`, also after the first expired. A comp is refused (`active_comp_exists`) while another comp of the account is active, also when two comps are created at once; a comp applies before a trial.
- A paid subscription supersedes a grant while its entitlements are not `inactive`. Once it stops entitling the account, an unexpired grant applies again.
- An expired or revoked grant falls back to the account's paid state, or to `inactive` (no features or limits) without one. Expiry is evaluated on every read; nothing needs to run at expiry.
- `billfn.services.grants.revoke({ billingAccountId, grantId })` revokes a comp; a trial cannot be revoked (`BILLFN_VALIDATION_ERROR`, `grant_not_revocable`).
- `GET /entitlements` and `getEntitlements` return the account's `grants`, newest first, as `{ id, kind, planKey, status, startsAt, expiresAt, revokedAt }` with the derived `status` (`active`, `expired` or `revoked`). The operator and reasons are not part of this subject-facing view; they stay on the `billfn.services.grants` results and the billing events.
- Creating and revoking record `billfn.grant.created` and `billfn.grant.revoked` billing events with the operator and reason. Where the database adapter supports transactions, the grant change and its event commit together, so a failed event write leaves no grant change. Without transactions (Drizzle SQLite) the change commits first and is the outcome: the grant stores its operator and reasons, a failed event write is retried once, and the request succeeds. An event still unrecorded is derived from the stored grant and recorded once by the account's next entitlements read (`getEntitlements`, `getUsage`, and the subscription and quota providers' reads) or grant create or revoke, whatever its outcome (also a refused or not-found request, and after the grant has expired or been revoked). Each missing event is written on its own, so one that still fails defers only itself to a later request, and grant statuses are derived after that repair. A read or grant request never fails because a missing event cannot be recorded yet.

## Quota Provider

`quotaProvider` is designed to be consumed by resource-heavy functions such as `filefn`.

```ts
const quota = await billfn.quotaProvider.checkQuota({
  principalId: "user_123",
  requestedBytes: 200,
  resource: "storage",
});

if (!quota.allowed) {
  throw new Error(quota.reason ?? "quota_exceeded");
}

await billfn.quotaProvider.recordUsage({
  principalId: "user_123",
  bytes: 128,
  resource: "storage",
});
```

Phase 1 quota behavior includes:

- negative usage deltas are rejected
- usage meter updates retry instead of doing a naive read-modify-write once
- limits come from the entitlement snapshot’s `limits`

## Why This Matters

If every consumer reaches straight into `subscriptions`, billing logic will drift across the codebase. By keeping integration points at the entitlement and quota level, provider churn stays local to BillFn.
