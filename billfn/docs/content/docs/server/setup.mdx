`@billfn/core` is the server-side heart of BillFn. You create it with `createBillFn(config)` and then either mount its `router` or call the service methods directly.

## Config Surface

```ts
type BillFnConfig = {
  db: Adapter;
  catalog: BillFnCatalog;
  namespace?: string;
  basePath?: string;
  providers?: Partial<Record<BillingProviderName, BillFnProviderAdapter>>;
  billingAccountResolver?: BillingAccountResolver;
  metrics?: MetricsEmitter;
  queue?: QueueAdapter<{ type: "webhook-event"; provider: BillingProviderName; providerEventId: string }>;
  auth?: {
    resolveSubject?: (request: Request) => Promise<BillableSubject | null> | BillableSubject | null;
    /** Trust a `subject` sent in the request; only for trusted server-to-server callers. */
    allowClientSubject?: boolean;
  };
  refunds?: {
    /** Approves `POST /billfn/subscriptions/refund`; without it the route answers 403. */
    authorize?: (input: BillFnRefundAuthorizationInput) => Promise<boolean> | boolean;
  };
  checkout?: {
    isPriceEligible?: (input: {
      billingAccountId: string;
      planKey: string;
      price: BillFnPriceDefinition;
    }) => Promise<boolean> | boolean;
  };
  /** Receives lifecycle events at least once through the `lifecycleEvents` outbox; see Lifecycle events. */
  onEvent?: (event: BillFnLifecycleEvent) => Promise<void> | void;
  now?: () => Date;
  generateId?: (prefix: string) => string;
};
```

## Recommended Production Wiring

```ts
import { createBillFn, createBillFnError, type BillingAccountResolver } from "@billfn/core";
import { createDodoProvider } from "@billfn/provider-dodo";

const billingAccountResolver: BillingAccountResolver = {
  async resolve(subject) {
    if (subject.organizationId) {
      return {
        billingAccountId: `ba_org_${subject.organizationId}`,
        ownerType: "organization",
        ownerId: subject.organizationId,
      };
    }

    if (subject.principalId) {
      return {
        billingAccountId: `ba_user_${subject.principalId}`,
        ownerType: "user",
        ownerId: subject.principalId,
      };
    }

    return null;
  },
};

const billfn = createBillFn({
  db,
  catalog,
  billingAccountResolver,
  auth: {
    // Resolve the subject from your own session or token check, never from
    // a header or field the browser can set.
    resolveSubject: async (request) => {
      const session = await getSession(request);
      if (!session) return null;
      // A cookie session also needs a CSRF check on writes, or another site
      // can post with the user's cookie.
      if (request.method !== "GET" && !(await verifyCsrf(request, session))) {
        throw createBillFnError({ code: "BILLFN_UNAUTHORIZED", message: "CSRF check failed" });
      }
      return { principalId: session.userId };
    },
  },
  providers: {
    dodo: createDodoProvider({
      apiKey: process.env.DODO_API_KEY!,
      webhookSecret: process.env.DODO_WEBHOOK_SECRET!,
      environment: "live_mode",
    }),
  },
});
```

`getSession` stands for your app's own authentication (a signed session cookie
or a verified bearer token), and `verifyCsrf` for its CSRF check (for example a
token header that must match the session), as in the
[multi-region Workers recipe](/docs/recipes/multi-region-workers).

## Who the Router Acts For

Every route that reads or changes an account (`/entitlements`, `/usage`,
`/checkouts`, `/checkouts/verify`, `/subscriptions/*` and `/purchases/restore`)
needs a subject:

- With `auth.resolveSubject`, the subject is whatever it returns. A `subject`
  in the request body or query string is ignored. Returning `null` answers
  `400 BILLFN_VALIDATION_ERROR`; throw `BILLFN_UNAUTHENTICATED` to answer 401.
- Without a resolver, these routes answer `401 BILLFN_UNAUTHENTICATED`.
- `auth.allowClientSubject: true` makes the router take the `subject` from the
  request body or query string when no resolver is set. Any caller can then
  read or change any account, so use it only when every caller that can reach
  the router is trusted, such as a backend-only deployment behind its own
  authentication.

## Refunds Through the Router

`POST /billfn/subscriptions/refund` is off by default. Refunds move money, so
the host decides who may ask for one through `refunds.authorize`. The route
first parses the body (400 when it is not a JSON object), resolves the subject
(401 or 400 as above), checks the mode and amount (400, see below) and finds
the subscription and charge it would refund (404 or 409). Only then does it call `refunds.authorize` with the request, the
subject, and the exact target: `billingAccountId`, `subscriptionId`,
`providerSubscriptionId`, `providerChargeId`, `mode` (default `full`),
`amount` (minor units of `currency`), `currency` (the subscription's catalog
price currency, the one BillFn records the refund in) and `reason`. When the subscription has no charge id, Apple refunds
by its subscription reference (it revokes the original transaction); Dodo
needs a charge id and answers `400 BILLFN_VALIDATION_ERROR` without one, even
after the hook approved. Anything
but `true` answers `403 BILLFN_UNAUTHORIZED`, and without the hook every
refund that reaches this step does:

```ts
const billfn = createBillFn({
  // ...
  refunds: {
    // Operators only, and the session check above has already run. A
    // self-service policy (for example one refund per charge within 14 days)
    // would check the subject's history here instead; to enforce "once"
    // against concurrent requests, reserve the charge atomically in your own
    // store here, because two requests can both see no earlier refund. Keep
    // the reservation when the refund call fails: the provider may already
    // have refunded, so check its refund records before releasing it.
    authorize: async ({ request }) => (await getSession(request))?.role === "billing-operator",
  },
});
```

If the subscription changes while `refunds.authorize` is deciding (a renewal
or a cancellation), the refund answers `409 BILLFN_CONFLICT` instead of
refunding the state that was approved; retry it.

Every refund, through the router, `billfn.refundCharge()` or the admin
package, checks its mode and amount before the provider is called: `full`
takes no `amount`, and `custom` or `prorated_remaining_period` needs a
positive integer `amount` in the currency minor unit (BillFn does not compute
a prorated amount; the caller supplies it). A `mode` of `null` is not the
default. Anything else answers `400 BILLFN_VALIDATION_ERROR`, as does a
partial refund on Apple, which refunds only whole transactions. A refund, cancel, change, resume or sync never creates a billing account; a
subject without one gets `404 BILLFN_NOT_FOUND`.

The router refund acts on the resolved subject's own account. To refund
another account, use `@billfn/admin` or call `billfn.refundCharge()` from host
code, which do not use this hook.

Production must set `environment: "live_mode"` with a live mode Dodo key. The
Dodo adapter calls Dodo's test mode (`https://test.dodopayments.com`) when
`environment` is not set, where a live key is rejected.

## Discounted Prices

A catalog price can carry an `eligibility` tag, such as `first-purchase`, to
mark it as restricted:

```ts
{
  priceId: "price_pro_dodo_month_intro",
  provider: "dodo",
  providerProductId: "pdt_pro_month_intro",
  currency: "USD",
  amount: 6,
  kind: "subscription",
  interval: "month",
  eligibility: "first-purchase",
}
```

`createCheckout` accepts an optional `priceId`. It must be a price of the
requested plan for the requested provider, and for the interval when one is
given; otherwise checkout fails with `400 BILLFN_VALIDATION_ERROR`. Without
`priceId`, checkout uses the first matching price that has no `eligibility`
tag, so a tagged price is never sold by default.

For a tagged price, checkout calls `checkout.isPriceEligible({ billingAccountId,
planKey, price })` before it creates a session or calls the provider. Only a
`true` result sells the price. Any other result fails with
`403 BILLFN_PRICE_NOT_ELIGIBLE`, and so does every tagged price when the hook is
not configured. Untagged prices never reach the hook. Checkout charges the
catalog price, never an amount from the request.

`changeSubscription` applies the same gate to its target price: moving a
subscription to a tagged price calls the hook first, and anything but `true`
fails with `403 BILLFN_PRICE_NOT_ELIGIBLE` before the provider is asked or a
change request is recorded. The admin plan change goes through the same method
and is gated the same way; there is no operator override.

The hook runs once, when the session or change is requested. Two checkouts for a
`first-purchase` price started before either completes can both pass, so a hook
that allows one discounted purchase should also count the account's pending
discounted checkouts.

```ts
const billfn = createBillFn({
  db,
  catalog,
  checkout: {
    isPriceEligible: async ({ billingAccountId, price }) =>
      price.eligibility === "first-purchase" &&
      !(await hasPaidBefore(billingAccountId)),
  },
});
```

## Subject Precedence

When both an authenticated subject resolver and a request body subject are present, the auth-resolved subject wins. That avoids spoofing another account by passing a different `subject` payload.

## What `createBillFn()` Returns

The instance exposes:

- `router`
- `getSchema()`
- `getCatalog()`
- `createCheckout()`
- `verifyCheckout()`
- `cancelSubscription()`
- `syncSubscription()`
- `restorePurchases()`
- `getEntitlements()`
- `getUsage()`
- `handleWebhook()`
- `services.events.dispatch()` and `services.events.list()` for the [lifecycle event](/docs/server/lifecycle-events) outbox
- `subscriptionProvider`
- `quotaProvider`

## Integrating the Router

The router is built with `@superfunctions/http` and uses `basePath` with `/billfn` as the default.

```ts
const router = billfn.router;
```

If your app already has its own routing layer, you can also call the service methods directly and wrap them in your own transport.
