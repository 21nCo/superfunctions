BillFn’s router divides its surface into:

- consumer-facing reads
- operational billing writes
- provider webhook ingestion
- operational reconciliation

## Status and Read Routes

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/billfn/status` | Health-style capability response |
| `GET` | `/billfn/catalog` | Returns the configured billing catalog |
| `GET` | `/billfn/entitlements` | Returns billing account, entitlement snapshot, and current subscription |
| `GET` | `/billfn/usage` | Returns usage and limit information for the account |

`/billfn/entitlements`, `/billfn/usage` and every write route below act for the subject that `auth.resolveSubject` returns. Without a resolver they answer `401 BILLFN_UNAUTHENTICATED`, unless the host sets `auth.allowClientSubject: true`; the router then takes the body `subject` when it names one, and otherwise the subject in the query params (for reads and writes alike). Only trusted server-to-server callers should use that mode, because any caller can name any account. See [Setup](/docs/server/setup#who-the-router-acts-for).

## Write Routes

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/billfn/checkouts` | Create a checkout session |
| `POST` | `/billfn/checkouts/verify` | Verify a checkout and project subscription state |
| `POST` | `/billfn/subscriptions/cancel` | Cancel a subscription when the provider supports it |
| `POST` | `/billfn/subscriptions/change` | Change a subscription to a target price id |
| `POST` | `/billfn/subscriptions/resume` | Resume or reactivate a subscription |
| `POST` | `/billfn/subscriptions/refund` | Create a refund or provider-managed revoke flow; answers 403 unless `refunds.authorize` approves the resolved refund target ([Setup](/docs/server/setup#refunds-through-the-router)) |
| `POST` | `/billfn/subscriptions/sync` | Re-fetch normalized subscription state from the provider |
| `POST` | `/billfn/purchases/restore` | Restore a purchase into an existing billing account context |

When a plan has multiple prices for the same provider, pass `priceId` to `/billfn/purchases/restore` so the provider can select the correct recurring or one-time restore flow. BillFn can infer the price when the purchase reference matches a known checkout or when only one provider price exists.

Lifecycle responses can return `operationStatus: "applied"` or `operationStatus: "requires_action"`, plus an optional `clientAction`.

## Operations Routes

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/billfn/ops/reconciliation/jobs` | Queue a reconciliation job |
| `GET` | `/billfn/ops/reconciliation/jobs/:jobId` | Fetch a reconciliation job |
| `POST` | `/billfn/ops/reconciliation/jobs/:jobId/run` | Run a reconciliation job immediately |
| `GET` | `/billfn/ops/owner?provider=&ref=` | Whether this region owns a provider reference (internal token; see [Regions](/docs/server/regions)) |

## Webhooks

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/billfn/webhooks/:provider` | Parse, dedupe, and project provider webhook events |

Current provider support:

- Dodo ingests and replays webhooks
- Apple ingests App Store Server Notifications v2 and notification history backfills

## Checkout Request Example

```json
{
  "planKey": "pro",
  "provider": "dodo",
  "interval": "month",
  "customer": {
    "email": "user@example.com",
    "name": "Nucleus User"
  },
  "successUrl": "https://app.example.com/settings/billing/success",
  "cancelUrl": "https://app.example.com/settings/billing/cancel"
}
```

## Requests

Routes that take a JSON body require a single `content-type` of `application/json` (or another `type/subtype+json`); anything else, such as a cross-site form post sent as `text/plain`, answers `400 BILLFN_VALIDATION_ERROR` before the route acts. Routes without a body, such as `POST /ops/reconciliation/jobs/:jobId/run`, and the provider webhook routes do not check it. A body that middleware already started reading is refused too. Request bodies, webhook deliveries included, are limited to 256 KiB; the webhook ingress applies the same limit before any owner lookup. Checkout `metadata` is an object of at most 20 keys (up to 40 characters each) with string (up to 500 characters), number or boolean values. The host remains responsible for CSRF protection of cookie sessions (see [Server setup](/docs/server/setup#recommended-production-wiring)).

## Responses

Successful responses use the shared envelope shape:

```json
{
  "ok": true,
  "data": {
    "checkoutSession": {
      "checkoutSessionId": "chk_123"
    }
  },
  "meta": {
    "timestamp": "2026-04-20T00:00:00.000Z"
  }
}
```

Failures remain envelope-based:

```json
{
  "ok": false,
  "error": {
    "code": "BILLFN_NOT_FOUND",
    "message": "not found",
    "status": 404,
    "retryable": false
  },
  "meta": {
    "timestamp": "2026-04-20T00:00:00.000Z"
  }
}
```

Error `details` never carry a provider's raw response body or BillFn configuration (bundle ids, catalog price ids); the router leaves them out of the response (BillFn does not log them).

The client SDKs preserve this shape instead of flattening it away.
