title: Reconciliation
description: Queue-driven replay, provider backfills, and operational job control.
---

BillFn Phase 2 adds a first-class reconciliation layer instead of treating webhook replay and subscription repair as ad hoc scripts.

## Routes

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/billfn/ops/reconciliation/jobs` | Queue a reconciliation job |
| `GET` | `/billfn/ops/reconciliation/jobs/:jobId` | Read job state |
| `POST` | `/billfn/ops/reconciliation/jobs/:jobId/run` | Execute a queued job immediately |

These routes require `operations.authorize(request)` to succeed.

## Job kinds

- `webhook-event`
- `webhook-replay`
- `subscription-sync`
- `account-scan`
- `notification-history-backfill`

## Events for subscriptions BillFn has not seen

A verified webhook whose subscription or payment reference matches no local subscription or checkout session no longer fails with `BILLFN_NOT_FOUND`. It is acknowledged with a 2xx response once it is stored or applied; a metadata bootstrap that then fails to replay retained events fails the delivery as described below, so the provider redelivers it:

- When the provider record carries `billfn_billing_account_id` metadata naming an existing billing account, and its product is in the catalog, BillFn creates the subscription from the provider record and applies the event. Two deliveries racing to create the same subscription end with one row: the loser of the unique `provider + providerSubscriptionId` insert applies its event as an ordered update.
- Otherwise the event is stored in `unlinkedWebhookEvents` with status `unlinked`, with a `reason`: `billing_account_metadata_missing`, `billing_account_not_found` (metadata names an account that does not exist; no account is created) `price_not_found`, or `provider_reference_replaced` (see below). A row is identified by `provider + providerEventId`, so a redelivery stores nothing new. Replay finds it by `providerReference` (the provider subscription id, or the charge id for a one-time payment) and by `providerSecondaryReference` (the charge, when the event names both).
- An event whose reference matches a subscription whose billing account is gone is stored with reason `billing_account_unavailable`; its reference is never rebound to another billing account.

An unlinked event expires after 90 days and an expired event is never replayed. Expired rows are deleted only when another unlinked event is stored, so 90 days is not a deletion guarantee.

When a reference is later linked, by checkout verification, a restored purchase, a metadata bootstrap, an event that links it through its checkout session, or the next event for that reference, BillFn replays its unexpired unlinked events in provider event-time order (events without a provider time go last). An event older than the subscription's current provider state is marked `skipped`; an applied event is marked `replayed`. An event without a provider time is ordered, and saved as the provider-state time, by when it was stored. An applied event's lifecycle billing event is keyed by its provider event, so a redelivery, a replay, or a replay taken over after an interrupted run records it once. Checkout verification, restore, subscription sync (the public call and `subscription-sync` / `account-scan` jobs) carry the provider's live state, as do the cancel, change, resume and refund responses that include `billingState` (a change scheduled for the next renewal may return none, and then only records the request). A read saves the time its provider call started as the subscription's provider-state time (`billfnProviderEventOccurredAt` metadata, which never moves backwards), so any later replay or delivery of an event that occurred before the read is skipped rather than applied over the live state. The comparison uses the provider's event time and the BillFn server clock, so clock skew between them shifts that boundary. In the other direction, when an event that occurred after the read started was applied while the read was in flight, the read only adds its provider references to the subscription: the subscription keeps the event's status and entitlements, and the call returns that newer state.

A committed mutation is ordered by when its provider call returned instead. An event applied while the mutation was in flight does not discard the mutation's state: if the event occurred before the return, the mutation's state is saved with the return time; if it occurred after the return, the event keeps its state. In both cases BillFn reconciles the subscription with a provider read, never repeating the mutation: a `subscription-sync` job when a queue is configured, otherwise an inline sync when the provider supports it, either one also reading for the price the raced event wrote under the same rules as a window read below (a failed read records `subscription.mutation.reconcile_failed` and the mutation still succeeds). If that read fails, whichever state was saved stands: the mutation's for an event inside its window, the event's for one after the return. The mutation's window runs from just after its provider call started up to and including when it returned, and an event that occurred inside it cannot be ordered against the mutation, so it is never applied over it. When such an event is delivered or replayed after the mutation, its missing references are still linked and BillFn reads the subscription from the provider inline, in the same delivery, webhook job or replay (`subscription.mutation.window_event`), and applies the live state. The read is made for the plan and price the mutation saved; if it fails or returns no state and the event names another catalog price, a read for that price is made (a provider such as Apple reads only the live product), and it counts only when the state it returns names a catalog price, through `providerProductId` (the Apple adapter sets it from the signed transaction's product) or the raw record, however the first read failed; otherwise it counts as failed. The catalog price the live record names wins, and every subscription sync applies it too: an exact catalog price id first, then a provider product id. A product several catalog prices share names the saved price when it is one of them, else the first of them when they all belong to one plan (so a metadata bootstrap still resolves it); across plans the saved price is kept and a bootstrap is stored with `price_not_found`. When the provider has no subscription read, the mutation's state stands (`subscription.mutation.window_event_unreconciled`). When no read succeeds, the mutation's state stands too and the event is not applied: with a queue a `subscription-sync` job is enqueued, carrying the event's price for the same read sequence, and the event is acknowledged; without one a delivery fails with `BILLFN_PROVIDER_ERROR` so the provider redelivers it, and a replayed event stays retained with that error without holding back the events after it, after which the operation that triggered the replay fails with it so its retry reads again. A delivered event is applied first: one after the mutation's return closes the window, so the retained event is then skipped and the delivery succeeds. If writing the read's entitlements or its lifecycle entry (keyed by the event) fails, the delivery, webhook job or replay fails and the window stays open, so the retry reads and applies again and records the entry once. A state write at or after the return, or a finished reconcile of that window (never a newer mutation's), closes the window, and no write moves the provider-state time backwards.

An event that is skipped as older than the subscription's provider state still links its references. Its status, periods and entitlements are not applied and the provider-state time is kept, but a provider subscription or charge id the subscription does not have yet is added, unless another subscription already holds it. An existing reference is never replaced by an older event. For example, when checkout verification links a subscription whose live record has no charge yet, the first payment event, even if it occurred before the verification, links its charge, so refunds by charge and later charge-only events resolve to the subscription.

Linking covers every reference a subscription gains, not only the first one. When an event or a replayed event, applied or skipped, adds a subscription or charge reference to an existing subscription, the unlinked events stored for the new reference are merged into the same event-time ordered replay before the next event is applied, so an event naming a charge the subscription held only between two replayed events is applied at its position. A reference the subscription regains later in the same replay is looked up again, so an event stored for it while it was replaced, or one the replay visited then and left `unlinked`, is replayed too. One run replays at most 500 events; one that reaches that bound with events left fails retryably like a lease conflict and records reason `bounded` when deferred after a mutation. A queue worker continues a bounded run that finished events in a fresh queue message, so a long backlog does not use up the five lease-conflict attempts after which a message is dead-lettered; a bounded run that finished none counts as a lease conflict. Every call that applies live provider state (listed above) replays the unlinked events for the subscription's references after it writes, whether or not that call added a reference, so a retry after an interrupted replay still applies them, and it returns the subscription and entitlements after the replay.

An event that finds no link is checked again before it is stored: if another delivery or a verification linked its reference in the meantime, the event is applied to that subscription instead. An event stored while a link commits is replayed right after it is stored.

A replayed event can replace one of the subscription's references, for example a renewal that moves it to a new charge. A retained or delivered event that names only the replaced reference then no longer resolves to the subscription, and is never applied to it. It stays `unlinked` with reason `provider_reference_replaced`, as it would have if the events had been delivered in order, and is replayed if its reference is linked again. A delivered event is checked again after every replay, including one another run finished. The replay continues with the events after it.

Whenever a write drops one of a subscription's references (a delivered or replayed event, a provider read or mutation response, or a bootstrap's ordered update), it first records that reference in `replacedProviderReferences`, one row per provider and reference. While no subscription holds the reference, an event naming it is stored with reason `provider_reference_replaced` and never bootstraps a subscription, whichever billing account its metadata names and whether it is redelivered, reprocessed by `webhook-replay`, or delivered for the first time with a new event id. Because the record is written before the subscription, a failure or process stop after the write cannot undo it. A subscription that holds the reference again, including the winner of a race that kept it, resolves its events first, so they are still applied or replayed there.

The same write also marks each retained event on the dropped reference that names no reference the subscription keeps (including one left unread inside a mutation window, or one a replay run holds) with reason `provider_reference_replaced`, as does the end of a replay pass for a reference it saw the subscription lose to another run. Such an event no longer fails the operation and is not counted as left at the 500-event bound. An event that also names a kept reference still resolves to the subscription, so it keeps its reason and is replayed or retried as before.

If recording fails during a committed provider mutation, the mutation still succeeds and is never repeated: its own subscription write saves the reference pending (`billfnPendingReplacedReferences` metadata and the indexed `replacedReferencesPending` flag), with or without a queue. An event naming a pending reference is treated as replaced for every billing account, the same as a recorded one, and the next write of that subscription records the pending references and clears them.

The check before a bootstrap is ordered against these writes. Recorded references are never deleted, a pending reference is set only by the write that drops it, and a later write records a pending reference before it clears it. The check runs after the lookup that found no subscription holding the reference, and reads in the opposite order: pending references first, then recorded ones, then the retained event. A write that clears a pending reference between those reads has already recorded it, so a concurrent first-time event is still stored with reason `provider_reference_replaced`.

Except after a provider mutation (below), the operation that triggered a replay succeeds only once every retained event for the reference that still resolves to the subscription is `replayed` or `skipped`:

- A replay stops at an event it cannot apply and leaves it and the later events `unlinked`, with the error recorded. Without a queue, an event inside a mutation window whose provider read fails is the exception: it stays `unlinked` with the read error and the replay continues with the later events (with a queue, a `subscription-sync` job reconciles it instead and the operation does not fail on it). In both failing cases the operation then fails with the recorded error: the webhook receipt stays unprocessed and the provider redelivers it (with a queue, the webhook job fails and can be rerun with `webhook-replay`), and checkout verification, restore or sync can be called again (a queued sync job is retried after a lease conflict like a webhook job).
- An event claimed by another replay run, including a run interrupted before it released the event, holds its claim for 15 minutes. The operation fails with `BILLFN_CONFLICT` until the claim is finished or expires, and the next attempt after expiry takes the claim over. Without a queue the provider redelivers the webhook; with a queue the webhook or sync job message is retried after the lease, like any lease conflict.

Cancel, change, resume and refund are different: once the provider has applied the mutation, retrying the call would repeat it (a second refund, for example). They save the provider's state, record their `*.requested` billing event and return their result even when the replay does not finish. The unfinished events stay retained, the `webhook.unlinked.replay_deferred` metric is recorded, and with a queue and a provider that supports subscription sync a `subscription-sync` job is enqueued to replay them. Otherwise the next webhook, sync or live read for the subscription replays them. If reading the subscription back after the replay fails, the call returns the state it wrote and records `webhook.unlinked.replay_refresh_failed`.

## Importing existing provider subscriptions

A subscription created before BillFn (for example a legacy Dodo subscription, or an Apple purchase made without BillFn's `appAccountToken`) has none of the ownership metadata checkout verification and restore require, so its events are stored unlinked with reason `billing_account_metadata_missing`. An operator binds it with `billfn.services.subscriptions.import`, which is not a public route; `@billfn/admin` exposes it as the `import-subscription` action.

```ts
await billfn.services.subscriptions.import({
  provider: 'dodo',
  providerSubscriptionId: 'sub_...', // or, for Apple, originalTransactionId
  billingAccountId,
  planKey: 'nucleus',
  operator: { id: operatorId, type: 'user', requestId },
  reason: 'legacy cutover'
});
```

- The billing account must exist, unless `subject` is given: then the account is created for it and must be `billingAccountId`.
- The provider adapter's `importSubscription` reads the subscription by its reference and checks only that the record is that subscription (Dodo `GET /subscriptions/:id`; Apple `GET /inApps/v1/subscriptions/:originalTransactionId`). The product on the record must be a subscription price of `planKey`, which selects the price.
- The state is applied as a live provider read: the read's start becomes the provider-state time, the unlinked events stored for the reference are replayed (events that occurred before the read are marked `skipped`, later ones applied), and the call returns the subscription and entitlements after the replay. A replay that does not finish fails the call; calling it again finishes it.
- Import is idempotent per provider reference: importing a reference already bound to the same billing account syncs it again and returns the same subscription. A reference bound to a different billing account, including by a concurrent import, fails with `BILLFN_CONFLICT` and nothing is written, as does one a subscription write replaced. Racing imports into the same account end with one subscription.
- Every successful import records a `billfn.subscription.imported` billing event with the provider reference, plan, price, status, `operator` and `reason`, before the replay, so an import whose replay must be retried is still recorded.
- The subscription's `billfnImportedAt` metadata keeps when it was first imported. The Apple adapter's subscription sync does not expect a BillFn `appAccountToken` on an imported subscription (it still checks the product); the binding is the operator's.

## Worker

Use `createBillFnReconciliationWorker(config)` with the same BillFn config you mount in your server.

```ts
import { createBillFnReconciliationWorker } from "@billfn/core";

const worker = createBillFnReconciliationWorker(config);
try {
  await worker.runNext();
} catch (error) {
  // The failed message is already released or dead-lettered; log and keep polling.
}
```

If you provide `queue`, webhook ingestion and manual ops jobs both enqueue `billfn-reconciliation` work items. If you do not provide a queue, webhook reconciliation is processed inline.

`config.queue` must be a lease-based `QueueAdapter` from `@superfunctions/queue` 0.2, such as `MemoryQueueAdapter` or the durable `DatabaseQueueAdapter`. `FlowFnQueueAdapter` no longer implements that interface and cannot be used here.

Each `runNext()` call claims one message with a 15-minute lease and returns `null` when none is available. The queue lease is extended whenever the job's own processing lease is renewed. On success the message is acked. When another runner holds the job's lease, the message is released for retry, up to 5 deliveries. Any other failure dead-letters the message and `runNext()` rethrows the run's error. BillFn does not run a loop: callers drive `runNext()` and should catch its errors.
