BillFn Phase 2 adds a first-class reconciliation layer instead of treating webhook replay and subscription repair as ad hoc scripts.

## Routes

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/billfn/ops/reconciliation/jobs` | Queue a reconciliation job |
| `GET` | `/billfn/ops/reconciliation/jobs/:jobId` | Read job state |
| `POST` | `/billfn/ops/reconciliation/jobs/:jobId/run` | Execute a queued job immediately |

These routes require `operations.authorize(request)` to succeed.

## Job kinds

- `webhook-event`
- `webhook-replay`
- `subscription-sync`
- `account-scan`
- `notification-history-backfill`

## Events for subscriptions BillFn has not seen

A verified webhook whose subscription or payment reference matches no local subscription or checkout session is acknowledged with a 2xx response instead of failing with `BILLFN_NOT_FOUND`:

- When the provider record carries `billfn_billing_account_id` metadata naming an existing billing account, and its product is in the catalog, BillFn creates the subscription from the provider record and applies the event. Two deliveries racing to create the same subscription end with one row: the loser of the unique `provider + providerSubscriptionId` insert applies its event as an ordered update.
- Otherwise the event is stored in `unlinkedWebhookEvents` with status `unlinked`, keyed by provider and provider reference (the provider subscription id, or the charge id for a one-time payment), with a `reason`: `billing_account_metadata_missing`, `billing_account_not_found` (metadata names an account that does not exist; no account is created), `price_not_found`, or `billing_account_unavailable`.

Unlinked events are kept for 90 days. Storing a new unlinked event deletes rows past their `expiresAt`, and an expired event is never replayed.

When a reference is later linked, by checkout verification, a restored purchase, a metadata bootstrap, an event that links it through its checkout session, or the next event for that reference, BillFn replays its unexpired unlinked events in provider event-time order (events without a provider time go last). An event older than the subscription's current provider state is marked `skipped`; an applied event is marked `replayed`. An event without a provider time is compared by when it was stored. Checkout verification, restore, subscription sync (the public call and `subscription-sync` / `account-scan` jobs) and the provider responses to cancel, change, resume and refund all carry the provider's live state. Each saves the time its provider call started as the subscription's provider-state time (`billfnProviderEventOccurredAt` metadata, which never moves backwards), so any later replay or delivery of an event that occurred before the read is skipped rather than applied over the live state. The comparison uses the provider's event time and the BillFn server clock, so clock skew between them shifts that boundary. In the other direction, when an event that occurred after the read started was applied while the read was in flight, the read only adds its provider references to the subscription: the subscription keeps the event's status and entitlements, and the call returns that newer state.

Linking covers every reference a subscription gains, not only the first one. When an event or a replayed event adds a subscription or charge reference to an existing subscription, the unlinked events stored for the new reference are replayed before the operation succeeds, under the same ordering rules. Every call that applies live provider state (listed above) replays the unlinked events for the subscription's references after it writes, whether or not that call added a reference, so a retry after an interrupted replay still applies them, and it returns the subscription and entitlements after the replay.

An event that finds no link is checked again before it is stored: if another delivery or a verification linked its reference in the meantime, the event is applied to that subscription instead. An event stored while a link commits is replayed right after it is stored.

A replayed event can replace one of the subscription's references, for example a renewal that moves it to a new charge. A retained event that names only the replaced reference then no longer resolves to the subscription. It stays `unlinked`, as it would have if the events had been delivered in order, and is replayed if its reference is linked again. The replay continues with the events after it.

Except after a provider mutation (below), the operation that triggered a replay succeeds only once every retained event for the reference that still resolves to the subscription is `replayed` or `skipped`:

- A replay stops at an event it cannot apply and leaves it and the later events `unlinked`, with the error recorded. The operation then fails with that error: the webhook receipt stays unprocessed and the provider redelivers it (with a queue, the webhook job fails and can be rerun with `webhook-replay`), and checkout verification, restore or sync can be called again (a queued sync job is retried after a lease conflict like a webhook job).
- An event claimed by another replay run, including a run interrupted before it released the event, holds its claim for 15 minutes. The operation fails with `BILLFN_CONFLICT` until the claim is finished or expires, and the next attempt after expiry takes the claim over. Without a queue the provider redelivers the webhook; with a queue the webhook or sync job message is retried after the lease, like any lease conflict.

Cancel, change, resume and refund are different: once the provider has applied the mutation, retrying the call would repeat it (a second refund, for example). They save the provider's state, record their `*.requested` billing event and return their result even when the replay does not finish. The unfinished events stay retained, the `webhook.unlinked.replay_deferred` metric is recorded, and with a queue and a provider that supports subscription sync a `subscription-sync` job is enqueued to replay them. Otherwise the next webhook, sync or live read for the subscription replays them.

## Worker

Use `createBillFnReconciliationWorker(config)` with the same BillFn config you mount in your server.

```ts
import { createBillFnReconciliationWorker } from "@billfn/core";

const worker = createBillFnReconciliationWorker(config);
try {
  await worker.runNext();
} catch (error) {
  // The failed message is already released or dead-lettered; log and keep polling.
}
```

If you provide `queue`, webhook ingestion and manual ops jobs both enqueue `billfn-reconciliation` work items. If you do not provide a queue, webhook reconciliation is processed inline.

`config.queue` must be a lease-based `QueueAdapter` from `@superfunctions/queue` 0.2, such as `MemoryQueueAdapter` or the durable `DatabaseQueueAdapter`. `FlowFnQueueAdapter` no longer implements that interface and cannot be used here.

Each `runNext()` call claims one message with a 15-minute lease and returns `null` when none is available. The queue lease is extended whenever the job's own processing lease is renewed. On success the message is acked. When another runner holds the job's lease, the message is released for retry, up to 5 deliveries. Any other failure dead-letters the message and `runNext()` rethrows the run's error. BillFn does not run a loop: callers drive `runNext()` and should catch its errors.
