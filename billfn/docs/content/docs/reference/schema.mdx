`getSchema()` in `@billfn/core` currently returns version `6` with sixteen table definitions.

## Tables

| Table | Purpose |
| --- | --- |
| `billingAccounts` | Stable internal owners for user or organization billing state |
| `subscriptions` | Normalized provider subscription snapshots |
| `checkoutSessions` | Checkout lifecycle and provider reference ids |
| `entitlementSnapshots` | Current feature and limit projection for an account |
| `usageMeters` | Current usage per billing account and resource |
| `usageLedger` | Append-only usage deltas |
| `webhookReceipts` | Dedupe and audit trail for provider webhook deliveries |
| `billingEvents` | Internal normalized billing event stream |
| `refunds` | Normalized refund and revoke operations |
| `subscriptionChangeRequests` | Subscription change intent and fallback tracking |
| `reconciliationJobs` | Operational replay and sync jobs |
| `reconciliationCursors` | Provider backfill cursors |
| `unlinkedWebhookEvents` | Verified webhook events waiting for their provider reference to be linked, kept 90 days |
| `replacedProviderReferences` | Provider references a subscription write dropped, so no event naming them bootstraps another subscription |
| `entitlementGrants` | Trials and comps that grant a plan's entitlements without payment until an expiry |
| `lifecycleEvents` | Outbox of lifecycle events awaiting or after delivery to the host `onEvent` handler |

## Important Indexes

Phase 1 relies on a few critical indexes:

- `subscriptions.provider + providerSubscriptionId` as a unique provider reference
- `subscriptions.provider + providerChargeId`
- `checkoutSessions.provider + providerCheckoutId`
- `checkoutSessions.provider + providerSubscriptionId`
- `checkoutSessions.provider + providerChargeId`
- `entitlementSnapshots.billingAccountId` as a unique current snapshot
- `usageMeters.billingAccountId + resource` as a unique usage meter
- `webhookReceipts.provider + providerEventId` as a unique dedupe key
- `unlinkedWebhookEvents.provider + providerEventId` as a unique dedupe key
- `unlinkedWebhookEvents.provider + providerReference + status` and `provider + providerSecondaryReference + status` for replay on link
- `unlinkedWebhookEvents.expiresAt` for the 90-day retention purge
- `replacedProviderReferences.provider + providerReference` as a unique key
- `subscriptions.provider + replacedReferencesPending` for the subscriptions holding references not yet recorded as replaced
- `entitlementGrants.billingAccountId + createdAt` for an account's grants
- `entitlementGrants.expiresAt` for the `lifecycle-events` job's expiry sweep
- `lifecycleEvents.status + nextAttemptAt` for due events

## Example

```ts
import { getSchema } from "@billfn/core";

const schema = getSchema();
console.log(schema.version);
console.log(schema.schemas.map((table) => table.modelName));
```

The Python SDK mirrors schema version `6`. Both helpers expose the same sixteen logical model names and mark record identifiers as unique.

## Migrations

### Schema 5 to 6 (`@billfn/core` 0.6.0)

Version `6` adds one table, `lifecycleEvents`, one optional string field, `lifecycleEventIds`, to `subscriptions`, `checkoutSessions` and `entitlementSnapshots`, and, on `entitlementGrants`, one optional boolean field, `eventsPending`, and two indexes, `entitlement_grants_expires_idx` on `expiresAt` and `entitlement_grants_events_pending_idx` on `eventsPending, updatedAt`. Create them before deploying `@billfn/core` 0.6.0 with an `onEvent` handler: with one, subscription, checkout and grant writes write to `lifecycleEvents`, and the `lifecycle-events` reconciliation job reads `entitlementGrants` by `expiresAt` and, without transactions, by `eventsPending`. Without transactions, a write with lifecycle events also sets `lifecycleEventIds` on its row, and a grant write sets `eventsPending` until its billing event is recorded (see [Lifecycle events](/docs/server/lifecycle-events#consistency)). Without a handler BillFn never reads or writes the table or the fields. No backfill is needed (the fields are null): events are recorded for changes from the deploy on, apart from the few listed in [Events after a deploy](/docs/server/lifecycle-events#events-after-a-deploy). The migration is additive, so rolling back to 0.5.x leaves the table, fields and indexes unused (and any pending events undelivered).

| --- | --- | --- |
| `id` | string, unique | yes |
| `type` | string | yes |

| `occurredAt` | string | yes |

Indexes: `lifecycle_events_status_next_attempt_idx` on `status, nextAttemptAt` and `lifecycle_events_billing_account_idx` on `billingAccountId, createdAt`.

### Schema 4 to 5 (`@billfn/core` 0.4.0)

Version `5` adds one table, `entitlementGrants`. Create it before deploying `@billfn/core` 0.4.0: every entitlement read (`getEntitlements`, `subscriptionProvider`, `quotaProvider`, `getUsage`) of an account whose paid entitlements are missing or `inactive` reads it (`getEntitlements` always does, and without transactions every read does, to record missing grant events), and `billfn.services.grants` writes it. A trial's id is `grant_trial_<billingAccountId>`, so the unique `id` allows one trial per billing account; comps are numbered `grant_comp_<billingAccountId>_<n>`, and the next number is taken only while the latest comp is not active, so the unique `id` also allows one active comp at a time. No backfill is needed. The migration is additive, so rolling back to 0.3.x leaves the table unused (and its grants without effect).

### Schema 3 to 4 (`@billfn/core` 0.2.0)

Version `4` adds two tables, `unlinkedWebhookEvents` and `replacedProviderReferences`, and one optional boolean field to `subscriptions`, `replacedReferencesPending`, with the index `subscriptions_replaced_references_pending_idx` on `provider, replacedReferencesPending`. Create them before deploying `@billfn/core` 0.2.0: webhook processing writes to `unlinkedWebhookEvents` as soon as an event names a provider reference BillFn has not linked, every subscription write that drops a provider reference writes to `replacedProviderReferences` first, and a committed mutation that cannot do so sets `replacedReferencesPending`. Existing rows need no backfill (the field is null). The migration is additive, so rolling back to 0.1.x leaves the tables and the field unused.
