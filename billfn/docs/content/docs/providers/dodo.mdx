`@billfn/provider-dodo` is the most complete BillFn provider in Phase 2.

## Install

```bash
npm install @billfn/provider-dodo
```

## Create the Adapter

```ts
import { createDodoProvider } from "@billfn/provider-dodo";

const dodo = createDodoProvider({
  apiKey: process.env.DODO_API_KEY!,
  webhookSecret: process.env.DODO_WEBHOOK_SECRET!,
});
```

Optional config:

- `environment`: `"test_mode"` (default, `https://test.dodopayments.com`) or `"live_mode"` (`https://live.dodopayments.com`)
- `baseUrl`: overrides the environment's host
- `fetch`
- `webhookSignatureHeader`

The adapter calls Dodo's test mode unless `environment: "live_mode"` is set; use a test mode key (`dodo_test_...`) in test mode and a live mode key in live mode.
The default webhook signature header is `webhook-signature`.

## What the Adapter Does

- creates a Dodo checkout session (`POST /checkouts`) for the catalog price checkout selected, with the price's trial and BillFn metadata (`billfn_checkout_session_id`, `billfn_billing_account_id`, `billfn_product_id`, `billfn_price_id`, `billfn_currency`)
- verifies checkouts by following the checkout session to its payment and subscription, checking the BillFn metadata on each; a declined payment the customer retried in the same session is replaced by the session's current payment
- syncs subscriptions
- cancels subscriptions
- attempts direct subscription changes and falls back to replacement-checkout orchestration
- resumes subscriptions when the provider allows it; a held subscription that is also scheduled to cancel gets its scheduled cancel cleared in a second request
- keeps a cancel, plan change, resume or refund that Dodo accepted as applied even when Dodo's answer or the read after it is unusable; a billing state is recorded only from an answer that is this subscription with a Dodo subscription status, otherwise the next webhook or sync supplies it
- creates refunds: a full refund by payment id, a partial one through the payment's line items in the currency the customer paid. BillFn records the refunded amount in the currency of the subscription's current catalog price, so a partial refund is refused unless the payment's `billfn_price_id` is that price and its `billfn_currency` is the currency the customer paid. A renewal payment, which carries no BillFn metadata, takes both from its subscription; a payment made before a plan change or without the metadata can be refunded in full or in Dodo
- restores purchases
- verifies webhook signatures and parses webhook events

## Webhook Behavior

Dodo webhooks fail closed in Phase 1:

- `webhookSecret` must be configured
- `webhook-id`, `webhook-timestamp`, and `webhook-signature` must be present
- the Standard Webhooks signature covers the webhook id, timestamp, and raw request body
- invalid signatures raise `BILLFN_WEBHOOK_SIGNATURE_INVALID`
- malformed JSON becomes a BillFn validation error
- parsed events carry `signatureVerified: true`

Webhook receipts are then deduped in core by provider plus provider event id.

## Status Mapping

Dodo statuses are normalized into BillFn statuses such as:

- `active` (`active`, or a `succeeded` payment)
- `paused` (`on_hold`, `paused`)
- `grace` (`past_due`)
- `canceled` (`cancelled`)
- `expired`
- `failed` (`failed`, or a `failed` or `cancelled` payment)
- `pending` (`pending`, or a payment still processing)

Refund and dispute webhooks carry no billing state, and a declined renewal payment leaves the subscription to Dodo's subscription events.

That normalization lets the rest of the system stay provider-neutral.
