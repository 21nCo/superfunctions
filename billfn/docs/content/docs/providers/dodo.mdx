`@billfn/provider-dodo` is the most complete BillFn provider in Phase 2.

## Install

```bash
npm install @billfn/provider-dodo
```

## Create the Adapter

```ts
import { createDodoProvider } from "@billfn/provider-dodo";

const dodo = createDodoProvider({
  apiKey: process.env.DODO_API_KEY!,
  webhookSecret: process.env.DODO_WEBHOOK_SECRET!,
});
```

Optional config:

- `environment`: `"test_mode"` (default, `https://test.dodopayments.com`) or `"live_mode"` (`https://live.dodopayments.com`)
- `baseUrl`: overrides the environment's host
- `fetch`
- `webhookSignatureHeader`
- `now`: the clock that dates a refund or dispute revocation; pass the same clock as BillFn's `now` when you set one

The adapter calls Dodo's test mode unless `environment: "live_mode"` is set; use a test mode key (`dodo_test_...`) in test mode and a live mode key in live mode.
The default webhook signature header is `webhook-signature`.

## Upgrading from 0.7.0

`@billfn/provider-dodo` 0.7.0 called Dodo's live mode by default; 0.8.0 calls test mode by default. A production wiring that does not set `environment` must add `environment: "live_mode"` when it upgrades, or every Dodo call fails against the test host.

## What the Adapter Does

- creates a Dodo checkout session (`POST /checkouts`) for the catalog price checkout selected, with the price's trial and BillFn metadata (`billfn_checkout_session_id`, `billfn_billing_account_id`, `billfn_product_id`, `billfn_price_id`, `billfn_currency`)
- verifies checkouts by following the checkout session to its payment and subscription, checking the BillFn metadata on each; a declined payment the customer retried in the same session is replaced by the session's current payment. A checkout created by 0.7.0, which recorded its payment as the checkout, is verified from that payment without a checkout session
- syncs subscriptions
- cancels subscriptions
- attempts direct subscription changes and falls back to replacement-checkout orchestration
- resumes subscriptions when the provider allows it; a held subscription that is also scheduled to cancel gets its scheduled cancel cleared in a second request
- keeps a cancel, plan change, resume or refund that Dodo accepted as applied even when Dodo's answer or the read after it is unusable; a billing state is recorded only from an answer that is this subscription with a Dodo subscription status, otherwise the next webhook or sync supplies it. An immediate plan change whose read is unusable returns the subscription's stored state, so BillFn records the new price (a price that shares the old one's Dodo product could not be told apart later) with nothing else changed
- creates refunds: a full refund by payment id, a partial one through the payment's line items in the currency the customer paid. BillFn records the refunded amount in the currency of the subscription's current catalog price, so a partial refund is refused unless the payment's `billfn_price_id` is that price and its `billfn_currency` is the currency the customer paid. Each line item's `refundable_amount` must be a nonnegative integer in minor units; a fractional, negative or unsafe balance is refused before the refund is sent, and a valid balance is still split across the line items in order. A renewal payment, which carries no BillFn metadata, takes both markers from its subscription; a payment made before a plan change, a renewal after a plan change (its subscription still carries the checkout's `billfn_price_id`), or a payment without the metadata can be refunded in full or in Dodo
- bounds every Dodo HTTP call, including the response body, to 30 seconds. A read that misses the deadline returns a retryable provider error unless Dodo has already returned a status that determines the result. A change with no response returns a non-retryable provider error because Dodo may already have applied it. A subscription change or refund stays applied if Dodo returns a success status and the body stalls. Checkout creation also requires the session details, so a stalled success body returns a non-retryable provider error
- restores purchases
- verifies webhook signatures and parses webhook events

## Webhook Behavior

Dodo webhooks fail closed in Phase 1:

- `webhookSecret` must be configured
- `webhook-id`, `webhook-timestamp`, and `webhook-signature` must be present
- the Standard Webhooks signature covers the webhook id, timestamp, and raw request body
- invalid signatures raise `BILLFN_WEBHOOK_SIGNATURE_INVALID`
- malformed JSON becomes a BillFn validation error
- parsed events carry `signatureVerified: true`
- a subscription event or subscription payment names its Dodo product, not the `billfn_price_id` its checkout recorded: Dodo keeps the checkout metadata through plan changes, so BillFn picks the price from the product and the subscription's recorded price. Only a one-time payment names its checkout's catalog price

Webhook receipts are then deduped in core by provider plus provider event id.

## Status Mapping

Dodo statuses are normalized into BillFn statuses such as:

- `active` (`active`, or a `succeeded` payment)
- `paused` (`on_hold`, `paused`)
- `grace` (`past_due`)
- `canceled` (`cancelled`)
- `expired`
- `failed` (`failed`, or a `failed` or `cancelled` payment)
- `pending` (`pending`, or a payment still processing)

A refund or dispute that takes the money back revokes a one-time purchase. That means a `refund.succeeded` webhook with `is_partial: false`, a partial `refund.succeeded` once Dodo reports the payment's `refund_status` as `full`, or a `dispute.lost` or `dispute.accepted` webhook. Dodo marks the refund of a remaining balance as partial too; BillFn does not add up refund amounts itself, since with adaptive currency they are not comparable with the payment total.

A partial refund whose payment does not list it as succeeded yet is a stale read: the delivery fails with a retryable error, and Dodo redelivers it on its retry schedule. If the payment still does not list the refund after Dodo's last retry, a later checkout verification or restore revokes the purchase once Dodo reports the payment's `refund_status` as `full`.

The adapter reads the charge's payment from Dodo to tell a one-time purchase from a subscription charge:

- for a one-time purchase it records `canceled`, matched by the charge, so the purchase stops granting entitlements;
- a subscription charge is left to Dodo's subscription events, which report whatever Dodo did with the subscription.

The recorded state is dated when that read started (by the adapter's `now`), or at the signed event time when that is later. Checkout verification and restore have already matched the payment to a one-time price, so a reversed payment there is revoked, unless the payment also names a subscription it charges (a mixed cart): BillFn cannot revoke the one-time item alone, so that read fails with `409 BILLFN_CONFLICT` and leaves both as they are. A webhook has no price to go by: it classifies the payment by its subscription fields, and a reversed payment it cannot classify fails with a retryable provider error instead of granting access. If the read fails, answers another payment, or does not say whether the payment belongs to a subscription (neither a `subscription_id` of `null` nor a `subscription_ids` list), the delivery fails and Dodo retries it. A refund or dispute links only through its charge, never through checkout metadata. Other refund and dispute webhooks (partial refunds that leave part of the payment paid, pending refunds; opened, challenged, won, expired or cancelled disputes) carry no billing state. A full refund that BillFn creates through `refundCharge` is revoked by its `refund.succeeded` webhook. With several regions behind one webhook ingress, a refund or dispute names only its payment, so it reaches the region that already holds that charge (unless the refund's own metadata names a `billfn_region`, which BillFn never sets on refunds; don't set it on refunds you create in Dodo). One delivered before any region has linked the charge goes to the default region, as other events without routing metadata do. The purchase's region then still revokes it on the next checkout verification or restore, which read the payment's refunds and disputes.

Dodo keeps a refunded or charged-back payment's own status `succeeded`. Checkout verification, restore and payment webhooks therefore treat a one-time payment with a succeeded full refund, a `refund_status` of `full`, or a lost or accepted dispute as `canceled`, so a revoked purchase cannot be restored. A declined renewal payment leaves the subscription to Dodo's subscription events.

That normalization lets the rest of the system stay provider-neutral.
