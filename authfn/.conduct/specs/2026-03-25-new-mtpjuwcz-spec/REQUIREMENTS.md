## EXAUTH-001

- ID: `EXAUTH-001`
- Priority: `P0`
- Statement: The repo MUST add a multi-example `authfn/examples` workspace portfolio containing `shared`, `password-sessions`, `otp-recovery`, `social-oauth`, `account-settings`, and `multi-region-routing`.
- Rationale: The user explicitly wants focused examples rather than one bloated example.
- Acceptance criteria:
  - Root workspaces include `authfn/examples/*` and `authfn/examples/*/*`.
  - All five example roots exist and each contains `README.md`, `package.json`, `playwright.config.ts`, `server/`, `client/`, and `e2e/`.
  - `authfn/examples/shared` exists as a private shared workspace package.
- Test vectors: `TV-EXAUTH-001`
- Notes: A single catch-all example does not satisfy this requirement.

## EXAUTH-002

- ID: `EXAUTH-002`
- Priority: `P0`
- Statement: The portfolio MUST use one shared example harness plus one canonical browser/server stack instead of per-example ad hoc infrastructure.
- Rationale: Focused examples stay maintainable only if the duplicated infrastructure is centralized.
- Acceptance criteria:
  - `authfn/examples/shared` exports seed, demo-route, fake-provider, event, and selector helpers.
  - Example servers use Express plus `@superfunctions/http-express`.
  - Example clients use Svelte 5 plus Vite and consume `@authfn/client` and/or `@authfn/svelte`.
- Test vectors: `TV-EXAUTH-001`, `TV-EXAUTH-002`
- Notes: Shared utilities MAY differ internally per scenario, but the package boundary MUST exist.

## EXAUTH-003

- ID: `EXAUTH-003`
- Priority: `P0`
- Statement: Every example server MUST use Postgres with Drizzle and MUST consume auth tables generated by `@superfunctions/cli` instead of hand-written auth table definitions.
- Rationale: The examples should teach the intended downstream integration path.
- Acceptance criteria:
  - Every example server has `superfunctions.config.ts`, `drizzle.config.ts`, and `src/db/generated/authfn-schema.ts`.
  - Every example server exposes a `db:generate` script that runs `superfunctions generate-schema`.
  - Auth table definitions are imported from the generated file.
  - No example server defines hand-written Drizzle tables for authfn core or plugin auth tables.
- Test vectors: `TV-EXAUTH-003`, `TV-EXAUTH-004`
- Notes: Example-specific non-auth demo tables remain undefined and are not required by this bundle.

## EXAUTH-004

- ID: `EXAUTH-004`
- Priority: `P0`
- Statement: `@authfn/core` and `@superfunctions/cli` MUST interoperate so that `superfunctions generate-schema` can derive real authfn schemas from example `createAuthFn(...)` source files with bundled plugin factory calls.
- Rationale: Without this, the CLI-backed schema-generation requirement is not actually executable.
- Acceptance criteria:
  - `@authfn/core/package.json` includes `superfunctions.initFunction = "createAuthFn"` and `libraryNames = ["authfn"]`.
  - CLI parsing preserves function-call descriptors with callee name and arguments.
  - `@authfn/core.getSchema(...)` resolves bundled plugin descriptors into schema-contributing plugins.
  - Unknown bundled plugin descriptors fail deterministically with a structured invalid-config error.
  - CLI integration tests cover at least password, OTP, social, API key, 2FA, and multi-region descriptor resolution.
- Test vectors: `TV-EXAUTH-004`
- Notes: Runtime-only function values MAY remain undefined during schema generation if schema shape does not depend on them.

## EXAUTH-005

- ID: `EXAUTH-005`
- Priority: `P0`
- Statement: The `password-sessions` example MUST demonstrate the full email/password browser-session lifecycle and verify it with Playwright.
- Rationale: This is the smallest canonical authfn browser story and must be crystal clear.
- Acceptance criteria:
  - The example supports sign-up, sign-in, current-session fetch, session listing, revoke-session, and sign-out.
  - The UI exposes stable selectors for all controls the test uses.
  - The Playwright suite resets state before assertions.
  - Negative authentication attempts surface the canonical authfn envelope.
- Test vectors: `TV-EXAUTH-005`
- Notes: The current authfn password flow is email/password, not username/password.

## EXAUTH-006

- ID: `EXAUTH-006`
- Priority: `P0`
- Statement: The `otp-recovery` example MUST demonstrate verify-email OTP, OTP sign-in, and password reset with deterministic inbox inspection and Playwright coverage.
- Rationale: OTP and recovery flows are distinct enough to warrant a dedicated example.
- Acceptance criteria:
  - The example wires both password and email-OTP plugins as needed for the covered journeys.
  - `GET /demo/otp/latest` returns the latest deterministic code for the requested purpose and email.
  - The Playwright suite verifies both success and replay/invalid failure paths.
- Test vectors: `TV-EXAUTH-006`
- Notes: The demo inbox is allowed only because this is an example fixture.

## EXAUTH-007

- ID: `EXAUTH-007`
- Priority: `P0`
- Statement: The `social-oauth` example MUST demonstrate provider start, callback completion, and disconnect using local fake providers rather than live external OAuth services.
- Rationale: OAuth flows are important authfn capability, but external dependencies would make the example brittle.
- Acceptance criteria:
  - The example provides fake provider endpoints for Google, GitHub, and Apple-compatible flows.
  - The UI exposes one action per provider plus disconnect.
  - The Playwright suite verifies at least one successful provider flow and at least one disallowed redirect failure path.
- Test vectors: `TV-EXAUTH-007`
- Notes: Provider branding in the UI is allowed, but the flows remain local fixtures.

## EXAUTH-008

- ID: `EXAUTH-008`
- Priority: `P0`
- Statement: The `account-settings` example MUST demonstrate API-key lifecycle and 2FA enroll/confirm/challenge/disable behavior and verify both via Playwright.
- Rationale: These are post-login management features that should not bloat the initial sign-in examples.
- Acceptance criteria:
  - The example supports API-key create/list/revoke.
  - The example supports 2FA enroll, confirm, login challenge completion, and disable.
  - The suite validates that a revoked key fails and that an invalid 2FA code fails.
- Test vectors: `TV-EXAUTH-008`
- Notes: This example SHOULD sign in through password before entering the settings surface.

## EXAUTH-009

- ID: `EXAUTH-009`
- Priority: `P0`
- Statement: The `multi-region-routing` example MUST demonstrate region lookup and wrong-authority correction across two local authorities without relying on public DNS or external infrastructure.
- Rationale: Multi-region routing is a first-class authfn differentiator and deserves its own focused example.
- Acceptance criteria:
  - The example runs two server authorities with fixed local URLs.
  - The UI can submit identifier lookup and display authority guidance.
  - Wrong-authority continuation returns canonical redirect guidance.
  - Correct-authority continuation succeeds and is covered by Playwright.
- Test vectors: `TV-EXAUTH-009`
- Notes: Same-host different-port authorities are acceptable for local determinism.

## EXAUTH-010

- ID: `EXAUTH-010`
- Priority: `P0`
- Statement: `@authfn/client` MUST expand to cover the official auth routes required by the new examples so the portfolio does not hand-roll browser auth HTTP logic.
- Rationale: The examples should teach the official client surface rather than custom fetch wrappers.
- Acceptance criteria:
  - The client adds typed methods for API keys, 2FA challenge/disable, social disconnect, runtime lookup, and region lookup.
  - Client tests cover successful calls and canonical failure envelopes.
  - The `account-settings` and `multi-region-routing` examples consume these typed methods.
- Test vectors: `TV-EXAUTH-010`
- Notes: Demo-route helpers MAY still use plain fetch because they are not part of the public auth client.

## EXAUTH-011

- ID: `EXAUTH-011`
- Priority: `P1`
- Statement: Example UIs and demo endpoints MUST expose stable contracts designed for deterministic Playwright selectors and test control.
- Rationale: End-to-end fixtures only remain trustworthy if their UI and test-control contracts are stable.
- Acceptance criteria:
  - The documented `data-testid` families exist in the rendered UIs.
  - Shared demo routes expose reset, events, and OTP retrieval with canonical envelopes.
  - Missing selector or scenario contracts fail with deterministic example-specific error behavior or test assertions.
- Test vectors: `TV-EXAUTH-002`, `TV-EXAUTH-011`
- Notes: Playwright tests SHOULD not depend on text-only selectors when a stable test id exists.

## EXAUTH-012

- ID: `EXAUTH-012`
- Priority: `P1`
- Statement: The portfolio MUST ship with an index README plus per-example docs and scripts for install, run, schema generation, DB push, and end-to-end verification.
- Rationale: These examples are documentation assets as much as test fixtures.
- Acceptance criteria:
  - `authfn/examples/README.md` lists all examples and their purpose.
  - Every example README documents `dev:server`, `dev:client`, `db:generate`, `db:push`, and `test:e2e`.
  - The commands in the docs match actual package scripts.
- Test vectors: `TV-EXAUTH-012`
- Notes: Documentation may reference a shared Postgres setup.

## EXAUTH-013

- ID: `EXAUTH-013`
- Priority: `P0`
- Statement: The entire example portfolio MUST be deterministic and runnable without external SaaS dependencies, and its verification suite MUST detect unintended external network use.
- Rationale: The examples are intended to be stable end-to-end fixtures, not flaky demonstrations.
- Acceptance criteria:
  - Playwright suites pass with local fake delivery and local fake providers only.
  - A documented verification path exists for running the suites against a local Postgres instance.
  - Tests or helper guards fail when a scenario attempts live external provider traffic.
  - Shared demo reset produces reproducible seeded state between runs.
- Test vectors: `TV-EXAUTH-002`, `TV-EXAUTH-007`, `TV-EXAUTH-013`
- Notes: The examples MAY use Docker Compose to provision Postgres locally, but MUST also support a direct `DATABASE_URL`.
