`kind: "memory"` provides a process-local adapter. Durable PostgreSQL needs the SQL in `memoryfn/typescript/migrations`: apply `0001-initial.sql`, then `0002-memory-lifecycle.sql`, then `0003-document-sources.sql`, using a migration role in the intended application schema. The first migration creates pgvector-backed tables with `vector(1536)`; the second adds revisions, tombstones, and an active-row index; the third adds nullable source-key, content-hash and chunk-index columns with a live-source index for source-keyed document chunks. No migration provisions a database, grants, or Hyperdrive. Exact vector search works without an approximate index.

## Inject a caller-owned PostgreSQL adapter

```ts
import postgres from "postgres";
import { drizzle } from "drizzle-orm/postgres-js";
import { memoryfn } from "@memoryfn/core";
import { PostgresAdapter, memories, memoryRelationships } from "@memoryfn/core/storage/pg";

const client = postgres(connectionString, { prepare: false, max: 5 });
const adapter = new PostgresAdapter(
  drizzle(client, { schema: { memories, memoryRelationships } }),
);
const memory = memoryfn({ storage: { kind: "adapter", adapter } });

// The caller owns this client. Closing MemoryFn does not close it.
await memory.close();
await client.end();
```

Use an injected adapter when the host controls request or Worker lifetimes, pooling, and Hyperdrive options. `kind: "pg"` with a URL creates an owned client; `memory.close()` closes it. Passing a `connection` option to the factory's PostgreSQL branch is rejected: inject a `PostgresAdapter` instead.

PostgreSQL storage fixes embedding dimensions at 1536. The factory requests that dimension and rejects a conflicting embedder configuration, including with an injected `PostgresAdapter`.

The `StorageAdapter` contract requires scoped `insertMemories()`, `insertRelationships()`, `searchVectors()`, `getMemory()`, `updateMemory()` (compare-and-update), `deleteMemory()`, and the source-keyed document methods `getSourceState()`, `replaceSource()` and `deleteSource()`; `close()`, `transaction()` and `replaceSourceIfChanged()` are optional. Without `replaceSourceIfChanged()` the adapter serves every memory operation and `forgetBySource()`, and `upsertDocument()` fails with `MEMORY_DOCUMENTS_UNSUPPORTED` before any provider call; it is never emulated by a state read followed by `replaceSource()`, which would race. `searchVectors()` takes an optional `excludeSources` flag that leaves out rows with a source key; `add()` sets it when it looks for duplicates and conflicts, so new content is never merged into a source's chunks or facts, in one `searchVectors()` call per path with the same `topK` as before (1 for deduplication, 3 for conflict resolution). An adapter that stores source rows, through `replaceSource()` or `replaceSourceIfChanged()`, must honour the flag, leaving source rows out before it ranks and truncates to `topK`; the built-in memory and PostgreSQL adapters do. `add()` also drops any source row an adapter returns anyway, without querying again, so an adapter that ignores the flag can only make `add()` miss a duplicate or conflict candidate (storing an extra ordinary memory), never change a source row or fail. Immutable-ID tombstones and scope checks are required for equivalent behavior. A source is one tenant, the exact container tag set and a source key; `replaceSource()` must tombstone every live chunk of that source and insert the new chunks atomically, serialized per source, so concurrent replacements leave exactly one chunk set live. `replaceSourceIfChanged()` validates and limits its input like `replaceSource()`, then reads the source's state inside the same serialization: when the live chunks all carry the given content hash it writes nothing and returns `{ unchanged: true, state }`, otherwise it replaces the source and returns `{ unchanged: false, memories }`, so of concurrent calls with one hash at most one writes. In PostgreSQL that read follows the source locks; two such calls made concurrently through one transaction can both write, and exactly one chunk set still stays live. The PostgreSQL adapter runs source writes at READ COMMITTED; inside an enclosing transaction at another isolation level it rejects them with `MEMORY_SOURCE_ISOLATION_UNSUPPORTED` before writing. Its advisory lock is re-entrant within one database session, so each source write makes its whole change in one statement: writes through one transaction, from any adapter or savepoint on it, still leave exactly one chunk set live. Before that statement it row-locks the source's live chunks, so a relationship insert that already locked a chunk commits first and its relationship is removed with the chunk. The advisory lock is keyed on the tenant and source key, so sources that share a key but differ in container tags share one lock by design. A transaction that writes several sources must take them in one consistent order over tenant ID and source key, for example sorted by tenant ID and then source key; if two transactions take the same sources in opposite orders, PostgreSQL detects the deadlock and aborts one of them, and the caller reruns that whole transaction. Every adapter rejects a source call over its input limits with a `MemorySourceLimitError` (`code` `MEMORY_SOURCE_LIMIT_EXCEEDED`) before any lock or write: a tenant ID or source key longer than 1 KiB (1,024 bytes) of UTF-8, or a set of distinct container tags totalling more than 64 KiB (65,536 bytes) of UTF-8 (a repeated tag counts once), in `getSourceState()`, `replaceSource()` and `deleteSource()`; a replacement content hash longer than 1 KiB of UTF-8; a replacement of more than 16,384 chunks, checked before the chunk array is read; and a replacement whose chunks total more than 256 MiB, counting the UTF-8 bytes of each chunk's type, content, JSON-serialized metadata and JSON-serialized embedding (so escaping inside metadata counts), measured on a copy of each chunk taken once at call time, which is what the adapter writes. The content hash and the container tags are not counted in that total; their own limits above bound them. An omitted or empty chunk type is written, and counted, as `conversational`, and omitted content as an empty string; a chunk whose type, content, ID or `isLatest` has another type, or whose ID is empty, is rejected with `MEMORY_SOURCE_CHUNK_INVALID` before any lock or write, as is a chunk ID in the PostgreSQL adapter that is not a UUID in a spelling PostgreSQL accepts. The limits are exported as `MAX_SOURCE_IDENTITY_BYTES`, `MAX_SOURCE_TAG_BYTES`, `MAX_SOURCE_CHUNKS` and `MAX_SOURCE_REPLACE_BYTES`, from the package root and from `@memoryfn/core/storage/pg`, together with `MemorySourceLimitError`; `instanceof MemorySourceLimitError` matches the error from either entry point. In PostgreSQL a replacement is still one statement: the tenant, source key and content hash are bound once, every source statement binds the distinct container tags once (in a `source_tags` common table expression, from which a replacement rebuilds the given tag order), each chunk's type, content and metadata are sent unescaped as their own parameters, and only the fixed-shape fields (chunk index, ID, embedding, latest flag and timestamps) are sent as JSON in `json` parameters of bounded size. Within the limits the parameter count stays below the driver's limit, and a replacement at every limit, with its content hash and distinct tag set each sent once, stays below about 260 MiB of parameters, well below PostgreSQL's 1 GB protocol message limit. The given tag order is sent as one position per tag, repeats included, and each chunk stores the full given tag array; the limits do not count repeated tags, so a tag array with very many repeats can still exceed a PostgreSQL limit, and that statement fails without changing the source. With a drizzle cache, these lock reads and `getSourceState()` always go to the database, so a read inside a transaction never caches state that may roll back, and every source write invalidates cached reads of both `memories` and `memory_relationships`. Rolling back a savepoint undoes every later write in that transaction, including source writes from concurrently open savepoints. Source container tags must all be non-empty strings; a sparse tag array is rejected with `MEMORY_SCOPE_REQUIRED`. A source tenant ID, source key or container tag that contains an unpaired UTF-16 surrogate or NUL is also rejected with `MEMORY_SCOPE_REQUIRED` (and such a content hash with `MEMORY_SOURCE_HASH_REQUIRED`) before any lock or write: PostgreSQL text would store a lone surrogate as U+FFFD, so two different keys would name one stored source. A conflict resolution that changes several records requires `transaction()`; an adapter without it rejects that conflict before writing.

`kind: "sqlite"` requires an explicit adapter. The factory does not create SQLite storage. `qdrant` is present in a legacy type union but has no factory implementation. Review the [source lifecycle guide](/docs/reference/storage-lifecycle) and [adapter interface](https://github.com/21nCo/super-functions/blob/dev/memoryfn/typescript/src/storage/adapter.ts) before implementing a custom store.
